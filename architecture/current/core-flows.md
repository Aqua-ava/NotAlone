# 现行核心流程

> 状态：已采纳的流程边界；UI 形态和 API 路径尚未设计。

## 1. 导入与关系资料采纳

```text
用户手动选择联系人
  -> 创建 source_document 和 background_task（type=import）
  -> 按固定模板创建 background_task_step
  -> Worker 依次执行 parse、normalize、extract_memory、index
  -> 进入 verifying，确定性检查来源、隔离、数量和索引一致性
  -> 验证通过后任务 succeeded
  -> 异步提取的 memory_candidate 按规则自动采纳（带来源、标记 auto、可撤销）
  -> 用户可随时查看、修正、撤销或删除已采纳资料
```

规则：一次导入只属于一个联系人。检测到多位联系人混杂、说话人不能可靠区分或文件已损坏时，任务必须失败或要求拆分，不能静默归并。

OCR、转写、时间线提取和长历史冲突检查是未来可选的后台专职处理；它们都向主流程返回带来源的结构化结果，不能直接写入已采纳资料。关系提取的触发点、输入窗口、证据契约与全自动采纳见 ADR-002。提取在后台异步执行：任务空闲时生成、跳过活跃或短暂会话、不与回复生成抢占额度。

## 2. Mac 微信前台会话增量同步

```text
用户首次确认“当前微信会话 -> 联系人”的绑定，并开启同步
  -> 微信在前台且该会话可见时，检测聊天区域画面变化
  -> 仅捕获聊天区域的最小画面，进行本地 OCR
  -> 解析说话人、顺序和可用时间线索
  -> 归属校验：确认该批次可唯一归属到已确认的绑定
  -> 与该绑定下已有 message 去重
  -> 仅把新增消息写入该联系人的原始消息层
```

同步只覆盖用户正在查看的一对一会话，不会读取其他 App、后台微信、未打开的会话，也不会切换会话或滚动历史。无法确认会话绑定、OCR 无法可靠区分说话人或消息顺序时，必须暂停写入并要求用户确认。

归属校验失败（绑定失效、匹配不唯一、说话人或消息顺序无法可靠区分）时，该批次 `session_capture` 保持未归属临时态：不写入任何联系人的 `message` 层，不参与检索，并在确认超时或用户停止同步时清除。必须经用户重新确认绑定后，才能恢复写入。

同步得到的是原始消息，不是长期关系事实。后续模型据此产生 `memory_candidate`，并按 ADR-002 全自动采纳写入 `confirmed_memory`（带来源、标记 auto、可撤销）。

### 2.1 同步连续性与用户补录

前台 OCR 不能获知用户在手机或未打开 Mac 微信期间的消息。恢复观察时，系统必须以已有消息与新画面中识别出的重叠消息作为连续性锚点；不能仅凭“又识别到新消息”宣称历史完整。

- 有可靠重叠锚点时，新增消息标记为 `continuous` 并正常去重写入。
- 没有可靠锚点时，已识别的新消息可以按来源写入，但该段会话覆盖状态标记为 `possible_gap`；回复上下文和 UI 不得把此状态表述为完整历史。
- 用户可明确启动“补录此段对话”：用户自己在已绑定、前台可见的微信会话中滚动，应用只持续观察聊天区域、OCR 与去重，不点击、不滚动、不切换会话。补录重新连接到已存锚点后标记为 `backfilled`。
- 用户也可把缺失片段作为单联系人文本导入；该输入创建普通 `source_document`，沿用来源追踪和级联删除规则。
- OCR 未可靠识别原始发送时间时，必须保留时间未知或低置信状态，不能以采集时间伪装为消息发生时间。

### 2.2 快捷键触发候选回复

前台会话同步开启后，NotAlone 在已绑定会话可见且画面变化时自动执行本地 OCR、去重并把可靠识别的新增消息写入数据库；这条采集与入库路径不需要用户按快捷键。

用户需要回复建议时按下全局快捷键。系统确认当前微信会话仍对应原有绑定后，从数据库读取该联系人的最新消息和必要历史，进入候选回复生成。

- 快捷键只触发候选回复生成，不触发、开启或替代自动 OCR 同步。
- 当前会话绑定仍然唯一、最新画面已完成可靠识别时，系统直接生成候选，不要求用户每次重复确认联系人。
- 若画面已经变化但本轮 OCR 尚未完成，系统应等待识别完成或明确提示“正在识别”，不得静默使用旧消息生成候选。
- 会话变化、绑定失效、匹配不唯一或 OCR 置信度不足时，系统暂停生成并展示本次识别结果与联系人范围，只有用户修正或重新确认后才能继续。
- 系统不得用昵称、消息正文或模型推断静默选择联系人，也不得把低置信度 OCR 结果写入消息层或回复上下文。
- 手工输入当前消息只作为 OCR 不可用时的显式兜底方式，不是 Mac 产品正常流程；使用兜底时仍需由用户选择联系人。

## 3. 候选回复生成

```text
前台同步已自动 OCR、去重并把可靠识别的新增消息写入数据库
  -> 用户在已绑定的 Mac 微信会话中按下全局快捷键
  -> 系统验证当前会话绑定，并读取该联系人的最新消息和必要历史
  -> OCR 尚未完成时等待或提示；绑定或识别异常时要求用户确认
  -> 确定性代码执行联系人/授权校验
  -> 执行确定性请求风险预检并展示核实提醒
  -> 表达方向为空时只提供模型方向建议，用户选择或修改后确认
  -> 读取用户明确给出的表达方向，组装当前消息、近期对话、常驻卡和可用 Skill 精简目录
  -> LangChain create_agent 在有界循环中按需创建 Todo，并向 UI 输出多步骤进度
  -> 按需调用 Skill、联系人检索、当前时间及经过授权的只读日历/网络搜索 Tool
  -> 根据 Tool 结果继续查询，普通回复不强制创建 Todo
  -> 在六轨上下文内返回 1-3 条带依据引用的 reply_candidate，或返回澄清需求
  -> 校验输出结构、引用与禁止动作并持久化本次运行轨迹
  -> UI 显示候选或澄清问题，以及本次实际使用的上下文范围
  -> 用户选择、编辑、手动发送
```

回复运行时固定为确定性外壳 `validate_scope -> assess_request_risk -> assemble_initial_context -> create_agent bounded Tool loop -> validate_agent_output -> persist_trace -> return_result`。内部循环使用 LangChain `create_agent`，并接受 LangGraph 作为底层 runtime；v1 不直接手写自定义 `StateGraph`。若以后出现明确的暂停恢复或复杂固定流程，可以把整个 `create_agent` 作为自定义图中的节点。完整边界见 `../drafts/agent-runtime.md`、ADR-006 与 ADR-009。

v1 的检索应可解释：先用联系人过滤，再用时间、关键词、资料类型、采纳状态和显式有效期排序。每个候选应能回看"本次用了哪些近期消息和已采纳资料"，但不必把完整历史给模型。

每次候选回复任务都必须由用户确定表达方向：`rewrite_draft` 以用户已有草稿确定基础方向，并允许用户补充约束；`reply_to_message` 可以由用户直接输入方向，也可以在方向为空时请求模型提供建议。模型建议必须由用户选择或修改后确认，不能自动成为表达方向；确认前不得进入候选回复生成。系统随后在已验证的联系人范围内自动组装与该方向相关的回复上下文，用户不需要逐项选择材料。UI 必须允许用户查看实际选入项，并在重新生成前从本次上下文中移除不适用材料或补充遗漏材料；这类调整只作用于本次生成，不得静默修改长期关系资料。从本次上下文移除材料也不等于删除其来源或权威记录。

### 3.0 上下文组装层级（v1）

生成请求的上下文按"六轨"组装，历史本身永不进入提示词，每轨都只取少量：

1. **轨一 硬规则（代码层，必加载）**：不自动发送、联系人隔离、高风险标记。确定性代码规则，不是记忆提示词（见 3.4）。
2. **轨二 回复 Skill（按需加载）**：只加载本次选中的一个不可变版本，作为可撤销的策略参考，不作为联系人事实，不覆盖当前请求、近期对话或硬规则（见 3.7）。
3. **轨三 常驻卡（固定加载）**：`owner_preference`（全局层）+ 该联系人标记 `carry` 的常驻事实（5-10 条），每次生成必带，不依赖检索。
4. **轨四 按需检索**：模型可在运行预算内分别调用消息检索和确认记忆检索 Tool；结果仍按 3.1 排序并经应用层校验。
5. **轨五 近期对话（最强事实依据）**：该联系人的近期 `message`，是当前语境的最直接依据。
6. **轨六 风格样本（最弱）**：最多 5 条低权重参考（见 3.6）。

组装原则：冲突时硬规则和用户当前明确要求优先，近期对话压过旧记忆，Skill 只指导回复方式而不改变事实。超预算先移除风格样本，再移除低分按需检索结果；已选 Skill 仅保留完成当前策略所需的最小正文。记忆是辅助回忆层，不是规则——安全规则只放轨一代码层，不放记忆或 Skill 正文。

当前时间、授权日历和公开网络搜索结果是本次请求的外部 Tool 证据，不构成第七条关系上下文轨，也不自动写入长期关系资料。日历 Tool 只读；网络搜索不默认携带聊天正文、联系人身份或关系资料。实际使用的 Tool、查询类别和结果引用进入本次运行轨迹。

#### 持续聊天与滑动上下文

同一联系人的聊天是长期连续的消息线程，不因生成一次候选而创建新的聊天窗口。每次生成仍创建独立的 `reply_request` 和上下文快照，用于复现本次实际使用的消息、资料、Skill 与规则；这项审计边界不等于切断后续聊天上下文。

模型输入按 token 预算动态滑动，而不是按固定分钟数强制切断：`SummarizationMiddleware` 保留当前待回复消息和最近原始消息，把较早运行消息压缩为可重建摘要，长期事实继续从该联系人的权威资料中检索。摘要只属于 Agent runtime state，不写入 `confirmed_memory`；来源或联系人删除时必须失效相关摘要和 checkpoint。时间间隔只作为判断当前话题活跃度的弱信号；联系人切换、用户明确结束或话题明显变化可以降低旧片段权重，但不得删除历史，也不得阻止后续按来源重新检索。具体 token、消息和时间阈值必须经真实使用数据与候选质量评估后再确定。

### 3.1 检索排序规则（v1）

联系人过滤后，按以下优先级降序排序；键相同则落到下一键比较：

1. **采纳状态**：`confirmed_memory` 优先于 `memory_candidate`；`pending` 候选仅用于展示线索，不进入生成上下文。
2. **显式有效期**：`valid_at <= now <= invalid_at` 的资料优先；无有效期的资料视为长期有效，排在未过期之后、已过期之前。
3. **时间**：资料创建或消息发送时间更近者优先。
4. **资料类型**：共同事实与禁忌优先于偏好与一般备注（分类见 `domain-data.md`）。
5. **关键词**：与当前消息的文本重叠或语义相关度更高者优先。

### 3.2 上下文预算（v1，写入生成接口入参约束）

生成请求的上下文是硬性预算，超出即截断，不允许把完整历史塞入提示词：

- **近期消息**：最多 50 条，且合计不超过 8k token；超出按时间取最近部分。
- **已确认资料**：最多 20 条。
- **常驻卡**：轨三固定 5-10 条（含 `owner_preference` 与联系人 `carry` 条目）。
- **回复 Skill**：最多 1 个不可变版本；目录摘要与完整正文分别计入选择调用和生成调用预算。
- **风格样本**：最多 5 条，且只作低权重参考（见第 4 节）。
- **截断策略**：按 3.1 的排序从队尾截断，并在生成接口返回本次实际使用的引用清单，用户可回看"用了哪些、丢了哪些"。

模型/Tool 调用次数、单次返回数量、总 token、超时和重试次数属于可配置运行预算，具体初始值在实现与合成评估时确定。联系人隔离、删除状态、只读 Tool 和禁止外部发送不属于可调预算。

### 3.3 检索缺口处理（降级与明示）

模型可以根据已返回证据在运行预算内调整关键词、时间范围或资料类型后继续查询；Tool handler 必须拒绝重复、越界或超预算请求。所有查询和实际命中均记录在运行轨迹中。预算内仍为空时，UI 明示“未检索到相关记忆”，区分“没查到”与“没资料”。空结果率和查询轮数作为是否调整检索策略或引入向量检索的前置观测数据（见 M10）。

### 3.4 高风险内容交互

高风险内容（转账、验证码、地址、借款、承诺、见面安排、关系冲突）由独立适配层的确定性规则标记，不混入生成提示词。命中时仍可检索并生成，但生成前必须展示核实提醒；判定规则放独立模块，便于更新和测试。

注意：风险字段只影响生成环节的核实提醒，不阻塞记忆的自动写入（见 ADR-002 全自动采纳）。安全保险在发送环节：候选回复带依据引用，由用户选择并手动发送。

### 3.5 引用展示契约

每条候选回复必须携带依据引用：`retrieval_segment`/`source_span` 标识、入选原因、排序分数与状态（消息/已采纳资料/风格样本），并单独记录实际使用的 `skill_version_id` 与选择原因。用户可回看"为什么用了这些上下文和套路"，便于发现误导入、过期资料或不合适的策略。

### 3.6 风格样本权重

v1 风格样本送入提示词但权重受限：最多 5 条、明确标注为“参考的表达样本”，不参与事实推断，不覆盖当前语境判断。若后续发现干扰生成，降为仅离线参考。

### 3.7 回复 Skill 的两级加载

Skill 采用 progressive disclosure：LangChain `create_agent` 组合 Deep Agents `SkillsMiddleware`，middleware 只从当前 owner/contact 的受控 discovery backend 发现已启用版本，并通过 NotAlone 定制提示词把 `name + description` 等精简目录放入模型上下文。模型需要完整策略时调用受控只读 `read_file(file_path, offset=0, limit=1000)`；该 Tool 只接受目录中已列出的 `SKILL.md` 虚拟路径，经 `SkillPort` 校验范围、状态和不可变版本后返回正文，不是通用文件系统读取。定制提示词不展示 `allowed-tools`，也不引导模型访问 supporting files 或执行脚本。

用户显式选择 Skill 时，应用层通过同一个 `SkillPort` 校验并预加载，不要求模型再次调用 `read_file`。自动模式可以不加载 Skill；加载成功时 UI 必须展示本次使用的名称和版本并允许用户关闭或更换。每次最多使用一个不可变版本；Skill 本身只提供经校验的策略文本，其内容不能注册 Tool、MCP、Shell、文件写入、子 Agent 或外部资源访问。

Skill 库管理不属于 Agent Loop。用户可以在独立入口创建、禁用、删除或从网络明确安装 Skill；安装和更新先校验并固化不可变版本，候选回复运行时只读取已经启用的版本。Skill 目录缓存必须绑定 `owner_id + contact_id + skill_library_revision`；任一项变化时，下一轮运行先清除旧目录、旧 Skill Tool 结果和包含旧 Skill 正文的摘要，或使用新的运行状态。采用 `SkillsMiddleware` 不等于采用完整 `create_deep_agent`，候选回复不启用 Deep Agents 的通用文件系统、Shell、Subagent 或长期任务 harness。

消息检索和确认记忆检索 Tool 的模型参数只包含查询意图、limit 和允许的时间范围；已验证的 `owner_id + contact_id` 通过 runtime context 注入并传给 `RetrievalPort`，不能由模型提供或修改。返回携带引用标识、采纳状态、有效期、排序分数与检索器版本，用于复现与审计“本次为何返回这些结果”。

高风险内容，包括转账、验证码、地址、借款、承诺、见面安排和关系冲突，必须提醒用户自行核实；系统既不能自动发送，也不能替用户做最终决定。

### 3.8 草稿改写与生成回复

同一个全局快捷键支持两种输入模式。按键时微信输入框已有文字，默认进入 `rewrite_draft`；输入框为空，默认进入 `reply_to_message`。浮动窗口顶部必须提供分段控件，允许用户在“改写草稿”和“生成回复”之间手动切换，不设置第二个快捷键。

```text
rewrite_draft
  -> 读取用户已经输入的草稿
  -> 保留原意，结合当前联系人语境改写

reply_to_message
  -> 读取数据库中该联系人的最新对方消息和近期对话
  -> 直接生成可回复的候选

两种模式
  -> 沿用候选回复生成的风险预检、Skill、检索和六轨上下文
  -> 在用户明确的表达方向内生成 1-3 条措辞或语气不同的 reply_candidate
  -> 用户选择、编辑并亲自发送
```

`rewrite_draft` 中，草稿本身确定本次基础表达方向；用户可以再补充“简短一点”“别太主动”等约束，但不必重复说明草稿已经表达的立场。模型可以调整措辞、语气和结构，但不得改变原意或添加用户没有表达的事实、承诺和情绪。草稿可以是完整句子，也可以是尚未组织好的零散想法。

`reply_to_message` 中，最新对方消息是本次待回复对象；模型只能在用户明确给出的表达方向内探索自然、更有趣或更直接的措辞，不得自行改变用户立场、决定是否推进关系或替用户做决定。两种模式都继续遵守依据引用、联系人隔离、高风险提醒和禁止自动发送的既有约束。

### 3.9 候选回复浮动窗口

用户按下全局快捷键后，NotAlone 在当前微信窗口旁显示独立的候选回复浮动窗口，不遮挡聊天内容。窗口至少展示已确认联系人、本次识别的待回复消息、上下文状态和 1-3 条候选回复。

- 窗口顶部使用“改写草稿 / 生成回复”分段控件；默认选择由快捷键触发时微信输入框是否有文字决定，用户可以手动切换后重新生成。
- “生成回复”模式提供表达方向输入；方向为空时不能生成候选，但可以单独请求模型给出方向建议。建议不预选，用户必须选择或修改其中一条并确认后才能生成。
- 每条候选都可以在浮动窗口内编辑和复制，并能展开查看本次使用的依据；窗口不得写入微信输入框或发送消息。
- `TodoListMiddleware` 对多步骤请求创建 Todo 时，窗口展示精简步骤与当前进度；普通回复没有 Todo 时不显示空的进度区域。Todo 只描述本次运行计划，不进入关系资料或后台任务状态。
- 本次生成绑定一个已持久化的上下文快照。生成后识别到的新消息不得静默替换该快照；窗口应提示上下文已有更新，由用户重新生成。
- 浮动窗口取得键盘焦点后，微信不再是前台应用，自动 OCR 同步随即暂停。用户返回微信后，系统重新校验前台会话绑定，再恢复自动同步。
- 浮动窗口关闭后不改变前台同步开关；解绑、暂停同步或联系人校验失败时，不得继续使用旧窗口为该会话生成候选。

### 3.10 关系分析任务边界（未来）

分析数月聊天、整理关系变化时间线或跨大量证据复核矛盾，不属于候选回复任务，也不能因用户打开聊天窗口或按下候选回复快捷键而自动开始。未来若提供关系分析任务，必须由用户从独立入口主动创建，明确联系人、时间范围和资料范围，并在独立界面展示进度与报告。

第一阶段不实现关系分析任务，也不为其预先引入完整 Deep Agents harness；候选回复使用独立的 `SkillsMiddleware` 不改变这条边界。只有明确功能证明需要动态规划、大量中间材料、跨进程恢复或多个专业子 Agent 时，才比较普通 Worker、直接 LangGraph 与完整 Deep Agents；无论采用何种 runtime，结果都不能自动发送到外部聊天渠道。

## 4. 表达样本沉淀

```text
用户完成编辑并自行发送
  -> 用户主动选择“作为表达样本保存”
  -> 保存最终文本与对应联系人
  -> 后续仅在该联系人范围内作为低权重风格参考
```

产品不能从第三方聊天渠道自动获知发送结果，也不能把所有生成候选或复制动作自动归纳为长期偏好。

## 5. 删除与修正

```text
用户删除来源、关系资料或联系人
  -> 创建 background_task（type=delete，scope 限定 account/contact/source）
  -> 计算消息、候选、确认资料、索引和缓存的影响范围
  -> 执行级联删除或失效
  -> 重新建立受影响联系人的检索索引
  -> 展示完成状态与未能删除的原因
```

修正关系资料应保留修正时间和原始来源关联，但不需要长期保存已被用户要求删除的私密正文。删除和重试过程应显示进度、失败原因和结果，不能在后台静默失败。

删除来源时，其规范化 `message` 无条件级联删除；仅由该来源支持的已确认资料无条件级联删除。用户若想保留某条内容，必须先执行"另存为不依赖该来源的手动资料"（切断与原来源依赖），再删除来源。删除流程须覆盖跨来源场景：一条已确认资料被多个来源支持时，删除其中之一只移除该证据，删除全部来源后资料才失效。

## 6. 后台任务边界

后台任务只处理用户已经触发的资料：导入、解析、规范化、索引、候选提取、删除和重建。已启用的前台会话同步可在画面变化时运行本地 OCR 和去重，但它不是全局后台抓取。关系提取按 ADR-002 的调度策略异步执行：任务空闲时生成、跳过活跃或短暂会话、不与回复生成抢占额度。v1 可使用同一应用内的任务表和 worker；只有并发量、可靠重试或部署规模成为真实问题时，再引入独立队列和 worker 服务。

`jobs` 的运行方式固定为“任务记录 + 步骤记录 + Worker”，完整约束见 ADR-007：

```text
API 创建 background_task 与固定 background_task_step
  -> Worker 使用租约领取下一条可执行步骤
  -> 普通处理器执行解析、规范化、索引或校验
  -> 只有语义步骤经 ModelPort 调用 AI
  -> Worker 原子更新步骤状态和业务引用
  -> 全部业务步骤完成后进入 verifying
  -> 确定性验证通过后标记 succeeded
```

- v1 不先引入 Airflow、Temporal 或独立消息队列；Worker 可以是同一代码库、同一云服务器上的独立 Python 进程，PostgreSQL 同时承担权威任务状态与领取协调。
- 导入、级联删除和重建索引可拆为步骤；一次候选回复仍由基于 LangGraph runtime 的 `create_agent` 同步执行，前台 OCR 的单个轻量增量通常不创建步骤清单。
- `background_task_step` 是持久化工作记录，不是 Agent prompt 或模型 Todo；步骤及依赖由代码模板确定。
- AI 只返回某个语义步骤的结构化结果。Worker 和确定性校验器拥有状态迁移权，AI 不得领取任务、修改状态或宣布成功。

不在 v1 实现：读取非前台聊天应用、全量后台同步所有会话、自动切换或滚动微信会话、自动发送、无预算的开放式自治循环或为短文本回复强行调用多 Agent。
