# 现行领域与数据契约

> 状态：已采纳的产品约束；云端 PostgreSQL 是权威业务库，具体字段类型和表结构仍待实现时确定。

> 后续目标：记忆时间状态、可追溯概览与自动 Skill 生命周期由[ADR-048](../adr/048-memory-skill-evolution-lifecycle.md)及[正式规格](../../.scratch/memory-skill-evolution/spec.md)局部细化；独立集成候选现已完成联系人与本人概览的合成验证，下方 v1 数据对象仍描述基础约束；真实模型质量与实际 App／微信另验。

## 核心原则

1. 每次回复请求由用户明确选择一个联系人，服务端不得根据消息正文、昵称或历史猜测联系人。
2. 所有联系人范围的读写均先以 `owner_id + contact_id` 过滤，再做内容检索或排序。
3. 原始资料、规范化消息、模型候选资料、已采纳关系资料和表达样本必须分层保存。
4. 长期资料必须保留来源、证据类型、创建时间、采纳状态和删除入口。
5. 即使部署初期只服务一个用户，也必须显式持久化 `owner` 与 `owner_id`，以保证数据隔离和未来多用户演进不需要迁移核心数据模型。

## 数据对象

独立 App 首版按 [ADR-065](../adr/065-manual-input-standalone-first-release.md)增加手动输入确认：用户明确选择既有联系人后，独立记录 `manual_contact_confirmation` 的内部执行标识，不创建 `channel_identity` 或 `conversation_binding`。昵称仍仅展示，同名联系人互相独立。旧 `conversation_binding_id` 存储槽在手动模式引用该标识；实际请求必须显式声明手动来源，且重新核验 `owner_id + contact_id` 与确认记录。渠道查找、CLI、前台定位和读取授权仍只认真实桌面绑定，不能查找或回退到手动确认。

粘贴的对方当前文字通过 `input_kind=current_chat`、明确的 `pasted_direction` 和独立的 `user_current_chat` 依据保留来历；这是用户提供、未经渠道核验的文字，不冒充本人草稿或规范消息，不进入记忆提取。仅在显式生成后沿助手讨论与候选生命周期保存，并继承相同的删除路径。

| 对象 | 必要职责 | 关键关联 |
| --- | --- | --- |
| `owner` | 资料所属用户。 | `owner_id` 是所有私密数据的第一层隔离键。 |
| `owner_channel_identity` | owner 在外部聊天渠道中的已验证身份。 | 通过 `owner_id` 关联；`external_id` 是渠道标识，不是 `owner_id`；同一 owner/channel v1 只保留一个 active 身份。 |
| `owner_memory` | 用户本人的长期事实资料，跨联系人范围的回复都可使用（见 `CONTEXT.md` 的“本人记忆”）。 | 属于 owner，不绑定 `contact_id`；与联系人关系记忆使用同一评分器、阈值和排序，但使用独立的 3 条/240 字符预算，不固定全量加载。 |
| `contact` | 用户手动创建或选择的具体联系人。 | `contact_id` 是 NotAlone 创建的稳定内部身份；昵称、备注和渠道身份是可变或可重新确认的信息。 |
| `conversation_binding` | 用户确认的桌面聊天会话与联系人的绑定。 | 保存聊天 App、账号范围、外部会话定位标识、display name 映射、选中会话元数据和备用视觉指纹、绑定状态与最近验证时间；已建立且唯一的映射可自动切换，不能把 display name、视觉指纹或 `talker` 当作 `contact_id`。 |
| `source_document` | 一次原始导入的文本、截图或语音原始引用。 | 属于一个联系人；保留来源定位、导入时间、导出器名称与版本（可获取时）、用户确认范围、确认时间、确认方式和删除状态。 |
| `session_capture` | 前台会话同步中一次画面变化产生的端侧视觉观察记录。 | 只用于前台状态、display name、选中会话元数据和备用视觉指纹；默认不保存原始视觉帧，也不作为 CLI 消息正文来源。未归属时为仅含 `owner_id` 的临时态。 |
| `local_wechat_observation` | 本地微信 CLI 从一个外部会话读取的一次文字增量来源记录。 | 显式关联 `owner_id + contact_id + conversation_binding`，保存外部会话定位标识、CLI 版本、`local_id`/`cursor`、读取时间、`from_me`/sender 和 `capture_mode`（live/cli_catchup）；不保存全量导出文件。 |
| `background_task` | 一次完整的长时后台工作，取代独立的导入/删除/重建任务表。 | `type` 区分 import/delete/reindex；`scope` 声明作用域（account/contact/source）；状态为 `queued/running/verifying/succeeded/failed/cancelled`，记录总体进度、失败原因、重试与关联来源。删除任务不得跨越隔离边界。 |
| `background_task_step` | `background_task` 下可恢复、可重试的固定执行步骤。 | 关联父任务并保存 `step_type`、顺序、状态、尝试次数、输入/输出业务引用、错误分类和 Worker 租约；不保存完整聊天正文。只用于确实需要逐步恢复或展示进度的长任务。 |
| `message` | 统一的规范化文字消息。 | 显式冗余 `owner_id + contact_id`，并保存说话人、正文或明确的媒体占位信息、可用时间戳；来源字段（`source_document` 或 `local_wechat_observation`）仅用于定位与删除，不承担隔离过滤。渠道专属字段不是所有消息的必填字段。 |
| `memory_candidate` | 模型或规则从资料中提取的待采纳关系线索。 | 关联证据消息并保留 `self/contact/shared` 主体；不能被检索为已知事实。 |
| `confirmed_memory` | 自动采纳或手动录入的共同事实、偏好、禁忌、关系资料。 | 关联一个或多个来源证据、采纳方式（auto/manual）、删除状态、分类与有效期；不保存固定常驻模式。 |
| `contact_memory_index` | 当前联系人有效关系记忆的精简主题目录。 | 按 `owner_id + contact_id` 隔离，由固定主分类和系统自动生成的子主题组成；是可重建投影，不是新的事实源；召回第一期不再用它筛选候选，只提供 `memory_revision` 快照用于生成前后复验。 |
| `relationship_overview_projection` | 联系人与本人资料的可重建依赖清单。 | 联系人按 `owner_id + contact_id`、本人按 `owner_id` 独立构建；保存底层 ID、revision、状态、摘要、来源世代与实际构建时间，不保存正文、原话或模型摘要；回复只沿清单导航到合法底层依据。 |
| `style_sample` | 用户明确主动保存的最终表达样本。 | 属于owner/contact；记录必要的非正文来历及真实原始来源依赖，按ADR-044独立于助手会话留存，不是普通候选或已发送证明。 |
| `reply_skill` | Skill 库中的一份独立回复策略目录项。 | 属于 owner；当前用户导入的 Skill 默认全局适用，名称在同一 owner 内唯一，保存简述、来源类型、状态和当前版本。一个 `reply_skill` 只代表一种策略。 |
| `reply_skill_version` | 一次不可变的回复 Skill 正文快照。 | 发布后不可修改，保存经校验的 `SKILL.md` 正文、来源定位、内容摘要和校验结果；更新必须产生新版本。删除清除正文、来源定位和关联资源，并保留最小删除记录。Skill 声明不能扩大可执行 Tool 或权限。 |
| `reply_skill_resource` | 与一个不可变 Skill 版本绑定的受控辅助资源。 | 保存包内相对路径、媒体类型、大小、内容哈希和内容定位；只允许按需只读加载，不能执行、外部下载或跨范围读取。 |
| `reply_request` | 一次面向已选联系人的表达生成请求。`rewrite_draft` 以用户草稿确定基础表达方向，并可附加约束；`reply_to_message` 使用用户直接输入或用户确认后的模型方向建议。 | 固定所属联系人，内嵌本次实际检索到的上下文快照（`retrieved_context`），并记录幂等请求键、请求状态、输入模式、最终表达方向、方向来源（草稿/直接输入/已确认建议）、可空的显式前序候选、实际使用的 `skill_version_id`、选择原因与置信度。 |
| `reply_candidate` | 模型给出的可编辑候选回复及风险说明。 | 关联一次回复请求；不会自动发送。 |
| `retrieved_context` | 本次回复实际使用的检索上下文快照（作为 `reply_request` 内嵌结构）。 | 含隔离键、检索条件（时间窗口、关键词、limit）、引用列表与排序分数，用于"为什么用了这些上下文"的回看。 |

## 资料分层

```text
source_document
  -> message
      -> memory_candidate
          -> confirmed_memory
              -> contact_memory_index（自动生成、可重建）

conversation_binding
  -> session_capture（前台状态与 display name 线索）
  -> local_wechat_observation
      -> message

reply_request（内嵌 retrieved_context 快照）
  -> reply_candidate
      -> style_sample（仅用户明确采纳时）

reply_skill
  -> reply_skill_version（发布后不可变）
      -> reply_request（记录本次实际使用的版本）

background_task
  -> background_task_step（固定步骤、独立状态与重试）
```

## v1 导入身份与规范化约束

- v1 只实现单用户、单微信账号下的联系人导入，不实现跨账号或跨渠道联系人合并。即使如此，`contact_id` 仍由 NotAlone 创建；`sender_wxid` 等外部标识只作为渠道身份或来源元数据保存（见 ADR-008）。
- `owner_id` 只能来自 NotAlone 当前运行身份：本地个人版本可读取受控配置，服务器版本必须来自已验证登录身份。首次导入可以在用户显式初始化动作中生成 owner，并把文件中的本人渠道身份保存为 `owner_channel_identity`；导入文件不能直接指定或覆盖 `owner_id`。
- owner 的 `sender_wxid` 必须与 active `owner_channel_identity` 一致；缺失、多个或变化的本人渠道身份必须停止导入并要求初始化、恢复或重新绑定。
- 首次导入允许用户创建联系人或选择已有联系人，并保存 `source_document_id`、确认的 `contact_id`、确认时间和确认方式（`manual_create`/`manual_select`）。新来源与已有渠道身份不一致时必须停止导入并重新确认。
- 一份来源只属于一位联系人。整份文件必须先完成确定性校验，再以一个事务写入联系人、来源和全部消息；损坏、混合联系人、群聊或绑定不一致时不得部分写入。
- 同一文件重复提交时返回原导入结果，不重复写入。新文件与已有消息部分重叠时停止导入，不自动跳过、覆盖或合并；明确的增量导入需另行定义用户工作流。
- 规范消息的共同字段是隔离键、说话人、正文或媒体占位信息、可用时间戳和来源定位。微信的 local/server id、talker 等字段保存在来源元数据中；本地 CLI 消息可以使用它们做增量游标和去重，但不能替代 `contact_id`。
- 有正文但缺少时间戳的记录可以导入并标记时间未知；只有明确媒体类型时可保存结构化占位信息；正文和媒体信息都缺失时拒绝该记录。系统不得编造时间或媒体内容。
- 用户手动提交的原始 JSON 可以随来源保存用于复核，但不进入回复检索，也不默认发送给外部模型。重新解析必须产生可追踪的规范化版本，并明确使相关记忆和索引失效或重算，不能无记录地覆盖旧结果。

## 后台任务状态约束

- `background_task` 表示用户看到的一次完整工作；`background_task_step` 表示其中一个可单独恢复的执行单元。短回复和单次轻量操作不得为了统一形式强行拆步骤。
- v1 的步骤由任务类型对应的确定性模板创建，例如导入为 `parse -> normalize -> extract_memory -> index -> verify`；模型不得自由新增、删除、跳过或重排步骤。
- Worker 领取步骤时写入 `worker_id`、`lease_expires_at` 和原子状态变更。同一时刻只允许一个有效租约；Worker 崩溃后，过期租约可被重新领取。
- 步骤处理器必须使用幂等键，重复执行不得产生重复 `message`、`memory_candidate`、索引条目或删除副作用。
- 父任务只有在所有业务步骤成功后才能进入 `verifying`；验证通过才进入 `succeeded`。验证失败必须进入 `failed` 或回到明确的可重试步骤，不能由进度百分比或模型结论直接宣布成功。
- 同一 `owner_id + contact_id` 的任务先串行；不同联系人未来可以并行。临时网络或模型错误最多自动重试 3 次，手动重试复用原任务并跳过已成功步骤。
- 任务不提供 v1 用户取消入口；来源删除时停止相关未完成步骤。活动任务持续保留，终态任务保留 90 天后清理；任务记录只保存元数据和业务引用，不保存聊天正文或模型完整输入输出。

- `memory_candidate` 必须有 `pending`、`confirmed`、`rejected` 或 `invalidated` 等明确状态，且候选正文、`self/contact/shared` 主体与证据范围可复核；人工确认不得丢失主体，`self` 候选必须进入 owner 级记忆。
- 按[ADR-046](../adr/046-source-bound-dimension-evidence.md)，候选可保存带版本的 `dimension_evidence`，包含完整同范围窗口、活动来源、无正文定位／摘要、语用标签快照与四类可空依据。旧 NULL 保持未知，不重建标签、回填或重新采纳。读取时复核当前来源；来源、正文、范围、有效期或语用状态变化均不能复用旧依据。来源当前不等于语义正确或维度获批。
- [ADR-047](../adr/047-bounded-source-semantic-proof.md)已批准版本二的可空语义依据合同，现已实现并完成隔离验证；由服务端独立核完整关系，未名指称不能靠模板推归属。另按[ADR-060](../adr/060-author-arrival-quote-representation.md)增加可信单消息完整作者引句的有限包装分支，该分支单独保存无正文的来源全文／包装全文与内外层作者定位，能力由服务端逐项核定，不因依据非空或引句对齐即签全部维度。版本1／旧NULL不升级，业务迁移与真实质量资格分别验证。
- [ADR-063](../adr/063-bounded-runtime-evidence-and-source-dependencies.md)已采纳并完成隔离工程验证的新记录合同，将完整窗口的新鲜度依赖与正文成立的必需消息区分。新evidence4记录原target集合并逐项核能力，候选、确认资料及本人资料持久保留一组必需消息的合取依赖；同消息的多个有效来源仍互为替代。确认、修正版、拒绝指纹及owner回退不得丢失该依赖；旧记录继续沿原替代来源语义，不回填或重解释。
- `confirmed_memory` 默认允许满足置信度与风险门槛、并落在**已放行维度**上的模型提取记忆自动写入（见 ADR-002、ADR-024、ADR-036）：必须带来源证据、标记 `auto`、可一键撤销；带敏感或未知风险标签的候选必须先留在 `pending`，用户手动录入或修正时标记 `manual`。模型不能未经来源证据直接写入。
- `confirmed_memory` 保留候选来源链：记录从哪个 `memory_candidate` 采纳而来（`source_candidate_id`，手动创建时为空），同时保留来源证据列表；采纳后仍可回看候选证据与采纳方式。
- 语用解释先于记忆采纳：模型必须在有限的同联系人窗口中结构化标记说话行为、断言状态和修辞状态；确定性规则只允许“确定、字面、非歧义陈述”进入自动采纳门，计划、假设、条件、转述、纠正和未知状态只能留在 `pending`，问题、玩笑、讽刺和夸张默认不生成长期候选（见 [语用解释规格](pragmatic-interpretation.md) 与 ADR-026）。
- 语用解释不能证明现实世界真伪；模型不返回记忆状态或写库动作。当前实现将语用阻塞原因以 `pragmatic:*` 风险标签保留在候选中，结构化备选解释和用户可见理由属于提取结果，不得写入完整模型提示词或内部推理。
- 来源语义核验补充语用解释（ADR-033）：逐条核对正文、主体与限定，核验证据片段必须来自候选既有来源且包含主消息。支持仅继续原采纳门，未知追加 `semantic:*` 风险，无支持拒绝；未核验候选不得自动采纳。不新增永久“已核验正确”标签，不回填旧资料。核验正文的临时留存限制已由 ADR-037 修订为独立、可删除的完整提取追踪，要求见 [记忆提取完整追踪](memory-extraction-trace.md)，实现状态以代码与验证为准。
- `rejected`/`invalidated` 候选随其来源删除，或短期保留供用户复核后清除；不长期堆积，与来源级删除语义一致。
- `style_sample` 只能由用户明确采用其最终回复后创建。用户选择某个候选不等于同意把它长期保存。
- 按[ADR-044](../adr/044-explicit-style-sample-retention.md)，删除助手会话保留此前主动保存的独立样本，但清除讨论和使用痕迹，不保留会话正文副本。删除样本或其原始聊天来源仍清理相关派生内容；会话关联不能代替或切断来源依赖。[基础生命周期](../../.scratch/authentic-expression/issues/04-style-sample-lifecycle.md)已有合成 HTTP／隔离 PostgreSQL 及普通页面自动证据；完整跨场景组合仍由真实表达06接续，不代表真实 App 或真人质量验收完成。
- Skill 库可以包含多个相互独立的 `reply_skill`；每个 `reply_skill` 面向一种沟通场景，可包含不同回应方向的方法分支（ADR-043），不是无关场景的总包，也不是联系人事实、表达样本或 Tool。
- 用户可以创建、禁用、删除或明确导入回复 Skill。v1 导入用户明确选择的本地 Skill 包；未来若支持网络安装，仍必须使用同一份目录与版本模型，并保留来源定位、内容摘要与校验结果，固化为新的不可变版本。
- 一次候选被采用不得自动沉淀为 Skill；模型不得自行创建、下载、更新、删除或启用 Skill。
- Skill 自动匹配只决定本次是否加载已存在版本，不得自动创建、改写或启用 Skill。`reply_request` 保存实际使用的 `skill_version_id` 与选择原因；版本仍存续时可以复现完整策略，用户删除 Skill 后只能核对最小删除记录，不能恢复已删除正文。
- v1 每次最多加载一个 `reply_skill_version`。完整正文不得进入常驻提示词；只有当前范围内的目录摘要进入 Skill 选择上下文，选中后才按版本加载经校验的 `SKILL.md` 正文和必要的 Skill 辅助资源。
- Skill 库使用 owner 级单调递增的 `skill_library_revision`。同一 owner 下导入、更新、启用、禁用或删除任一 Skill，都必须在同一事务中递增该 revision；所有联系人范围的旧 Skill 目录缓存随之失效。v1 不维护联系人级 revision。
- 同一 owner 下 `reply_skill.name` 唯一，即使一个 Skill 全局适用、另一个限定联系人，也不能重名。重名安装或更新如何呈现给用户仍由 Skill 管理模块决定，读取端不得自行覆盖或改名。
- 删除回复 Skill 时，清除所有版本的 `SKILL.md` 正文、辅助资源和来源定位；只保留 Skill/version 内部标识、名称、简述、内容摘要、删除时间与删除凭证。引用该版本的历史 `reply_request` 和候选可以保留审计关联，但不得据此恢复正文或资源。

## 候选回复请求状态与幂等

- 幂等范围是已验证的 `owner_id + contact_id + request_key`。第一次请求固化规范化输入摘要；之后同键且同摘要的调用不能创建第二份 `reply_request` 或候选。
- 已完成请求重放原有持久化结果；同键但输入摘要不同返回稳定冲突；有效租约内仍在运行的请求返回稳定的“处理中”，不得并行执行第二次。
- 失败请求或租约过期的运行请求可以使用同一 `request_key` 重试，并记录尝试次数；重试复用原请求身份，只有成功持久化一次候选结果后才进入完成状态。
- 继续历史候选必须由用户显式提交 `continued_from_candidate_id`。存储层再次校验该候选与当前 owner/contact 一致；未显式提交时不得自动选择“最新”或推断“未发送”的候选。

## 资料分类与有效期（v1）

`confirmed_memory` 必须携带分类枚举与可空的 `valid_at` / `invalid_at` 字段：

| 分类 | 含义 | 说明 |
| --- | --- | --- |
| `common_fact` | 共同事实 | 双方共享、长期稳定的客观事实，如家庭、工作、住址。 |
| `preference` | 偏好 | 喜欢或不喜欢的事物，如食物、话题、礼物取向。 |
| `taboo` | 禁忌 | 应避免提起的话题或雷区。 |
| `recent_state` | 近期状态 | 过期的临时状态，如"这个月在减肥""最近在加班"；按提取侧要求应带可推算的 `invalid_at`（本轮尚未实测模型遵守率）。 |
| `relationship_note` | 关系备注 | 无法归入以上分类的备注；用户可编辑、可自定义标签。 |

- 分类枚举 v1 只取上表少量值，用户可编辑；不建立复杂本体，不为枚举之外的自由语义建模。
- 有效期字段：`valid_at` 为该资料生效时间（缺省为采纳时间），区间为半开区间 `[valid_at, invalid_at)`；`invalid_at` 为失效时间。禁止默认永久保留是**提取侧要求**：期望模型为短期资料推算并填写 `invalid_at`，而不是存储层已实现的默认行为。
- 提取侧要求：短期信息仍入库，但必须带可推算的失效时间——`recent_state` 的临时状态、当天或次日的日程与写明期间的短期安排，都按来源 `occurred_at` 推算并填写 `invalid_at`；瞬时状态（如"还没吃饭"）的失效时间不得超过当天结束。只有真正长期有效的事实才留空，结束时间无法推算时也留空。来源时间缺失、naive 或无法核实时不推算、留空，不得猜测或用当前时间补。
- 相对日期以来源 `occurred_at` 自带的 UTC 偏移为"当地"参考推算"当天／次日／本周"；"周"仍按当地历周从周一零点到下一周一零点。提取侧只写字段，不做按固定天数套用失效时间的确定性兜底。
- 实现状态（2026-10-05）：以上短期有效期口径只落在提取提示词与 `EXTRACTION_SCHEMA` 的描述，以及评测用例的期望里；**模型遵守率尚未实测**，当前**没有**确定性兜底（不给近况套固定过期天数，也不在落库时改写 `invalid_at`）。因此短期记忆仍可能被永久保留，实际行为以模型评测结果为准。触发重新评估的条件与记录见 `.scratch/memory-extraction-accuracy/issues/11-release-ledger-and-next.md` 的"复核修订（2026-10-05 短期时效口径）"。
- 默认当前事实召回按 H2 规则使用分类与有效期，排除已过期资料。ADR-048 的明确历史导航只允许仍有合法来源的实际旧版本作为“历史／当前未核实”参考，不能把过期或已修正资料当作当前事实；真实删除后不得借历史保留。

### 记忆时间信息

候选、联系人记忆和本人记忆分别呈现以下时间，历史已完成操作也保留来源时间：

| 时间 | 来源与含义 |
| --- | --- |
| 来源聊天时间 | 同范围、活动来源支持的直接规范消息发送时间；多条引用形成范围。 |
| 保存／录入时间 | 该候选或记忆版本实际保存的时间；修正的新版本有自己的保存时间。 |
| 生效／失效时间 | 现有 `valid_at` / `invalid_at`，继续控制是否可检索。 |

来源时间由确定性代码依据实际引用计算，不由模型猜测。仅引用整个导入资料或本地
微信观察记录时，不以该资料的全部消息范围、导入时间或读取时间冒充直接证据日期。
来源消息缺少时间或无法核实时，界面明确显示未知或不完整。保存时间未知时也保留未知。
旧资料读取时投影已有时间，不改正文、采纳方式、版本身份或有效期。

来源聊天时间表示“当时说过”，不保证事件恰在当天发生；无失效日也不证明历史状态
今天仍成立。检索和生成须保留这些时间含义，不把过去的资产、工作或临时状态改成现状。

固定 main 的独立集成候选现已复用源票01的读取时派生：`current_status` 区分历史、当前未核实、当期区间和稳定资料，原因随生成快照保留；当期区间只核实原话时间适用范围，不认证现实真伪。旧临时状态无结束时间保持当前未核实，稳定事实采用有限确定性识别，不为所有资料统一设置寿命。原事实、采纳决定、有效期及来源不回写，合成验证与真实语义质量分开。

## 记忆自动维护机制（v1）

记忆由确定性门槛和版本化写入维护质量；满足门槛、且维度已放行的低风险候选可自动采纳，未放行维度与敏感／未知风险候选都安静待确认（见 ADR-002、ADR-024、ADR-036）：

第四门按 ADR-046 对相关维度做合取，现行集合为保守超集；每项须有当前有效依据并分别获批，日期优先键仅保留作兼容诊断，不能遮蔽其他项。生产指代／转述依据尚保持未知，不能用合成结构通过替代真实质量或完整字段能力。默认空表及语用、0.7、风险门不变。

1. **重复才信**：一次性或低置信表达只进入 `memory_candidate` 候选池；同一主题在多次独立场合出现后，才自动采纳为长期 `confirmed_memory`。单次情绪性表达不得直接升级为长期偏好。
2. **过期自动失效**：`confirmed_memory` 携带 `valid_at`/`invalid_at`；已过期资料不进入生成上下文，仅在 UI 显式展示为"已过期"供用户修正或删除。
3. **近期对话压过旧记忆**：检索与组装时，近期 `message` 优先于旧记忆；新旧冲突时以近期对话为准，旧记忆自动降权。
4. **联系人记忆目录**：系统从当前有效的 `confirmed_memory` 自动生成精简目录，主分类沿用 `common_fact`、`preference`、`taboo`、`recent_state`、`relationship_note`，子主题由系统自动整理。目录受严格预算约束，不包含全部记忆正文，也不成为新的事实源；召回第一期只保留版本复验职责。
5. **按请求自动选择**：每次候选回复以当前正文（待回复消息或改写草稿）为 query，对有效联系人与本人记忆做确定性中文词法评分：覆盖率低于 `0.15` 不注入；联系人记忆最多 5 条且合计不超过 600 字符，本人记忆最多 3 条且合计不超过 240 字符，两类独立计费；排序依次按相关性、`manual` 优先、置信度、有效期与稳定标识。阈值与预算为模块常量，标定见 `docs/memory-recall-evaluation-baseline.md`；用户不需要设置固定、排除或其他记忆模式。
6. **修正与重建**：用户可以查看、修正或删除关系记忆。单条变化优先增量更新目录；批量变化、版本不一致或更新失败时合并为重建任务，旧目录在新目录验证成功前继续保留。

### 纠错保护的集成状态

[正式集成02](../../.scratch/memory-skill-integration-preparation/issues/02-correction-and-erasure.md)在独立集成候选中接入人工纠错与否决保护，尚未合入main。相同规范消息上的旧证据不能因正文、分类、主题或主体改写而重新自动采纳；新增来源引用不等于新增规范消息。真正新消息只产生带原人工决定的待确认差异，确认时在范围锁事务中复验完整参与窗口、来源世代和完整决定标识。自动替代只作用于原先确切的自动版本，新版本写入与旧版本失效同事务提交，不追随新人工叶版本。

此状态只说明合成HTTP、PostgreSQL和React验证到的工程行为；默认维度放行表保持为空，真实模型语义质量与实际App/微信未据此验收。事件扩展、概览、资料升级和Skill生命周期仍按正式集成任务图接续。

### 联系人记忆目录最小契约

v1 逻辑上每位联系人只有一份当前 `contact_memory_index`。具体使用单表还是关联表留到实现时确定，但必须包含：

- `owner_id + contact_id`：目录所属范围。
- `built_from_memory_revision`：生成目录时对应的联系人记忆版本。
- `status`、`created_at`、`updated_at`：目录是否可用及其生成时间。
- `topics`：自动生成的主题目录；每项只含 `category`、一行 `topic_summary` 和对应的 `memory_ids`。
- 目录最多保留少量主题入口（v1 建议上限 20 个）；它不复制记忆正文，命中后按 `memory_ids` 重新读取事实。

每位联系人的关系记忆集合维护单调递增的 `memory_revision`。新增、修正、删除、重新分类或修改有效期时必须递增；版本号只用于检测目录是否过期，不要求每次变化都立即完整重建。只有 `status` 可用且 `built_from_memory_revision` 等于当前 `memory_revision` 的目录才参与版本复验，否则标记待更新并由合并后的任务处理。

召回第一期的候选直接来自 L1 的当前有效记忆，由正文词法评分选择；`topic_summary` 仍只是导航提示，不是关系事实，也不再是选择的必经路径。任何进入回复上下文的记忆都必须重新校验 `owner_id + contact_id`（本人记忆只校验 `owner_id`）、状态和有效期；目录版本通过 `memory_revision` 快照在生成前后复验。本人记忆由 owner 范围单独选择，不复制到每位联系人的目录中。

ADR-048 的概览导航继续复用上述检索接口和词法排序；请求指定的底层 ID 有界，
历史模式不能变成全历史扫描。快照保存生成时的导航修订及全部实际参与依赖，外部
回执只描述模型可见的最终输入。缺失或 null 的旧回执不补成“已查空”或“已查到”，
原版本证明缺失也不能借新来源恢复；实际底层读取仍是正文和来源的权威。

## 隔离与查询约束

任何联系人范围对象都应至少含有：

```text
owner_id
contact_id
created_at
updated_at
status
```

在数据访问层，联系人范围查询的输入必须同时提供 `owner_id` 和 `contact_id`。不允许存在“按昵称搜索所有资料后再选择”的内部便利查询；跨联系人的汇总视图也只能返回非私密、用户主动请求的聚合结果。

`message` 必须显式冗余 `owner_id + contact_id`，不得仅通过 `source_document` 或 `session_capture` 间接推导；检索过滤必须基于 `message` 自身携带的隔离键，而不是依赖来源关联。

`conversation_binding` 的首次建立、display name 改名映射和备用视觉指纹变化必须经用户确认。已确认且唯一的 display name + 选中会话元数据映射可以自动定位到外部 `talker`/`username`；无法区分时才使用视觉指纹，仍没有唯一匹配时必须暂停该次自动定位，不得据此猜测消息归属。CLI 后台读取独立依赖已确认的稳定绑定；前台定位失败不阻塞已有绑定的读取（ADR-030）。

`session_capture` 是联系人范围对象中唯一允许不携带 `contact_id` 的豁免：它存在一个“未归属临时态”，此时仅含 `owner_id`、不含 `contact_id`。该状态只用于前台 display name 观察和归属判断，必须满足以下规则：

- 未归属的 `session_capture` 不得产生任何 `message`，也不得参与检索。
- 归属成功的 `session_capture` 必须冗余 `owner_id + contact_id` 并关联已确认的 `conversation_binding`，此后只作为观察证据，不产生 CLI 消息正文。
- 归属失败（匹配不唯一、绑定失效、display name 或头像不可读、视觉指纹不一致）时，该批次必须丢弃或标记未归属，且必须按临时数据在明确时间点清理，不能静默累积或降级为“默认属于某人”。

## 来源与删除语义

- 每条 `message` 必须能定位到 `source_document` 中的原始片段或原始文件引用，或者定位到 `local_wechat_observation` 的已绑定会话、CLI 版本、读取时间、外部消息 ID 与游标；本地 CLI 来源不要求保存全量导出文件。
- 每条候选和已确认资料应保存支持它的消息或来源列表，不能只保存一个无法解释的摘要。
- 删除一个 `source_document` 时，必须清除其规范化消息、仅由它支持的候选资料、索引和缓存。
- 删除一个已归属的 `session_capture` 或 `local_wechat_observation`，或解除其会话绑定时，必须按相同语义清除其规范化消息、派生候选资料、索引和缓存。
- 未归属的 `session_capture` 不产生 `message` 或任何派生资料；其临时数据在归属确认超时或用户停止同步时一并清除。
- 只由被删除来源支持的 `confirmed_memory` 无条件级联删除，不存在"默认"或"视情况"保留的口子。用户若想保留内容，唯一路径是主动执行"另存为不依赖该来源的手动资料"：该操作创建一条与来源无关的新 `confirmed_memory`（来源证据列表置空、候选来源链字段置空），并切断与原来源的依赖，此后原来源的删除不再影响它。
- 去重后的 `message` 是一条规范化实体，可以由多个来源引用共同支持；同一稳定消息 ID 不产生重复消息。删除一个来源时只移除该来源引用，仍有其他有效来源时保留消息；所有来源引用都删除后，才删除消息及仅由它支持的派生资料。
- 一条已确认资料有多个来源时，删除其中之一只移除该证据；没有剩余证据时按无条件级联删除规则失效，除非用户已执行"另存为手动资料"。
- `deleted` 只表示来源及其派生数据已经清除且通过不可检索验证；删除请求、执行中和失败必须使用不同状态，不能把软隐藏或待处理记录标成 `deleted`。
- 导错联系人时不得直接修改来源或消息的 `contact_id`；必须删除错误来源及派生资料，再由用户重新选择联系人并导入。
- 已删除文件被用户再次主动选择时，应重新预览、重新确认并创建新的来源记录，不能依据文件哈希静默恢复旧数据。
- 删除联系人时必须清除其来源、消息、关系资料、回复候选和会话绑定。完成后只允许保留删除时间、操作结果和内部操作编号组成的最小删除凭证，不保留联系人名称、来源文件名、文件哈希或聊天内容。
- 08 的联系人物理清理适配入口先按 contact→owner 锁清理该联系人偏好的完整派生闭包，再去除无正文墓碑的联系人身份并物理清除联系人；保留owner级失效操作身份，拒绝旧全局保存操作重放。全局偏好曾用于其他联系人而后收窄范围的历史依赖同样清除。偏好外键使用 RESTRICT，避免直接 SQL 绕过闭包；当前没有整体联系人删除产品入口，该适配器不代表此产品流程已经交付。
