# 核心流程

> 状态：已采纳的流程边界；UI 形态和 API 路径尚未设计。

## 1. 导入与关系资料采纳

```text
用户手动选择联系人
  -> 创建 source_document 和 background_task（type=import）
  -> 解析为规范化 message
  -> 保存来源定位和任务状态
  -> 异步提取 memory_candidate 并按规则自动采纳（带来源、标记 auto、可撤销）
  -> 用户可随时查看、修正、撤销或删除已采纳资料
```

规则：一次导入只属于一个联系人。检测到多位联系人混杂、说话人不能可靠区分或文件已损坏时，任务必须失败或要求拆分，不能静默归并。

OCR、转写、时间线提取和长历史冲突检查是未来可选的后台专职处理；它们都向主流程返回带来源的结构化结果，不能直接写入已采纳资料。关系提取的触发点、输入窗口、证据契约与全自动采纳见 ADR-002。提取在后台异步执行：任务空闲时生成、跳过活跃或短暂会话、不与回复生成抢占额度。

## 2. Mac 微信前台会话增量同步

```text
用户首次确认“当前微信会话 -> 联系人”的绑定，并开启同步
  -> 微信在前台且该会话可见时，检测聊天区域画面变化
  -> 仅捕获聊天区域的最小画面，进行本地 OCR
  -> 解析说话人、顺序和可用时间线索
  -> 归属校验：确认该批次可唯一归属到已确认的绑定
  -> 与该绑定下已有 message 去重
  -> 仅把新增消息写入该联系人的原始消息层
```

同步只覆盖用户正在查看的一对一会话，不会读取其他 App、后台微信、未打开的会话，也不会切换会话或滚动历史。无法确认会话绑定、OCR 无法可靠区分说话人或消息顺序时，必须暂停写入并要求用户确认。

归属校验失败（绑定失效、匹配不唯一、说话人或消息顺序无法可靠区分）时，该批次 `session_capture` 保持未归属临时态：不写入任何联系人的 `message` 层，不参与检索，并在确认超时或用户停止同步时清除。必须经用户重新确认绑定后，才能恢复写入。

同步得到的是原始消息，不是长期关系事实。后续模型据此产生 `memory_candidate`，并按 ADR-002 全自动采纳写入 `confirmed_memory`（带来源、标记 auto、可撤销）。

### 2.1 同步连续性与用户补录

前台 OCR 不能获知用户在手机或未打开 Mac 微信期间的消息。恢复观察时，系统必须以已有消息与新画面中识别出的重叠消息作为连续性锚点；不能仅凭“又识别到新消息”宣称历史完整。

- 有可靠重叠锚点时，新增消息标记为 `continuous` 并正常去重写入。
- 没有可靠锚点时，已识别的新消息可以按来源写入，但该段会话覆盖状态标记为 `possible_gap`；回复上下文和 UI 不得把此状态表述为完整历史。
- 用户可明确启动“补录此段对话”：用户自己在已绑定、前台可见的微信会话中滚动，应用只持续观察聊天区域、OCR 与去重，不点击、不滚动、不切换会话。补录重新连接到已存锚点后标记为 `backfilled`。
- 用户也可把缺失片段作为单联系人文本导入；该输入创建普通 `source_document`，沿用来源追踪和级联删除规则。
- OCR 未可靠识别原始发送时间时，必须保留时间未知或低置信状态，不能以采集时间伪装为消息发生时间。

## 3. 候选回复生成

```text
用户选择联系人并输入当前文字消息
  -> 组装五轨上下文（硬规则 + 常驻卡 + 按需检索 + 近期对话 + 风格样本）
  -> 显示本次将使用的上下文范围
  -> 生成 1-3 条 reply_candidate（每条带依据引用）
  -> 用户选择、编辑、手动发送
```

v1 的检索应可解释：先用联系人过滤，再用时间、关键词、资料类型、采纳状态和显式有效期排序。每个候选应能回看"本次用了哪些近期消息和已采纳资料"，但不必把完整历史给模型。

### 3.0 上下文组装层级（v1）

生成请求的上下文按"五轨"组装，历史本身永不进入提示词，每轨都只取少量：

1. **轨一 硬规则（代码层，必加载）**：不自动发送、联系人隔离、高风险标记。确定性代码规则，不是记忆提示词（见 3.4）。
2. **轨二 常驻卡（固定加载）**：`owner_preference`（全局层）+ 该联系人标记 `carry` 的常驻事实（5-10 条），每次生成必带，不依赖检索。
3. **轨三 按需检索**：根据当前消息，按 3.1 排序检索相关旧 `message` 与 `confirmed_memory`。
4. **轨四 近期对话（最强）**：该联系人的近期 `message`，是当前语境的最直接依据。
5. **轨五 风格样本（最弱）**：最多 5 条低权重参考（见 3.6）。

组装原则：越靠内越强越新，越靠外越弱越旧；冲突时近期对话压过旧记忆；超预算从轨五起向外截断。记忆是辅助回忆层，不是规则——安全规则只放轨一代码层，不放记忆提示词。

### 3.1 检索排序规则（v1）

联系人过滤后，按以下优先级降序排序；键相同则落到下一键比较：

1. **采纳状态**：`confirmed_memory` 优先于 `memory_candidate`；`pending` 候选仅用于展示线索，不进入生成上下文。
2. **显式有效期**：`valid_at <= now <= invalid_at` 的资料优先；无有效期的资料视为长期有效，排在未过期之后、已过期之前。
3. **时间**：资料创建或消息发送时间更近者优先。
4. **资料类型**：共同事实与禁忌优先于偏好与一般备注（分类见 `01-domain-data.md`）。
5. **关键词**：与当前消息的文本重叠或语义相关度更高者优先。

### 3.2 上下文预算（v1，写入生成接口入参约束）

生成请求的上下文是硬性预算，超出即截断，不允许把完整历史塞入提示词：

- **近期消息**：最多 50 条，且合计不超过 8k token；超出按时间取最近部分。
- **已确认资料**：最多 20 条。
- **常驻卡**：轨二固定 5-10 条（含 `owner_preference` 与联系人 `carry` 条目）。
- **风格样本**：最多 5 条，且只作低权重参考（见第 4 节）。
- **截断策略**：按 3.1 的排序从队尾截断，并在生成接口返回本次实际使用的引用清单，用户可回看"用了哪些、丢了哪些"。

### 3.3 检索缺口处理（降级与明示）

检索是单次静态查询；结果为空或低于阈值时，必须放宽时间窗口/关键词再查一次，并在结果中标注“降级”。仍为空时，UI 明示“未检索到相关记忆”，区分“没查到”与“没资料”。降级率作为是否引入向量检索的前置观测数据（见 M10）。

### 3.4 高风险内容交互

高风险内容（转账、验证码、地址、借款、承诺、见面安排、关系冲突）由独立适配层的确定性规则标记，不混入生成提示词。命中时仍可检索并生成，但生成前必须展示核实提醒；判定规则放独立模块，便于更新和测试。

注意：风险字段只影响生成环节的核实提醒，不阻塞记忆的自动写入（见 ADR-002 全自动采纳）。安全保险在发送环节：候选回复带依据引用，由用户选择并手动发送。

### 3.5 引用展示契约

每条候选回复必须携带依据引用：`retrieval_segment`/`source_span` 标识、入选原因、排序分数与状态（消息/已采纳资料/风格样本）。用户可回看"为什么用了这些上下文"，便于发现误导入或过期资料。

### 3.6 风格样本权重

v1 风格样本送入提示词但权重受限：最多 5 条、明确标注为“参考的表达样本”，不参与事实推断，不覆盖当前语境判断。若后续发现干扰生成，降为仅离线参考。

检索接口入参必须携带 `owner_id + contact_id`、当前消息、limit 与时间窗口；返回携带引用标识、采纳状态、有效期、排序分数与检索器版本。检索器版本用于复现与审计"本次为何返回这些结果"。

高风险内容，包括转账、验证码、地址、借款、承诺、见面安排和关系冲突，必须提醒用户自行核实；系统既不能自动发送，也不能替用户做最终决定。

## 4. 表达样本沉淀

```text
用户完成编辑并自行发送
  -> 用户主动选择“作为表达样本保存”
  -> 保存最终文本与对应联系人
  -> 后续仅在该联系人范围内作为低权重风格参考
```

产品不能从第三方聊天渠道自动获知发送结果，也不能把所有生成候选或复制动作自动归纳为长期偏好。

## 5. 删除与修正

```text
用户删除来源、关系资料或联系人
  -> 创建 background_task（type=delete，scope 限定 account/contact/source）
  -> 计算消息、候选、确认资料、索引和缓存的影响范围
  -> 执行级联删除或失效
  -> 重新建立受影响联系人的检索索引
  -> 展示完成状态与未能删除的原因
```

修正关系资料应保留修正时间和原始来源关联，但不需要长期保存已被用户要求删除的私密正文。删除和重试过程应显示进度、失败原因和结果，不能在后台静默失败。

删除来源时，其规范化 `message` 无条件级联删除；仅由该来源支持的已确认资料无条件级联删除。用户若想保留某条内容，必须先执行"另存为不依赖该来源的手动资料"（切断与原来源依赖），再删除来源。删除流程须覆盖跨来源场景：一条已确认资料被多个来源支持时，删除其中之一只移除该证据，删除全部来源后资料才失效。

## 6. 后台任务边界

后台任务只处理用户已经触发的资料：导入、解析、规范化、索引、候选提取、删除和重建。已启用的前台会话同步可在画面变化时运行本地 OCR 和去重，但它不是全局后台抓取。关系提取按 ADR-002 的调度策略异步执行：任务空闲时生成、跳过活跃或短暂会话、不与回复生成抢占额度。v1 可使用同一应用内的任务表和 worker；只有并发量、可靠重试或部署规模成为真实问题时，再引入独立队列和 worker 服务。

不在 v1 实现：读取非前台聊天应用、全量后台同步所有会话、自动切换或滚动微信会话、自动发送、自治循环或为短文本回复强行调用多 Agent。
