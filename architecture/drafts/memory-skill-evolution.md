## 目标与阅读方式

让 NotAlone 在用户授权的资料范围内持续整理记忆，从回复经验中提出可复用的表达方法，并由用户集中审核后使用。设计持续参考腾讯 TencentDB Agent Memory、Hermes 和其他有一手证据的方案，逐项说明借鉴机制、产品适配和验证结果。

下文按 **8 个完整功能**组织。Q1～Q19 是这组讨论中的问题编号，不是 19 个开发任务，也不沿用其他草图的 Q 编号。一个完整功能可以包含多个交付阶段；正式任务要在规格明确后按完整、可验证的行为拆分。

## 8 个完整功能

| 完整功能 | 用户最终得到什么 | 对应讨论 |
| --- | --- | --- |
| 1. 记忆持续更新 | 系统保留历史、识别新旧变化、去重，并分清计划、约定和已发生事件。 | Q1、Q3、Q5 |
| 2. 记忆纠错 | 用户纠正或否决后，旧错误不因换个说法重新出现；依赖旧依据的候选可识别变化。 | Q7、Q9 |
| 3. 长期概览 | 能查看与一位联系人的关系变化，以及用户本人的稳定事实和偏好，并追溯依据。 | Q2、Q19 |
| 4. 检索辅助回复 | 回复能找到同一联系人内的相关资料，必要时有界补查原话；语义检索经比较评估后再启用。 | Q4、Q10 |
| 5. 明确表达偏好 | 用户明确要求长期保持的表达偏好可保存；单次要求仍只作用于当前回复。 | Q6a |
| 6. 自动学习 Skill | 系统自动发现可复用的方法，提出新建、更新或合并草稿，展示对照例子，集中审核后发布。 | Q6b、Q11a、Q11b、Q14、Q15、Q18 |
| 7. 根据反馈调整 Skill | 能分清用户是在改当前回复、某条方法，还是整个 Skill，并在明确的联系人和场景范围内调整。 | Q16、Q17 |
| 8. 现有资料升级 | 已有资料按批次比较新旧结果，保留用户确认、纠正和否决，避免升级覆盖人工决定。 | Q8 |

Q12 是交付顺序，Q13 是整体验收要求，适用于上述功能，不单独算作产品功能。

## 1. 记忆持续更新

**已确认：**

- 过去成立的状态保留为带来源和时间的历史。没有新证据时，当前状态可以是未知或未经核实；不能仅因缺少结束时间就认定它一直成立。（Q1）
- 重复资料自动去重。来源明确、通过质量门槛的低风险变化可以自动更新，必须标记 `auto`、保留版本且可撤销；关系敏感、依据模糊或风险较高的变化交给用户确认。（Q3）
- 计划、约定和已经发生的事件分开保存。“约好下周见面”不等于“已经见过面”。同类事件发生在不同时间时可以是不同事件；窗口重叠提取出的同一次事件应合并证据。（Q5）

这里确认的是目标行为，不是扩大当前自动采纳权限。现行来源核验、风险门槛和按维度放行继续有效；未获放行的维度不能因本草图变成自动采纳。

**待设计：**历史状态、当前核实状态和错误失效的表示；新旧关系的判定与来源绑定；合并和替代时的原子更新及删除依赖。

## 2. 记忆纠错

**已确认：**

- 被纠正或否决的旧结论，不能仅凭相同旧证据、换一种表述又被提出或采纳。旧记录可以保留供追溯；确有新证据时，可以提出新的待确认结论。（Q7）
- 历史回复可以保留，但依据发生变化时应显示这一点。再次使用时复验依据，必要时生成新候选；来源删除仍按删除规则处理，不能借“保留历史”留下应删除的内容。（Q9）

**待设计：**如何记录用户否决针对的含义与证据，如何区分重复错误和真正的新证据，以及哪些历史候选需要失效提示或清理。

## 3. 长期概览

**已确认：**

- 分别维护与一位联系人的关系变化概览，以及用户本人的稳定事实、偏好概览。条目能回到来源；推测出的性格、动机不能作为事实混入。（Q2）
- 后台概览以有依据的经历和变化为主。深入的性格、动机或关系判断由用户明确请求后独立开展，并展示不确定性和依据。（Q19）

Q19 确认的是分析触发边界；独立分析入口和完整分析功能是否纳入本轮交付，需要正式规格另定。现有主题目录主要用于导航和版本复验，不能直接宣称已经提供上述完整概览。

**待设计：**概览的来源依赖、事实与推断的展示、更新和删除，以及如何以有界资料支持回复。

## 4. 检索辅助回复

**已确认：**

- 保留关键词检索作为基线，评估语义检索作为补充。只有对照结果证明减少遗漏且没有不可接受的错误匹配后，才考虑启用；具体模型、部署和向量方案尚未选择。（Q4、Q10）
- 检索不足时，可以在已授权的同一联系人资料内有界补查原始消息。返回结果保留来源、时间和状态，生成前复验。（Q4）

现行第一期仍采用确定性中文词法评分。语义检索的评估独立推进，不能把本草图当作启用决定。

**待设计：**比较数据、漏召回和误召回的指标、合格门槛、出站范围、失效与删除路径。真实资料和真实模型调用范围另行确定。

## 5. 明确表达偏好

**已确认：**先支持用户明确要求长期保存的表达偏好；当前回复的意图和要求优先。（Q6a）自动从表达样本推断长期风格不纳入本阶段，未来是否开展另行确定。

用户说“这次简短一点”，不能静默转成长期偏好。表达样本继续按现行规则由用户主动保存；自动提出 Skill 草稿不等于自动保存表达样本。

**待设计：**长期偏好的保存、查看、修改、删除及与当前意图的冲突处理。

## 6. 自动学习 Skill

这里的“方法”是可重复使用的回复做法，例如“先回应对方的感受，再说明情况”，或“提出邀请时给对方容易拒绝的余地”。它影响如何表达；联系人事实、对方的心理动机以及一次性的回复要求不因此成为通用方法。

**已确认的完整流程：**

1. **自动发现材料。**从助手讨论、用户修改和纠正，以及同一已授权联系人内与任务相关的聊天和后续反应中选择材料。用户无需逐条手工挑选；这不扩大到任意文件、网络资料或其他联系人的聊天。（Q11a）
2. **判断是否值得学习。**明确纠正优先处理，普通经验按增量批次整理。一次处理可以没有新 Skill；优先检查能否改进现有方法，避免重复创建。（Q11b）
3. **提出草稿和范围。**生成新建、更新或合并建议，展示来源、方法、场景和适用范围。系统区分通用方法与依赖特定联系人或场景的做法，解释范围建议，由用户在审核时确认。（Q6b、Q14、Q15）
4. **展示对照。**用同一输入对比旧版本或不用该 Skill 与新版本的回复，检查是否符合当前意图、有没有编造事实或承诺、范围是否合适。样例有帮助不等于已证明所有真实场景都有效。（Q18）
5. **集中审核并发布。**新建、更新和合并草稿进入统一的“待审核”入口，轻量提醒，用户可以接受、修改、拒绝或暂留。审核通过前，新草稿不用于回复；更新草稿不替换现有生效版本。合并替代旧条目也必须先获确认。（Q6b、Q15，以及集中审核决定）

面向更广范围的 Skill 必须清除联系人身份、私人细节和个别人的事实。去掉姓名只是必要处理之一，不能据此认定方法通用。发布版本保留版本关系和来源，允许回滚；回滚不得恢复已删除来源或内容。

**待设计：**草稿、审核与发布的数据和状态契约，材料选择预算，范围确认方式，方法定位，版本冲突、合并和来源删除处理。以上流程尚未实现。

## 7. 根据反馈调整 Skill

**已确认：**（Q16、Q17）

| 用户反馈 | 系统应做什么 |
| --- | --- |
| “以后对这个人别再用这个方法”且对象明确 | 立即在明确范围内停用对应方法，不等待集中审核。 |
| “这句太生硬了” | 先改当前回复；有可复用改进时提出草稿，不直接停用整个 Skill。 |
| 对方没回复、回复慢或变冷淡 | 只作为有限的观察材料，不直接认定方法无效。 |
| 没说清是在改哪条方法或什么范围 | 先处理当前回复；需要长期修改时，再澄清目标和范围。 |

调整应落在用户明确表达的最小对象和范围：当前回复、Skill 内的一条方法，或整个 Skill；同时分清联系人和场景。已经明确的指令直接执行，不重复询问。永久修订走审核和版本发布；明确停用立即生效，两者不能混为一谈。

**待设计：**稳定定位某条方法的接口，联系人和场景范围的表达，局部停用与整个 Skill 启用状态的关系，以及撤销、合并后定位和版本复验。

## 8. 现有资料升级

**已确认：**新规则作用于已有资料时，按批次展示新旧差异，保留人工确认、纠正和否决，不静默覆盖。（Q8）

**待设计：**重处理的资料和时间范围、模型调用预算、恢复和回滚、人工决定保护、来源删除后的清理。普通任务水位续跑不等于全面升级。本草图没有授权立即重跑旧资料、回填新字段或重新采纳。

## 第三方机制如何参考

参考机制与选用框架分别判断。每个完整功能都应先核对一手实现，说明适配联系人隔离、人工发送和删除要求后是否仍值得采用，再用验证结果支持决定。

| 参考项目 | 可以借鉴的机制 | NotAlone 需要明确的适配 |
| --- | --- | --- |
| [腾讯 TencentDB Agent Memory](https://github.com/TencentCloud/TencentDB-Agent-Memory) | 分层整理原始会话与记忆；去重；从任务经验生成 Skill，并优先复用或更新。 | 分层不能把推断自动升成事实；团队、用户或 Agent 范围不能替代联系人范围；自动学习需要独立草稿、用户审核和来源删除依赖。 |
| [Hermes](https://github.com/NousResearch/hermes-agent/blob/main/agent/background_review.py) | 后台识别纠错和可复用经验；由模型判断是否有内容值得保存，可以不产生新方法。 | 学习材料限于授权范围；写入或启用长期方法前集中审核，不能直接照搬默认写入策略。 |
| [DSH 官方架构](https://deepseek-harness.github.io/deepseek-harness/en/reference/) | 插件组合、运行循环、SDK 和会话机制，作为可替换执行层的候选。 | 不接管业务事实、权限、审核和删除；必须验证裁剪后的能力与现有路线相比是否有收益。 |

腾讯机制的代码核对基于 `badbd21` 快照：`MemoryCore/src/utils/pipeline-factory.ts`、`pipeline-manager.ts`、`MemoryCore/src/core/record/l1-dedup.ts`、`MemoryCore/src/core/skill/conversation-add/add-handler.ts`、`skill/prompts/skill-review-prompt.ts` 和 `skill/skill-tools.ts`。Skill 内容评判不能等同于 NotAlone 的用户发布审核；第三方支持 DSH 接入，也不能单独证明 DSH 更适合本产品。

## DSH 是否适合作为基座

### 当前结论

DSH 指 DeepSeek Harness。**现已搁置选型，尚未选择或切换，也不作为本轮任务的前置。**当前候选回复仍是 `LangChain create_agent + Deep Agents SkillsMiddleware`；DSH 是未来可重新讨论的备选。

NotAlone 继续负责联系人身份、`owner_id + contact_id` 隔离、来源和时间、候选校验、审核、任务状态、删除和人工发送。PostgreSQL 继续保存权威业务状态；运行时会话或日志不能代替它。

### 已核对的接口事实

- [Python SDK](https://github.com/deepseek-ai/deepseek-harness/blob/master/python/sdk/README.md) 通过子进程与 Harness 通信；原生插件采用 TypeScript/JavaScript。Python 领域服务需要受控桥接，不能当成同进程直接替换。
- [`sdk-minimal`](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/bundle/sdk-minimal/README.md) 的默认能力仍包括 Shell 等；“minimal”不等于 NotAlone 的只读运行配置。它也不默认提供 Skills、后台任务和压缩等完整组合。
- [会话日志插件](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/session/session-log-deepseek/README.md) 有额外日志上传能力；不能默认带入敏感业务范围。关闭上传也不等于删除已有本地或远端日志。
- 持久化、恢复和自定义 Tool 需要核对整个生命周期。恢复时必须重新验证权限、来源、版本和删除状态，不能因存在 session resume 就宣称业务恢复安全。

这些是接口和默认行为的资料证据，不是 NotAlone 集成验证；具体版本和配置要在比较前固定。

### 建议的公平比较方案（待设计定稿，尚未执行）

使用相同的合成材料和模型配置，比较现有路线与裁剪后的 DSH：

1. 自动选择材料并生成一个 Skill 草稿。
2. 用同一输入生成旧版本或无 Skill 与新草稿的对照回复。
3. 草稿落库为待审核；进程重启后仍可查看和审核。
4. 审核前删除来源，验证草稿不能继续引用或发布无效内容。
5. 验证不同 Owner、联系人和场景不会串用；超时、重试、重复提交不产生重复发布。

比较接入与维护成本、失败恢复、范围和删除、响应时间及调用量。先写验收条件，再决定是否需要执行原型；真实模型调用、出站和真实资料范围不由保存草图自动授权。

**初步接口建议：**等待审核属于 NotAlone 的持久业务状态，AI 生成草稿后可以结束；用户日后通过审核时，确定性代码复验来源、范围和版本后发布。需要修改内容时再发起新一轮生成。这样是否足以满足恢复需求，应与持续运行方案比较后确定，不提前认定必须采用长时间暂停的 Agent。

## 交付顺序与验收

**已确认交付顺序（Q12）：**

1. 先完善记忆时效、新旧更新、纠错和防止重复错误。
2. 再完善事件与约定、关系和本人概览，并接入回复。
3. 再推进 Skill 自动学习、集中审核、版本和使用反馈。

语义检索比较独立开展，达标后才考虑启用。表达偏好、已有资料升级及独立分析的实际交付范围和依赖，在正式规格中明确。

**已确认整体验收（Q13）：**从原话到提取、新旧合并、概览、回复实际引用，再到用户纠错和来源删除，检查完整链路。代码和合成测试、真实模型质量、最终原生 App 与渠道集成分别报告，不能互相代替。真实资料范围和调用预算在执行前另定。

目前已按[仓库工作流](../../docs/agents/workflow.md)形成正式规格并发布15张已确认任务，下一阶段是按票实现。沿用现有基座，测试从公开 HTTP、隔离 PostgreSQL 与当前 React 控制器验证完整用户行为，DSH 不再阻塞此路径。
