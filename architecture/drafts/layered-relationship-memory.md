## 用户目标

在已有带来源的记忆之上，自动维护可阅读的主题资料和简短长期背景，并在回复时按明确规则使用。用户无需逐条组织文档，但能查看依据、修正资料和删除内容。

本轮同时设计 L2 与 L3。两层保留到底层记忆及原始来源的追溯关系，整理结果不成为新的事实源。回复策略继续由既有 Skill 生命周期管理。

## 已确认的产品决定

| 编号 | 决定 | 具体含义 |
| --- | --- | --- |
| Q1 | L2 按持续主题整理。 | 例如工作与项目、沟通偏好、重要经历；新资料补入相关主题，具体事件及时间变化保留在文档中。这里的“场景”不同于回复 Skill 的聊天场景。 |
| Q2 | L3 第一版以有依据的长期背景为主。 | 归纳明确事实、偏好和重要关系背景，保留来源与不确定性；自动性格、动机推断与回复策略另行讨论。延续 ADR-048 的概览边界。 |
| Q3 | 联系人与本人两种范围都支持，分别管理。 | 联系人资料始终按 `owner_id + contact_id` 隔离；本人资料只从合法本人记忆整理，不为整理画像自动跨联系人查询聊天。 |
| Q4 | 两层只整理已采纳且来源有效的记忆，包括手动录入。 | 待确认候选继续使用既有独立未确认参考轨，不进入 L2/L3。当前默认自动采纳放行表为空，新候选通常需确认后才进入长期整理。 |
| Q5 | L3 背景、L2 目录及按需正文，与 L1 动态检索组合使用。 | 开启关系语境后，把当前联系人及本人的简短 L3 作为系统上下文中的背景资料，先提供 L2 目录，需要时再读正文。各部分有独立预算，资料不成为回复指令。此项修订见 ADR-067。 |
| Q6 | 首次覆盖已有合格记忆，之后随变化增量更新。 | 短时间多次变化合成批次，后台更新相关 L2/L3；前台回复优先，用户也可手动刷新。不是逐条聊天触发两次全量模型调用。 |
| Q7 | 校验通过的整理结果自动生效，标记“系统整理”，可以撤回。 | 不逐篇要求人工审核；歧义或校验失败的版本不使用，也不借整理采纳或修改底层记忆。 |
| Q8 | 区分事实纠错与整理纠错。 | 事实错误修改关联底层记忆；底层正确而总结有误则反馈并重新整理。补充新背景通过手动新增记忆，不维护固定人工正文段落。 |
| Q9 | L2/L3 不可用时回退既有检索，继续回复。 | 更新中、校验失败或失效的受影响资料暂不加载；只用仍合法 L1 和当前聊天，并展示整理状态。删除或纠错后的旧摘要不继续使用。 |
| Q10 | 在现有资料页提供入口，并明确区分停用与删除。 | 使用“主题资料”“长期背景”名称。首次选择联系人范围及是否包含本人后开启；停用停止整理和回复加载、仍可查看合法结果；删除整理结果清除生成正文及历史版本并关闭该范围，底层记忆另行管理，重新开启才生成。 |

领域术语的权威定义见 [CONTEXT.md](../../CONTEXT.md) 的“场景文档”和“长期画像”。现有“长期概览”仍是上位概念，不将底层本人记忆改名为画像。

## 现行约束与待复审点

- [ADR-048](../adr/048-memory-skill-evolution-lifecycle.md)允许可追溯概览，不自动开展深入性格或动机分析。Q2 沿用此边界。
- [ADR-011](../adr/011-automatic-relationship-memory-index.md)原定不固定全量加载普通联系人／本人记忆；[ADR-028](../adr/028-lexical-memory-recall-phase-1.md)规定生产词法检索和独立预算。用户在 Q5 选择 L3 背景及 L2 目录的分层加载，[ADR-067](../adr/067-layered-scenario-and-profile-context.md)为此提供明确的局部修订；L1 词法检索和原预算保持，新增层不能挤占或绕过它们。
- [现行领域数据](../current/domain-data.md)、[核心流程](../current/core-flows.md)和[隐私删除](../current/privacy-deletion.md)将当前概览限定为无正文投影与底层导航。新增生成正文应使用明确的新对象及删除依赖，不直接向原投影追加正文。
- 来源删除、人工纠错、范围隔离、时间状态和迟到结果复验继续适用。L2/L3 的正文、版本、缓存、任务产物及回复使用副本均须进入相应生命周期。
- 当前默认自动采纳维度放行集合仍为空，见[默认值](../../backend/src/notalone/memory_extraction/dimensions.py)与[放行台账](../../docs/memory-adoption-dimension-release-ledger.md)。选择只整理已采纳记忆，意味着新的待确认候选不会自动进入 L2/L3。

## 完整链路

下面是已整体确认的工程方向；具体 schema、接口标识和预算数值在正式实现规格与评测中细化，不以候选名称或未标定数值冒充已实现合同。

```text
同范围的已采纳记忆／手动资料
  → 捕获有限输入及版本、来源依赖
  → 整理受影响的 L2 主题文档
  → 以当前 L2 和对应底层依据生成简短 L3
  → 校验结构、引用、时间含义、忠实度及输入是否仍有效
  → 通过后原子保存正文版本和依赖，标记“系统整理”并自动生效

一次开启关系语境的回复
  → 固定联系人及本次资料版本
  → 加载本人／当前联系人 L3 背景和 L2 目录
  → 原有 L1 动态检索
  → 需要时通过独立只读 Tool 读取目录中的 L2 正文
  → 记录实际使用的正文、版本和来源
  → 生成前后、最终提交时复验
```

### 生成与更新

1. 复用合法概览读取边界，逐项筛出当前 scope 内可证明来历的已采纳条目。概览读取成功不等于全部 entries 可参与：`manual_entry` 和 `source_supported` 才可进入，`unknown` 不以当前叶或后续人工操作补签旧证明。合法历史与当前分开表示，已纠错、否决、删除和不合法版本不能借历史重现。首次整理仅使用合格记忆，不重提全部历史聊天或升级旧证据。
2. 由有限输入中的事实决定主题归组；同一主题保持稳定身份，名称变更不代表新联系人或新事实。首轮建议系统自动组织主题，减少用户分类负担；主题合并、拆分仍需保留引用映射。
3. L2 用结构化段落保存正文，每段绑定底层记忆 ID、版本与时间状态。标题和目录提示若使用了资料内容，也继承实际来源依赖。
4. L3 可以参考当前 L2 以选取长期背景，但每条内容仍回指底层记忆；校验使用对应底层依据，不能只拿旧摘要证明新摘要。实际读入 L2 的完整生成依赖递归继承到 L3，不能只展开最终引用的段落。L3 无需复述全部 L2，短期状态不因压缩变成长期特征。
5. 模型只提出结构化归组或摘要，不操作数据库、读取新范围、采纳候选或发布 Skill。程序检查字段、范围、引用、版本及预算；这些检查本身不证明语义忠实，忠实度需独立评测及逐次检查。
6. 后台合并同 scope 的变化，记录目标修订；同批次重复执行幂等。模型调用前后和最终保存时复验输入，存在更正、删除或版本变化时不保存迟到结果。合法新变化留待后续批次，不无限追逐更新。
7. L2 提案、忠实度核验、L3 提案及其核验每次调用分别取得后台许可，并在调用间释放，允许前台插入；只进入 Worker 或绑定 `background_scope` 不会自动取得优先级保护。已经发出的 SDK 请求无法由现有优先级器强行中断，需要有限超时及结果复验，不能承诺后台永不增加前台等待。
8. 本人生成与核验使用单独的内容白名单：合法本人记忆正文、时间状态和本次必要引用标识。真实来源由后端校验，不把完整 `OverviewEntry`、lineage、联系人姓名／来源定位或多个联系人原话序列化给模型。联系人整理也不因本功能新增原话补查；需要原话重核的旧记录保持未合格状态。

一次有界批次建议将“L2 归组与摘要提案”“L2 忠实度核验”“L3 提案”“L3 忠实度核验”作为最多四个语义步骤；没有新增或无需改动时跳过相应调用。首次资料较多时按有限批次完成，记录覆盖数量及剩余量，不将部分处理显示成全量完成。临时调用失败按既有上限重试，结构错误、无依据或矛盾不反复重试掩盖；预算耗尽暂停并明确显示，用户可继续。

逐次核验以已准入的底层记忆为含义对照，检查主体、否定、计划／已发生、时间、条件及适用范围。结构检查不证明真实世界事实，独立模型核验也不等于人工质量验收。生成模型与核验器的合同分别可替换和评测，不能把提案自报置信度当作自动生效证明。

### 建议的数据对象与模块接口

| 建议对象／接口 | 职责 | 权威边界 |
| --- | --- | --- |
| `memory_scenario` 与版本 | 保存 L2 的稳定主题身份、当前版本及有依据的段落。 | 生成正文单独存储；不扩写现有无正文概览表。 |
| `memory_profile` 与版本 | 保存 L3 的短背景及逐条依据。 | 联系人和本人 scope 分开；不能写回 L1 或长期回复偏好。 |
| 整理输入／派生依赖 | 记录实际参与的底层版本、来源、L2 版本和生成规则身份。 | 直接引用用于解释；全部参与输入用于复验和删除，二者不可混同。 |
| `organization_generation` | 保存同范围的 L3 版本、L2 目录及各正文版本的集合。 | 本次读取固定一个可复验版本集合，不能分别拿“最新画像”和“最新目录”混成一次快照。 |
| `LayeredMemoryPort` | `capture(scope)` 返回有界且一致的资料快照，`read_scenario(snapshot, id, range)` 读取该快照内正文，`validate(snapshot)` 复验依赖。 | 三个方法共同封装范围、版本、预算和来源规则；不向模型暴露任意文件路径或由模型指定 owner/contact。 |
| `MemoryOrganizationService` | 捕获批次、编排有限模型提案、校验、保存版本。 | 复用 Worker、优先级与出站台账；业务状态不放入 Agent checkpoint。 |
| `read_memory_scenario` | 回复时读取本次目录中的 L2 文档或有界段落。 | 独立于 Skill 的 `read_file`；受 scope、冻结版本及累计调用／输入预算限制。 |

这些名称是候选接口，尚无对应实现；整理模块内部集中持有批次、归组、模型提案、版本和失效处理，调用方不用各自复现这些规则。模型 Adapter 可用受控合成实现替换，PostgreSQL Adapter 负责真实来源和事务复验；测试与实际调用跨同一 Interface。最终拆分复用现有模块，不为每个层级引入独立运行服务。

### 本人级任务与一致性

在既有任务模块增加显式的整理 scope 判别：联系人整理任务与本人整理任务分别持有真实 ContactScope 或 OwnerScope。仅新整理类型允许 owner-only；既有导入、观察、来源删除等任务继续要求原联系人和来源字段，不把其 `contact_id` 无条件改成可空，也不创建假联系人。

本人整理按 owner 唯一排队及去重，由本人集合修订驱动；不同联系人带来的本人资料变化合到同一目标版本，防止两个联系人任务竞争覆盖本人 L3。提交使用 owner 锁及同连接复验；联系人捕获和既有任务继续遵守原锁序，不在已持 owner 锁时另开连接反向申请 contact 锁。

幂等键包含 scope、目标资料修订、规则版本和启用／删除世代。模型调用在事务外执行；保存时在短事务内复验输入及当前世代。先写待生效版本，校验完成后原子切换版本集合，半份 L2 或仅新画像不会被当成完整新快照。关闭、删除或纠错发生后的迟到结果不能再次激活。

### 回复使用与预算

- L3 和目录位于系统消息内的明确资料区；应用规则明确其是待参考数据，不能执行其中的命令。当前意图、确定性权限和来源／时间校验仍由既有边界处理。
- 本人与联系人 L3 分区展示，L2 目录也带真实 scope。目录只列有限的主题提示和版本化入口；完整正文通过工具读取。本人来源中的原联系人不成为跨关系原话补查入口。
- L1 仍按 5 条／600 字符、本人 3 条／240 字符、未确认参考 3 条／300 字符的原规则运行。L2/L3 使用新增独立预算，并纳入完整请求的容量估算；同一事实重复出现不算多份独立证据。
- 新增预算的初始值应在合成资料上标定，再作为可回归的契约固化。超预算按完整条目或段落选择，不能截半句话、更不能静默扩大模型容量或丢掉当前用户输入。
- 回看依据时展示实际进入模型的 L3 条目、L2 目录／正文及其版本和来源；仅用于失效／删除的隐藏依赖不冒充实际引用。
- L2/L3 更新中、失败、失效、停用或没有合格内容时，不加载受影响资料，回复继续沿合法 L1 与当前聊天。未受影响且复验通过的其他主题仍可用；不从旧缓存补回无效版本，也不等待后台整理才允许回复。

### 具体内容示例（合成资料）

以下不是用户真实资料，只演示两层怎样保持含义和时间。

| 合成底层记忆 | L2“工作与项目”可如何表达 | L3 可如何表达 |
| --- | --- | --- |
| 联系人明确说：“部署前喜欢多测试几遍。”有来源、无撤销。 | “部署习惯：明确偏好多次测试后部署。”附记忆与来源引用。 | “工作偏好：部署前多次测试。”附同一底层依据。 |
| 联系人在 10 月 1 日说：“这周加班，挺累。”没有后续核实。 | “历史记录：10 月 1 日提到当周加班、疲惫；目前状态未核实。” | 不据此写成“长期工作压力大”或“目前很累”。 |
| 联系人说：“约好下周见面。” | 记录为计划／约定，保留日期及未验证结果。 | 不压缩成“双方已经见面”。重要背景如需保留，明确为当时的约定。 |

## 启用、查看与纠错

在现有关系资料页增加“主题资料”和“长期背景”，产品文案不要求用户理解 L2/L3。首次选择要整理的联系人与是否包含本人，展示合格记忆数量、用途、既有模型接收范围及调用预算后开启；不会因新增联系人自动扩大整理范围，也不引入新供应商或新资料来源。

| 操作 | 明确行为 |
| --- | --- |
| 查看 | 展示范围、更新时间、系统整理标记、当前／历史／未核实状态、覆盖进度及可追溯引用。 |
| 刷新 | 基于仍合法的已采纳资料请求一次有界重建；复用任务及幂等状态，不建立第二套同步。 |
| 事实有误 | 导向关联底层记忆的现有修正入口，先撤下受影响整理版本，再生成新版本；人工决定不被自动覆盖。 |
| 总结有误 | 标出整理内容并记录问题，停止使用受影响版本，再从合法底层依据重新整理；不反向修改正确的底层记忆。反馈保留目标及来源依赖，不能让同一错误只换措辞重现。 |
| 补充背景 | 主动新增合法手动记忆，再参与整理；不是直接固定一段无来源的画像正文。 |
| 撤回本版 | 本版退出回复加载；不自动退回已经失效、被纠错或受删除影响的旧版。没有合格替代版时回退 L1。 |
| 停用 | 停止本范围后台整理和回复加载；仍可查看来源有效的现有文档，底层记忆保留。 |
| 删除整理结果 | 关闭本范围整理，擦除生成正文、旧版本、相关任务输入输出、缓存及受影响使用副本；保留最小无正文世代记录防止迟到恢复。底层记忆另行管理，用户重新开启才允许再生成。 |

停用期间真实来源删除仍正常清理派生内容，不因保留查看入口跳过删除。删除底层记忆或来源依照原有影响范围处理；单纯删除派生结果不声称已删除原记忆、聊天或外部模型副本。

### 贯穿全流程的删除要求

L2/L3 的正文、历史版本、目录提示、生成输入输出、人工处理痕迹、任务产物、缓存及已使用它们的回复副本，均登记真实来源依赖。来源进入删除流程后先阻止旧内容继续读取或提交，再按现有生命周期擦除对应敏感内容；其他来源存在不自动证明旧模型总结可以保留，重建须使用仍合法材料。自动重试、手动刷新和旧请求恢复均不得恢复应删内容。

## 验证与交付建议

### 工程验收

先使用合成资料与受控模型 Adapter，通过同一业务 Interface 验证；真实 PostgreSQL、HTTP 与 React 接入再验证事务和展示。必须覆盖：

- 同主题持续更新、新增／合并主题、首次完整覆盖及增量去重；没有合格资料时正常为空。
- 联系人、本人、不同 owner 隔离；未知来历、待确认、已否决和应删资料进入 L2/L3 为零；本人不发出多联系人原话。
- 当前与历史、计划与已发生、明确偏好与临时状态不被互换；未核实资料不能由摘要升级为确定当前事实。
- L3 引用底层依据、L2 的递归依赖与实际显示引用分别正确；模型读过但最终未引用的输入仍进入删除链。
- 首次和更新的有限调用、输入预算、重复提交、租约接管、崩溃恢复及前台优先；本人多联系人变化汇合到唯一 owner 任务。
- 读取一个一致版本集合；生成前后、保存、回复提交各处的纠错／删除／停用竞态，迟到结果不能恢复内容。
- 停用、撤回、刷新、删除整理结果与删除底层资料的不同语义；生成正文、历史、任务输入输出、缓存、实际使用副本均验证无应删残留。
- L2 目录、完整正文及 L3 的独立预算和完整请求容量均不超限；超限、失败、无命中和未完成分别显示，不阻断原有回复。
- 原 L1 词法回归门槛继续通过，已有 Skill 的最多一个版本、资源读取及方法政策不因新资料工具改变。

以上隔离、删除、版本、权限、预算及状态不变量不允许失败后继续加载。纯单元或模拟通过不能代替 HTTP／真实数据库的事务验证，也不能代替真实 App 的交互验收。

### 内容质量与启用门槛

实现规格先固定合成数据、逐条支持关系及人工标注；覆盖主体、否定、时间、计划、条件、冲突、修正及长期／临时区分，每类至少 15 个独立场景。评测按生成条目判定是否被依据支持，并人工审阅总结与原事实的对应；事实主体、时间性质、否定含义、跨联系人泄露等关键错误必须为零。不以“引用 ID 存在”或模型自报置信度代表忠实。

另用同一回复输入对比原 L1 与加入 L2/L3：检查能否利用分散背景、无关背景是否引入误导、Skill 方法是否被资料中的文字污染，以及新增输入量、延迟与调用量。评测报告同时给出失败例与覆盖限制。具体长度、主题数量和调用预算在此数据集上标定并固化；尚未标定的数值不能成为生产默认。

工程功能可以先在受控合成环境完成；自动生效用于真实资料前，必须完成实际候选模型的上述质量验证和整理用途／范围确认。未通过或尚未验证时不自动加载生成正文，保留现有 L1 路径。真实模型质量、App 验收与新的外发用途不由本设计文档代替。
