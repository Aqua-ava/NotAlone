# 聊天回复策略草图

> 状态：草案。记录日期：2026-10-09。用户确认本轮内容应保留为草图，尚未形成完整规格，不替代 `architecture/current/` 或已采纳 ADR，也不代表功能已经实现。

讨论中的产品草图分为收到消息后的回应与主动联系两条路径。以下内容记录用户在讨论中认可的方向，整体方案仍在探索，不作为现行实现规格。

**收到消息后的回应：理解对方的表达 → 用户选择回应方向 → 生成候选回复。**

1. **系统识别表达**：结合待回复消息与有界上下文，给出语用解释，例如邀请、提问、倾诉或拒绝，并说明依据与歧义；不以猜透联系人深层动机为前提，也不把推测当作事实。
2. **用户选择表达方向**：系统可以建议接受、拒绝、先了解等方向，但由用户选择、修改或自行填写并确认。识别的是联系人的表达，选择的是用户自己的回应意愿。
3. **系统生成候选回复**：按已确认的表达方向生成可编辑候选并展示依据，由用户修改后亲自发送。本次选择不得静默成为长期偏好。

**主动联系：明确用户的目的 → 用户选择开口方式 → 生成候选开场白。**

1. **明确本次目的**：用户主动发起请求并确认联系人，说明为什么想联系对方、想表达什么或希望达到什么结果；不要求对方先发来新消息。
2. **用户选择开口方式**：系统结合该联系人的关系资料与有界聊天历史，建议问近况、分享共同兴趣或接续旧话题等方式。目的明确后，开口方式可与对应候选一起展示，供用户比较、选择和修改，不要求先单独确认方式。如果用户只有“想找他聊聊”的想法，系统先帮助探索目的和开口方向，不替用户决定关系目标。
3. **系统生成候选开场白**：在已确认的表达方向内生成带依据、可编辑的候选，使用真实背景，不虚构共同经历、事实、情绪或承诺；由用户亲自发送，本次选择不得静默成为长期偏好。

两条路径的共同原则是：先明确用户想表达什么、希望达到什么结果，再决定具体怎么说。用户尚未想清楚时，系统提供方向建议，由用户确认；期望结果不代表能够保证对方的反应。

讨论中认可的交互细节（Q1–Q8）：

- 提供“回应消息”和“主动聊聊”两个可切换的场景入口。回应消息时明确本次待回复消息，主动聊聊时从用户目的开始；不能仅因存在历史消息就判定用户在回应。
- 对联系人的语用解释用一句简短说明展示，保留歧义，并允许用户纠正；随后提供少量回应方向建议，用户可以选择或自行填写。
- 用户尚未明确回应方向时，建议按不同的回应意愿区分，例如“解释近况”“表达想念”“提议见面”，并简短说明各自适用情况；不以同一意愿的语气变体代替方向选择。用户选定方向后，再生成措辞或语气不同的候选；用户已明确方向时仍直接生成。
- 用户已明确说明表达方向，例如“帮我拒绝，语气柔和一点”，即可直接生成，无须再点一次方向确认。只有方向不明确时才提供建议供用户确认。
- 主动联系时允许直接输入目的；目的不明确时结合背景提供少量建议。目的明确后，展示不同开口方式及对应候选，不把目的和方式拆成必经的两次确认。
- 缺少时间、地点等细节时，能自然表达就先生成不含虚构细节的候选；只有缺失信息会改变用户立场或造成误解时，才追问一个关键问题。
- 用户可直接提出“太热情了”“自然一点”“换个话题”等修改要求；系统保留已确定的目的，只调整用户指出的部分。用户也可明确改变目的，无须从头操作。

Skill 讨论已恢复，当前认可的职责与粒度见下文 Q16、Q17；具体介入阶段和实现形式仍待讨论。此处不修订既有 Skill 架构约束，不将草图直接视为现行规格。

现行核心流程中的 `rewrite_draft` 与 `reply_to_message` 是既有输入模式设计；上述场景入口与既有控件、接口的具体映射尚待设计，不将主动联系自动等同于回复最新对方消息。

## 方向依据与纠正（Q9、Q10）

- **Q9：说明方向依据**。每个建议方向用一句话说明为什么适合，并以真实背景为依据；没有相关证据时只说明适用条件，例如“如果你也想见面，可以顺势邀约”，不承诺或预测对方一定会有某种反应。
- **Q10：纠正后更新建议**。用户纠正系统对联系人表达的理解后，按纠正重新给出方向；若用户已明确自己的回应意愿，则保留该意愿，只调整相关建议和措辞。本次纠正只用于当前任务，不自动成为长期关系事实。

## 方向建议与目的推进（Q11–Q13）

- **Q11：当前目的优先**。用户本次明确的目的与历史聊天习惯不一致时，以本次目的为准。历史仅帮助理解背景和调整表达，不将用户拉回过去的相处方式，例如不能因过去热情就覆盖本次“想保持距离”的要求。
- **Q12：意愿不明时提供不同方向**。用户尚未明确目的时，结合上下文给出少量不同回应意愿的方向，不默认用户想答应或拒绝。例如对“周末有空吗”，可以建议先询问事情、表示有空并愿意了解，或表示这次不方便；这些是待用户选择的方向，不是系统已确认的用户事实或立场。
- **Q13：复杂目的先推进下一步**。当最终目的难以通过一句话达成时，围绕该目的确定本次消息能推进的一步。例如恢复联系时先接上共同话题，不强求一句话恢复关系。展示候选时说明本句主要完成哪一步，不保证最终结果。

## 目的冲突与背景不足（Q14、Q15）

- **Q14：目的与说法冲突时说明取舍**。用户要求的说法可能不利于其明确目的时，指出矛盾并提供可选方案，不擅自改变目的。例如用户想缓和关系又要求讽刺对方时，说明讽刺可能加重冲突，并提供直接表达不满、保留沟通空间的替代方式，由用户决定优先表达什么。
- **Q15：背景不足时依据已有信息建议**。缺少聊天历史或关系资料时，仍可依据当前消息和用户目的提供方向，不假设双方熟悉、暧昧或存在矛盾。只有缺失背景会明显影响建议时才追问，不以编造背景补足信息。

## Skill 的场景与方法（Q16、Q17）

- **Q16：按沟通场景组织**。通用流程负责理解情况、明确目的、确认方向及生成和修改候选；Skill 面向一类沟通场景，提供更细的判断与处理方法。用户明确纠正：场景是正在发生的沟通情境，例如收到邀约；接受、拒绝、先问清楚属于回应方向，不应当作场景拆分 Skill。场景是匹配线索，用户目的决定具体用法，联系人背景提供真实依据。首批场景清单尚未确定。
- **Q17：同一 Skill 包含多种处理方法**。一个 Skill 处理一类沟通场景，内部支持不同回应方向，并根据用户目的和背景选择处理方法，不固定套用话术，也不必为委婉、直接或保留余地等表达变体分别建立 Skill。以邀约场景中的拒绝方向为例，拒绝一次邀请与不希望以后再被邀约需要不同处理；判断所需信息优先从已有上下文取得，不意味着每次都逐项询问用户。

此前“拒绝与边界表达”的示例混淆了场景与方向，不再作为场景划分依据。早先撤回的“先确定方向，再匹配 Skill”建议未被采纳；后续重新编号的 Q18–Q20 见下文。当前未创建、安装或验证对应 Skill。

## Skill 的介入与自动选用（Q18–Q20）

- **Q18：主动邀请与收到邀请共用一个场景 Skill**。两者作为不同分支，分别关注如何提出邀请与如何回应邀请，共用安排、意愿和边界方面的判断。
- **Q19：可以在方向确认前介入**。场景明确时，Skill 可以先辅助理解情况并整理方向建议；用户明确意愿后，再按对应方法生成候选。加载 Skill 不等于确认用户立场，用户已明确方向时无需重复确认。
- **Q20：重叠场景按当前主要任务匹配**。第一版每次至多使用一个 Skill。例如约久未联系的朋友吃饭时，选用邀约 Skill，将久未联系和恢复联系的目的作为背景；尚未决定邀约时，不因可能存在该方向就直接当作邀约任务。
- **启用后由系统自动选用**。用户启用 Skill 后，系统在用户发起的聊天辅助任务中，根据场景和可用 Skill 的描述自动匹配、按需加载，无需用户每次手动选择。启用不代表每次强制加载；没有合适 Skill 时使用通用流程。展示实际使用的 Skill，并允许用户关闭或更换；表达方向仍由用户明确或确认。

关系类型、熟悉程度、语气和用户方向作为处理条件，不分别拆成 Skill。场景可以重叠，例如久未联系后的邀约，按 Q20 的当前主要任务原则匹配。普通问候等通用流程足以处理的任务不必单独建 Skill，后续依据案例中反复出现、确有独特判断方法的问题再考虑扩展。

## 通用流程与 Skill 的职责边界（Q21、Q22）

- **Q21：通用流程独立完成聊天辅助**。即使没有 Skill，系统仍应完成理解情况、明确或帮助选择表达方向、生成及修改候选。事实依据、不确定性处理和用户立场约束属于通用流程，不依赖某个 Skill 才生效。Skill 补充场景中的判断经验、方法及适用条件、常见错误和案例，不是基础功能的必需条件。
- **Q22：Skill 不覆盖本次用户意愿**。Skill 建议与用户本次明确目的或表达意愿不一致时，以用户本次意愿为准；可以解释方法的取舍，但不能以“通常更有效”为由擅自改变目的或增加承诺。产品既有硬边界仍然适用。

## 研究后的方向验证与连续聊天（Q23–Q28）

本节对应研究后新一轮提问中的 Q1–Q3 及后续讨论，沿用本文编号记录用户已确认的意思。

- **Q23：方向集合以能找到想表达的意思为主要判断**。例如对方邀请吃饭，系统提供接受、拒绝、先问时间，用户想拒绝并能直接选到，就说明这组选项有用；不要求系统提前猜中用户最终选择或将其排在第一。该判断不代表其他选项可以不合理，也不等于已经测得产品准确率。
- **Q24：按连续聊天考虑回应**。用户可以一句表达一个意思，分多条消息发送，也可以追发或等对方回复后继续交流。例如先关心近况，再回应邀请，不要求把全部意思压进一条候选，也不将整段聊天限定成独立的单轮问答。具体多条候选的展示与后续更新方式尚待讨论；每条消息仍由用户亲自发送。
- **Q25：记忆辅助建议，不排除其他合理立场**。方向建议结合当前消息、近期聊天及相关记忆。即使用户过去经常接受某人的邀请，这次仍应提供拒绝等合理选项，不能仅凭历史习惯替用户确定本次意愿。
- **Q26：方向不合适时可以换一组**。用户可以请求系统重新提供一组方向建议，不必先写出自己的方向；用户已有想法时，也可以直接说明，沿用明确方向后的生成流程。
- **Q27：未选方向时随新消息更新建议**。在当前聊天辅助任务中，用户尚未选择方向，对方又补发消息且系统已在授权范围内取得时，应结合前后消息更新理解和方向建议。例如邀约后补充“还有几个老同学”，建议应考虑这一新情况。此约定不扩大消息读取授权；正在编辑候选时按 Q28 处理，已选方向但尚未编辑时的更新方式仍待讨论。
- **Q28：编辑中的回复不因新消息自动覆盖**。用户正在修改候选回复时，对方又发来消息，系统保留正在编辑的内容，并提醒“对方有新消息”，由用户决定是否更新回复，不自动覆盖用户的修改。
