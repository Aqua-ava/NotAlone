## High 优先级改进（阻塞实现前必须决定）

### H1. 隔离键逐对象落实（领域）

> 状态：已采纳（2026-08-02）。已更新 `01-domain-data.md` 数据对象表与隔离/删除语义、`02-core-flows.md` 同步流程。

**问题**：`message` 未声明直接携带 `owner_id + contact_id`，仅经 `source_document`/`session_capture` 间接关联，与"先按隔离键过滤再检索"的约束冲突；`session_capture` 存在"未归属联系人"状态，与"所有联系人范围对象都含 `contact_id`"矛盾。

**为什么重要**：隔离键是隐私的根基。某个对象不直接带键，查询时容易漏过滤，可能查到其他联系人的数据；"未归属"状态不定义豁免规则，隔离键会被静默绕过。

**建议**：
- `message` 显式冗余 `owner_id + contact_id`，来源字段仅用于定位与删除。
- 显式定义未绑定 `session_capture` 的临时态（仅 `owner_id`、无 `contact_id`）及其归属/丢弃规则，作为联系人范围对象的豁免。

### H2. 检索规则量化（检索与生成）

> 状态：已采纳（2026-08-02）。已更新 `02-core-flows.md` 3.1 排序规则与 3.2 上下文预算。

**问题**：结构化检索只有定性描述（"按时间、关键词、资料类型、确认状态排序"），无可执行规则；"近期对话"窗口无定义，存在放大到完整历史的风险。

**为什么重要**：排序规则和上下文预算直接决定回复质量与隐私——预算过大则模型昂贵、可能串资料；过小则漏关键信息。不定死无法实现，也无法测试。

**建议**：
- 定义 v1 排序键优先级：确认状态 → 显式有效期 → 时间 → 资料类型 → 关键词，给出各键比较语义。
- 定义硬性上下文预算：近期消息条数与 token 上限、确认资料与风格样本条数上限、超预算截断策略，写入生成接口入参约束。

### H3. 出站台账（隐私）

> 状态：已采纳（2026-08-02）。已更新 `03-privacy-and-deletion.md` 模型适配器约束、删除保证与最小验证清单。

**问题**：删除保证要求"界面明确已发送至外部模型/存储的数据的独立删除路径"，但无出站台账记录"哪些数据、何时、发往哪个供应商/模型"；`ModelGateway` 只登记模型名、请求时间与字段类别。"外部副本独立删除"无法执行。

**为什么重要**：没有台账，"删除外部副本"是空话——不知道外部有什么就删不掉。这是隐私承诺的执行基础。

**建议**：将出站记录列为 `ModelGateway` 强制输出：非正文标识（联系人 id、来源 id、条目 id）、供应商、用途、时间、保留期与删除能力；台账参与级联删除并纳入验证清单。

### H4. 云端模块划分与客户端形态（工程）

> 状态：已采纳（2026-08-02）。已新增 `05-cloud-engineering.md`，并在 `README.md` 登记模块清单、端云职责与认证设备方案。

**问题**：职责清单只拆了功能域，未定义模块化单体内部模块划分（ingest、contacts、memory、retrieval、reply、jobs、gateway 等）及客户端↔云端各自边界；客户端整体形态（桌面 App/CLI、端侧 OCR 如何组织）未定义。

**为什么重要**：不拆清楚，写代码时模块互相纠缠（文件 IO、模型调用、存库、UI 混在一起），违反 `AGENTS.md` 的职责拆分要求。

**建议**：
- 为云端模块化单体定义内部模块清单与职责边界。
- 明确 v1 客户端形态与端云职责划分（端侧：采集/OCR/去重/展示确认；云端：解析/索引/生成/删除），把"同步适配器"提升为正式模块边界。
- 为每条跨端流程（导入、同步去重、确认持久化、删除级联）固化 API 契约与数据结构。

### H5. 认证与设备绑定（工程）

> 状态：已采纳（2026-08-02）。已在 `05-cloud-engineering.md` 定义最小认证与设备绑定方案，并列为云端落地前置决策。

**问题**：文档只把 `owner_id` 作为隔离键，未定义用户认证、设备注册、会话令牌、解绑清理；单设备起步未为多设备演进预留接口。

**为什么重要**：先建库后补身份认证最容易出隔离漏洞——拿到数据库可能直接读。删除时若不回收设备级数据，会留下残骸。

**建议**：落地云端服务前先定义最小认证与设备绑定方案（账号/令牌、设备注册、绑定会话隔离、解绑清理），并在删除流程纳入设备级数据回收。

### H6. 删除语义统一（领域）

> 状态：已采纳（2026-08-02）。已更新 `01-domain-data.md` 来源与删除语义、`02-core-flows.md` 删除流程。

**问题**："只由被删除来源支持的 `confirmed_memory` 默认也应删除"中的"默认"削弱了删除保证；会话同步去重与"删除来源即清除其规范化消息"存在跨层冲突，可能误删或产生孤儿消息。

**为什么重要**：删除是隐私承诺。"默认"一词留下不删的口子；多来源归属不清则删除行为不确定，用户删了可能删不干净或误删。

**建议**：
- 将"默认"改为无条件级联删除，保留"另存为不依赖来源的手动资料"为唯一保留路径，并明确该操作切断与原来源依赖。
- 明确去重后的归属策略：`message` 只归属一个来源（删除即连带），或支持多来源引用（剩余证据失效规则）；删除测试须覆盖跨来源场景。

### H7. 资料分类与有效期必须决定（领域）

> 状态：已采纳（2026-08-02）。已在 `01-domain-data.md` 定义 v1 分类枚举（common_fact/preference/taboo/recent_state/relationship_note）与 `valid_at`/`invalid_at` 字段。

**问题**：核心流程检索排序直接依赖"资料类型、确认状态、显式有效期"，但 `confirmed_memory` 分类枚举与有效期字段在"尚未决定"清单中悬而未决。

**为什么重要**：这是检索功能的前置依赖，不定没法实现排序；有效期字段正好解决"他这个月减肥"这类会过期的资料（可借鉴 `research/ragflow.md` 的 `valid_at`/`invalid_at`）。

**建议**：把分类与过期策略移入必须决策项，给出 v1 最小形态（少量、可编辑的分类枚举 + `valid_at`/`invalid_at` 字段）。

### H8. 加密与密钥管理前置（隐私）

> 状态：已采纳（2026-08-02）。已在 `03-privacy-and-deletion.md` 将加密与密钥管理列为云端生产前置阻塞项，明确明文存储假设并纳入验证清单。

**问题**：文档标注安全边界"已采纳"，但端侧缓存加密、云端静态加密、密钥管理、备份策略全部未决；权威库在当前定义下以未决加密状态落地。

**为什么重要**：这是"声明"与"实际"不一致——文档看似安全，代码落地时数据是明文存储，没有加密保证。

**建议**：加密与密钥管理设为云端数据进入生产的前置阻塞项；决策前明确记录权威库为明文存储假设，纳入验证清单与风险登记。

## Medium 优先级改进

### M1. 公共后台任务抽象（领域）

> 状态：已采纳（2026-08-02）。`01-domain-data.md` 以 `background_task` 取代 `import_job`/`deletion_job`，含 `type` 与 `scope` 字段。

**问题**：`import_job` 与 `deletion_job` 职责重复，各建各的表，且未声明隔离键或作用域。

**为什么重要**：任务作用域不清，删除任务可能跨越隔离边界误删；重复结构增加维护成本。

**建议**：定义公共 `background_task`（type 区分 import/delete/reindex），增加 scope 字段（account/contact/source），避免删除任务跨越隔离边界。

### M2. `retrieved_context` 对象化（领域）

> 状态：已采纳（2026-08-02）。`01-domain-data.md` 定义 `retrieved_context` 为 `reply_request` 内嵌快照。

**问题**：`retrieved_context` 出现在分层图但对象表无定义，`reply_request` 的"记录本次实际检索到的上下文"责任边界不清。

**为什么重要**：相当于图纸上画了房间却没写是什么，实现时无处安放"本次用了哪些上下文"。

**建议**：决定其是 `reply_request` 内嵌快照还是独立对象；若独立须含隔离键、检索条件与引用列表。

### M3. `confirmed_memory` 保留候选来源链（领域）

> 状态：已采纳（2026-08-02）。`01-domain-data.md` 增加 `source_candidate_id` 与采纳方式记录。

**问题**：`confirmed_memory` 的证据关联未定义到候选层，"候选→确认"链路断裂。

**为什么重要**：确认后无法回看这条资料从哪条候选来，审计和修正困难。

**建议**：增加可空 `source_candidate_id` 记录从哪个候选确认而来，手动创建时为空，同时保留来源证据列表。

### M4. 候选状态保留策略（领域）

> 状态：已采纳（2026-08-02）。`01-domain-data.md` 明确 rejected/invalidated 候选随来源删除或短期保留复核。

**问题**：`rejected`/`invalidated` 候选的保留与删除策略未定义。

**为什么重要**：被否掉的资料不清理会永久堆积，占用存储并可能造成困惑。

**建议**：随来源删除或短保留供复核，与来源级删除语义一致。

### M5. 检索缺口处理（检索与生成）

> 状态：已采纳（2026-08-02）。`02-core-flows.md` 3.3 定义降级再查与"未检索到"明示。

**问题**：检索是单次静态查询，无迭代修正机制，检索不到时可能静默生成。

**为什么重要**：结果差时系统可能瞎编或假装正常，用户无法区分"没查到"和"没资料"。

**建议**：结果为空或低于阈值时放宽时间窗口/关键词再查一次并标注降级；仍空时 UI 明示"未检索到相关记忆"；记录降级率作为引入向量检索的前置数据。

### M6. 高风险内容与检索交互（检索与生成）

> 状态：已采纳（2026-08-02）。`02-core-flows.md` 3.4 定义独立适配层确定性规则与核实提醒。

**问题**：高风险内容（转账、验证码、地址、借款、承诺）与检索上下文的关系未定义。

**为什么重要**：高风险内容命中时仍要提醒核实，但规则不混入生成提示词，否则污染生成逻辑。

**建议**：确定性规则标记高风险当前消息，命中时仍可检索但生成前必须展示核实提醒；高风险判定放独立适配层。

### M7. 引用展示契约（检索与生成）

> 状态：已采纳（2026-08-02）。`02-core-flows.md` 3.5 定义引用契约（segment 标识、入选原因、分数、状态）。

**问题**：引用展示无数据契约，难以支撑"为什么用了这些上下文"。

**为什么重要**：用户看到"根据你的聊天记录回复"时不知道是哪几条；没有引用契约也无法发现误导入或过期资料。

**建议**：候选回复每条依据引用必须携带 `retrieval_segment`/`source_span` 标识、入选原因、分数与状态。

### M8. 风格样本权重量化（检索与生成）

> 状态：已采纳（2026-08-02）。`02-core-flows.md` 3.6 定义送入提示词（≤5 条、标注参考）与降级路径。

**问题**：`style_sample` 的"低权重"未量化，是否进提示词未定。

**为什么重要**：权重和条数不定，风格样本可能喧宾夺主或完全无效。

**建议**：明确 v1 是否送入提示词、条数与权重上限；若送入则纳入引用展示（标注"参考的表达样本"），否则仅作离线参考。

### M9. 检索记录生命周期（检索与生成）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 定义检索日志保留期、级联清除与用户删除入口。

**问题**：检索日志（入选引用、分数、检索器版本）数据模型未定义。

**为什么重要**：日志涉及私密引用，不属于长期关系资料，没有生命周期策略会无限堆积且删除语义不清。

**建议**：定义持久化与否、保留周期、级联清除与用户删除入口，需单独生命周期策略。

### M10. 检索质量度量（检索与生成）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 定义空结果率/降级率/拒绝率/纠错率与触发升级条件。

**问题**："只有在可测量的检索问题出现后，才引入向量检索"但无度量指标与阈值。

**为什么重要**：没有指标，"可测量"就无法执行，也无法判断何时该升级到向量检索。

**建议**：定义空结果率、降级率、用户拒绝率、引用纠错率等指标与采集点，超阈值且有真实用户反馈才评估向量检索；引入向量检索列为需重新过隐私评审的独立决策。

### M11. Embedding 隐私条款（检索与生成）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 补充 embedding 条款（向量化时机、发送字段、留存删除、隔离约束）。

**问题**：Embedding 的向量化时机、发送字段、留存删除未写入文档。

**为什么重要**：文本变向量发给外部服务涉及敏感数据，未定约束即无治理。

**建议**：补充 embedding 条款：向量化时机与位置、发送字段与供应商核验、留存与删除语义、不得绕过联系人隔离；列为需新增数据处理影响说明的决策点。

### M12. 检索接口契约落地（检索与生成）

> 状态：已采纳（2026-08-02）。`02-core-flows.md` 补充入参（隔离键、当前消息、limit、时间窗口）与返回（引用、确认状态、有效期、分数、检索器版本）。

**问题**：`retrieve`/`delete_by_source`/`rebuild_contact_index` 未落地接口契约。

**为什么重要**：无契约则实现与测试无法对齐，权限与状态校验无处安放。

**建议**：定义入参（隔离键、当前消息、limit、时间窗口）与返回（segment 引用、确认状态、有效期、分数、检索器版本）。

### M13. 数据流表补删除行（隐私）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 数据流表新增"删除/级联清除"行。

**问题**：数据流表只枚举正向流程（采集、OCR、同步、提取、回复），删除操作无数据流描述。

**为什么重要**：删除是跨存储面的级联过程，没有数据流描述就无法落到可执行边界。

**建议**：新增"删除/级联清除"行，明确触达存储面（消息、候选、确认资料、索引、缓存、任务产物、出站台账）与权威库；删除任务接入同一数据流模型。

### M14. ModelGateway 契约与硬失败（隐私）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 定义接口契约：仅接受隔离键域内结果、发送前校验规模与字段白名单、未知政策硬失败。

**问题**："不越权查历史""不允许把整个历史发送给模型"是规范要求，无执行机制。

**为什么重要**：没有机制保证，越权上下文可能混进调用而不自知。

**建议**：定义接口契约：仅接受隔离键域内检索结果、发送前校验上下文规模与字段白名单、供应商政策未知时硬失败，配套单元测试。

### M15. 级联删除事务化（隐私）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 删除保证第 5 条建模为可重试幂等 `background_task`，逐存储面确认。

**问题**：删除保证未定义顺序、原子性、幂等与部分失败的补偿。

**为什么重要**：级联中断会遗留孤立索引或候选资料，且无重扫/校验机制。

**建议**：建模为可重试幂等后台任务，逐存储确认删除结果，失败可续跑，结束后复核"删除后不可检索"；日志只记存储键与条目 id。

### M16. 日志正文硬禁止（隐私）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 将"默认"改为硬禁止，日志只含哈希或条目 id，定义留存与清除任务。

**问题**：网关日志用"默认"限定词，为完整正文入日志留出无约束通道。

**为什么重要**："默认"一词等于没有硬规则，删除后日志仍可能残留可恢复正文。

**建议**：改为硬禁止：日志只含内容无关引用（哈希或条目 ID），定义留存期限与清除任务，验证清单增加"日志不含可恢复正文"断言。

### M17. 验证清单扩展（隐私）

> 状态：已采纳（2026-08-02）。`03-privacy-and-deletion.md` 补充网关拒绝、出站白名单、日志正文残留、外部副本删除路径断言。

**问题**：最小验证清单缺 ModelGateway 拒绝越界、出站载荷白名单、日志正文残留、外部副本删除路径提示等断言。

**为什么重要**：清单缺项则这些隐私保证无法被自动验证。

**建议**：逐项补充：(a) 网关拒绝越界上下文与未知供应商政策、(b) 出站载荷字段白名单、(c) 日志正文残留检查、(d) 外部副本删除路径提示验证。

### M18. 供应商准入表（工程）

> 状态：已采纳（2026-08-02）。`05-cloud-engineering.md` 增加供应商准入表与安全门要求。

**问题**：未按用途（生成/抽取/OCR/转写）评估供应商数据处理明细，`ModelGateway` 的"记录发送范围"停留在设计层面。

**为什么重要**：供应商留存、训练使用、删除 SLA 不明就生产调用，敏感资料可能长期留在外部。

**建议**：为每个模型用途建立候选供应商数据处理表（发送字段、地域、留存、训练使用、删除 SLA），选定后写入 ADR；满足安全门方可生产调用。

### M19. 密钥与代理调用（工程）

> 状态：已采纳（2026-08-02）。`05-cloud-engineering.md` 定义云端代理调用、密钥加密轮换与吊销流程。

**问题**：`ModelGateway` 未回答密钥存储位置、轮换、解绑/删账户时吊销。

**为什么重要**：密钥管理缺失，泄露或吊销不了都会造成数据安全漏洞。

**建议**：采用云端代理模型调用（端侧不持有供应商密钥），定义静态加密与备份，密钥轮换/吊销纳入删除与解绑流程；补齐前不将私密资料写入云端存储。

### M20. 对象存储目录与删除（工程）

> 状态：已采纳（2026-08-02）。`05-cloud-engineering.md` 定义目录结构、对象级加密、生命周期策略与删除一致性。

**问题**：对象存储目录结构、对象级加密、生命周期策略未定义，对象删除与 `deletion_job` 的一致性未定。

**为什么重要**：原始文件是大对象，无目录/加密/生命周期策略则难以治理和删除。

**建议**：接入前定义目录结构（owner/contact/source）与对象级加密、生命周期策略；把"对象删除"作为 `deletion_job` 可重试步骤，为外部副本声明独立删除路径与留存期限。

### M21. 测试工程组织（工程）

> 状态：已采纳（2026-08-02）。`05-cloud-engineering.md` 定义先建 Python 包与 unittest、合成夹具、CI 可重复验证。

**问题**：只规定了"测什么"，未规定测试工程如何组织（Python 包、unittest 目录、合成夹具、CI）。

**为什么重要**：没有测试工程骨架，跨端验证（同步去重、删除级联、不采集、不发送）无法落地。

**建议**：先添加 Python 包与 unittest 配置，为跨端流程编写合成夹具与本地验证脚本，以 CI 保证可重复验证。

## Agent 设计维度（人工补充）

> 原多维评审中该维度的自动化分析失败，以下为人工补充（依据 `AGENTS.md` 自动化与 Agent 部分、`research/ragflow.md` 补充调研）。

### A1. 关系提取触发与输入窗口

> 状态：已采纳（2026-08-02）。写入 `adr/002`：触发点（导入完成/增量累积阈值）、输入窗口（最近 N 轮）。

**问题**：`AGENTS.md` 定义主 Agent 作任务路由器、子 Agent 返回带来源的结构化证据，但未定义"关系提取"在何时、对哪段消息触发；RAGFlow 是单轮输入（User/Agent 各一条），NotAlone 是批量导入/增量同步，需要多轮窗口。

**为什么重要**：触发点和输入窗口不定，提取子流程无法实现，也无法对齐导入/同步的既有边界。

**建议**：定义提取触发点（导入完成后 / 同步增量累积到阈值时）与输入窗口（当前联系人最近 N 轮），写入 `02-core-flows.md` 提取子流程。

### A2. 提取确认层

> 状态：已采纳（2026-08-02）。写入 `adr/002`：低风险高置信自动写入（标记 auto、可撤销）/ 高风险或低置信待确认；`01-domain-data.md` 与 `AGENTS.md` 表述同步修订。

**问题**：`AGENTS.md` 规定"模型不能直接写入 confirmed_memory"，但自动提取方案需要允许低风险自动写入；文档未定义自动写入与人工确认的边界。

**为什么重要**：两条规则冲突，不确定边界就无法实现自动提取，也无法守住高风险人工确认的底线。

**建议**：采纳"低风险高置信自动写入（标记 auto，可撤销）/ 高风险或低置信待确认"分层，明确 `confirmed_memory` 的写入路径，同步修订 `AGENTS.md` 对应表述。

### A3. 提取失败可见性

> 状态：已采纳（2026-08-02）。写入 `adr/002`：`memory_candidate` 增加 `extract_failed` 状态，保留证据与失败原因，用户可查可重试。

**问题**：RAGFlow 提取结果不可解析时静默放弃；NotAlone 需要失败可见。

**为什么重要**：静默失败用户完全不知道，可能长期缺失资料而无人察觉。

**建议**：`memory_candidate` 增加 `extract_failed` 状态，保留证据与失败原因，用户可查可重试。

### A4. 子 Agent 证据契约

> 状态：已采纳（2026-08-02）。写入 `adr/002` 证据契约（事实文本 + 支持消息引用 + 置信度 + 风险等级 + 有效期）。

**问题**：子 Agent"返回带来源的结构化证据"未落成数据结构。

**为什么重要**：无契约则主 Agent 无法校验子 Agent 输出，证据链无法形成。

**建议**：定义子 Agent 输出契约：事实文本 + 支持消息引用列表 + 置信度 + 风险等级 + 有效期（valid_at/invalid_at），与 `memory_candidate` 字段一一对应。

### A5. 风险分级判定

> 状态：已采纳（2026-08-02）。写入 `adr/002`：确定性风险规则放独立适配层，命中高风险必须人工确认。

**问题**：高风险类型（钱/地址/健康/承诺）自动提取需硬性排除，文档未定义判定。

**为什么重要**：高风险资料一旦记错并按它生成回复，后果由用户承担，必须有人工关口。

**建议**：定义确定性风险规则（关键词/类型枚举）放独立适配层，命中高风险时候选必须等待人工确认，不自动写入。
