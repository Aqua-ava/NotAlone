# ADR-175：修复同步通过后清理被取代绑定下无派生引用的旧副本

已被[ADR-177](../177-retire-source-recertification-and-cleanup.md)替代（2026-11-07）：本次用户确认的存量清理完成后，副本清理请求、自动／离线执行流程及专用运行能力退役。被引用旧消息、来源及必要删除等价事实继续保留；下文只记录一次性清理的历史决定。

部分替代（2026-11-07）：[ADR-176](../176-in-place-source-recovery.md)。ADR-176 的原地恢复不产生新绑定副本、不登记新的副本清理请求；已有请求、存量离线清理和引用保护继续有效。

状态：已替代（ADR-177）。原记录：已采纳（2026-11-07）；实现与合成库测试已完成，真实库副本演练见[验收记录](../../../docs/verification/superseded-binding-cleanup-20261107.md)。用户已明确同意在与 [ADR-144](144-preserved-history-source-recertification.md)“旧消息保留”条款冲突时直接覆盖该条款（覆盖范围见下）。存量副本只出清单，执行须另行取得用户确认。

与 ADR-144 冲突；重新讨论的原因是：ADR-144 的“保留旧资料”让每次修复同步都在新绑定下完整重读一遍历史，而旧绑定下的整份副本从此不再参与任何读取（读取资格只认现行绑定），只是越积越多。真实库实测：一位联系人经三次修复得到 4 份，各约 1.4 万条，库内该联系人约 5.7 万条消息；全库 34 个被取代绑定共约 8.1 万条消息。这些副本占用存储，并拖慢每次对该联系人的扫描、计划和删除；而其中绝大部分没有被任何记忆、候选回复或整理条目引用。

## 决定

- **清理对象**：联系人在同一会话下已撤销、曾被修复同步显式替换（`history_source_recertification` 有从该绑定指向新绑定的记录）的绑定，在该会话现行绑定已由修复认证通过之后，称为**被取代绑定**。其下**没有任何派生引用**的消息，连同它自己的来源记录（`capture_record`）、别名、引用及其尝试、媒体附件与托管文件，以及因此清空的抓取页，被清理。
- **保留对象**：仍被记忆（引用与要求消息）、候选回复输入、回复上下文、运行输入、步骤输入、执行事件来源、整理条目引用的消息，及其全部来源记录；被保留的引用者引用的目标消息；有隔离记录的消息（撤回和系统替换的终态抑制证据）；所有非规范来源记录（排除／隔离，终态抑制的原始证据）；`history_source_terminal`、来源排除、清空边界、围栏历史、认证操作审计和读取授权记录。引用判定是一份登记表（`superseded.ts` 的 `retainingReferences`），不是约定；测试按真实 DDL 枚举全库，新增表一旦引用消息或来源记录而未登记就失败。
- **覆盖 ADR-144 的哪些条款**：只覆盖“旧消息、原始来源、记忆、助手结果及必要来源审计保留”中**无派生引用的旧消息与原始来源**这一部分——它们在修复通过后不再保留。ADR-144 的其余内容不变：入口与确认、来源核验、从空游标完整遍历、围栏与原子启用、无正文审计、幂等与取消、旧失证来源及实际依赖它的派生结果保持不可用、记忆／助手结果／必要来源审计保留、来源删除排除与清空边界与终态抑制继续生效、跨代次删除闭包（[ADR-161](../161-proved-legacy-source-suppression-mapping.md)）。被保留的旧引用者仍可按 ADR-144 追溯其来源，删除某条来源时仍按原闭包规则清理剩余的跨代次副本。
- **不是用户删除**：走统一删除账本的内部范围 `superseded_history`（只含联系人标识），但不写 `history_deletion_fence`、来源排除或清空边界，不推进联系人资料代次，不撤销读取授权，不影响终态抑制，因此不会阻止以后重读，也不改变任何已有删除保证。该范围不属于 `installedDeletionScopes`（对外可请求的用户删除范围），没有 HTTP 入口。
- **触发与续跑**：`Finalize` 与修复完成在同一事务登记 `history_superseded_cleanup(owner, contact)`；完成回调排队后台清理，应用重启后只续跑已登记的请求和账本里未结案的清理操作。**不会**自动清理没有登记的存量副本。
- **有界、不阻塞同步**：每个操作最多处理 5000 条消息，批次上界（`display_no`）在计划时固定到 `accepted_generation`，使同一操作的重新收集只落在同一范围；一位联系人清完需要若干个操作，逐个结案。每个操作的清除是账本里一条条短事务（一条消息束一个目标），不持有长事务；操作结案前仍按删除框架的规定做一次压缩，期间存储 Worker 独占数秒（约与库体积成比例）。清理内部串行，全局一次只推进一位联系人。
- **互斥与门禁**：联系人必须有效，且没有来源连续性围栏、没有 `history_deletion_fence`、没有进行中的修复，没有其他未结案的联系人／账号删除或媒体清除，且现行副本非空；任何一条不满足就不计划、不清除。每条消息在清除的写事务内再次复验是否仍可清（被取代、未被引用、门禁仍成立），否则跳过而不报错；账本在核验时重新收集，使跳过后又变得可清的对象下一轮继续。进行中的清理不阻止新的修复（修复的“有未完成删除”检查与记忆侧的“有未完成删除即暂停”检查都排除该范围，因为它只删除不被任何记忆引用的资料）。
- **存量**：此前累积的副本不自动清理。先用只读清单工具按联系人给出可清／保留消息数与媒体文件数和字节（匿名编号），用户确认后用离线工具（App 完全退出后，先备份）执行，执行路径与自动清理相同。

## 影响与边界

- 现行绑定的副本从修复通过那一刻起是唯一完整副本；若新副本因源端后来删除或撤回而比旧副本少，旧副本中独有的、无引用的消息不再保留——这正是用户确认覆盖的部分，已被记忆等引用的消息仍在。
- 新读取只创建现行绑定的引用（来源资格要求 `m.binding_id=g.binding_id`），因此被取代绑定下的引用只会减少，不会增加。
- 未采纳：整体删除旧绑定（部分消息被引用，会破坏记忆来源）；把保留逻辑写成手写 DELETE（绕过删除框架的闭包、持有者排空、文件身份与压缩核验）；先做增量读取避免重复副本（另起任务：旧新来源可证明同一物理来源时继承旧游标，需修改 ADR-144“空游标完整遍历”，不在本决定范围）。

实现入口：`backend-ts/src/history/sqlite/superseded*.ts`（判定、删除范围、续跑驱动、迁移 45）；规格见[微信同步](../../current/wechat-sync.md)“来源变化后的重新认证”段和[隐私与删除](../../current/privacy-deletion.md)“来源变化与重新认证”小节。
