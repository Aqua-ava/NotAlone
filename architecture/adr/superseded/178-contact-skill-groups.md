# ADR-178：按联系人分组限定可用的回复 Skill

已合并入[ADR-196：回复 Skill 的发现、启用与按需加载现行合并决定](../196-reply-skill-library-consolidated.md)（2026-11-18）：回复 Skill 的存储、发现、启用、数量与范围约束已收拢到该 ADR。下文保留为历史决定与原因，现行条款以该 ADR 为准。

> 状态：已合并（ADR-196）。原记录：已采纳（2026-11-11），依据用户要求“给不同的联系人使用不同的 Skill”：面对恋人、同事等不同对象使用不同的一套，也可以对某类人不使用 Skill。分组方案与“未分组联系人默认不使用 Skill”由用户在需求确认中选定。本文记录决定；代码、桌面界面与真实应用验收分别核验。
> 局部修订 [ADR-135](135-default-enabled-localized-skill-library.md)（包级默认启用不再等于对所有联系人可用）与 [ADR-136](136-multi-skill-reply-composition.md)（目录范围由“全部可用 Skill”收窄为“该联系人所在分组绑定的可用 Skill”）。目录授权、技术核验、来源资格、读取预算和人工发送边界保留。

## 决定

- 新增**Skill 分组**：用户自定义名称（如“恋人”“同事”），每个分组绑定若干已发现的 Skill 包。分组、绑定和联系人分配都属于一个 Owner，不跨 Owner 共享。
- 一位联系人至多归入一个分组。**未归入分组的联系人（含新自动建联的联系人）不使用任何 Skill**；分组绑定为空等同不使用 Skill。该默认值使升级后尚未分组的联系人回复立即变为无 Skill，这是用户选定的行为，界面须如实说明。
- 包级状态不变：只有 `enabled + verified + current` 的包才可能被使用，停用仍是全局总开关，分组绑定不能让停用或失效的包生效，也不改变默认启用来历。联系人实际可用集合 = 分组绑定 ∩ 全局可用包。
- 一次回复的目录、预加载、显式 `selectedPackageId` 和输入记录都只面向该联系人的分组范围；组外包不进入首次模型请求的名称与简介目录。显式选择组外包被拒绝。
- 回复冻结的运行修订携带联系人分组范围（联系人、分组标识、分组修订）。分配变化、分组改名或改绑定、分组删除都使在途运行在发送前、读取时和候选提交前的资格复验失败；缺少分组范围的修订不得带任何可用 Skill（失败即关闭）。无变化的保存不推进分组修订。
- “本组任一已启用策略失效则整体撤下”的降级只看本联系人所在分组，组外失效的包不影响该联系人。

## 内置“恋人”分组（2026-11-11 补充）

用户指出现有回复 Skill 全部属于恋人场景，不应要求逐个勾选。因此每个 Owner 自动拥有一个内置分组“恋人”：它使用全部 Skill（含之后新发现的），不逐包绑定，不可改名、改绑定或删除；用户只需把联系人归入它。同事等其他分组仍自选 Skill，未分组联系人仍不使用任何 Skill。内置分组仍受包级启停与来源资格约束。已存在同名“恋人”分组时转为内置并保留其联系人分配。通过追加迁移 52 的 `all_packages` 字段实现，不修改已发布迁移。

## 数据、删除与管理

- 追加迁移建立分组、分组绑定与联系人分配三张表；联系人或 Skill 包删除时对应分配／绑定级联清除，不修改已发布迁移，也不触碰原 Skill 目录。
- 联系人范围删除清除该联系人的分配，账号删除清除全部分组；分组名称和绑定不含聊天内容，但分配仍随联系人删除。
- 管理动作带确认与预期修订（分组修订、联系人当前分组），过期动作返回冲突，不覆盖用户后来的修改。分组管理只改变业务绑定，不读取 Skill 正文、不调用模型。

## 取舍与不做

不做按“关系标签”自动推断分组、按分组继承长期偏好、一人多组的叠加或联系人级覆盖层；这些会让“某个联系人为什么用了这个 Skill”难以说明，需要时另行复审。分组只决定可用范围，不改变 Skill 作为策略文字、不能授予 Tool 或发送能力的合同。
