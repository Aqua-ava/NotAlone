# ADR-035：待确认候选作为强制标注的未确认参考进入回复

> 状态：已采纳
> 决策日期：2026-10-05
>
> 本 ADR 落实 ADR-027 决策 5。它修订 ADR-005 第 1 节与 ADR-011 第 3 节中
> “`memory_candidate.pending` 不得进入生成上下文”的绝对表述，并解除 ADR-028
> 第 7 节“不做待确认候选注入”的第一期边界；对 ADR-024 第 2 节只作澄清
> （`pending` 仍不得进入“已确认记忆集合”），不改变其来源、版本化与 fail-closed
> 规则。ADR-026 语用分流、ADR-033 来源语义核验和自动采纳门槛均不变。

## 背景

现行回复链路的检索顺序把采纳状态作为第一排序键，并规定 `pending` 候选只能用于
展示线索、不得进入生成上下文（ADR-005、ADR-011、ADR-028）。代价是：所有没通过
自动采纳门槛的事实——计划、未定安排、证据不足的推断、敏感但用户确实需要提到的
信息——在回复里完全不可见，用户只能自己回忆。

用户已在 2026-10-05 明确产品语义：**待确认候选可以参与候选回复，但必须强制带
「未确认」标注、回复文本不得写成确定事实；用户否决过的候选永久不再参与。**
缺的不是“能不能用”，而是“用的时候不能被当成已确认资料”。

## 决策

### 1. 待确认候选是独立证据轨，不是已确认记忆集合的一部分

新增第 6 种证据类型 `pending_candidate`，与 `CONTEXT.md` 的“待确认候选”同名同义。
它由独立的检索入口 `RetrievalPort.search_pending_candidates` 提供，只返回同一
`owner_id + contact_id` 范围内、状态仍为 `pending`、仍在有效期内且来源可用的候选。

检索结果使用独立类型 `RetrievedPendingCandidate`，其状态字段只允许 `pending`：
已确认、已否决、已失效的候选在这条轨上无法表示。这样“pending 不进入已确认记忆
集合”由结构保证，而不是靠调用方自觉。`search_confirmed_memories` 与
`reply/tools.py` 的按需检索 Tool 继续只查已确认记忆。

### 2. 强制未确认标注，独立预算

待确认候选与已确认记忆使用互不占用的预算，并在同一确定性中文词法评分下选前缀
（沿用相关性阈值 0.15、不截断单条正文）：

- 联系人确认记忆：最多 5 条、合计 ≤600 字符（不变）；
- 本人记忆：最多 3 条、合计 ≤240 字符（不变）；
- 待确认候选：最多 3 条、合计 ≤300 字符。

每条 `pending_candidate` 证据的 `selection_reason` 必须写明“未确认候选、仅供参考、
不得当作事实”，其状态为 `pending`；模型输入同时透传 `status` 与
`selection_reason`。提示词明确规定：`pending_candidate` 只能用于提问、确认或保留
余地，不得表述为确定事实，不得当作已确认资料引用，也不得与 `confirmed_memory`
并列陈述。模型不能替用户确认，也不能因为内容看起来合理就升级它。

### 3. 只在允许历史证据的请求中注入

待确认候选与已确认记忆同属历史证据：`reply_to_message` 一律可用；
`rewrite_draft` 只有显式 `include_relationship_context=true` 才注入，且
`has_unauthorized_history` 把新证据类型计入历史证据，维持草稿模式边界。方向建议
阶段不注入，仍只使用最小上下文。

### 4. 生成前后重新复验候选现值

快照生成后，`validate_current` 对每条 `pending_candidate` 走独立校验分支：重新按
候选 ID 读取，要求仍在同一联系人范围内、状态仍为 `pending`、有效期仍成立、来源
仍可用、正文与来源集合未变。任一条件不成立即拒绝本轮，不削弱既有的消息、联系人
记忆、本人记忆和 revision 校验。候选在生成过程中被确认、否决、失效或来源被删除，
本轮候选一律作废。

### 5. 否决后永久不再参与

用户否决（`rejected`）的候选不再出现在待确认轨上；被确认的候选转入已确认记忆集合
并携带来源链。已删除来源支持、已删除或已失效的候选同样不可见，沿既有删除路径
保持“删除后不可检索”。

## 取舍

- **可用 vs 绝对隔离**：选择“可用但强制标注”。保住漏记方向的回复质量，代价是
  回复链路多一种证据类型和一条独立的复验路径。
- **独立类型 vs 复用已确认记忆类型**：选择独立类型。多一层数据契约，换取
  “pending 混入已确认集合”在类型层面不可表达。
- **独立预算 vs 共享预算**：选择独立。未确认参考不挤占已确认资料预算，也不因
  已确认资料多而被无声挤掉；代价是上下文总量上限增加 300 字符。
- **固定常量 vs 可配置**：选择固定常量，与 ADR-028 一致；调整需附评测更新。
- **不自动确认 vs 让模型判断**：选择不自动确认。模型只能提问或保留余地，确认与否
  仍由用户在应用内决定。

## 后果

- `reply_context_evidence.kind` 的 CHECK 约束需要迁移放行 `pending_candidate`
  （`037_pending_candidate_evidence_kind.sql`）；升级业务库前必须先应用该迁移，
  否则写入新证据类型会被数据库拒绝。
- 检索适配器承担“仍待确认、仍在有效期、来源可用”的过滤；内存适配器与 PostgreSQL
  适配器使用同一评分器与预算规则。
- 待确认候选的 3 条/300 字符预算尚未经正式评测标定，属于模块常量；后续放宽或收紧
  必须附召回评测证据。
- 用户否决、确认与查看候选的界面路径属于后续纵切：本 ADR 只保证后端不再把未确认
  候选写成事实，不证明 macOS 界面已完成展示与确认入口。
- 候选正文仍只保存在原有 `memory_candidate` 记录中，回复快照只引用候选 ID、正文、
  状态和入选原因，不新增事实源或“已证实”状态。

## 验证

- 单元：证据轨只承载 `pending` 状态；跨联系人隔离；已否决、已确认、已失效候选
  不可见；相关性阈值与独立预算（3 条/300 字符，不截断单条）；草稿未开背景时不查询
  也不注入；草稿越权时 `has_unauthorized_history` 判真。
- 单元：生成前后复验在候选被确认、否决、失效、越界、过期、正文或来源变化、被移除
  时拒绝本轮。
- 单元：模型输入包含 `status=pending` 与含“未确认”的入选原因，系统提示词包含
  “不得表述为确定事实”。
- 集成：PostgreSQL 待确认检索的范围、状态、有效期与来源删除过滤；`pending_candidate`
  证据可落库并在读取时保留未确认状态；真实 HTTP/生成链路中待确认候选进入模型输入，
  已否决候选不出现。
