# ADR-003：Mac 同步连续性与用户补录

> 状态：已采纳  
> 决策日期：2026-08-03

> 后续修订：CLI 消息连续性与自动补齐以 ADR-016、ADR-023、ADR-025、[ADR-030](030-confirmed-contact-background-sync-consent.md) 为准；本文保留最初 OCR 方案的背景及用户主动补录边界。

## 背景

Mac 微信前台会话同步只观察用户当前可见的聊天区域。用户在手机聊天、Mac 微信未打开、会话未显示或同步暂停期间产生的消息，不能被该机制自动看见。恢复前台 OCR 后，即使能识别到新消息，也不能证明中间没有缺失消息。

若系统把“识别到新消息”误写成“历史连续”，模型会基于残缺上下文生成回复或提取关系资料，且用户无法知道资料覆盖存在缺口。

## 决策

### 1. 连续性以内容锚点判定

恢复同步或开始一个新 OCR 批次时，系统使用已持久化 `message` 与新画面中的可识别消息建立重叠锚点：同一联系人、说话人、规范化文本和可用时间线索必须足以证明两段相接。

- 找到可靠锚点：新增消息的 `session_capture.continuity_status` 为 `continuous`，再执行去重和写入。
- 找不到可靠锚点：已识别的新消息仍可作为原始资料写入，但 `continuity_status` 为 `possible_gap`。该状态必须在会话覆盖信息与回复上下文中可见，不能宣称聊天记录完整。
- OCR 无法可靠区分说话人、顺序或联系人时，仍适用 ADR-001 的失败路径：不写入联系人范围的 `message`。

“新消息时间晚于最后一条已存消息”不是连续性证据；时间只能辅助锚点判断。

### 2. 用户主动补录，而不是程序遍历历史

当出现 `possible_gap`，用户可以明确启动“补录此段对话”：

```text
用户确认当前已绑定会话
  -> 用户启动补录
  -> 用户自己在微信中滚动到已存锚点附近
  -> NotAlone 仅观察当前聊天区域并 OCR / 去重
  -> 找到锚点并收集到后续可见消息
  -> 标记覆盖段为 backfilled
```

- `session_capture.capture_mode` 区分普通前台同步 `live` 与用户补录 `user_backfill`。
- NotAlone 不点击微信、不滚动、不切换会话、不读取数据库或私有目录，也不读取其他 App。
- 用户不愿意补录时，可把缺失片段复制为文本，在已选联系人下作为普通 `source_document` 导入；这不是给 Agent 开放微信数据库。

### 3. 时间与来源语义

- 原始发送时间无法从 OCR 可靠取得时，`message` 必须记录时间未知或低置信；不得以 OCR 采集时刻替代消息发生时刻。
- 每一条补录消息继续关联其 `session_capture` 或 `source_document`，删除来源、解除绑定和联系人删除时沿用既有级联删除规则。
- `possible_gap` 是覆盖状态，不是业务记忆，也不能被模型改写为关系事实。

## 后果

- `session_capture` 需要 `capture_mode` 与 `continuity_status` 字段；会话展示需要能显示“可能缺口”与“已补录”。
- 同步去重器必须支持锚点比较和跨屏补录去重，而不只比较本次运行中的重复行。
- 回复上下文应携带会话覆盖提醒；它提醒用户上下文可能不完整，但不阻止用户生成候选回复。
- 初始文本导入仍是第一优先级。补录是 Mac 前台同步投入日常使用前必须具备的配套能力，不替代文本导入。

## 验证要求

使用合成消息与界面验证：

1. 新画面包含已存锚点时，只写入锚点之后的新增消息并标记 `continuous`。
2. 新画面没有可靠锚点时，写入的来源段标记 `possible_gap`，回复上下文不声称完整。
3. 用户手动滚动补录时，应用不发出微信 UI 控制调用，跨屏重叠消息不重复入库。
4. OCR 时间未知时，不生成伪造的消息发生时间。
5. 删除补录来源或解除绑定后，其消息、派生候选、索引和缓存不可再检索。
