# ADR-023：全局 CLI 增量同步与前台 OCR 定位分离

> 状态：已采纳
> 决策日期：2026-09-01

> 后续修订：第 1 条默认全选由 [ADR-030](030-confirmed-contact-background-sync-consent.md) 改为首次默认不选；第 3 条关闭窗口永久跳过由 ADR-025 的重新开启后有界补齐替代。本文保留历史原因。

## 背景

ADR-001 和 ADR-016 最初把消息读取限制在微信前台当前会话；这保证了读取范围最小，却让用户无法在微信和 NotAlone 之间切换操作。当前 CLI 版本已经提供无 talker 的 `tail/watch --mode sessions --follow --jsonl` 会话级事件流，可以在不读取其他会话正文的情况下通知哪些会话发生变化。

## 决策

1. 用户首次在 App 内确认 CLI 可见的一对一会话集合。批量预览默认全选，但必须由用户最后一次确认；没有确认的会话不会创建绑定。
2. 总开关开启且 NotAlone 后端运行期间，只启动一个全局 CLI session 事件流。事件流只产生“哪个外部会话定位标识发生变化”的触发信息；正文读取仍只针对已确认绑定，并通过一次性 `tail <talker>` 读取。
3. 每个联系人独立保存 cursor。新绑定先保存 baseline 时间，之后只读 baseline 之后的新消息；已有 cursor 从 cursor 恢复。关闭 App 不启动后台读取进程；手动关闭总开关形成的窗口在重新开启后只前移水位、不写入，不启动隐藏进程。
4. 前台 OCR 仅负责微信是否在前台和当前会话定位。它不再是后台 CLI 写入的门禁；微信离开前台、OCR 暂时失败或 NotAlone 获得焦点只影响前台定位状态，不停止后台 CLI 同步。
5. 全局事件流不可用时，后台同步退化为有界的一次性轮询，按已绑定会话的 cursor 分批处理；即使全局流可用，也必须在事件队列清空后按固定预算对 active 绑定做定期 round-robin 安全对账，因为事件流不保证覆盖我方发送等变化。单个会话失败延后到后续轮次重试，不得占满队列；不得为每个联系人启动长 Follow 或无限重启。
6. 观察来源新增 `cli_background` 模式，用于区分全局后台 CLI 读取；保留 `live` 与 `cli_catchup` 供既有前台验证和补读路径使用。
7. 既有人工 Follow 验证控制面保留为兼容和真实微信冒烟入口，直到新路径完成脱敏人工验证；它不能改变正式 CLI 全量同步开关。

## 取舍与替代方案

- **继续要求微信前台**：拒绝。它直接造成 App 操作与同步条件互相抢占。
- **每个联系人一个 Follow 进程**：拒绝。进程数随联系人增长，关闭、退避和权限失败会扩散；全局会话事件流已经提供更小的进程面。
- **全局流直接读取所有消息正文**：拒绝。事件流只用于变化通知，正文仍由已确认绑定和独立 cursor 门控。
- **用 OCR 继续读取正文**：拒绝。OCR 只做前台定位，正文使用 CLI 的结构化文字事件。

## 后果

后台消息同步不再依赖微信当前焦点，用户可以在两个 App 之间自由切换。读取范围从“当前前台会话”扩大为“用户明确批量确认的一对一会话集合”，因此批量确认、绑定撤销、owner/contact 隔离、来源删除和本地开关必须保持严格。实际 CLI 版本、权限和消息事件形状仍需脱敏真实微信冒烟验证；在验证完成前，不能把新路径表述为端到端已证实。

### 2026-10-19 当前联系人调度修订

桌面将本次已选择的联系人登记为优先提示；提示只改变已确认绑定的读取顺序，不增加授权，且不依赖微信焦点或 OCR。后端只保留最新提示，并在每个绑定任务完成后重新调度；后台队列仍轮转前进。有待处理任务时立即继续，空闲时保留三秒检查节奏。确认绑定和诊断入口也使用同一有界切片。

每个切片的 CLI 命令共享三秒绝对截止时间，超时不采纳部分结果、不推进可靠游标，后续轮次重试。该预算不强行中断规范化或数据库事务，也不是消息发送至展示的延迟保证。状态仅提供当前优先联系人最近成功检查时间、排队、读取与入库耗时及失败码；尚未取得的指标保持空值。桌面自动重读状态并展示最近检查时间，不能把连接成功或检查成功表述为消息必已追平。正式范围及实测记录见[修复规格](../../.scratch/sync-priority-latency/spec.md)。
