# ADR-166：记忆自动处理总开关，默认关闭

状态：已采纳并实现（2026-11-05）。用户明确要求“实现开关，默认关闭”。本文局部替代 [ADR-152](152-history-and-incremental-memory-processing.md) 第 4 项“启动和后续调度自动重新发现并处理积压”，以及 [ADR-107](107-unified-memory-processing-lifecycle.md) 第 7 项“App 启动后自动续跑安全恢复的工作”的触发前提：二者仍然有效，但只在总开关开启时才会发生。

与 ADR-152 第 4 项冲突；重新讨论的原因是：历史导入后积压很大（本机约 6000 条待提取），启动即静默地把聊天文字发给外部模型服务并消耗额度，用户没有可靠的停手方式；现有“暂停处理”只作用于单个联系人卡片，无法整体停止。

## 决定

1. **总开关**：新增“记忆自动处理”总开关，保存在库的单例行（`database_instance.memory_auto_processing`，迁移 42），只存 0／1，不含聊天内容。**默认关闭**；既有库升级后同样关闭，开启必须由用户明确操作。
2. **关闭时不发起任何记忆模型调用**：调度器不扫描、不建轮；启动恢复积压、续后续整理登记、主题与概览整理（L2／L3）均不执行；用户显式的“开始／继续／历史初始化”入口返回明确的关闭原因，不静默忽略。消息同步、入库、查看已有记忆和用于回复不受影响。
3. **关闭动作**：正在执行的轮次按用户暂停的既有语义停在步骤边界——在途的一小批完成并提交，不再领取下一小批，不中止已发出的调用，因而不制造未知回执。后续整理登记留在持久队列。
4. **开启动作**：只继续由关闭动作本身暂停的轮次（沿原任务、原进度、原预算），并唤醒积压恢复、后续登记与调度扫描；用户在此之前手动暂停的轮次保持暂停。“由关闭动作暂停”的记录只在进程内保存，重启后丢失，此时这些轮次显示为已暂停，需用户在卡片上明确继续。
5. **单联系人暂停与总开关独立**：二者叠加时任一方为停止即不处理；开启总开关不解除任何手动暂停，也不扩大授权范围、不开启同步。
6. **界面**：记忆页顶部显示开关及当前状态说明；状态读取失败时开关不可用，不猜测开启或关闭；处理面板在关闭时提示原因并隐藏会被拒绝的“恢复本轮处理”入口。

## 影响与边界

- 迁移只增加一列，不读取、搬迁或改写任何聊天资料；升级后不会因此自动开始处理。
- 开关不改变来源核验、自动采纳（`auto`，可撤销）、删除闭包、预算与未知回执规则，也不新增外部发送能力。
- 已失败任务不因开启而被重置；是否自动恢复仍按 ADR-152 第 4 项的既有资格（已知失败仅自动恢复一次、暂停与未知回执保持）。

- 验证范围为合成资料：后台开关专项 7 项、桌面控制器与界面各 1～2 项；未用真实聊天或真实模型验证，也未做打包验收。
