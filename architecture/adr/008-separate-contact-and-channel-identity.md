# ADR-008：联系人身份与渠道身份分离

> 2026-10-21 设计审查：独立填写名称创建空白联系人的桌面入口已由 [ADR-084](084-topbar-contact-search.md)退役。本文身份分离、稳定内部标识和来源确认继续有效；导入／绑定事务内建立身份与独立创建不是同一能力，内部兼容接口的后续范围仍须单独决定。

> 状态：已采纳  
> 日期：2026-08-16

## 背景

NotAlone v1 只服务一个用户和一个微信账号。最简单的导入实现可以直接把微信导出记录中的 `sender_wxid` 当作 `contact_id`，但这会把用户确认的关系对象与某种输入格式提供的字段绑定在一起。联系人改名、来源字段变化或未来增加 OCR、语音和手工资料时，代码将无法区分“NotAlone 中的联系人”与“这份资料声称来自谁”。

## 决策

1. `contact_id` 是 NotAlone 创建的稳定内部身份，不取自昵称、备注、`sender_wxid` 或其他外部来源字段。
2. v1 仍只实现单用户、单微信账号和单联系人确认流程，不实现跨账号、跨渠道联系人合并。
3. 首次导入时，用户可以创建联系人或选择已有联系人。系统保存最小确认记录，包括来源、确认的 `contact_id`、确认时间和确认方式。
4. `sender_wxid` 等外部标识作为渠道身份或来源元数据保存，用于预览和一致性校验。它们不能替代 `contact_id`，也不能从导入文件中提供 `owner_id`。
5. 已有联系人名称可以修改而不改变 `contact_id`。新来源与已确认的渠道身份不一致时，系统必须停止并要求用户重新选择或创建联系人，不能静默改绑。

## 不采用的方案

- **直接使用 `sender_wxid` 作为 `contact_id`**：首版字段更少，但会让领域身份依赖微信导出格式，并使其他文字来源难以进入同一模型。
- **立即建立多账号、多渠道身份合并系统**：当前没有对应用户工作流，会增加绑定冲突和误合并风险。

## 后果

- 联系人确认仍是一个简单的首次导入步骤，不要求用户管理多账号或多渠道关系。
- 导入模型需要区分内部联系人身份、外部渠道身份和可变展示名称。
- 当前数据库迁移和 Python 导入模型仍直接把 `sender_wxid` 用作 `contact_id`，与本 ADR 不一致；后续必须通过单独的代码和数据库迁移任务修正，并验证已有数据迁移。本文档本身不代表该行为已经实现。

## 后续状态

上述实现缺口和 owner 渠道身份初始化由 ADR-013 处理；本段保留为 ADR-008 决策时的历史状态，不代表当前代码仍采用该旧行为。
