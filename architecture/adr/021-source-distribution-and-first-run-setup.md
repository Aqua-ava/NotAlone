# ADR-021：源码分发与双层首次配置

> 状态：已采纳
> 决策日期：2026-08-25
> 历史局部修订：ADR-039 退役 Swift 主界面构建和图形首启向导；当时保留的外置依赖边界已由下列独立版决定局部替代，现行桌面宿主见 ADR-040。
> 后续局部修订：[ADR-061](061-standalone-local-app-onboarding-and-updates.md)将独立分发目标改为随包管理本机后台与数据运行环境，替代下文仅外置依赖／只交付宿主的独立版边界；首版范围见 [ADR-065](065-manual-input-standalone-first-release.md)，已有资料更新见 [ADR-066](066-in-place-schema-updates-and-database-reuse.md)。源码开发路径保留，打包与运行打包版仍须用户明确提出发布任务。

NotAlone 将开源给其他用户使用，需要确定别人拿到仓库后如何跑起来。产品仍在快速演进，界面、后端与同步架构都在建设中。决定第一版采用源码 + 安装脚本的分发形态，并把首次配置拆成机器级与用户级两层。

## 决策

1. 分发形态为源码 + `setup` 脚本：脚本负责机器级事务（安装 Python 依赖、创建数据库、按顺序应用全部迁移、构建 Swift App 与探针），不做签名打包、不内嵌 Python 运行时或 PostgreSQL、不做自动更新。
2. App 首次启动向导负责用户级事务：填写模型供应商凭据（如 DeepSeek API Key）、初始化 owner。owner 初始化从"首次导入时显式执行"提前到 App 首启（修订 ADR-013 的初始化时机；初始化仍创建或恢复 owner 并保存渠道身份绑定路径，不改变身份分离语义），导入流程因此只保留联系人归属这一步。
3. 打包发布（App 内嵌运行时、双击即用）与容器化留待有真实外部用户反馈后再评估；届时必须新增 ADR，不得静默改变本决策的边界。

## 取舍

- **打包发布**：拒绝（暂缓）。签名、内嵌 Postgres、自动更新的工程量大，而产品形态尚未稳定，打包会放大每次变更的分发成本。
- **Docker Compose**：拒绝（暂缓）。主产品是原生 macOS App（探针需要屏幕录制权限与前台观察），容器化只覆盖后端一半，收益不对称。
- **全部靠文档、不做向导**：拒绝。让用户手编 `.env`、手动初始化 owner 会把首次体验门槛抬到不可接受，直接伤害开源可用性。

## 后果

开源用户的最低环境要求（macOS、微信桌面版、用户自装的 wechat-cli、PostgreSQL、Python 环境、屏幕录制权限）必须在 README 与 setup 脚本中如实声明；脚本失败时给出的引导是开源体验的一部分。owner 初始化提前后，首启向导与导入命令的 `--initialize-owner` 路径形成两个入口，需保持同一事务语义与幂等行为。本决策不涉及多用户运行时隔离：数据隔离键仍是 `owner_id + contact_id`，一份本地部署服务一个用户。
