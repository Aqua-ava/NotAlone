# ADR-025：CLI 后台同步自动补齐可检测缺口

> 状态：已采纳
> 决策日期：2026-09-08

> 后续修订：[ADR-083](083-automatic-sync-recovery.md) 将独立暂停／手动重试交互改为总开关统一控制与自动恢复，简化进度展示；本文的范围、baseline、可靠游标与去重约束保留。

CLI 后台同步的目标是开启期间的近实时增量读取，但仅跳过同步关闭窗口会让用户在重新开启后看不到已经发生的消息。决定在同步恢复、App 重启、CLI 恢复和手动检查时，针对已确认绑定的会话自动检测并补齐可检测的消息缺口；补齐从最后可靠位置开始，按批次写入文字消息并推进游标，稳定去重，保留不含正文的进度与失败记录。补齐不追溯 baseline 之前的历史，不读取未确认会话，不解析媒体正文，也不提供任何外部发送能力。

## 考虑过的方案

- **继续永久跳过关闭期间消息**：拒绝。实现简单，但会把“同步已开启”与“消息覆盖完整”混淆，形成静默缺口。
- **完全依赖用户手动导入或补录**：拒绝。用户已经明确希望系统自动完成已授权范围内的背景同步，不能把日常恢复负担转回用户。
- **开启后无边界地全量读取历史**：拒绝。会突破 baseline 和已确认会话范围，增加隐私、资源和重复数据风险。

## 后果

- 同步恢复后会产生额外的本地 CLI 读取和后台任务状态，App 必须展示缺口、进度、暂停、失败和“无法确认完整”等覆盖状态。
- 游标推进必须以后端成功写入来源与规范消息为前提；已有游标超前时需要从最后可靠位置修复，不能简单覆盖。
- 关闭同步仍然意味着关闭期间不读取；自动补齐只发生在用户重新开启同步之后，并且只处理当时仍然 active 的已确认绑定。
- 该决策扩展并修订 ADR-023 关于关闭窗口“只前移水位、不写入”的规则；ADR-003 中用户主动补充文字／单联系人文件、时间未知及来源隔离的边界继续有效；其滚动正文 OCR、视觉锚点与 session_capture 补录流程仅保留为历史，当前前台定位不得 OCR 聊天正文。
