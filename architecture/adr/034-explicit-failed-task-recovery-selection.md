# ADR-034：显式失败任务恢复按原任务领取

> 状态：已采纳
> 决策日期：2026-10-04
> 局部修订：ADR-018 的默认最早任务领取规则；全局串行锁与预检查规则保持。
> 后续局部修订：ADR-035 将指定原任务扩展至已确认的 HTTP 导入自动唤醒；失败恢复仍显式触发。

## 背景

与 ADR-018“只处理指定范围最早的一个后台任务”存在局部冲突；重新讨论的原因是用户已经确认失败任务的 HTTP／CLI 恢复需求。用户明确选择原失败任务后，如果执行器仍领取较早的其他任务，恢复动作将处理未选择的资料，原任务也可能继续停在排队状态。

## 决策

1. 未提供任务 ID 时，继续领取指定 `owner_id + contact_id` 范围内最早的可执行任务；首次领取后固定该任务，完成或失败前不切换任务。
2. 用户显式恢复原任务时，任务 ID 贯穿 HTTP／CLI、Worker 和数据库领取，跳过同范围其他排队任务。任务 ID 不能替代用户与联系人隔离键。
3. HTTP 恢复只将失败原任务排队，执行仍由用户显式触发；CLI 完成原有数据库、用户、联系人和模型预检查，并取得全局 Worker 锁后，才恢复并执行指定任务。锁忙或预检查失败不修改原任务。
4. 来源状态与失败状态在恢复事务内复核。导入只允许有效来源，既有删除任务允许在删除状态中收尾。成功步骤跳过，失败步骤重新获得现有的最多三次自动尝试，不扩充预算、模型权限或来源范围。
5. 业务任务 ID 与 Worker 执行器 ID 分开。持久查询返回原任务及步骤的最小状态、计数和错误分类，不保存正文。

## 取舍与后果

显式恢复暂时优先于同联系人更早的排队任务，以兑现用户选择并限制本次处理范围；默认启动仍遵守最早领取规则。此例外不引入自动调度、多任务并行、通用队列优先级或更多模型额度。

公开 HTTP／CLI 合成验收覆盖原任务身份、跳过成功步骤、较早任务不执行、跨范围拒绝、每轮重试预算，以及预检查或全局锁失败后状态不变；这些证据不代表真实模型质量或正式环境部署验证。
