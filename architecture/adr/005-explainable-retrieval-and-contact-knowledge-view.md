# ADR-005：可解释检索与联系人知识视图

> 状态：已采纳  
> 决策日期：2026-08-04

## 背景

NotAlone 需要在生成候选回复前，从当前联系人的历史中找回近期对话、共同事实、偏好、禁忌和表达样本。传统的“分块 -> embedding -> 向量召回 -> rerank”链路会引入难以解释的排序：回复失准时，难以区分问题来自分块、向量化、召回、重排还是上下文截断。

对 NotAlone 而言，检索正确性、来源可回看、联系人隔离和资料删除，比极致压缩上下文成本更优先。聊天和关系资料又天然具有联系人、时间、说话人、分类、有效期及来源等结构，不应在 v1 先被降格为无结构的向量块。

## 决策

### 1. v1 采用联系人范围内的可解释检索

生产服务不直接对私密文件调用 shell `grep`。这里的“grep 路径”是指在权威 PostgreSQL 数据上，以 `owner_id + contact_id` 为前置条件执行的关键词、短语和全文检索，再结合确定性业务字段排序。

检索顺序如下：

```text
当前消息
  -> 联系人隔离过滤
  -> 生成并记录检索计划
  -> 关键词 / 短语 / 全文命中
  -> 按时间、类型、有效期和状态排序
  -> 从命中消息向前后有限轮次展开
  -> 组装带引用的有界上下文
```

- `confirmed_memory` 以完整资料卡为检索单位；其分类、`valid_at` / `invalid_at`、采纳状态和来源证据均参与过滤或排序。
- `message` 的命中单位是一条规范化消息。选中后只能在同一联系人下展开有限的相邻轮次或同一来源时间段，不使用固定 token 大小的任意 chunk。
- 任何检索、展开和排序均不得跨 `owner_id + contact_id` 边界；`memory_candidate.pending` 不能作为已知事实进入生成上下文。
- 回复 Skill、近期对话、常驻卡和风格样本仍按 `02-core-flows.md` 的六轨规则组装，不因全文检索而把完整历史送入模型；Skill 不属于 Retriever 的事实命中，由 `SkillPort` 单独按版本加载。

### 2. LLM 只提出可审计的查询与阅读计划

LLM 可以根据当前消息提出检索词、近义表达、实体、时间线索、资料类型和建议的上下文扩展方向。例如“他最近怎么样”可提出“加班、项目、面试”等候选词。

该输出不是检索结果，也不是事实判断。程序必须校验联系人隔离和上下文预算后，执行实际查询与展开。每次 `retrieved_context` 至少记录：

```text
检索词与变体
时间窗口、资料类型和状态过滤条件
每条命中的引用标识、入选原因和排序分数
从何处向前后扩展、实际展开的范围
检索器与查询计划版本
```

用户应能从 `reply_candidate` 回看“搜了什么、命中了什么、为何带入这段上下文”。LLM 不能静默替换命中资料、凭摘要写入事实，或把未引用的内容包装成已检索证据。

### 3. 联系人知识视图是可回溯投影，不是新的事实源

可为联系人提供类似 Wiki 的可浏览视图：常驻卡、近期状态、关系时间线和来源链接。该视图由 `message`、`confirmed_memory` 及其来源关系投影而来，每项必须能回到消息片段、来源、时间、状态和删除入口。

LLM 可以帮助生成标题、索引词或阅读路线，但其生成文本不能脱离来源成为权威资料。关系事实的权威性仍遵循 `source_document/session_capture -> message -> memory_candidate -> confirmed_memory` 的既有契约。

### 4. 检索失败按可见的降级路径处理

关键词结果为空或不足时，程序可按既有规则放宽时间窗口、使用已记录的词语变体再查一次，并明确标注“降级”。仍无结果时，必须区分“未检索到相关记忆”与“没有可用资料”；不得用模型猜测伪装为检索结果。

### 5. 向量检索是后续可比较的补充路径

embedding、向量数据库和 rerank 不作为 v1 前提。只有空结果率、降级率、候选拒绝率、引用纠错率持续异常，并有真实反馈表明主要根因是同义表达或长历史漏检时，才单独评估引入向量路径。

届时应将它先作为关键词检索的补充候选集，而非静默替换主路径；在同一组匿名化或合成查询上比较两条路径的引用正确性、覆盖率和用户纠错情况。向量、文本和来源必须使用同一隔离与级联删除语义，并重新完成数据处理影响评审。

## 不做什么

- 不在生产服务中对用户私密资料执行不受访问控制的 shell `grep`。
- 不以固定 token 长度切分聊天记录，也不把 LLM 摘要当作没有来源的长期事实。
- 不在 v1 部署独立向量数据库、embedding 服务或 rerank 服务。
- 不把检索计划、命中来源或上下文扩展过程隐藏在模型调用内部。
- 不因检索能力提升而改变联系人确认、来源删除、候选可编辑或人工发送边界。

## 后果

- `retrieval` 模块需要实现联系人过滤后的全文检索、确定性排序、相邻消息展开、上下文预算和 `retrieved_context` 快照。
- 需要选择并验证 PostgreSQL 中文全文检索的分词、短语匹配和索引方案；这属于实现前技术决策，不预设特定扩展或供应商。
- 生成接口需要接收并持久化受限的查询计划与实际检索轨迹，检索记录仍遵循既有的保留期和删除规则。
- 验证至少覆盖合成资料上的联系人隔离、关键词命中后的上下文展开、空结果与降级标记、引用可回看、来源删除后不可检索，以及 LLM 查询计划不能越过过滤和预算约束。
