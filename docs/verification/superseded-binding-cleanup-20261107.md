# 被取代绑定副本清理：实现、合成库测试与真实库副本演练（2026-11-07）

决定见 [ADR-175](../../architecture/adr/175-clean-superseded-binding-copies.md)（部分覆盖 ADR-144 的旧消息保留条款，用户已同意）。本记录只含聚合数字：不含联系人姓名、聊天内容或可识别夹具。

## 结论

- 修复同步通过（`Finalize`）后，同一联系人被取代绑定下**没有任何派生引用**的消息，连同来源记录、别名、引用及其尝试、媒体附件与托管文件、清空的抓取页，由统一删除账本的内部范围 `superseded_history` 分批清理；仍被记忆、候选回复、整理条目等引用的消息保留。清理不写删除围栏或排除项，不推进资料代次，不撤销读取授权。
- **存量副本没有清理。** 真实库只做了只读清单；执行需要用户确认。
- 真实库的完整副本上演练：唯一当前可清理的联系人（3 个被取代绑定）清理 42,379 条消息、295 个托管媒体文件（249,898,559 字节），保留 206 条被引用的消息；清单数字与实际结果逐项一致，所有引用表、终态抑制、排除项、围栏、读取授权和联系人资料代次一行未变，库校验 `integrity=ok`、`foreignKeys=ok`。

## 合成库测试（`backend-ts/test/sqlite-superseded-cleanup.test.mjs`，15 个用例）

场景：一位联系人经 3 次真实修复同步得到 3 个被取代绑定 + 1 个现行绑定，每个绑定 6 条消息（4 文字 + 2 图片），旧图片带真实托管文件；部分旧消息被整理条目、记忆（候选＋要求消息＋引用）、候选回复输入、引用、隔离记录引用。另有一位对照联系人。

- 只删未引用：12 条可清消息全部清掉，6 条被引用的消息（含被保留载体的引用目标、隔离记录）保留；`processing_item`、`memory_required_message`、`memory_citation`、`reply_context_item`、`reply_candidate_input_source`、隔离记录的行数一行不变；现行副本与对照联系人不变。
- 媒体：未引用消息的托管文件从磁盘擦除，被记忆引用的旧图片文件与现行文件保留。
- 非用户删除：删除围栏、来源排除、清空边界、终态抑制、读取授权、联系人资料代次前后相同。
- 幂等；有界分批（批次大小 4 → 3 个操作逐个结案）；中断续跑（计划后退出，新实例按原操作续清；某目标失败后沿原操作完成）；计划后新增引用的消息被逐条复验保留。
- 门禁：来源连续性围栏、进行中的其他删除挡住清理并保留请求标记，条件解除后继续；联系人删除一并清除标记。
- `Finalize` 登记：与修复完成同一事务登记请求，登记时不删除任何东西；接上 `onCompleted` 后修复通过即自动清理。清理后仍可再次修复同步（被隔离为撤回的消息由终态抑制延续），再次清理刚被取代的副本。
- 迁移 45：在带有既有账本行（操作、目标、校验、墓碑）的 44 版库上重建 `deletion_operation`，行原样保留、外键检查通过。
- `sqlite-superseded-references.test.mjs`：按真实 DDL 枚举全库，任何引用 `message`／`capture_record` 而未登记到 `retainingReferences`／`ownedReferences` 的表使测试失败。

## 真实库副本演练

方法：对运行中的 App 数据库做只读 `VACUUM INTO` 得到一致快照；媒体目录用 APFS 克隆复制。克隆后文件的 inode 与创建时间变了，账本里的文件身份复验会正确拒绝删除（`deletion_file_identity_changed`），所以演练前仅在副本里按真实文件重新登记身份（脚本只改副本）。副本放在会话临时目录。真实库未写入。

## 数据处理影响与剩余风险

- 演练只用真实库的只读快照副本；真实库只被只读打开，未重启 App，未点击任何“修复同步”。副本与临时产物位于会话临时目录。
- **迁移 45 会在新代码首次打开真实库时自动应用**（重建 `deletion_operation`、新增 `history_superseded_cleanup`）。应用后旧代码会报 `schema_too_new`；在 1.2 GB 副本上升级用时约 10–16 秒。上线前建议备份。
- 存量清理的执行路径是离线工具 `backend-ts/scripts/maintenance/clean-superseded-history.mjs`（App 完全退出后运行，先备份，`--confirm-clean` 与名单数量一致），与自动清理同一套代码。**未对真实库运行。**
- 清理期间存储 Worker 在每次压缩时独占约 8–13 秒（1.2 GB 库）；一位联系人的一次修复约需 3 次压缩。压缩遇长读者会使操作停在未结案，服务按间隔重试并在下次启动续跑。
- 新副本若比旧副本少（源端后来删除或撤回），旧副本中独有、无引用的消息不再保留，这是用户确认覆盖的部分。
- 第二阶段“修复改为增量读取”（旧新来源可证明同一物理来源时继承旧游标）不在本任务范围；在它落地前每次修复仍会读入一份完整新副本，只是旧副本会被清掉。
- 15 位围栏中的联系人尚未批量修复；修复会逐位触发清理，且每位的现行副本在下次修复通过后成为被取代副本。
