# 大聊天记录分段同步与中断恢复验证

日期：2026-11-03。状态：实现、自动验证、独立审查、新读取器启用与跨 App 恢复验收完成；本轮不宣称全部联系人已同时追平。

## 变更与范围

针对大联系人占用共享读取器、未完成历史在中断后重新开始的问题，支持 `durableHistory` 的读取器可提供部分历史检查点。正常共享同步每处理最多 32 页或达到约 1 秒预算后，在下一页请求检查点；它与该页消息在同一 SQLite 事务中接受，然后释放当前会话并将续读排到队尾。预算在页间检查，不是对单次原生调用或总等待时间的硬性截止。

恢复时重新核验范围与来源，创建新的固定快照，以最后业务已接受的检查点核对未读身份、变化行及待确认的缺失身份。未变化的已接受正文不重复投影；检查点前尚未持久化的片段可以重放并按现有身份去重。终页 `resumeCursor`、部分历史 `checkpointCursor` 与进程内分页游标分别使用；部分历史不会被报告为完整覆盖。旧读取器没有新能力时沿用原行为。

规范见 [ADR-164](../../architecture/adr/164-resumable-history-slices.md) 与[现行微信同步规格](../../architecture/current/wechat-sync.md)。实现基于 `48ef475636ff8b9acf22825fa3b4932d54818fc6`，隔离工作树实现提交为 `06ccce5affb701ddd9284b808bac27d33914cfd9`。主仓有并行修改，因此采用任务补丁集成，并补跑相邻来源重验唤醒回归；本任务主仓提交为 `d6241977a`，保留并行任务的来源重验唤醒改动，不捎带提交；后续实机基线包含该修复提交 `4e203405e`。

## 同负载对照与性能边界

原生投影对照使用相同合成加密 WCDB：首批接受 16 条后中断，旧方式重新建立完整历史目标，新方式从持久检查点恢复。

| 消息总数 | 无部分检查点的累计正文投影 | 使用部分检查点的累计正文投影 |
| --- | --- | --- |
| 48 | 64 | 48 |
| 1,000 | 1,016 | 1,000 |

另一用例每 16 条强制释放选择或重建原生会话，1,000 条完成 63 个片段，累计正文投影 1,000，重复正文为 0。这里的 Go “重启”是在同一测试进程内销毁并重建 `notaloneHistorySession`；不能描述为操作系统进程重启。实际子进程 PID 更换由上述 TS 渠道用例单独覆盖。

轮转用例包含两个各 80 页的大联系人和一个 1 页的小联系人：小联系人在两位大联系人的首片之后即获得执行权，每位大联系人在此之前最多处理 32 页，不必等待两份历史结束。隔离消息导致覆盖仍不完整时也保持该行为；正常让出不产生失败文案。

这些计数证明减少重复正文读取及有界让出，不代表总耗时同比降低。每次恢复仍扫描页身份索引，检查点仍序列化完整索引／摘要；本次没有据此声称十万条聊天、磁盘总吞吐、CPU 或端到端耗时已提高。上述合成负载不含模型或界面，真实数据规模下的总耗时另需实测。

## 开发实例与升级验证

仅使用 `pnpm run dev` 开发实例，不打包或发布。旧实例两次退出均停在 `stopping`；观察时数据库队列为 0、只读 CLI 空闲。确认进程归属后先向旧 CLI 发送 SIGTERM，但未解除停读等待；随后向后台发送 SIGTERM，再通过 Computer Use 重试，App 才完成退出。此过程没有收到原始停读请求的 `stopped` 回执，**不能记为正常停读验收通过**。

新读取器的来源别名已通过固定源码对核验。285 个已选范围的旧新元数据对照全部为 `verified`，耗时 35.289 秒，正文 `page` 调用为 0。对照过程中发现第 97 个范围是无消息表的空会话，新能力按合同不声明；原比较器却要求每个范围都有该能力。已修正比较器并增加有表／空目标混合回归，空目标保持能力缺席，没有因此更改原生制品。

开发配置已切换到新读取器。最终切换前的实例正常退出，随后通过 `pnpm run dev` 启动；Computer Use 确认本机服务连接、原有 `selected` 范围及后台同步开启。新制品接受了 100 位联系人的 416 页，16 位保存了非终页检查点，另有 83 个历史任务到终页，表明未完成大历史与其他联系人能够轮转。

正式 `/api/sync/disable` 返回 200／`disabled`，5.832 秒；刷新实际 App 后显示“后台正文同步已关闭”。关闭后约 90 秒内分页保持 416，原有消息全部保留。285 位绑定、授权与稳定身份逐项比较未变。随后正常退出 App，开发 App、后台和只读子进程均退出；再次 `pnpm run dev` 后正式状态仍为关闭、分页仍为 416。通过实际 App 重新开启原范围后，16 位抽样的未完成联系人全部生成了新的接续检查点；与停读时保存的检查点摘要相比，16／16 保留了此前 2,608 个身份条目，继续覆盖 2,442 个条目。此处证明真实原生进程重建后继承了已接纳基线并继续推进；不是通过业务捕获表测得的“重复正文投影为 0”，后者只由前述合成对照覆盖。

收尾观察累计有 106 位联系人接受新制品分页、670 页，17 位具有部分检查点、178 个历史任务到达终页（同一联系人可有后续任务，不能将任务数当作人数）。当时新制品最新历史任务的失败码均为空，来源连续性围栏为 0，原有消息记录全部保留。App 保持开发运行，原范围同步恢复开启。

升级后全范围仍在逐步接续：聚合状态曾为 `degraded / history_source_continuity_unverified`，同时新制品实际接受分页的人数继续从 106 增至 223，未出现持久来源围栏。本轮的 16 人跨 App 恢复证据不等同于新制品对全部 285 人已完成终页验收。

状态页在本轮仍偶有超过客户端预算的读取失败；它在升级前已经存在，实际停读先用正式接口完成再刷新 UI 核对。本次未声称状态页加载性能已修复。

## 数据处理、清理与剩余限制

检查点保留身份索引、页摘要和待核对身份，不增加正文或密钥副本；沿用 HMAC、来源／制品绑定、目录 0700／文件 0600 和联系人删除登记。页消息与恢复点同事务接受，迟到响应不能绕过暂停、撤销或删除；较新但未接受的原生响应不得取代业务仍使用的父检查点。

没有扩大联系人授权、恢复用户撤销项、清除来源围栏或加入外部发送能力。合成测试不处理私人资料；实机记录只保留聚合状态和必要摘要，不提交联系人身份、聊天正文或截图。

检查点缺失时可以重新建立基线；损坏或身份不符仍拒绝。同身份字节级原位回滚维持既有限制。旧读取器兼容路径仍可能占用读取器直至终页。本任务构建目录由约 408 MB 清理为约 16 MB，移除自有构建缓存／工具链并保留 source、bin、lib、manifest 和升级证据；旧读取器保留作回滚。主仓实现提交后完整可达历史与工作区隐私检查为 0 命中，验证文档提交后再次执行完整可达历史与工作区隐私检查；结果以本轮实际输出为准。
