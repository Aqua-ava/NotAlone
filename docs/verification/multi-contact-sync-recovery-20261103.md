# 多联系人同步恢复与分范围验收

日期：2026-11-03。用户要求覆盖全部已加入联系人，并实际验证多位联系人；本记录不以单联系人成功代替全部范围通过。

## 已实现

- 共享读取器切回联系人建立新历史目标后，始终唤醒首次历史接续；已有新持久增量检查点时解除旧快照的调度阻塞，不能复用失效游标。
- 空闲守卫失效后，只有仍允许正常使用元数据续证的联系人自动请求恢复；真实来源围栏和撤销授权不自动解除。
- 历史记忆调度先跳过未完成历史，并单独计算阻塞条件，避免重复统计未使用的增量输入。调度顺序、到期规则和模型配置保持。
- 各领域同时收到关闭请求，全部排空成功后才关闭共享微信进程、模型和 SQLite；任何失败保留共享资源供原操作重试。
- 来源读取预检在同一事务选择元数据重验或严格代次检查，避免认证刚完成或瞬时守卫超时被旧预检结果重新围栏。真实来源变化仍停读。
- 旧读取器来源按 ADR-161 独立证明所选物理表，正式重新认证保留撤回抑制；已完成审计只用于后续删除与排除闭包，不恢复旧资料资格。维护意图位于 SQLite 目录外，启动归属检查只认可私有固定文件，未知对象继续保留并拒绝。
- 两个历史协调器使用只含原授权字段的轻量目录。定点唤醒只查询相关联系人的覆盖，仍核对所有排队与在途任务的授权；全局唤醒、重试、绑定换代和停止继续保持原规则。

## 自动检查与性能

- 8 位合成联系人、真实共享窄协议进程、SQLite 与双协调器连续两轮普通定时同步，每位后续消息均保存且去重。原实现第一轮停在新历史目标，修复后通过；相关四模块 69 项通过。
- 独立停车与空闲失效回归 2 项通过，覆盖真实失证继续拒绝；相关合跑 9 项通过。
- 关闭死锁回归先失败后通过，关闭模块 8 项通过。合并态的关闭、历史扫描与停车回归共 11 项通过；后台类型检查通过。
- 历史扫描语义回归先失败后通过；相关历史自动处理与双队列 11 项通过。另有旧 `content` 字段预期失败已在未修改实现单例复现，不计为通过。
- 同一份真实资料只读备份、285 联系人、相同查询按 ABBA 比较：原两次 31.04／20.85 秒，精简后 14.23／13.74 秒；均值 25.95 → 13.99 秒，SQL 读取 345760 → 176756。返回 168 位到期联系人及顺序、下一到期时间完全相同。备份未改，不输出正文或身份。
- 原子预检新增 4 项回归覆盖空／非空目标与真实失证区分，相关 51 项通过。旧来源证明、跨代次删除、原认证与异步生命周期、启动归属的主仓最终合跑 99 项通过，直接 TypeScript 检查通过。另验证未知来源键方案与旧不受支持证据不能借新认证进入读取。
- 实际同步设置页曾在 12 秒客户端预算内失败；单次真实状态请求测得 35.05 秒，另一次 21.83 秒，响应约 168 KB 且可正常解析。当前 SQLite 队列中，廉价资格查询一次测得执行 0.468 ms、排队 715.456 ms，不能用增加超时掩盖排队。
- 同一只读备份交替比较状态批量大小 4／16，返回全部 285 位及顺序、完整内容一致，热缓存总 SQL 时间均约 2.6–2.7 秒。减少批次没有加速 SQL；固定高频背景负载下，16 位批次的状态延迟和前台等待反而增加。因此已回退该候选，保留原 4 位公平读取，不增超时或响应预算；继续针对重复全目录扫描定位根因。
- 定点调度比较使用同一份 285 人只读备份、同一目标和授权目录；覆盖结果统一投影为已完成以隔离调度成本，禁止原生读取和写入。覆盖查询 285 → 1，SQL 2288 → 10，三次中位耗时 3800 → 36 ms。目录授权字段与顺序摘要一致，轻量目录由 7 次 SQL 降为 2 次，移除无关正文计数。
- 真实共享窄协议子进程、SQLite 与双协调器的 8／32 人合成工作负载，各连续两轮保存新增消息、隔离和去重通过。32 人覆盖查询 690 → 224、耗时 2.51 → 1.85 秒；8 人耗时 0.73 → 0.82 秒，没有把小样本结果描述为加速。隔离相关检查 135 项通过，合入主仓后的最小相关检查 60 项及类型检查通过。
- 优化后新开发实例一次状态请求 5.06 秒、200、285 位，低于客户端 12 秒预算；实际设置页正常显示已开启。这是同范围真实可用性复验，不将不同运行时的后台负载差异当作固定加速倍数。
