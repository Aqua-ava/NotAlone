# 微信同步与真实模型流程验收（2026-11-01）

## 范围与方法

用户指定唯一联系人，并批准向该会话发送一条固定同步测试消息。真实微信仅发送该条消息一次。真实模型只使用该联系人的最近 10 条有效文字；正文、稳定身份、来源映射和详细账本保存在仓库外的端侧私有证据中。

微信同步使用当前已授权范围、正常渠道和默认业务库。模型验收将选定的原文、说话人和时间复制到隔离 SQLite 资料目录，使用合成运行身份并保留私有原始身份映射；另一合成联系人没有输入。关闭回放目录的读取总开关。使用正常官方 DSH profile、已配置的 DeepSeek、提示词、工具、预算和权限，没有直接调用供应商来替代产品流程。

锁定与安装的 DSH 均为 `0.2.1-rc.2`，Cordis 为 `4.0.5`。没有新增或猜测 DSH 接口。桌面验收只运行 `pnpm run dev`，没有打包。

## 同步与上下文

- 指定联系人的完整历史重读两次，保存消息身份及计数不变。
- 批准的新增消息先由正常增量入库，来源为 `incremental`、说话人为本人；随后完整重读，仍只有一条消息和一个原始来源，消息总数由 104 增至 105。
- 发现旧助手消息端口和普通候选默认上下文仍按保存位置取近期消息。修复后实际助手读取函数通过认证后端连读两页，共 40 条无重复、按时间降序，首屏包含最新验收消息。新版统一工作区原有时间读取保持不变。实现、回归及既有扩大检查失败见[聊天时间验收](contact-chat-time-order-20261101.md)。
- 当前授权绑定共有 285 个，持久连续性围栏交集为 19 个，指定验收联系人不在其中。重启后待续证的临时失效租约不能算作持久围栏。早先仅记录 18 个围栏聚合数，缺少当时成员快照，表内也没有创建时间，无法确认额外一项的时间和原因。
- 现有“清空聊天再读取”会删除旧资料及依赖，却保留持久围栏，正式渠道仍拒绝恢复。初轮诊断未在真实库上清空、删除围栏或替换授权。用户随后明确采纳保留旧资料并重新认证来源，决定见 [ADR-144](../../architecture/adr/144-preserved-history-source-recertification.md)；新入口已完成 23 个实际范围的恢复（包括后续新观测围栏），证据见[来源重新认证验收](source-recertification-20261101.md)，不将其混作上述初轮既有能力。

## 真实模型与桌面结果

- 共 4 次真实请求，均观察到成功响应；无未确认请求结果。累计预算上限为 8 次，两轮独立 Agent 评估均记为 `unchanged`，不是质量改进实验。
- 第一轮完成 10/10 条文字目标，没有提取场景、候选或正式记忆。这些测试文字不含可支持的长期关系事实，零记忆是本次负例的预期结果。
- 第二轮在相同输入与表达要求下使用默认 Skill 库：发现并启用 92 项，持久输入事件和实际 App 均确认载入一项结束聊天的 Skill 正文。三组候选忠实表达用户本次要求，没有补写关系经历或对方态度。
- Computer Use 在隔离开发 App 中查看这次已完成结果，确认 10/10、无新记忆、无已发布主题资料。修复了空提取已结束但文档视图仍宣称处理中的问题，页面现显示“当前尚无已发布的主题资料”。实现与相关检查见[混合记忆调度验收](hybrid-memory-scheduling-20261101.md)。
- 实测另发现“对方／我”范围切换时，旧范围的释放广播会误撤下新范围。修复生命周期后，实际 App 中“对方→我→对方”均自动显示正确空结果，不再需要手动刷新；真正来源失效及旧读取迟到的保护由实际控制器到 React 的回归覆盖。
- 实际小窗显示三组真实候选、依据和实际 Skill；手工编辑保存为第 2 版，标记继承依据尚未重新核验，选用后明确显示不代表已发送。通过精确选择文字和键盘复制，粘贴到本地草稿核对一致，随后清除草稿。没有将候选发送到微信，也没有再次生成。

## 限制

本轮证明指定联系人的真实同步和受限原文的正常模型流程，不代表全部会话同步成功，也不代表隔离身份与默认业务库之间已直接串联执行模型请求。没有长期事实，因此没有完成真实模型的 L2/L3 正向发布验收，没有加速生产等待窗口。

4 次请求中有 1 次 token 用量未知；已知部分为输入 8,813、输出 148，不能当作完整总量。所有费用均未知。首轮验收脚本的目录监听曾未被 WAL 内容变化唤醒，读取确认产品任务已完成后仅修正验收等待，没有重复调用模型。
