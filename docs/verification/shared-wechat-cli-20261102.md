# 单进程微信读取核验（2026-11-02）

## 结果与范围

按 [ADR-151](../../architecture/adr/151-shared-wechat-cli-process.md) 实施单个共享 `wechat-cli notalone-history` 进程，联系人历史、增量、引用、图片、账号元数据和前台名单均通过独占租约串行使用。没有保留按联系人创建常驻进程的正常宿主入口。

切换释放快照、会话游标、图片令牌和观察基线；轻量来源证明继续受同一账号及消息文件守卫保护。切回重新核验授权、来源及已接受检查点。暂停、撤销、删除和退出排空在途及排队读取，旧通道迟到关闭不能清除新联系人的选择。停止订阅可解绑，不随切换次数积累退休通道。

## 实机与限制

通过 `pnpm run dev:status` 复用当前项目开发路径，Computer Use 正常退出旧宿主，切换已核验读取器后以 `pnpm run dev` 启动；源码变更由开发监督器安全重启。开发前基线为 274 个 CLI、合计 RSS 约 1242 MiB；新实例多次采样为 1 个 CLI，RSS 约 30～57 MiB。两者是同一授权范围的运行采样，处于不同的检查点重建阶段，不是全量完成后的严格同负载内存基准。

在实际同步设置页关闭总开关后，接口返回 `sync_enabled=false`、CLI 数为 0；重新开启保持原先所选范围并恢复单进程。界面正常连接，微信前台名单曾返回已确认绑定匹配；微信不在前台时观察接口返回暂停，未发送任何外部消息。共享进程在开发监督器重启后恢复；重启去重、A/B 正文隔离及持久增量的精确断言由上述合成集成检查覆盖。

实机最初发现引用协调器的空闲等待漏掉正在等租约的请求，已修复并补回归。随后采样显示主要 CPU 消耗位于 SQLite worker 查询，且实际历史捕获持续增长（一次核验已有 130 批；末次运行的 116 批具有 116 个不同输出游标），不是重复同一页。已有同来源记录按原去重路径复用，新增捕获不一定新增消息或来源记录。新制品必须建立自身绑定的检查点，历史较多的联系人首次遍历期间会占用串行读取器；本轮不宣称 285 个范围均已追平，也不把未重验范围的临时不可用或 13 个原有围栏标为已修复。

未改变模型出站范围、消息发送能力或资料删除规则。读取过程中复查原有授权、来源范围、删除围栏和排除记录摘要保持；同步开关的读代次按正常产品行为变更。原生守卫不持续认证表结构或前台登录账号，切回仍需来源重验，既有原地回滚限制保持。

已清理本轮未启用的第一版构建（408 MiB），保留最终开发读取器和原读取器回滚依据；原有其他任务产物不作清理。
