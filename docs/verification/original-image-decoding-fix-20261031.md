# 原图解码与资源绑定修复验收

日期：2026-10-31。范围：修复 [ADR-137](../../architecture/adr/137-original-image-authorized-sync.md) 的真实微信图片读取，并验证能否取得及保存原图。

## 已确认的缺陷

- 正式 `wechat-cli notalone-history` 的 `image-open` 可复现 `history_image_original_unavailable`。同一获准图片行的 498 字节元数据实际为 Zstd、存储标记为 4，旧代码直接解析 XML，未进入文件读取便失败。
- 解压后的图片 XML 有 big URL、明文 MD5 和正 HD 长度，但 HD 宽高为 0。旧实现将未提供尺寸当成无效原图，缺少独立的实际内容尺寸表示。
- 消息与唯一资源 Info 的 packed-info 有相同缓存键；它与 XML 的明文 MD5 不同。缓存文件确实存在，旧代码却用明文 MD5 作文件名。
- 选定图片的封装文件为 42,018 字节，HD 明文声明为 41,987 字节。旧代码混同这两个长度；同 Info 下多个 image detail 的相同封装长度也不能用 variant 猜原图质量。

## 修复

- 身份已核准的单条图片内容采用 256 KiB 输入／输出上限解压；解码内存／窗口上限 8 MiB、单并发，坏帧及存储标记矛盾拒绝，不返回原 XML。
- 消息与唯一 Info 的缓存键各须唯一且相同，只取同会话、月份下该键的 `.dat`／`_h.dat`，不读 `_t.dat`，不搜索其他目录。
- v3 证明绑定 Info ID、全部排序唯一的匹配 detail ID 及行属性，按文件实际封装字节数匹配资源长度；代表 detail 的 variant 不作为原图证据。
- 原图资格仍由 big URL 声明、HD 明文长度、完整明文 MD5／SHA-256 和有效解码尺寸核验；未声明的 HD 尺寸用 `null`，不伪造。保存前继续由 Swift 校验器完整解码。
- 分开保留元数据无效、本机文件缺失、缺少图片密钥和质量未核验状态。只有声明 v3 的组件启用修复版同步；旧失败按 `image_sync_v2_` 幂等版本重试一次，清除与已有原图排除规则不变。

## 真实结果

- 实际调用锁定源码构建的 `wechat-cli`，通过授权范围内的 `notalone-history` 图片协议验收；该只读构建没有开放通用 `media` 命令。
- 选定图片的消息、Info、缓存键及本机 `.dat`／`_h.dat` 已对应；文件为微信 V4-format2 加密缓存。修复后的正式 `image-open` 返回 `history_image_key_unavailable`，不再被漏解压或错误文件名提前拒绝。
- 当前配置、同账号既有配置、已配置环境均无图片 AES／XOR 密钥；非交互查询 CLI 受保护的本机运行密钥存储也没有既有记录。未获取或打印密钥，未触发授权提示、扫描微信进程、注入、远端图片下载或模型调用。
- 正常宿主自动产生修复版处理记录；正式媒体 GET 返回 200、`kind=image`、`state=active`、`latestAttempt.errorCode=needs_image_key`、文件数 0，原消息保留。验收时真实原图成功保存数仍为 0，不能宣称落盘验证成功。
- 正式 `/history/sync` 返回 200／`complete`，前后均为 609 条消息及 6 条修复版自动图片尝试，重扫无重复。
- 对照升级前备份，旧消息内容与身份、旧消息别名均无缺失或变化；授权、绑定、核验、账号、会话、停读围栏、来源排除、删除围栏摘要保持一致，外键检查为 0。
- 实际 App 可连接新宿主；媒体面板文案／预览沿用生产组件与 CSP 的隔离浏览器验证。最近聊天材料入口仍按既有规则只展示文字，没有为展示图片而改变生成资料。

真实验收结论：已修复定位和解码适配缺陷，能找到关联的本机加密文件；当前缺少图片解密密钥，尚不能保存经过验证的真实原图。成功解密、完整验证、受管保存与预览链路仅有合成图片通过证据。
