# 联系人聊天时间与分页修复（2026-11-01）

## 问题与原因

用户截图中的聊天记录从 2026 年近期消息直接跳到 2021 年。通过当前已授权联系人的专用历史接口复现：首页 20 条记录遗漏 9 条较新的消息，却返回多年以前的记录。只比较时间和内部身份，没有导出聊天正文。

最小合成复现仅需按“近期、旧历史、最新”的顺序保存三条消息，首页取两条即可重现。后台原先按 `display_no` 入库顺序分页；桌面合并时也优先按 `displayPosition` 排序。保存位置只能提供稳定位置，不能表示发送时间。

## 修复

- `history-messages` 专用读取改为发送时间降序，时间相同以精确保存位置降序分页，未知时间排在已知时间之后。游标仍为同范围的稳定消息身份，后续页按相同排序键续读。
- 桌面合并使用相同规则，保留微秒尾数及大整数位置，不让后补旧记录挤入近期消息。
- 保留 `ordering=unknown`，展示顺序不冒充渠道认证的精确先后。页面相应说明同时间及未知时间的限制。
- 旧 `/messages`、回复及记忆的读取合同保持不变；沿用原有 owner、contact、当前来源和隔离过滤。没有修改原始消息时间、补造时间、重导入或迁移数据。

## 开发实例恢复

热更新时另发现数据库受管目录中放有历史备份。`deletion.compact` 要求该目录只包含当前数据库和受控 sidecar；这些备份导致恢复清理重复执行完整整理并被残留检查阻断，影响后台握手。

保留严格校验，将 5 个历史备份及同组 2 个 sidecar 从应用资料根的 `managed/sqlite/` 原子移到 `backups/sqlite/`。移动前核对没有打开引用、目标不存在；移动后逐一核对设备、inode 和字节数不变，共保留 3,748,769,792 字节。当前数据库及其 sidecar 未移动，受管目录额外文件数归零。此前验收记录命名的这些备份应从新目录恢复。

启动诊断仅记录固定动作名、SQL 模板摘要和耗时，没有记录参数、密钥或聊天正文；临时诊断代码在收尾前移除。只读完整性及外键检查均通过，没有绕过检查或延长超时预算。

进一步记录的固定错误码为 `history_source_not_available`：某个旧副本来源失效时，媒体启动中的逐文件资格复验会让整个宿主退出。新增服务回归在两个联系人各保存一图后，将其中一方来源变为未核验；修复前启动失败。修复只在启动遍历中跳过这一明确的来源失效错误，保留原访问拒绝、文件及状态，其他错误继续抛出。另一联系人副本仍可访问，不借恢复启动扩大资格。

`cd backend-ts && node --test test/sqlite-media.test.mjs test/sqlite-media-host.test.mjs` 23 通过；最终两工作区类型检查通过。独立只读复核确认失效副本在读字节前被拒绝、后续预览仍受原来源资格约束。9 项既有清理现均为 completed，后台正常连接。
