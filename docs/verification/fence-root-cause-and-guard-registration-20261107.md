# 重启围栏调查与守卫登记误判修复（2026-11-07）

## 结论与完成边界

已证实并修复一条误围栏机制：原生守卫登记文件或进程监听时，同时取出了其他监听项排队中的正常目录 `NOTE_WRITE`，却把任何返回事件都当作登记失败；该错误被转换为 `history_source_unverified`，后台可在正文读取、目标创建和守卫续租之前写入围栏。

**历史归因：未复现。** 00:05 备份在旧版代码及当前实际读取器上的正常元数据重验均成功，未重现该批围栏；当时的入口和错误码未保存在围栏表，现存开发日志已覆盖到之后的启动。用户已确认历史日志无法恢复，本轮不再寻找。上述原生缺陷不能写成这 219 条历史围栏的根因，也不能据此宣称正常使用已经端到端修好。

**已证实的历史事实：** 00:05→11:03 新增 219 位围栏，全部是此前“修复同步”成功的联系人；期间没有新的读取目标或抓取页，守卫租约和连续性范围与 00:05 逐行相同，运行代次从 1215 到 1219，发生四次重启。这些事实缩小候选路径，但没有记录具体写入入口。

按用户追加验收，本轮同时交付每次新增围栏的常驻本机诊断：实际入口、联系人编号前 8 位、固定分支编号及时间；已知来源错误可另记白名单错误码。轮转、留存、事务提交和删除规则见下文。

未合并主工作区、未切换真实读取器或重启真实 App。新的开发读取器仅在隔离工作树构建，尚未进行固定制品配对的来源别名升级与启用验收。真实库和原备份均只读，没有点击“修复同步”；现场仍为 15 条围栏。

最后一轮的副本首次迁移到当前 schema 45 时超过普通开库 60 秒预算；仅该副本已完成迁移，随后按正常开库重跑并成功。没有提高产品超时、修改真实库或以迁移超时解释历史围栏。以上实际读取器均为现有配置制品，隔离构建的新原生制品未换入，因此不把此结果写成新制品启用验收。

静态状态也不支持“修复完成后写入的 scope 必然不能重验”：

- 219 位有效未围栏联系人实际计算 `normalUseRevalidationCandidate` 均为 true；未围栏联系人的最新有序目标均保存 normal-use 支持档。
- 221 份 scope 的表均为 `[partition, instance]`；scope 与最新目标的 `checkedPartitions` 集合相同，目标转移均为 `same`。
- 重新认证经普通 `history.begin` 保存有序目标与支持档；Activate、Finalize 均要求该目标完整。其保存格式与 `priorNormalUse` 接受格式相符。
- 旧版与实现基线的候选、旧支持档与目标转移判据相同；后续空目标复用改动不改变这些判据。
- 前台名单使用独立元数据客户端；同步状态查询只读 coverage/guardCheck，不直接写围栏。
- 正常重启且当前支持档为 normal-use 时，来源准备、首次同步和增量同步会带 proof 续租，不直接走无 proof 的 `guardAcquire`。

仍符合历史“围栏新增、零目标／抓取、租约和 scope 不变”形态的入口是：`withExclusiveChannel` 的回调在 armGuard 前由 `inspect`／`target` 抛出来源失证错误，随后 `history.markContinuityLost` 只写围栏。原生登记缺陷能够产生这种错误；它是否在该历史窗口实际发生，仍缺直接证据。

## 确定性红灯与最小修复

真实 macOS kqueue，合成临时目录，文件实例和进程身份不变：

1. 登记目录监听；创建或删除普通旁车；再登记固定消息文件。
2. 已建来源守卫；创建普通旁车；再登记真实存活进程。

修复前，第一组两个子例稳定报 `source_guard_watch_failed`，第二组报 `source_process_unverified`。用例直接覆盖正式 `add`／`WatchProcess`，没有修改真实微信目录。

```sh
go test -count=1 -run 'TestNotalone(GuardFileRegistrationAllowsPendingSidecarWrite|SourceProcessRegistrationAllowsPendingSidecarWrite)$' ./cmd/wechat-cli
```

旧代码退出 1，修复后退出 0。两个登记调用均改为仅提交 changelist，不接收或消费排队事件；原有 `Check`／`checkEvents` 随后仍区分事件类型并核对路径、打开实例、分片名单及进程身份。系统调用登记错误仍通过 errno 返回，没有删除围栏、重签来源或修改认证规则。

新增安全用例保留真实 rename 后复原、文件替换、新增分片、`EV_ERROR`、`EV_EOF` 和系统调用登记失败的拒绝；既有进程退出与真实 WCDB 旁车测试继续通过。

## 常驻诊断的实现与验收

全部 `fenceContinuity` 分支使用固定 G/T/N/A/R/L 编号；重新认证失败的直接 INSERT 使用 C01，编号说明见[围栏诊断指南](../guides/history-continuity-diagnostics.md)。只有实际新增行才产生事件，已有围栏不重复写。存储事务仅缓冲固定字段，每次尝试独立缓冲；提交后写文件，回滚丢弃，普通日志失败不逆转已提交围栏或放宽读取。

日志固定为应用资料目录下 `logs/history-continuity.jsonl`，当前加三份归档，每份最多 1 MiB，保存 7 天，在启动和追加时淘汰。仅白名单入口、分支、8 位前缀与错误码能落盘，0700 目录、0600 文件；不输出姓名、聊天、备注、完整编号、账号、路径、异常正文或凭据，不自动上传。

整联系人／账号删除在原任务封存前清理相应诊断。清理入口复核持久删除 runner、运行代次与计划修订，从已授权删除范围派生前缀，不接受任意路径或前缀；清理失败使删除任务受阻。普通来源删除与历史清空不清除此类无正文故障诊断，仍受留存预算约束。额外故障用例核对：追加失败后围栏仍提交且新同步停读；日志清除失败时联系人／账号删除均受阻；伪造删除 runner 不得清除日志。
