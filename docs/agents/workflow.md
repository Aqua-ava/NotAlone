# Agent 工作流

涉及功能、Bug、架构或测试改动时先读本文件；产品硬边界、通用规则和读取入口见根 `AGENTS.md`。

## 工作模式

- **讨论模式**：用户仅询问方案、解释、诊断、评审或状态时，分析并报告结论，不修改项目代码或真实业务数据。诊断可在授权范围内运行检查，使用隔离的合成或匿名化资料及临时产物复现问题；按工程工作流清理本次临时资源。读取真实资料、外部模型调用和消息发送仍须遵循既有范围与授权。
- **实现模式**：用户明确要求实现功能、修复 Bug 或指定 ticket 时，在当前 ticket 或 spec 范围内连续完成文件编辑、测试和重构，无需逐项询问。

### 决策模式

只有影响结果的选择无法从用户指令、已有授权和项目上下文可靠判断时，才暂停受影响的步骤并询问；不依赖该决定的工作继续推进：

- 功能范围或用户意图无法推断，或实际实现需要超出当前 spec／ticket。
- Module 的 Interface 或 Seam 会影响整体架构，且尚未确定。
- 真实用户数据的删除或迁移、外部发送、正式环境操作或 push 尚无明确授权。

用户已经明确授权的动作按其范围继续；测试失败后的常规修复和不改变约定行为、范围的实现调整自行决定。用户作出决策后继续当前流程，不把一次决策解释成对其他范围的授权。

## 子 Agent 协作

本仓库开发任务允许主 Agent 主动委派。任务可独立拆分且能提高效率或核验质量时，直接使用子 Agent，无需用户逐次指定或确认；适用技能明确要求子 Agent 或并行工作时，按技能执行。

- **独立探索**：将互不依赖的代码或文档问题交给子 Agent，明确问题与证据范围；主 Agent 同时推进不依赖其结论的工作。
- **并行实现**：将无阻塞关系的任务交给不同子 Agent，明确各自负责的文件或模块，按需隔离工作树。告知执行者还有其他 Agent 在协作，应适配已有修改；主 Agent 负责集成与最终验证。使用 `implement-spec` 时，按其任务图调度已就绪的 tickets。
- **独立审查**：使用 `code-review` 时，按技能分别启动 Standards 和 Spec 审查子 Agent；缺少 spec 时按技能跳过 Spec 轴并说明。

短文字回复、简单单点修改和紧密依赖的步骤由主 Agent 完成。委派时提供目标、来源指针、职责边界和完成条件；子 Agent 返回带来源的结构化证据，实现任务同时报告文件变更与验证结果。子 Agent 不得直接发送外部消息或改写用户确认事实；既有数据、桌面占用和 Git 授权边界继续适用。

工具不可用或并发槽不足时，使用可用的串行路径并说明实际限制，不把能力限制解释成缺少用户授权；质量诊断的独立验收无法完成时按[质量诊断工作流](quality-diagnosis.md#停止与结案)保留缺口。

## 质量诊断与收敛

记忆提取、整理或回复质量的诊断、模型对照与真实资料验收，执行[小批诊断与累计预算](quality-diagnosis.md)。紧密依赖的质量任务默认一个修复负责人加一个独立验收 Agent；没有独立接口边界不增加并行会话。

## 工具选型

简单需求使用最小本地工具；只有标准化、可替换的边界确有价值时才使用 MCP。当前工作流没有证明需要时，不预先实现自治 Agent Harness、定时自动化或聊天渠道自动化。

## 主流程

### 1. 明确问题和约束

结合用户请求、现有代码和相关文档确定目标、范围与约束。有实质设计或范围疑问时使用 `grill-with-docs`；已明确的简单工作直接继续。难以定位的故障使用 `diagnosing-bugs`，先建立能复现故障的反馈回路。

完成条件：能够判断哪些行为需要改变、哪些边界必须保留，以及下一步是否需要用户决策。

### 2. 按不确定性与规模分支

- 需要通过可运行答案确定状态、业务逻辑或界面时，使用 `handoff` → `prototype` → `handoff` 回到原工作流；Module、Interface 或 Seam 不清楚时使用 `codebase-design`。
- 范围明确、可在当前会话完成的任务，直接进入实现；不强制创建 spec 或 ticket。
- 多会话工作使用 `to-spec` 和 `to-tickets`。目标过大且路径不清楚时先使用 `wayfinder`；原始外部 Bug 或请求需要形成可执行任务时使用 `triage`。

完成条件：实现所需的关键 Interface、Seam 和可验证行为已明确；重大未知按决策模式处理。

### 3. 按需形成 spec 和 tickets

`to-spec` 将讨论结果按[任务约定](issue-tracker.md)发布为 spec，记录用户问题、解决方案、Implementation Decisions、Testing Decisions、测试 Seam 和 Out of Scope。

`to-tickets` 将 spec 拆成可独立验证的 tracer-bullet tickets，记录真实的 `Blocked by` 关系。用户已授权拆分和发布时，按已确认范围完成；需要新的产品范围取舍时按决策模式处理。已由 `to-spec` 产生的 tickets 不再经过 `triage`。

完成条件：每个 ticket 在新上下文中有足够信息交付完整行为，阻塞关系正确并已按依赖顺序发布。

### 4. 实现与收尾

1. 有 ticket 时按[任务约定](issue-tracker.md)读取 ticket 和 spec；按[领域文档](domain.md)及[工程工作流](engineering.md)核对适用约束。
2. 实质功能或 Bug 的 ticket 在已约定的 Seam 上使用 `tdd`，以 red → green 的垂直切片推进；文档或低影响修改按实际风险选择验证。
3. 从最小相关检查开始，按影响范围扩大；复用仍有效的结果。
4. ticket 完成后使用 `code-review` 检查 Standards 和 Spec；无 spec 时按技能说明处理。其他任务按风险选择审查方式。
5. 按工程工作流完成仅含本任务变更的本地提交，报告实际变更、验证结果、数据影响和剩余风险；是否另写 ADR 或验收记录按[决策与文档记录](#决策与文档记录)。

完成条件：约定范围内的行为和相关修复已完成，验证与审查的结果及缺口有据可查。

## 决策与文档记录

文档服务于实现，不是每个改动的必经产物。默认只维护 `architecture/current/` 这一份现行规格。

- **ADR 已冻结**：现有 ADR 保留为只读历史，不再更新、不补回链，也不为“补充”它们而新建 ADR。现行规格对 ADR 的链接保持有效，仅在解释不足、冲突或复审取舍时查阅。
- **不再为实现细节、修复或补丁新增 ADR**：设计变化直接改 `architecture/current/` 对应段落，并在该段写一句原因和被替代的旧条款；其余依据写进提交信息。
- **例外**：只有决定改变根 `AGENTS.md` 的产品硬边界（联系人映射、数据隔离、授权范围、删除路径、人工发送）时，才新增一份短 ADR，一页内写清决定、原因和放弃的方案，并同步现行规格。
- **验收记录**：仅桌面真实验收，或隐私、删除、同步类改动，才在 `docs/verification/` 写一份只含计数、阶段和结果的记录；其余把验证结果写进提交信息，不另建文件。
- **止损**：同一机制出现第三份补充决定、需要专用修复工具，或保护的触发范围明显偏大（例如覆盖多数联系人）时，停止继续打补丁，回到“明确问题和约束”重审设计粒度，并按决策模式询问。

## 技能不可用时

以上技能按任务触发；先查看当前可用技能及本机已知技能目录并读取对应说明。确实不可用时，按相应步骤和完成条件继续，并说明缺口；无法独立完成的审查不能标为独立审查。用户明确指定技能且找不到时，按上层指令报告，不能冒称已使用。

## 其他入口

- `diagnosing-bugs` 发现没有可测试的 Seam 时，转入 `improve-codebase-architecture` 或 `codebase-design`。

## 阶段边界

在 grill、设计、spec、tickets 和实现之间，根据上下文是否仍然有用选择继续、`clear`、`handoff`、subagent 或 `compact`。完成一个 ticket 后使用新上下文处理下一个 ticket；在 `to-tickets` 之前保持同一条思考链，除非上下文接近 smart zone 上限。
