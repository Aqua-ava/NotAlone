# macOS 权限与启动排障

本文是当前开发入口的操作说明。日常使用 Electron 热更新、TypeScript／DSH 与 SQLite；按[工程工作流](../agents/engineering.md)先检查开发状态。各日期实测、旧 Python／PostgreSQL、Swift App、手工选区、打包和签名记录已完整移至[历史记录](../history/macos-permissions-history.md)，只在追溯相应版本时读取。

## 先确认正在运行的实例

在仓库根目录执行 `pnpm run dev:status`。已有当前项目的开发实例就复用；没有才运行 `pnpm run dev`，启动后重新核对状态及 App 中的连接结果。Agent 启动常驻进程的后台方式见工程工作流。开发脚本只支持可选的绝对路径 `--user-data-dir`，不接受自行指定开发端口；隔离实例检查也须使用同一目录。

React／CSS 保存后热更新，main、preload、共享代码与后台源码变化由监督器安全重启。发现打包版时，核对归属后通过应用菜单正常退出；停读未获确认时先完成停读，不强杀、不并行创建另一实例。常规开发与验收不能启动旧包、重签应用或解除发布门禁来排查权限；发布例外必须来自用户明确提出的发布任务。

不要把资料位置或权限问题变成数据库重置。保留原 SQLite、控制面记录、媒体与模型配置；缺失、损坏或身份不符时核验现场，不删除文件、锁或备份，不换一个新空库来获得“连接成功”。

脚本依据：[开发入口](../../desktop/scripts/dev.mjs)、[状态检查](../../desktop/scripts/development-status.mjs)、[发布门禁](../../desktop/scripts/release-policy.mjs)。新环境安装见[源码启动指南](new-environment-hot-start.md)。

开发监督器断开时，窗口可能仍在完成首次打开。就绪通知先检查 IPC 连接，并通过发送回调处理检查之后才断开的竞态；失败后请求正常退出，继续使用认证停读和恢复入口，不弹出未捕获的 `ERR_IPC_CHANNEL_CLOSED`。启动命令输出“开发模式”仅说明构建器已启动，必须再核对 `dev:status` 中宿主与监督器及实际界面；失联宿主不能视为热更新可用。

旧握手所指后台已经退出时，桌面将启动请求交回受控启动器，由它在互斥内重新核验进程、握手与临时目录归属后恢复。PID 仍存活或状态无法确认时继续按原握手认证，不自动启动第二位写者；不要手工删除握手来绕过检查。

## 区分两条读取链路

| 链路 | 用途与有效范围 | 权限／失败判断 |
| --- | --- | --- |
| 外置微信 CLI | 读取用户已确认账号和联系人范围内的本机历史及增量；应用运行且同步总开关开启时才读，关闭或退出即停读。 | macOS 对微信应用数据的访问取决于实际启动链和责任进程；工具版本或 `status` 可运行，不等于受保护数据库可读。 |
| 前台定位探针 | 仅在微信前台、会话可见的唯一窗口分析端侧内存画面，再仅 OCR 顶部名称区域；原始帧默认不落盘、不上传。 | 需要当前运行链路的屏幕录制权限。权限检查成功不等于名称、联系人或完整产品闭环已验证。 |

两者独立。录屏权限不授予正文同步资格，CLI 同步不以 OCR 或微信前台为门；CLI 失败也不能回退为正文 OCR。前台不会点击、切换或滚动微信，不读取其他 App，也不识别聊天正文或联系人列表。产品中的最终消息由用户亲自发送。

首次连接按[微信同步规格](../../architecture/current/wechat-sync.md)先确认账号，再选择联系人并确认同步；工具准备、名单访问和正文授权分开。默认仅所选会话；全部私聊是明确授权后的产品范围，不能因历史文档中的一次启用就假定当前入口、账号或资料已获授权。账号检测及连接状态不代替来源、历史覆盖或图片可读性的验证。

## 屏幕录制权限

启动、热重启和“重新检测”只做静默预检，不主动弹系统请求。用户明确选择授权按钮后才请求系统权限；权限入口本身不读窗口、不截图、不做 OCR。检查中的操作合并为一个，避免重复请求。

1. 先核对实际开发宿主、配置探针路径及当前页面的权限状态。系统设置里同名旧 App 的开关不能证明当前进程可用；独立终端探针的成功也不能代替 App 链路验证。
2. 缺权限时使用 App 的显式授权／系统设置入口，再在同一开发链路重新检测。只检查权限，不用额外截图或正文读取来试探。
3. 已授权仍失败时先区分路径、签名身份、前台条件和实际固定错误。不要反复撤销／添加权限、重签、重置 TCC 或给其他进程扩大授权来“试试看”。没有责任归属证据就记录未知。
4. 需要重启时核对旧实例已正常退出及新实例的实际路径；同名应用再次被打开不自动证明已完成冷启动。权限就绪以后，名称关联与联系人选择仍按现行规则单独核验。

系统权限项的名称可能包含音频；当前前台定位不采集声音。不以完整磁盘访问、辅助功能、自动化、麦克风或摄像头授权作为默认修复。历史验收中临时授予的权限只属于原轮次和范围，不能沿用成常驻产品要求；同一实际轮次未结束时也不反复撤销重加。系统需要用户认证时只保留一个待处理操作，解锁后重新核对精确条目。

实现依据：[权限控制器](../../desktop/src/main/screen-permission/controller.ts)、[当前配置解析](../../desktop/src/main/screen-permission/configured.ts)、[原生权限入口](../../native/macos/Sources/NotAloneSyncCore/ProbeCore.swift)。视觉范围与名称关联以[现行微信规格](../../architecture/current/wechat-sync.md#前台识别与联系人跟随)为准；历史 0.90 阈值、手填 profile 与选中行 OCR 不作为当前排障门槛。

## 微信应用数据访问

`Operation not permitted`、文件访问拒绝、账号检测成功但正文不可读等现象，先按实际操作区分权限、来源认证、账号配置、密钥覆盖和工具兼容性，不直接判为同一个问题。核对本次 supervisor → Electron／Node → CLI 的实际责任进程；一次终端授权不能推定所有开发或 App 启动方式都已授权。

只在原授权范围内使用公开状态和固定错误定位。不要为“测试能否读取”扩大联系人范围、启动持续监听或重做首次密钥初始化；不要输出配置内容、数据库路径中的身份信息、密钥、会话名称或聊天正文。来源无法认证时保持停读，按当前来源恢复流程处理，不能清库、解除围栏或扩大系统权限绕过。

外置工具安装及配置见[桌面说明](../../desktop/README.md#外置微信工具)。[2026-10-23 初始化记录](../history/wechat-first-run-troubleshooting-20261023.md)只证明那次具体环境的结果：存在未覆盖密钥与降级状态，关闭临时权限后的持续读取未复验，不能复制为当前通用安装或重签流程。

## 启动阶段与安全诊断

正常入口通过 SQLite 控制面核对受控资料与实例身份，再启动 DSH 后台。当前后台为以下阶段写入固定诊断，界面使用相应错误码；阶段用于定位失败范围，不单凭阶段推定根因。

| 诊断阶段 | 界面错误码 | 核查方向 |
| --- | --- | --- |
| `runtime` | `backend_startup_runtime_failed` | Node／DSH 运行组件与当前源码依赖。 |
| `configuration` | `backend_startup_configuration_failed` | 受控配置、模型及后台配置是否有效；不打印配置内容。 |
| `storage` | `backend_startup_storage_failed` | 原 SQLite 的权限、身份、结构及完整性；保留资料现场。 |
| `modules` | `backend_startup_modules_failed` | 业务模块装配及固定错误类别；不回退旧后台。 |
| `handshake` | `backend_startup_handshake_failed` | 当前后台连接发布及宿主握手。 |

安全记录位于实际握手路径附加 `.startup-diagnostic.json` 的文件；正常受管名称为 `sqlite-backend.info.startup-diagnostic.json`。它只含 `version`、`stage`、`cause`、`recordedAt`，采用固定白名单，受限权限 `0600`，读取上限 512 字节。每个启动阶段覆盖保存，连接发布成功清除，失败保留最近阶段；文件缺失或不合法就没有可采纳的诊断，不从旧日志补造结果。

`cause` 仅为 `pending`、`process_exit`、`unexpected_failure`、`permission_denied`、`configuration_invalid`、`storage_mismatch`、`storage_unavailable`、`timeout` 之一。它不保存异常原文、stderr、堆栈、配置、路径、密钥或业务正文；具体分类仍须结合当前代码及最小复现核对。诊断写入失败不能掩盖原失败或妨碍收尾。

合同与实现见[启动诊断](../../backend-ts/src/startup-diagnostics.ts)、[后台装配](../../backend-ts/src/sqlite-host-plugin.ts)、[界面阶段提示](../../desktop/src/renderer/backend-status.tsx)。对外提供诊断时使用固定状态与脱敏结果，不粘贴握手 token、环境变量或完整后台输出。

## 连接状态与停读确认

普通已有库的桌面预检查只核对受控位置、已完成的切换清单和可信配置，返回 `prepared`，不打开数据库或改动运行代次；正式后台在原库核对数据库与本人身份、结构及迁移账本，并在写锁内同一快照执行完整性与外键检查。没有新迁移时不再重复全库扫描；实际迁移保留升级前后检查，非 WAL 旧库在转换前另外检查。损坏、缺失或身份不符仍拒绝服务，不创建替代空库、不搬动或复制现有资料。

`prepared` 不表示数据库已经验证，也不表示服务已经连接。界面分别显示资料定位、正在连接、连接失败、正在停读、已停读和停读失败；读取状态失败可重读，不将普通启动等待描述为连接中断或自动重连。

认证状态新增 `shutdownProtocol: poll-v1`。支持该协议的桌面使用 `POST /api/runtime/shutdown/begin` 接纳停读，再仅向原地址、原凭据查询状态；后台排空业务和读取资源后才返回 `stopped`，并在认证状态响应完成后退出。后台停读各阶段都有硬上限（领域 10 秒并行、微信 3 秒、模型 5 秒、存储 5 秒；模型内真实在途调用最多等 3 秒，孤儿不等待），任一阶段挂住都不会让退出无限卡住：超时的资源只记入状态里的 `shutdownForcedResources`（固定名称，如 `history`、`modelOrphans`），其余收尾照常完成。客户端确认窗口为30秒，宿主保留一次最多4秒的原目标确认与自有进程清理；断线、超时和进程消失不作为停读成功。仅当后台超过该窗口仍未完成、且认证目标正是本 App 自有子进程时，才升级为 SIGTERM→SIGKILL 回收，确认进程退出后才算停读；后台明确报告失败、复用的他方进程或回收失败都保留重试入口。强制回收不改变业务资料：SQLite 为 WAL 崩溃安全，未结算的模型调用保留在台账，仍需用户在记忆处理中处理。旧同步停读接口保留。领域资源的可重试关闭失败不再永久缓存，但不将未知的官方模型运行时释放结果冒充删除或停读证明。

桌面退出前的本机清理失败与后台排空失败分开报告：`backend_shutdown_preparation_failed` 显示“退出准备未完成”，表示尚未取得后台停读确认；普通诊断只记录 `startup.shutdown_preparation_failed`、固定失败类别和耗时，不保留异常正文、堆栈或资料。修正清理回调后可沿同一退出入口重试。开发更新须先通过类型检查，失败或已过期的源码代次不发布、不触发退出，避免重构中已删除方法仍被旧回调调用。

以上不改变持久同步开关、联系人读取范围、来源资格或业务资料。验证与性能数据见[启动与停读修复记录](../verification/local-startup-and-shutdown-20261103.md)。

## 常见失败的处理边界

| 固定错误／状态 | 处理方式 |
| --- | --- |
| `configuration_invalid`、路径不可用 | 按[启动配置说明](../../desktop/README.md#非秘密启动配置与退出)核对非秘密绝对路径。当前 SQLite 页面只展示诊断；修改配置前正常退出并确认停读，再沿开发入口重新检查，不读取或回显密钥。 |
| `cli_unavailable`、`probe_unavailable` | 核对当前配置指向的可执行组件；各自影响微信读取或前台定位，不把缺工具等同于系统权限缺失。 |
| `sqlite_storage_failed`、`cutover_storage_failed` | 保留数据库和控制面，核对固定诊断、目标身份与路径权限；缺失或损坏不能自动换空库。 |
| `database_cutover_required`、`database_maintenance`、`cutover_*` | 按具体维护态核对授权、对象归属、停写与原操作进度；未确认时不清理未知对象、不切回旧库、不并行双写。 |
| `backend_handshake_invalid`、`backend_connection_failed` | 核对当前实例及启动阶段，使用公开重试；不要手工删除握手或复制其他实例的连接信息。 |
| `backend_shutdown_unconfirmed`／停读未获确认 | 使用“重试停读并退出”，等待原后台与渠道实际停读；不得手动强杀、移除文件或新开一份冒充停读成功。后台挂住超过等待窗口时，本 App 会自行回收自有后台进程并确认其退出，无需手动干预。 |
| `screen_capture_permission_missing` | 按上方录屏流程检查当前运行链路；不将录屏授权当作正文权限。 |
| `wechat_not_in_front`、前台未知、布局／名称失败 | 先区分真实前台、窗口和名称质量；需要时明确选择联系人。已知非权限失败不通过重新授权解决，失败观察不能沿用旧身份。 |

启动消息仍可能保留旧版本兼容码；出现 `python_unavailable` 或旧 PostgreSQL／迁移说明时，先核对是否运行到旧实例或旧配置，不因此安装 Conda、执行历史迁移或运行旧包。完整当前错误映射以[启动设置](../../desktop/src/renderer/StartupSettings.tsx)为准；旧错误台账留在历史记录。

## 修改权限或诊断时怎样补证

修改权限入口、`Info.plist`、签名、探针或用户可见启动错误时，同步更新本指南中的当前规则；新的实测另按工程工作流记录到对应验证材料，不继续往本文叠加日期日志。

记录最少且可核查的信息：触发动作、实际 App／探针版本与身份、父子／责任归属是否已知、静默检查还是显式请求、固定错误及实际停止状态。区分首次授权与重复提示、当前代码与旧构建、合成测试与真实 App、权限可用与联系人识别；未知项保持未知。私人名称、聊天、画面、证书主体和密钥不进入仓库证据。

先运行最小相关检查；实际界面与系统权限行为须由对应开发实例验证，静态构建或旧包通过不能代替。原始资料、来源、停读和删除边界见[隐私规格](../../architecture/current/privacy-deletion.md)，性能与诊断增长约束见[资料生命周期检查](../agents/scaling-and-data-lifecycle.md)。文档更新不替代这些验收。
