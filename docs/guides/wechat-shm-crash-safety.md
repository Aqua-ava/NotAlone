# 微信共享内存截短崩溃排查与防复发

状态：直接崩溃机制已确认，19:08 故障现场的截短进程及触发路径仍待取证；后续健康启动已采集真实文件操作，产品尚未修复或验收。

本指南回应反复发生的微信崩溃，保存脱敏证据与后续必验条件。原始报告、文件身份及隔离实验脚本保留在本机私有诊断目录，不提交账号、聊天、路径或原始进程转储。详细第三方源码调研保留于本机 `research/`，以下结论以引用的一手资料及本轮实测为依据。

## 反复出现的现场与修复时间线

时间均为本机 +0800，年份为 2026；四次崩溃均为 WeChat 4.0.6。

| 时间 | 核对结果 |
| --- | --- |
| 11/11 17:06:11 | `SIGBUS`、文件映射 `past EOF`，顶帧 `WeChat + 59959312` |
| 11/12 16:29:41 | 同类 `past EOF`，顶帧位于 `memset` |
| 11/14 13:10:10 | 同类 `past EOF`，顶帧 `WeChat + 59959312` |
| 11/14 14:07 | 提交 `57686962f` 延迟关闭 raw DB/WAL/SHM 句柄；提交明确尚未在真实微信验证崩溃影响 |
| 11/14 21:34／23:55 | 本轮使用的读取器制品构建／启动，源码核对已含该修复 |
| 11/15 19:08:29 | 含上述修复仍复发，顶帧 `WeChat + 59959312` |

11/15 内核 `apfs_pagein` 记录：映射文件当时仅 **3 字节**，微信却读取文件偏移 16384 后的页面，触发 `SIGBUS`。以设备与文件编号核对，该文件是微信消息库的原始 `message_0.db-shm`。事后文件恢复为 32768 字节，故仅在检查结束后比较大小会漏掉瞬时截短。

四份报告支持故障机制重复出现，不能据相似堆栈认定每次由同一进程或同一调用点触发。引用的 Codex 会话在 11/15 当轮只离线核查已存模型结果；同期常驻应用仍执行后台增量同步，崩溃后同步日志才出现本轮失败与来源不可用。

## 后续真实启动追踪（21:53）

用户在本机完成管理员认证后，采集约 60 秒 `fs_usage`，并通过 Computer Use 确认微信正常打开；没有发送消息。原始文件操作元数据仅留本机。独立解析核对得到：

| 事件 | 现场证据 |
| --- | --- |
| 读取器打开原始 `message_0.db-shm` 后执行 `ftruncate` | 同线程、同 FD、紧邻打开关联共 42 次；40 次线程归属已核对为同一个在用读取器进程，另两次线程已退出 |
| 读取器最后一次对应截短 | 21:53:25.305194 |
| 微信首次可见打开该文件 | 21:53:25.444231，比上述操作晚约 139 毫秒 |
| 微信自身初始化 | 21:53:25.444351 和 21:53:25.534214 也出现对应 `ftruncate` |
| 此后后台读取 | 读取器继续打开 SHM 至 21:54:12.605691，未再捕获读取器截短；事后只读探测 DMS128 由微信持有 |

这确认默认读取器实际会写入和初始化原始 SHM，也提供了健康锁保护下继续读取而不截短的自然对照。它**没有复现危险交叠或崩溃**：进程已启动不等于该目标文件已有映射；首次可见打开也不等于已证明的首次映射。微信与读取器都可能合法执行初始化，不能只按进程名称归责。

该系统版本 `fs_usage` 的截短长度字段高位显示异常，低 32 位为 3；不能将完整显示值当作真实长度。需结合此前内核实际三字节记录、固定库及隔离实验解释。首轮脚本过滤掉 `close` 及不带路径的映射事件，无法完整重建生命周期；已准备更完整的 10 分钟追踪，日志上限 50 MiB，尚须取得本轮实际结果。没有事件不能作为安全证明。

工具能力也有边界：[Apple `fs_usage` 实现][fs-usage]会输出 `open`、`close`、非匿名 `mmap`、`fcntl` 与 `ftruncate`，但未注册 `munmap`；`fcntl` 也不打印锁字节结构。完整追踪不能据此证明所有映射解除或 DMS 释放，需要同期文件身份、PID／TID、内核故障及必要的窄锁观测补证。输出后缀是 TID；ARM64 截短长度显示的高位拼接须按该工具实现核对。

## 已稳定复现的底层机制

当前实际 `libWCDB` 的 SHA-256：`4f05cafc4626a142afca1818f0a88c4092a13d5f4c83e30cd5125b558ba0417d`。它包含默认读写打开 SHM、DMS 判空后 `ftruncate(..., 3)` 的代码；固定版本一手实现见 [SHM 打开方式][shm-open]和 [DMS 与截短][dms]。

使用该库、完全合成的独立持有者／读取者进程，通过 SQLite VFS 的 `xSetSystemCall` 拦截并记录真实 `ftruncate`，逐项探测 DMS 字节 128，得到：

| 持有者状态 | 读取者配置 | DMS | 查询 | 截短到 3 字节 |
| --- | --- | --- | --- | --- |
| 正常 | 主库 READONLY | 保持 | 成功 | 0 次 |
| 正常 | READONLY + `readonly_shm=1` | 保持 | 成功 | 0 次 |
| 持有者额外打开再关闭自身 SHM FD | 主库 READONLY | 丢失 | 成功 | **1 次，32768 → 3** |
| 同上 | READONLY + `readonly_shm=1` | 丢失 | 成功 | 0 次 |

10 轮、40 个条件结果一致。该实验复现了与现场相符的截短机制，并验证共享内存只读的候选防护；它没有执行真实微信调用链，也没有证明真实截短进程。合成数据库、WAL、SHM 已清理，私有脚本与结果合计约 14 KiB；实验前卷可用约 60 GiB。未运行模型或发送消息。

## 不能省略的因果边界

- 主库 `SQLITE_OPEN_READONLY` 不等于旁车只读；默认 Unix VFS 仍会以读写方式打开原始 SHM。[固定源码][shm-open]
- POSIX `close()` 释放的是**调用进程自己**在同一文件上的锁。CLI 关闭自己的 FD 不能释放微信进程的锁；单凭 CLI 侧旧缺陷不足以解释微信仍使用映射时 DMS 为何被判空。[SQLite 官方锁风险说明][corrupt]
- 现有 raw FD 延迟关闭修复覆盖一条已知释锁路径，不能证明整个原库访问生命周期安全。源码与实际制品均已含修复，本轮仍复发，不能宣称它已彻底解决微信崩溃。
- 现有锁测试对 120–128 整段只执行一次 `F_GETLK`；返回范围内任意锁即可满足断言。后续须单独验证 DMS128 及实际读标记，避免“仍有一个锁”冒充“所有必要锁都保持”。见[当前测试](../../desktop/wechat-history/cmd/notalone_delta_locks_test.go)。
- 审计另发现未证明触发的异常顺序：活跃 tail 时 API 允许恢复另一个目标，缺失检查点可能留下两个 snapshot；单 snapshot 的 raw FD 延迟关闭未必保护另一 snapshot。正常调度的有效守卫与换人释放限制了这条顺序，不能归为本次根因。后续定位入口为 `native-client.ts:1175`、`continuity.ts:117`、`service.ts:635` 及 `notalone_protocol.go:914`。
- 尚未抓到 **19:08 崩溃瞬间**的 `ftruncate(fd, 3)` 归属、调用栈及同时刻 DMS 持有者。后续用户认证的健康启动追踪不能倒推旧故障责任。此前 LLDB 的 15 秒有界附加尝试未成功，自有调试进程已清理。不能指定读取器、微信自身或其他进程为已证明的旧故障执行者。

## 防复发完成条件

1. **取得归属证据。** 后续现场追踪限定为微信与读取器，保存在本机；至少关联截短操作、PID、文件身份，继续核对 DMS 与调用路径。无事件或短时未崩溃不能当作修复成功。
2. **原件不可写。** 优先验证从首次连接起强制原始 SHM 只读，覆盖元数据、历史、增量、图片与头像等所有原库入口。`readonly_shm` 是 Unix URI 参数，须正确使用 `file:` URI 与 `SQLITE_OPEN_URI`；已有可写 SHM 节点可能被后续连接复用，单独改一处不足。[打开与节点复用][shm-open]、[URI 约定][uri]
3. **保留一致性与失败。** 缺少 SHM、不能初始化、BUSY、IOERR 或来源变化时允许安全停读及有界重试；禁止回退为可写旁车、`immutable=1` 或 `nolock=1`。并发提交、checkpoint、WAL 回卷、取消与退出均需验证；不把顺序复制三文件当一致快照。[URI 约定][uri]、[固定版本 WAL 只读测试][walro]
4. **跨进程回归。** 除句柄关闭顺序，逐项核对 DMS、读标记和多连接／多快照关闭；观察实际打开模式与截短操作，不能只看结果行数、末态文件大小或函数调用次数。
5. **真实入口验收。** 按工程工作流复用 `pnpm run dev`，核对实际 App／微信、后台同步、增量去重、停读及崩溃／内核日志。合成实验不代替真实验收；本任务没有授权打包或外部发消息。

用户要求后续开发持续关注这一反复崩溃问题；根 `AGENTS.md` 已加入本指南的必读入口。当前保存的是证据与验收约束，不是“永不崩溃”的保证。
