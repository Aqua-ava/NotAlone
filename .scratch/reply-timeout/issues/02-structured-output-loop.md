# 大历史联系人回复生成时模型不产出结构化输出，预算内循环后失败

Type: bug
State: resolved

Blocked by: none

## 问题与范围

01 号任务修复后，桌面端对大历史联系人（约 1,100 条消息、22 个来源）执行「针对消息的回复生成」时，请求在约 4-6 秒内以 502 `reply_budget_exceeded` 失败，界面显示「本次生成尝试过多」。小历史联系人的改写/续生成不受影响（多次 200）。

进程内复现证据（真实模型、真实库、合成方向文本）：

- 每轮模型调用均未发出任何 `tool_calls`，也未产出 `ToolStrategy` 要求的结构化输出（`REPLY_RUNTIME_SCHEMA`），而是返回纯文本；langgraph/agent 对未命中停止条件的输出自动重试。
- 计数：4.1 秒内 6 次 `[llm/start]`、0 次真实工具调用，随后 `GraphRecursionError`（recursion_limit=12）→ `ReplyBudgetError`。
- 同一输入稳定复现（多次 run_failed，latency_ms 约 3.4-5.5 秒）；改写路径在小历史联系人上同版本代码多次成功，说明与「针对消息 + 大历史」的提示形态/上下文规模相关。

这正是 01 号 issue 原始现象（App 报超时但后端一直 running）的触发源：修复前该循环无上限；修复后表现为快速、可重试的明确失败。本任务的目标是让该场景正常生成可用，而不只是快速失败。

## 验收与测试边界

- 大历史联系人的「针对消息回复」能正常产出候选（或给出可操作的稳定拒绝原因），不再是每次预算失败。
- 保持 01 号任务的运行时限、步骤上限、错误码与收尾语义不回退；既有测试全部通过。
- 定位方向（择一或组合，需先验证）：结构化输出提示与 ToolStrategy 的配合（langgraph create_agent 对未命中结构化输出的重试行为）、上下文/证据预算对大历史的裁剪、系统提示对"先结构化再输出"的约束是否被长上下文稀释。
- 只使用合成或匿名化数据做测试夹具；不保存真实聊天。

## Answer

已实现并通过验证。

1、根因（真实库 + 真实模型进程内逐轮追踪确认，与任务原"大历史/长上下文"假设相反）：故障联系人的初始上下文只有 53 项证据、共 408 字符（1,103 条消息平均 7.7 字符）。真实链条是：模型先读取 Skill，再按需调用 `conversation_search`；该联系人消息极碎导致分词检索连续未命中（`empty`）；历史工具 3 次预算耗尽后返回的 `budget_exceeded` 只有状态码、没有"停止检索、立即输出"的可操作指令，模型继续换词搜索；`recursion_limit=12` 按每轮 2 步（模型 + 工具节点）计算，在最终结构化输出轮之前耗尽 → `GraphRecursionError` → 502 `reply_budget_exceeded`。另观察到第二条失败路径：模型偶发产出结构化输出但 `citation_ids` 非 UUID（`ToolStrategy` 对 JSON schema 字典不做校验，只能靠运行时校验兜底）→ `rejected_by_validation`。

2、修复三处：`HistoryToolAccess` 的 `empty`/`budget_exceeded`/`failed`/`timeout` 状态返回新增 `guidance` 字段，明确"停止调用任何历史工具、立即基于已有证据返回结构化候选"（`src/notalone/reply/tools.py`）；`BASE_SYSTEM_PROMPT` 增加历史工具 3 次硬预算与未命中/耗尽后的行为要求，`citation_ids` 改为"必须原样复制 evidence_id 且每条候选至少引用一个"（与 `ReplyGenerator` 校验一致），`REPLY_RUNTIME_SCHEMA` 同步修正描述并加 `minItems`；`recursion_limit` 12 → 16，为预算反馈后的最终输出轮留出余量，保持有界循环、步骤上限与 `ReplyBudgetError` 语义不回退。

3、测试：新增回归测试"预算耗尽后仍产出候选"（5 次搜索 + 最终输出在 16 步内成功，轨迹记录 3 次 empty + 2 次 budget_exceeded）与"无限重试仍以预算错误收尾"（≤8 个模型轮）；历史工具测试补 guidance 断言；步数上限断言按新语义更新为 8 个模型轮。合成模型改为每轮生成唯一 id 的 `AIMessage`，消除消息复用导致的去重伪影。全量 Python 735 项通过（2 项真实模型测试跳过）。

4、真实验证：以真实 Postgres 上下文、真实 Skill 库、真实模型对故障联系人同一条消息进程内复现，修复前稳定 3-4 秒内 `ReplyBudgetError`，修复后 5 次全部成功（3.8-10.5 秒），轨迹确认 3 次搜索未命中后立即输出结构化候选；仅使用用户已确认的方向文本，消息正文只在内存中流转，不打印不落盘。

剩余风险与备注：

- 该联系人检索连续未命中属于检索质量问题（分词搜索对超短消息的召回），不在本票范围；由 memory-skill-context/07 的检索评测线跟进。
- 模型输出仍可能偶发校验拒绝（`rejected_by_validation`，如引用了非 UUID 字符串）；错误码稳定、可重试，提示词已强化引用契约，未做自动重试。
- 追踪期间发现一条 11:53 的 `running` 请求为 01 号任务前的历史遗留，按既有 lease 过期语义收尾，与本票无关。
