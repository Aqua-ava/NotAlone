# 微信媒体提取：四票拆分提案

更新日期：2026-10-11。阶段：规格已确认，任务粒度与资源关联/公共测试接缝待认可，未发布issues。本提案从总览移回对应功能目录，未改变原规格。


父规格：[微信媒体资源提取与语音文件转换](spec.md)。以下粒度待认可后发布至原功能目录，不重复写一份不同范围的媒体spec。

| ID / 建议票名 | Blocked by | 完整交付与验收标准 |
| --- | --- | --- |
| D1 单条媒体的受范围定位与可删除缓存 | 无；需要精确资源关联契约，真实上游来源缺口沿Mac任务20的来源核查跟踪 | 用户显式指定已确认联系人及消息后，公开接缝返回单条原始资源的受控引用/状态，并能删除其自有缓存；同名/同时间多联系人不串读，范围不明拒绝，微信库只读。使用合成资源验证路径、来源删除、晚结果拒绝；真实资源验证单独限定范围 |
| D2 图片与视频按需可用 | D1 | 经同一公开接缝输出可探测的图片派生文件或视频引用，失败可解释且不泄露私密字段；删除来源后不可再读，不删除微信原文件。图片解码和视频元数据检查均通过 |
| D3 单条语音SILK与WAV | D1 | 精确定位一条语音，保留受控SILK及可播放WAV；时长可核、解码失败清理、来源删除和隔离通过；本地解码，不调用ASR。可与D2并行，复用D1已经确定的缓存/删除契约 |
| D4 手动入口完整验收 | D2、D3 | 用户在已确认联系人下显式指定消息，选择提取并获得结果/错误，删除后不可读，重试及迟到结果不复活；入口形态按正式规格和实现前讨论决定，不默认新增后台扫描或新的UI产品范围 |

D1提供可验证的单条资源生命周期，而非只建表；D2/D3各自贯通提取、结果和删除，不能把删除全推到最后。Mac任务20的来源核查是共享证据输入，不把“完整Mac交付成功”设为媒体实现前置。
