# 基于来源的记忆时间、适用条件与变化

Triage: ready-for-agent
State: open

> 2026-10-20：用户已确认功能方案，并明确要求通过 ask-matt 选择 skill 完成。本文为可审阅的实现规格；用户随后明确同意四票粒度、依赖与测试边界，授权发布并进入实现。尚未实现或验收，不以文档状态证明产品能力。

## Problem Statement

“时间待核实”没有说明未知的是日期、适用期限还是当前情况。已有来源时间、保存时间、有效期、事件阶段彼此独立，但字段尚未完整进入回复依据和分层记忆；新旧记忆裁决也缺少必要的时间与来源。历史资料因此可能被误作现状，条件性禁忌可能被误作永久规则，晚导入的旧消息可能被误作更新。

## Solution

根据同一已授权联系人范围内的相关原话及后续证据解释时间、保留条件和维护变化。每条事实使用其实际来源的日期；系统保存时间用于审计，当前时间只用于比较明确的适用区间。界面、检索、分层资料和生成快照共同保留这些含义，并明确未知、冲突及变化。

## User Stories

1. 作为用户，我希望旧聊天今天导入后仍显示原聊天日期。
2. 作为用户，我希望区分来源聊天时间、事件发生时段、记忆有效期和保存时间。
3. 作为用户，我希望“昨天／明天”以对应原话的日期和时区解释。
4. 作为用户，我希望多条消息中的相对日期分别使用各自的来源。
5. 作为用户，我希望“去年／上月”保留年／月精度，不被编成精确日期。
6. 作为用户，我希望“最近”等模糊时间保持模糊，不被设定固定寿命。
7. 作为用户，我希望来源时间或时区不可靠时保留未知。
8. 作为用户，我希望“当时这样说”不会被解释为“那天开始如此”。
9. 作为用户，我希望计划、约定、改期、取消和已发生分别保存。
10. 作为用户，我希望计划日期过去后仍不会被自动说成已经发生。
11. 作为用户，我希望有明确期限的资料按照原话完整期间使用。
12. 作为用户，我希望适用条件保留在资料、详情及回复依据中。
13. 作为用户，我希望条件变化不会被误解释为撤销原来的偏好或禁忌。
14. 作为用户，我希望后续补充、纠错、状态变化和矛盾分别处理。
15. 作为用户，我希望后来回忆早事不会仅因消息较新就覆盖当前状态。
16. 作为用户，我希望新补导入的更早聊天得到处理，且不因导入较晚而占据最新状态。
17. 作为用户，我希望每次修订可追溯到各版本实际依据。
18. 作为用户，我希望自动更新可以沿已有能力撤销，人工纠正不会被旧证据复活。
19. 作为用户，我希望联系人资料、本人资料、概览、背景和画像具有一致的时间含义。
20. 作为用户，我希望回复及其冻结依据保留生成时的日期、阶段、条件和未知。
21. 作为用户，我希望删除来源后，新增时间和条件依据也失去使用资格。
22. 作为用户，我希望系统只在回复确实依赖未知状态时请求澄清，而非逐条催促核实。

## Implementation Decisions

1. 复用现有来源投影、事件、有效期、版本与来源核验模块。来源范围仍由确定性代码按实际直接引用计算；模型不能填造来源或保存时间。
2. 时间表示区分原始时间表达、已解析值或区间、精度、锚点来源与核验结果。精度至少能表达年、月、日、具体时刻及未知；模糊表达保留原话。日历区间边界是计算表示，界面不得将年或月的边界伪装成事件准确发生时刻。
3. 模型负责识别日期含义、对应来源和语境；程序对支持的明确相对日历表达检查日期、时区、范围及精度。无法可靠解析的表达保留未知，不建立任意自然语言日期规则大全。
4. 事件发生时段、阶段、记忆有效期分别核验；来源消息时刻不是事实起始时刻，事件结束不等于整条记忆失去历史价值。保存时间和当前时间均不得补造事实日期。
5. 收敛旧的“生效时间缺省为采纳时间”和“无来源的瞬时状态默认当天结束”口径；仅有来源支持的期间进入事实适用期。短期且无期限的状态保留不确定性，不因此视为永久现状。提示、schema、核验、读取与现行规格同步。
6. 条件以可追溯的限定保存，包含条件原意、来源及后续有关条件变化的依据。第一版表达资料适用性，不构建通用规则引擎；条件未知、来源支持、出现相反证据均不能冒充现实认证。条件变化与撤销原主张分别核验。
7. 版本化扩展严格的事件与新元数据合同。旧记录、旧客户端读取入口和旧生成快照可兼容；旧资料缺字段保持未知，不从当前资料补写过去快照。新字段进入同一身份、摘要、来源复验与删除规则。
8. 各纵向切片贯穿候选、联系人／本人资料、概览、分层引用、回复上下文、工具补查及冻结／恢复依据。不能只在卡片显示而在生成或恢复时丢失阶段、条件或日期精度。
9. 更新裁决对候选与每个旧版本传入各自合法的原始来源、来源日期、事件时段、条件和版本身份；单条与批量使用同一语义合同。复用已有有界同联系人检索，按事项取证，不能把全部聊天无界送入模型。
10. 消息顺序、事件时间和摄入顺序分别处理。新补导入的早期消息必须可进入正式处理流程；若现有水位会遗漏，修复持久处理进度并验证重试／幂等。已有存量不因上线自动重提取，不扩大原同步授权。
11. 新旧关系区分补充、状态变化、错误纠正、历史补充及未解决矛盾。自动替代必须有语义与时间依据，缺依据时保留并存／待确认，不仅凭文本相似度、较新写入时间或较晚消息裁决。
12. 保留人工保护、原子更新／多父合并、合法撤销和错误／变化／未知退役原因。已确认错误不作为历史事实进入生成；“来源支持”始终不等于现实真伪认证。
13. 界面提供来源日期、明确适用期、事件阶段／精度、适用条件、后续变化和冲突的具体说明，替换笼统“时间已核实／待核实”。最近一次相关表述日期不能称“核实到某日”；来源不完整明确标注，保存时间留在详情。
14. 回复输入保留历史、计划、条件和不确定性。遵循现有输入/输出复验，不以提示词测试证明所有模型输出正确；只有回复实质依赖未知现状时才澄清。
15. 新增依据继承所属联系人／本人范围、原始消息及参与版本的删除依赖。删除、重试、恢复、迟到写入不能复活无效内容。
16. 不增加第三方记忆框架、图数据库、统一 TTL、时间自动核实后台任务或独立时间服务。腾讯仅参考证据更新，Graphiti 仅参考逐来源锚点思想。

## Testing Decisions

以下边界已随本次拆分确认，作为 TDD 约定；沿现有公开入口，不新增只供测试使用的业务接口。

| 测试边界 | 验证行为 | 不足以证明 |
| --- | --- | --- |
| 正式提取流程 → 独立核验 → 采纳及公开读取 | 来源锚点、日期精度、条件、错误提案拒绝与正确提案保留 | 真实模型泛化质量 |
| 公开资料／导入／版本 HTTP API 与真实隔离持久化 | 新旧合同、早期补导入、原子更新、隔离、删除、撤销和重试 | 桌面视觉体验 |
| 正式回复上下文、生成／保存／恢复接口 | 事件及条件进入模型输入和冻结依据，旧快照保持未知，迟到结果复验 | 提示词能保证任意输出正确 |
| 生产 React 控制器／页面及实际开发 App | 所有记忆入口与回复依据语义一致，可查看来源与版本 | 真实微信采集链路、模型准确率 |

测试采用独立合成资料和可控时钟／模型响应，先单例 red → green，再相关模块及有界全量。已有时间、事件、历史依据、更新与删除回归复用；每票交付自己的完整 API/UI/回复行为。实际 App 验收先核对并复用热更新实例，只使用 `npm run dev`，不打包；没有触发的微信采集与发送不能列为已验。

最终工程验收覆盖：跨日时区、多来源日期、日期缺失、部分精度、模糊时间、明确适用区间、计划到期、条件变化、矛盾、晚消息回忆早事、乱序补导入、重复导入、用户纠错、来源删除、旧快照和跨联系人隔离。独立语义质量评测另外报告误补日期、错误替代与正确记忆拒绝，不以工程通过宣称质量达标。

## Out of Scope

自动扫描／重提取真实存量聊天、扩大已确认同步范围、修改原始聊天日期、外部测试消息、无界全历史模型输入、从沉默推断现状、把条件变化视为解除禁忌、统一固定过期天数、引入上游框架、发布打包、部署、push 或 PR。

生产数据迁移执行不属于本规格确认；兼容迁移代码和隔离测试属于工程实现。已保存资料采用兼容读取，新语义覆盖后续正常处理及用户明确新导入，不能暗中重写旧事实。
