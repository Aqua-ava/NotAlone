# 05 — 回填暂停时当前联系人仍需实时读取

**What to build:** 后台补齐处于暂停、失败或不完整状态时，用户当前在 App 中查看的已确认联系人仍能按实时读取路径执行有界 CLI 增量读取；新消息应进入规范消息流，补齐生命周期状态保持原状。

**Blocked by:** None — 对已完成的后台同步调度进行回归修复

Triage: ready-for-agent
State: resolved

## 现象

2026-09-09 的用户授权测试中，微信/CLI 已能看到当前联系人产生的新消息，但数据库仍停在上一条规范消息，前端也没有更新；超过 11 分钟仍未入库。运行时该联系人的 `cli_backfill_state` 为 `paused`。

## 根因假设与验证

- 全局 `sessions` 事件流不保证覆盖我方发送，因此安全对账必须能够发现这类变化。
- 当前联系人优先加入安全对账队列时没有标记为 `live`；回填状态为 `paused` 时，非 `live` 读取会被门禁跳过。
- 回归测试应从 `CliBackgroundSync.cycle` 的公开行为观察到：优先联系人仍调用 CLI、写入消息并推进游标，同时状态仍为 `paused`。

## 验收条件

- [x] 当前优先联系人在回填暂停时仍走实时读取，不被暂停门禁跳过。
- [x] 实时读取成功后进入规范消息流并推进该联系人的独立游标，回填状态仍保持暂停。
- [x] 非优先联系人仍按既有有界 round-robin 预算处理，不扩大读取范围。
- [x] 不新增微信切换、滚动、输入或发送能力；不保存测试消息正文到任务记录。

## Answer

已修复。

### 根因

当前联系人虽然会被提升到安全对账队首，但此前没有带 `live` 标记：

1. 后台补齐为 `paused`、`failed` 或未完成时，普通读取会被 `_read_binding` 的门禁跳过；
2. 当前联系人从 round-robin 队列加入时没有标记 `live=True`；
3. 如果队列已提前建立，`_prioritize_pending` 只调整顺序，也没有把该联系人提升为 live 读取；
4. 全局 `sessions` 事件流不保证覆盖我方发送，所以不能只依赖事件通知。

因此这次问题是调度门禁漏掉当前联系人的实时安全读取，不是数据库写入本身变慢。

### 修复

- 当前优先联系人进入安全对账队列时统一使用 `live=True`；
- 当前联系人已在待处理队列时，同时补入待处理集合和 live 集合，再提升到队首；
- 读取成功后沿既有规范消息流写入并推进独立游标，补齐生命周期状态不被改写；
- 保持 `ObservationMode.CLI_BACKGROUND` 不变：这是全局后台 CLI 读取的来源模式，`live=True` 只是暂停门禁使用的内部实时读取标记，并不代表切换为前台观察模式，符合 ADR-023。

### 验证

- 回归测试先红后绿：
  `test_paused_backfill_priority_contact_still_reads_safety_sweep`；
  `test_priority_contact_already_pending_is_promoted_to_live_read`。
- Python 全量：769 通过，2 个受配置缺失影响的 smoke test 跳过；Swift：16 通过。
- `compileall`、`git diff --check` 和 macOS App 构建通过。
- 重启 App 后，之前已被 CLI 发现但未入库的 `ran` 事件被补入数据库，界面从 28 条更新为 29 条；这是历史待处理事件的恢复证据，不作为新消息端到端耗时指标。
- 仍需用户在最终构建运行后发送一条新的测试消息，才能完成真实微信新消息的秒级延迟验收；本任务没有新增发送能力，也没有代替用户发送。

## Comments

- 运行证据：CLI 原始只读路径已发现新事件；数据库采样仍为 28 条，前端仍显示 28 条。该证据仅用于本地测试联系人验收，不作为生产端到端证明。
- 评审决议：Standards 评审未发现硬性问题；Spec 评审指出已有待处理队列路径也必须提升为 live，已通过第二个回归测试和对应修复覆盖。`ObservationMode.CLI_BACKGROUND` 的保留是有意设计，不能把内部 `live` 门禁标记误解为前台观察模式。
