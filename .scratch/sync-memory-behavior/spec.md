# 同步、聊天清空与记忆处理规则

Triage: ready-for-agent
State: open

> 状态：2026-10-29规格定稿，实施未启动。已确认规则保持；ready-for-agent表示可供后续拆票，不表示真实渠道能力已认证。当前结构检查受原业务数据库不可连接、既有读取范围无法核验所阻；真实发送／撤回未执行，迁移／恢复按用户最新要求本轮不考虑并保留未验证。完整证据及限制见[定稿验证记录](../../research/wechat-spec-finalization-validation.md)。

## Problem Statement

用户希望控制同步哪些联系人、何时处理记忆，以及如何清空和明确恢复聊天。这些行为需要明确的用户操作、范围和失败语义，并与资料来源及删除路径保持一致。

## Solution

用户选择联系人后，同步其微信本机可读聊天；记忆处理由用户手动启动。聊天清空、历史恢复、暂停与失败处理遵循下方已讨论规则。数据保存与事务能力由[SQLite 数据库重建规格](../sqlite-database-rebuild/spec.md)和[统一数据库草图](../sqlite-database-rebuild/greenfield-design.md)描述。两份规格可分别细化和拆票，集成时核验实际实现的行为与数据合同。

## User Stories

- **US-04**：作为用户，我希望在同步设置中选择要同步的人，以控制读取范围。
- **US-05**：作为用户，我希望没有选择的人不被同步，新出现的私聊也不自动加入。
- **US-06**：作为用户，我希望选中联系人后首次自动同步本机可读取的已有历史，通过同步完成聊天接入。
- **US-07**：作为用户，我希望首次同步完成后继续增量同步新消息。
- **US-08**：作为用户，我希望同步中断后可以继续，并看到失败或历史不完整状态。
- **US-09**：作为用户，我希望取消某人的同步后停止读取该人的新消息。
- **US-10**：作为用户，我希望重新选中某人时补齐取消期间本机仍可读取的消息。
- **US-11**：作为用户，我希望同步总开关关闭或 App 退出时停止微信读取。
- **US-12**：作为用户，我希望文字保存正文，图片、语音及其他非文字消息暂以占位显示，保留消息位置。
- **US-13**：作为用户，我希望非文字占位不参与记忆提取，后续媒体理解单独设计。
- **US-14**：作为用户，我希望聊天记录持续保存，直到我主动清空某个联系人的全部聊天。
- **US-15**：作为用户，我希望清空 NotAlone 的聊天不影响微信原消息，也不自动恢复被清空的旧消息。
- **US-16**：作为用户，我希望以后可明确选择重新同步已清空的历史，并保留该操作的来源。
- **US-17**：作为用户，我希望清空来源时，依赖这些来源的记忆和派生资料得到清理或重新核验。
- **US-18**：作为用户，我希望手动点击按钮开始记忆处理，以控制模型调用的时机和费用。
- **US-19**：作为用户，我希望按钮按同步选择范围逐人处理，且不同联系人资料不混用。
- **US-20**：作为用户，我希望一轮只处理启动时已保存、尚未成功处理的文字，后来的消息等待下一次启动。
- **US-21**：作为用户，我希望处理失败的部分保留可重试状态，而已成功处理的内容不重复提取。
- **US-22**：作为用户，我希望暂停并继续记忆处理，已完成结果和进度得到保留。
- **US-23**：作为用户，我希望 App 退出或异常中断后保持暂停，重新打开后由我点击继续。
- **US-24**：作为用户，我希望处理中取消选中某人时停止该人的处理，其他已选联系人继续。
- **US-25**：作为用户，我希望处理中的聊天被清空时，该处理停止且不能把已删除的内容写回来。
- **US-26**：作为用户，我希望候选回复仍有依据、可以编辑，最终消息由我亲自发送。
- **US-27**：作为用户，我希望记忆按钮启动提取、核验保存、主题整理及长期概览的完整过程，以统一查看本轮进度和完成状态。
- **US-28**：作为用户，我希望同轮使用本次勾选联系人范围内的聊天整理本人记忆，并由同次暂停、取消及来源删除控制。
- **US-30**：作为用户，我希望普通暂停时先完成并保存正在处理的小批，再停止启动后续小批，以保留已经进行的工作。
- **US-31**：作为用户，我希望一个联系人处理失败时只让该人受阻，其他人继续；共用模型配置等通用故障则整体暂停。
- **US-32**：作为用户，我希望失败后保留进度，等待我手动继续，不自动重试模型请求。
- **US-33**：作为用户，我希望正常处理但未产生新记忆的聊天也记为处理成功，下次不重复处理，并与调用失败或处理受阻区别显示。
- **US-34**：作为用户，我希望首次历史同步尚未完成时清空聊天，也能阻止清空之前尚未读入的旧历史继续自动补入，之后的新消息仍继续同步。
- **US-35**：作为用户，我希望处理新增文字时可以参考同一联系人少量已处理的前文，但这些前文不重复成为本轮处理目标。
- **US-36**：作为用户，我希望明确选择某个人的“重新同步历史”时，恢复该联系人本机当前可读的全部历史。
- **US-37**：作为用户，我希望关闭同步总开关只停止微信读取，不中断已由我手动启动的记忆处理；需要停止记忆时使用独立暂停按钮。
- **US-38**：作为用户，我希望同步总开关关闭时，也能手动开始处理已勾选联系人已保存、尚未成功处理的文字聊天，以独立控制同步和记忆处理。

## 与其他方案的衔接

[四方案一致性约定](../sqlite-database-rebuild/map.md#plan-alignment)统一本轮目标。首次接入按新空SQLite重新核验身份和逐人授权；首用不得因模型就绪自动提取。非文字占位是正文同步的表示规则；单条媒体提取已确认推进并纳入统一数据库设计，由独立手动操作触发，媒体文件及占位均不成为本轮记忆输入。云端工程已取消，不列产品待办。

## 三份方案的共同规则（2026-10-29收敛）

本文负责同步、清空、记忆触发与控制；[媒体规格](../wechat-media-extraction/spec.md)负责单条媒体结果、质量与文件操作；[数据库统一设计](../sqlite-database-rebuild/greenfield-design.md)负责三者的表、键、状态和事务。三份是同一方案的不同部分，各自“范围外”不表示取消其他方案的已确认能力。旧讨论建议不能覆盖用户已确认规则。

| 操作或场景 | 三稿统一行为 |
| --- | --- |
| 正文同步与媒体 | 逐人勾选后读取文字和非文字消息元数据；非文字正文为空、保留占位。只对明确选定的一条图片/视频/语音消息手动取文件，不随同步、历史恢复或联系人选择下载；媒体不转写、不理解、不入记忆 |
| 关闭读取总开关 | 停止微信正文及媒体新读取，旧读取代次的在途结果不得提交；已保存文字的手动记忆处理可启动/继续，已勾选联系人合法SILK可手动本地重转；已有合法媒体仍可查看/播放 |
| 取消勾选联系人 | 停止该人的微信读取、记忆处理和本地媒体转换，立即撤销在途提交资格；保留仍合法的已保存聊天、记忆和媒体，媒体仍可查看/播放。取消勾选本身不是删除来源或联系人；重选不复活旧执行或解除清空抑制 |
| 暂停、退出与继续 | 普通记忆暂停允许当前有效小批收尾；退出后不自动续调模型，手动继续沿固定任务与成功步骤。媒体中断后旧执行终结，手动新操作建新尝试；二者只允许恢复既有合法本地清理，不因此自动读微信/调用模型 |
| 清空联系人聊天 | 删除该人全部已保存聊天正文、占位、来源及相关媒体原始件/播放件/临时件，清理或撤下待核验的依赖资料，并封禁在途结果；保留联系人及同步选择，可靠截断此前未读旧历史，之后新消息按有效读取资格同步 |
| 单独清除媒体 | 仅清所选消息的媒体副本、引用和敏感执行材料并撤销在途媒体提交；保留聊天占位，不清空联系人聊天、不改变正文同步边界；再次提取须新明确请求 |
| 重新同步历史 | 核验后只恢复所选联系人的本机可读消息，建立新来源/授权；不恢复旧记忆、助手会话、媒体副本或旧执行，不自动触发媒体提取/记忆处理 |
| 单独删除来源 | 按实际来源及文件产生链清理；同一规范消息有其他合法来源时可复核保留，但不得把旧执行的实际来源改指另一条记录来保住旧证明或媒体文件。联系人全部聊天清空覆盖其全部来源 |
| 文件和结果 | 媒体存应用自有目录，数据库记归属、状态和定位；缩略图或只有SILK可为明确部分结果。新结果验证后切换，不降低已有合法完整结果；共享删除账本清理自有副本，保留微信及用户外部原文件 |

“来源仍有效”与“当前允许从微信继续读取”分开核验：关闭开关或取消勾选不自动抹掉合法已保存资料；取消勾选仍撤销新处理和在途提交资格。需要模型的删除后重新核验进入用户手动处理范围，待核验期间不可用于生成；清理动作本身不隐式触发模型。

## Implementation Decisions

### 同步与删除

- 每个选中且身份已核验的联系人首次授权包含本机可读历史，然后进入增量；中断和重选后的缺口只在有效授权和同步开关允许时补齐。历史不可读、失败及覆盖不完整要可见，不虚报完整。
- 首次历史同步和后续增量使用统一规范消息规则。文字保存正文；非文字保存类型和明确占位，保留来源、发送者、时间及可用的稳定消息身份。未知类型不能静默当作文字；无法唯一识别的记录不能猜测合并。
- 本次重置不迁移过去的删除或撤销记录：首次同步可能重新读入旧 NotAlone 曾删除、但微信本机仍可读的内容。此行为只适用于这次明确要求的从零重建；新库产生的删除、撤销和排除决定不得被后台自动恢复。
- 清空联系人聊天是单独的用户操作，不自动取消同步；清空就是实际删除该联系人在 NotAlone 中保存的全部聊天正文和占位，不按来源类型区分。删除相关来源及派生消息时清除仅由这些来源支持的关系资料、本人资料、候选和含正文追踪；其他有效来源仍可支持的资料必须重新核验。删除标记只保留必要的无正文稳定身份；同步、补齐、删除和在途任务的并发须防止旧数据复活。
- 即使首次历史同步尚未完成，清空也终止清空之前旧历史的自动补入，不只删除已经保存的消息。若联系人仍被选中且总开关开启，清空后的新消息继续同步。需要持久保存不含正文的历史截断边界，并使旧历史任务和清空前在途结果失效；不能仅依赖已删除消息编号。精确边界如何由 CLI 可靠建立仍待查证，不能以 `local_id` 或秒级消息时间冒充准确的新旧分界。
- 产品不提供手动导入聊天记录的入口。用户已明确这一当前产品要求，不能将手动文件导入作为首次接入、恢复或重建流程；如代码残留相关旧入口及接口，实施时查证并按此范围收敛。来源模型仍保留 CLI 读取与不同捕获批次的追溯能力，不能因移除导入入口就删除来源关系。
- 用户明确选择某个联系人的“重新同步历史”时，恢复该联系人本机当前可读的全部历史，不要求每次先选日期；仅在本人渠道账号与联系人身份重新核验后建立新的来源与读取资格，不扩大到其他联系人。该操作不是撤销删除，不恢复旧来源、旧助手讨论、旧证明或旧记忆；恢复的文字仍遵守手动记忆处理规则。具体确认界面、历史截断与逐条抑制如何授权放行仍待设计，不能由普通重启、重选或后台重试触发。微信原消息和电脑上的原始资料文件不受操作影响。

- 回复资格沿用首用已确认合同：首次历史尚在进行时阻止生成；已明确不完整时，用户确认仅用已有部分后才允许，警告贯穿界面、后端和请求依据；不绕过身份/授权/删除保护。

### 记忆处理

- 默认不因同步新消息自动启动记忆处理。用户点击按钮，以当时已选联系人和已保存消息为本轮范围，按联系人隔离处理；后续到达消息等待下一轮。
- 关闭同步总开关只停止微信读取，不暂停已经由用户手动启动的有效记忆处理；总开关已经关闭时，也允许用户手动启动新一轮，范围仍限于已勾选联系人已经保存、尚未成功处理的文字，不为启动处理而读取微信新消息。记忆处理由独立暂停按钮控制；取消勾选某个联系人仍立即阻止其处理结果继续写入。微信读取资格与已保存资料的记忆处理资格分别核验，不能共用总开关作为门禁。
- 处理新增文字可以使用同一联系人少量已处理前文作为有界理解上下文；前文限于点击开始前已保存且仍有效的文字，不读取已删除内容或点击后才到达的消息。理解上下文与本轮提取目标分别记录，不重复增加待处理量或成功数量；实际参与的前文仍纳入来源核验、追踪及删除依赖。窗口数量与预算由后续实现查证确定，不在本轮拍定固定条数。
- 按钮启动完整的记忆处理过程：提取、核验并保存、主题整理、长期概览更新；只有本轮适用阶段全部完成才显示本轮完成。进度按实际阶段展示。
- 同轮从本次勾选联系人范围内的聊天整理联系人关系记忆和本人记忆。本人资料以用户为归属，不因归属不同而扩大读取到未选联系人；来源支持、控制状态和范围变化都需要复验。具体结构已由统一草图的processing_run/run_contact/task_contribution表达；本人范围只使用本轮已获准贡献，逐联系人复验取消与删除，不扩大固定输入。
- 仅以文字作为提取输入；非文字占位不进入记忆提取。成功、待处理、失败和已删除目标可区分，重新启动只处理未成功的有效目标；记忆自动采纳仍须来源核验、标记 `auto`、支持撤销，不冒充用户确认。
- 模型调用和本轮适用流程正常完成，但没有值得保存的新记忆时，相关目标仍标记为成功，展示“已处理，未产生新记忆”，后续不重复提取。该状态与调用失败、结果未知、解析或核验流程未完成分别记录，不以记忆条目数推断处理是否成功。
- 支持暂停和手动继续；退出、异常中断后不自动继续调用模型。取消选中一个联系人时停止其处理并保留已完成结果，其他仍选中联系人可继续。清空来源时取消相关任务并复验写入，避免删除后复活。
- 普通暂停采用小批边界：收到暂停请求后不启动新小批，正在执行且仍有有效授权、未被删除的小批可以完成并提交，随后进入已暂停。取消联系人或删除聊天属于范围失效，立即阻止相关结果继续写入，不沿用普通暂停的完成当前小批规则。
- 联系人自身资料或处理失败使该联系人受阻，其他有效选中联系人继续；所有人共用的模型配置等通用故障使整轮暂停，并展示可识别的原因。失败后不自动重试模型请求，等待用户明确继续。
- 数据模型分开保存本轮固定目标、每个目标的处理结果、任务控制和租约状态、模型请求回执。已发出但结果未知不等于没有执行；保留原调用回执、固定目标和作用域互斥，只能使用已保存结果或已证实的渠道能力核验。未能确认的调用保持unknown；用户手动继续也不能无条件重发同一未知请求，不伪造“未执行”或“无新记忆”成功。
- 模型调用、联系人记忆、本人记忆、候选、用户修改、来源追踪和回复上下文维持既有业务边界；同步和记忆处理的进度分别记录。

## Testing Decisions

- 测试以用户可观察的行为为准，优先通过实际业务入口检验；采用隔离的合成数据和临时 SQLite 库，不使用私人聊天或凭据。测试沿用现有同步、存储、记忆、删除和桌面操作边界；清空元数据屏障作为待实现的窄渠道适配合同单独验证，不冒称上游已有API，不把内部函数测试替代用户可见行为。
- 覆盖选中／未选中、新私聊、首次历史、增量、总开关与退出停读、取消与重选后的补齐、媒体占位、历史缺口、重试和重复同步。
- 覆盖清空联系人全部聊天、删除与同步／记忆在途并发、重启后的删除抑制、其他来源重新核验及用户明确重新同步历史；核对微信原消息未被修改，手动导入入口不可作为替代流程。
- 覆盖首次历史未完成、从未写入来源、整页旧消息未入库时清空，旧历史均不得继续补入；同秒新旧消息、乱序、清空期间到达消息及旧页迟到不得被简单时间判断掩盖。核对重启、重选和重试不解除边界，明确重新同步只恢复所选联系人的本机可读历史。
- 覆盖手动启动、固定本轮目标、成功与失败进度、暂停／继续、退出后保持暂停、取消单个联系人、排除媒体占位和其他联系人继续。
- 覆盖普通暂停的小批收尾与禁止启动下一批、暂停期间删除或取消立即失效、单联系人受阻而其他人继续、共用故障整体暂停、失败不自动重试及未知调用结果不被盲目重放。
- 覆盖记忆处理运行中关闭同步总开关：微信读取停止，仍有效的已启动处理继续；独立暂停按钮与取消单个联系人分别沿已确认语义生效。
- 覆盖同步总开关已关闭时手动启动新一轮：只消费仍勾选联系人已有的有效文字目标，不触发 CLI 读取，不处理未勾选联系人、媒体占位或已成功处理目标；独立暂停、取消联系人和来源删除保护继续有效。
- 覆盖正常处理无记忆产出时成功记账、再次点击不重复提取，以及失败或未知调用结果不被误记为“无新记忆的成功”。
- 覆盖已处理前文只作理解、不重复计数，点击后到达消息留待后轮，以及前文删除导致旧追踪和证明失效；前文不能扩大到其他联系人。
- 桌面交互按仓库桌面验收规则在热更新开发 App 中检查；合成测试与真实微信验收分别报告。

## 本轮技术查证结论

当前以[微信渠道二轮收敛方案](../../research/wechat-channel-resolution-v2.md)为准；首轮[CLI合同](../../research/sqlite-ready-cli-contract.md)保留源码证据。旧cursor仅靠local_id锚点、按(sort_seq,local_id)分页，跨分片并列可能漏项，不能沿用后宣称精确。二轮纠正此前把未来外部回填、UI点击瞬间精度混入Q24基础要求的扩大解释；Q24没有指定鼠标点击那一毫秒为清空边界。

消息身份按实际版本结构及生命周期支持档认证：账号实例、来源代次、分片沿革、表实例和声明主键共同定位一次出现；不要求server_id永久全球唯一，也不直接信任local_id。服务端编号后来补齐不重复建立message；编号用精确整数串。身份不足仍按Q32隔离，来源换代及迁移不能绕过旧排除；排序与身份分开，游标须包含全序续读和完整覆盖证据。

清空路线是一次操作持有全部相关只读WCDB连接，收集该联系人完整身份元数据集合S(B)，覆盖本机已有而NotAlone未读的旧页。只查询必要身份，不读旧正文或整库备份；当前消息查询会取正文，不能直接复用。每个分片使用独立observer和reader只读连接：全部observer取pre，全部reader实际读取固定快照，再由各原observer取post，短获取窗口pre/post分别相等并核验实例和分片覆盖后建立逻辑切面B；保持reader快照枚举时允许正常外部提交，不要求整个扫描期间静止。获取窗口变动只能在接受前有界重试；B是源快照切面，不是校验结束、清理结束或业务提交时刻。候选成员不能提前当正式排除，旧有效排除始终保留；完整集合与证明接受后B永久固定，重试不后移，新消息按新资格继续。

读取前、分段期间和接受前均复验总开关、联系人、账号及代次。关闭读取后不能偷偷查询身份元数据；缺可靠边界可先封禁旧写入并清理已保存资料，但须显示boundary_pending，不能宣称完成。未接受候选失败后仍未完成；已接受B的重启只继续原清理。未来从别处回填且B时本机不存在的历史另列兼容场景，未知类别不自动当新消息；不能据此否定完整S(B)覆盖本机旧历史的路线。

当前微信版本已由安装包确认4.0.6/build29387；真实源表结构检查因原业务库不可连接、既有开关和联系人范围无法核验而受阻，未读取微信库。固定官方源码同参数研究WCDB库的12/12合成原生断言、生命周期14/14内存合成合同与反例已有证据，分别见[原生报告](../../research/wechat-wcdb-native-results-v3.md)和[生命周期报告](../../research/wechat-lifecycle-validation-v3.md)。原生结果绑定研究动态库摘要，不能称原researchCache摘要或最终CLI/WCDB制品已通过。真实发送／撤回未执行；迁移／恢复按用户最新要求本轮不做，能力仍未验证，不作为规格定稿前提。完整真实渠道验收仍须证明正常写入下可建立边界、B后新消息不漏，以及相应支持档的状态与连续性，不能把全部拒绝当成功。SQLite、媒体及DSH路线见[统一设计](../sqlite-database-rebuild/greenfield-design.md)；本轮未启动实现，旧ADR替代范围在实施时显式修订。

### 已查到但尚未展开的现有合同

- 同一规范消息可关联多个来源，去重消息与来源引用不是一对一关系。移除手动导入入口后仍需处理重复捕获、历史与增量重叠的来源引用。联系人清空必须删除其全部聊天及引用；其他来源级删除则不能无条件删除仍有其他有效来源的消息。依据：[来源引用](../../backend-ts/database/migrations/021_message_source_ref.sql)。
- 消息稳定身份与续读位置不同；微信 `local_id` 不能当作全局单调游标。消息写入、处理记录与游标推进需要原子提交，并在提交前复验授权、账号、同步开关和删除状态。依据：[不透明游标](../../backend-ts/database/migrations/088_cli_opaque_cursor_order.sql)、[同步写入](../../backend-ts/src/sync/sync-incremental-store.ts)。
- 记忆处理包括提取、核验、主题整理及长期画像等阶段；只有提取完成并不等于整个过程完成。联系人范围与本人范围分别存在，用户已确认同轮处理，仍须设计两者的来源隔离及控制关系。依据：[记忆处理查询](../../backend-ts/src/memory/processing/query.ts)、[轮次](../../backend-ts/src/memory/processing/round.ts)、[控制](../../backend-ts/src/memory/processing/control.ts)。
- 现有自动记忆触发点包括同步后调度、轮次自动衔接及宿主启动恢复。需要逐一改成符合手动启动的门禁，不能只添加界面按钮。依据：[提取调度](../../backend-ts/src/memory/extraction/tasks/store-schedule.ts)、[宿主插件](../../backend-ts/src/host-plugin.ts)。
- 删除需覆盖本人记忆、候选、主题与画像、助手输入和版本、追踪与受管文件等派生内容；助手运行时存在库外 JSONL 会话。旧数据重置和日常清空都不能简单等同于删数据库行。依据：[跨领域删除](../../backend-ts/src/deletion/cross-domain-deletion.ts)、[助手运行时](../../backend-ts/src/reply/runtime/assistant-runtime.ts)、[运行时擦除](../../backend-ts/src/reply/runtime/assistant-runtime-erasure.ts)。
- 模型请求是否已发送、结果未知、业务结果已提交、消息已成功处理需要分别建模；重试不能无条件重新发起未知结果的模型调用。依据：[模型调用回执](../../backend-ts/database/migrations/110_model_call_receipt.sql)。
- 当前自动读取抑制仅覆盖已捕获消息的稳定身份，不能覆盖从未读入的旧历史；现有来源集合令牌不能替代单调清空代次。历史未完成还会阻止普通增量，清空需同时结束旧历史目标并可靠衔接新消息。依据：[抑制表](../../backend-ts/database/migrations/109_wechat_auto_read_suppression.sql)、[自动读取过滤](../../backend-ts/src/sync/sync-auto-read-suppression.ts)、[同步写入](../../backend-ts/src/sync/sync-incremental-store.ts)。

### 本轮已确认

- Q24：清空会截断此前尚未同步的旧历史，之后的新消息继续同步。
- Q25：允许同一联系人有界已处理前文辅助理解，不重复作为本轮目标。
- Q26：明确重新同步历史时，恢复该联系人本机当前可读的全部历史。
- Q27：关闭同步总开关只停止微信读取，已手动启动的记忆处理继续；暂停记忆使用独立按钮。
- Q28：同步总开关已经关闭时，仍允许手动处理已勾选联系人已保存、尚未成功处理的文字聊天；不因此读取微信新消息。

## 协作设计提案

以下内容从原数据模型草案移入本稿，作为已确认产品行为的执行合同；具体落库结构以[统一数据库设计](../sqlite-database-rebuild/greenfield-design.md)为准，早期数据模型草案仅保留讨论依据。实际执行仍须通过下述验收。

### 明确重新同步历史

用户明确选择单个联系人并确认恢复其全部本机可读历史后，创建独立操作身份、授权代次和新来源；保留旧删除决定的真实历史，不把它们全局清零。

恢复资格只属于该操作及核验过的联系人／账号，普通自动增量不能拿它作为解除所有抑制的凭证。恢复过程再次遇到清空、取消或身份变化时仍受最新代次控制。重叠消息去重，历史读取失败继续显示覆盖不足；恢复消息不自动重建记忆或恢复助手会话。

### 记忆处理与进度

一次点击先快照所选联系人和实际文字目标，再为各联系人建立有限轮次，并关联本人处理。目标包含具体消息身份、实际来源记录及接受时的解释修订（interpretation_revision，用于并发核验）；不建立聊天正文历史版本表。仅保存消息时间上界不够，因为稍后补入的更早消息也不属于启动时的固定集合。

提取窗口可以携带同一联系人点击前已保存的少量前文。前文即使已成功处理，也可作为本次候选的实际依据，但不重复登记为目标；完整窗口的来源与删除依赖仍必须保留。后到消息不得以“仅作上下文”为由绕入本轮。

本人提取应能回到贡献该资料的具体联系人窗口。本轮不能把多个人的聊天拼成某人的关系提取输入。对已形成的本人候选如何统一去重、合并及更新主题画像，需要独立本人阶段与版本检查；取消 A 后，A 的在途贡献失效，B 的工作继续，混合结果不能只删一个标签后继续提交。

进度至少分为四种事实：固定目标总数、提取核验已完成数、各阶段完成状态、模型调用状态。正常无新记忆是提取核验成功；主题和画像全部适用阶段完成，才是整轮完成。无须执行的阶段须明确记为不适用，不能把缺失记录当作完成。

普通暂停先阻止新小批，当前仍有效小批提交后显示已暂停；取消选择、清空和来源失效立即撤销相应提交资格。退出后不发起下一次模型请求，重启保持暂停。联系人自身失败只阻塞该人，共用故障暂停本次协调工作；手动继续复用合法回执和成功阶段，不盲目重放未知请求。

**控制边界已确认**：同步总开关只停止微信读取，不阻止已经手动启动且来源仍有效的记忆处理；关闭时也可手动新启动一轮，目标仍限于已勾选联系人已保存且尚未成功处理的有效文字。启动、领取和提交均须区分微信读取开关与记忆处理资格，不能把二者复用为一个布尔门禁。取消单个联系人、独立暂停与清空仍分别生效，不允许以启动处理为由重新调用 CLI 读取。

### 清空与跨存储清理（设计提案）

以下是需要实现证明的顺序提案，尚不是可执行算法：

1. 在联系人范围登记删除请求，推进单调清空代次，立即禁止旧聊天及依赖内容继续进入检索、恢复和结果提交；联系人本身与有效同步选择保留。
2. 撤销旧历史读取目标及相关处理资格。清空前已发出的 CLI 页和模型请求即使返回，也不能凭旧代次写回。普通暂停的小批收尾规则不适用于清空。
3. 建立不含正文、能覆盖尚未捕获旧消息的历史截断边界。取得精确渠道边界的流程、失败恢复与同时到达消息的归属仍需查证；不得假定 `Date.now()`、秒级发送时间或当前最大 `local_id` 已经足够。
4. 幂等清理该人已存消息、全部来源引用、捕获正文、候选、依赖记忆与版本、主题画像、助手输入和运行时文件、相关追踪与缓存，以及媒体原始件、派生播放件、临时件、替换待清理件和敏感定位/证明。跨联系人本人资料按真实来源逐项处理，不能直接删除用户全部本人资料。
5. 对其他合法来源仍支持的资料立即撤下失效证明，按现有依赖规则重新核验；若需要模型调用，进入用户明确启动的处理/核验范围，待核验期间不可用于生成；具体入口与阶段接线待实施验证，不能以清空为由隐式启动新模型请求。
6. 在有效同步选择及总开关下衔接新消息；删除复核与新代次消息分开，不把清空后的有效新消息一并清理。复核结束才显示清空完成。

**已核实缺口**：现有抑制表只登记已经捕获的消息身份；没有覆盖从未读入旧历史的联系人级截断边界。来源集合令牌能阻止部分在途旧页，但不能替代单调清空代次。现有历史未完成门禁还会阻止普通增量，不能只删行而不改变历史读取目标。

因此，精准新旧边界是实施前的技术前置条件。若锁定 CLI 无法可靠表达，必须明确受阻或覆盖缺口并继续设计，不能自行牺牲已确认的新消息同步目标，也不能声称现有代码已满足 Q24。
