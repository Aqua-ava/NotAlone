# 精简 DSH 与 TypeScript 后端迁移讨论

状态：讨论中；以下为用户逐轮确认的方向，不代表完整方案、实现授权或迁移完成。
日期：2026-10-23。

## 已确认方向

1. Q1：以统一 AI 执行底座、按需扩展能力和减少长期维护为主要目标，不预设回复质量提升。
2. Q2：保留现有用户功能与数据，直接替换底层框架。
3. Q3：通用能力优先采用官方插件；联系人隔离、来源、删除等业务规则自行保留。
4. Q4／Q6：最终把现有 Python 后端职责迁到 TypeScript，移除产品对 Python 后端的运行依赖；现有功能和数据保留。
5. Q5：优先减少维护，安装包体积暂不作为首期硬指标。
6. Q7：不要求所有业务插件化；普通 TS 模块承载业务规则，DSH 插件负责适当的扩展位置。
7. Q8：功能保持优先，尽量使用公开扩展接口，不修改 DSH 核心；不可避免的核心修改单独讨论。
8. Q9：按功能逐步迁移与验收，最终删除 Python 和旧框架；过渡期允许并存，每项业务有唯一执行和写入责任方，不长期维护双实现。
9. Q10：确定性业务流程由 TS 代码调度；模型参与的步骤复用统一能力，不把单次调用自动扩大为开放式 Agent 循环。
10. Q11：插件由开发阶段选择、验证并随产品交付；当前不增加用户任意安装或插件市场入口。

## 待讨论

- TS 业务后台与 DSH 的进程关系、取消及故障隔离。
- 数据库、既有资料与迁移期间的兼容及切换策略。
- DSH 临时会话、持续助手讨论、落盘与删除的职责。
- 迁移验收、正式采纳及实施顺序。

## 现行约束与证据边界

- 此方向与 ADR-006／009／010 的框架选择冲突；复审原因是统一底座及降低长期维护成本。正式方案需明确替代范围，当前不静默改写这些 ADR。
- 仍遵守联系人范围、来源核验、删除及用户亲自发送的硬边界；ADR-091 的不自动过程摘要规则保持。
- 前期只读核对发现 30 个 Python 源文件直接导入相关框架，涵盖回复、记忆处理、Skill 学习及评测；不是改动文件数或工作量承诺。
- DSH 插件组成、运行体积和功能等价尚未实际验证；未使用真实聊天、未调用模型、未执行迁移或打包。
