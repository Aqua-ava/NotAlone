# DSH 与 TS 后端迁移任务拆分建议

状态：待用户确认；以下为拟编号，不是已发布任务，未创建 issues 文件。
依据：[已采纳方案](../../architecture/adr/102-dsh-typescript-backend-migration.md)、[实施规格](spec.md)。

## 共同交付要求

- 每票交付一条可验证的行为链，包含必要的界面接线、存储、权限、删除、错误处理、单责任方切换和回退；不按“先写全部模型层，再写全部 API”横拆。
- 现有界面和公开业务合同尽量复用；普通 TS 业务模块与 DSH 共用官方 profile 后台，原生能力不重写。
- 删除与权限随每票交付；17 是整体删除入口接管及跨链验证，不是第一次实现删除。24 是组合演练，不是第一次验证切换。
- 数据迁移使用独立合成库，真实资料与模型验证另按已有授权范围；日常只用 npm run dev，优先复用实例，不打包、不发送外部消息。
- 01 的行为基线将明确已有缺口与原任务负责人；不把旧未完成能力冒充迁移基线，不恢复已退役功能。

## 依赖与规模说明

五阶段是默认推进顺序，不是虚构依赖：例如授权管理不依赖 L3 画像完成，增量同步也不依赖模型提取。未迁移的功能继续由唯一旧实现负责；已迁移功能不得越过其范围执行旧实现，过渡期间的删除和状态失效必须贯通。

05 的切换验证包括 TS 前台与仍在 Python 中的后台模型调用：采用可验证的共享仲裁或既有暂停／恢复机制，不能两套各自限流后破坏前台优先和全局并发。10 再接管后台任务；未验证该过渡合同不切换05。若05因此超过单上下文，发布前拆为可验证的检索／模型许可行为切片及候选交付，不能省略门槛。

15 的来源以01盘点的实际读取合同为准；若读取 L2／L3，则发布前补充13／14依赖，不提前假定。17 先接管已迁移资料的整体入口，19／20／22的新写入方须加入同一删除与失效合同，24再验全组合。20 的生成门禁复用已验收回复入口（其05前置由10传递）。

任何票实施前发现超出单上下文规模，应保持完整行为再拆分并更新依赖；不得把范围无限追加到22／23／26。01识别的既有未完成工作应关联原任务处理，不能按本拆分擅自重开另一份实现。

## 验收入口核对

建议以现有桌面控制器调用的 HTTP／事件业务入口为主，检查持久资料和用户可见结果；模型、任务等既有接口承担聚焦测试；新增宿主检查只覆盖进程、取消、关闭与故障恢复。该测试面不依赖 DSH 私有内部结构，方便证明新旧业务行为等价。

请审阅：26票的粒度、阻塞关系及上述验收入口是否合适，是否需要合并或进一步拆分。认可后再按仓库约定创建每票文件、Triage／State及规划索引；本文件不表示实现已开始。
