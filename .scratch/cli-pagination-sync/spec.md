# CLI 消息分页同步修复

## 问题与目标

已确认联系人积压超过 CLI 默认单页容量时，`has_more=true` 被误报为新鲜度失败；整页不入库、游标不推进，后续反复读取第一页。用户要求修复，并在开发版验证指定联系人的新消息正常同步和展示。

## 行为要求

1. 区分本页实时来源可信与整个会话已追平。实时来源、会话身份及事件均通过校验的中间页可入库；只有末页才报告补齐完成。
2. 每个调度片最多读取一页，保留既有 CLI 时间预算和联系人公平调度；后续页继续排队，不依赖新消息事件触发。
3. 每页来源、规范消息和游标提交成功后才前进；失败保留可靠位置，重试和重启均不漏消息、不重复新增消息。
4. 纯非文字页只保存计数和处理依据并推进可靠位置，不解析媒体正文；空中间页、无进展游标不能造成无限读取。
5. 开关关闭、解绑、baseline、同 owner/contact 隔离、暂停补齐与实时同步原有边界保持；不扩大授权或增加外部发送。
6. 未确认实时来源、跨联系人事件、超时、解析或持久化失败仍明确失败，不因允许分页而放松校验。

## 验证边界

- `LocalWechatCli.tail`：合成 CLI envelope 验证中间页、末页及拒绝条件。
- `CliBackgroundSyncEngine.cycle`：真实适配器接合成外部 CLI，通过公开接口验证逐页提交、调度、进度、失败恢复和停止。
- 相关后端模块与持久化集成：验证累计进度、可靠游标及稳定去重。
- 真实开发版 App：复用 `npm run dev`，核对指定联系人数据库、消息接口和实际窗口；不发送聊天消息，不提交私人资料。

## 范围外

不调整 CLI 默认页大小，不绕过新鲜度校验，不修改外置 CLI，不修复全局错误与联系人状态混显，不制作发布包、不推送远端。
