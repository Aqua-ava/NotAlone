## 2. 任务 A：核验拒绝数 4→9 的细分（离线、不调模型）

### 目的

R2 报告核验拒绝从 4 升到 9，但没有按原因细分，无法判断是合并后的句子更容易被拒，还是核验在拦我们期望它拦的东西。口径不可比时 R3 无法判断改动好坏。

### 做法

1. 取两份只读数据：基线（原 run `64a04000` 所在隔离副本）和 R2 副本。R2 副本位置见验收记录里的账本名 `extraction-prompt-tencent-alignment-r2`，路径在仓库外私有目录；找不到就问执行者，不要重跑。
2. 用 `?mode=ro&immutable=1` 的 URI 形式打开 SQLite（后端须已停止）。
3. 从 `execution_event` 的 `verification` 事件取每条候选的 `verdict` 与 `issues`，按下表输出，两份各一张：

| 维度 | 取值 |
|---|---|
| verdict | `continue` / `unverified_rejected` / `unsupported_rejected` |
| issues | `subject`、`meaning`、`insufficient_evidence`、其他 |
| 候选是否由合并产生 | 来源消息数 ≥ 2 为「合并」，否则「单句」 |
| 归属 | 联系人 / 用户本人 |

4. 额外统计「主体被拒」中走了发送者兜底（`subject_mentions` 为空且 `resolution=unique_context`）的条数。
5. 结论只回答三问：新增的 5 条拒绝主要是什么原因？是否集中在合并候选？是否与发送者兜底有关？

### 产出与通过标准

- 一页计数表，写入 `docs/verification/memory-auto-adoption-alignment-20261106.md` 的「R2 补充」小节，只含计数。

## 4. 任务 C：保留真歧义（R3）

### 问题定义

我们要的是二分：

- **真歧义**：同一句话有两种以上来源直接支持的读法（例如同一个数字既可能是年龄也可能是金额；一个「多赚点」既可能指行业收入也可能指别的收入）。必须保留 `alternatives` 非空，并继续拦下或至少带痕采纳。
- **细节没说**：只是没提到动作对象、范围、原因。应通过合并相邻句补全，补不全就不输出，**不填** `alternatives`。

R2 的结果是两类都变成空，第一类丢了保护。

### 改动方向（按成本从低到高，逐级尝试，上一级不够再进下一级）

1. **提示加正反例。** 在 `backend-ts/src/memory/extraction/prompts.ts` 的 `relationshipExtractionContract` 与 `alternatives` 描述里加入**合成的**对照例：
   - 「必须填」例：一个数字加省略单位的表达；一个「多赚点」类的省略对象表达。
   - 「不要填」例：「先了解下」「开始拷打」类省略对象的动作。
   - 明确写出：补全相邻句后仍无法唯一确定的真歧义，不得因「合并」而删掉 `alternatives`；合并只能补全细节，不能抹平两读。
   - 例子必须是合成句子，不得取自真实聊天。
2. **合并规则收紧。** 合并后若仍有多种来源支持的读法，输出时保留两读并列在 `alternatives`，而不是挑一个读法写成确定正文。
3. **代码层兜底（仅当 1、2 仍漏）。** 在核验或采纳前增加确定性检查：正文含「数量词省略单位」「代词省略所指」等易歧义结构且 `alternatives` 为空时，降级为待确认。先在离线样本上验证误报率，再决定是否上线。

### 验证

**步骤 1：合成探针（约 10 次外发）。**

- 构造约 10 个合成窗口：5 个真两读、5 个细节没说。每个窗口 2–4 条消息，不含任何真实人名或真实聊天。
- 通过标准：5 个真两读里至少 4 个 `alternatives` 非空；5 个细节没说里至少 4 个 `alternatives` 为空。样本很小，只作方向性证据。

**步骤 2：同窗口重测（约 16–20 次外发）。**

- 在 `prepare-rx.sh` 新建的副本上，对 2026-03-30 10:22–10:42 文字窗口重提取。
- 对照 R2：`alternatives` 非空占比应高于 0/15，且低于基线 6/18；两条真歧义文本（收入族、数字族）的 `alternatives` 应恢复非空；核验拒绝按任务 A 的口径不得上升。
- 由独立 Agent 判定 outcome。无法判定记 `unknown`，不记 `improved`。

### 预算与账本

- 新建问题账本，沿用 `docs/agents/quality-diagnosis.md` 的「准备总账管理工具」。
- 额度建议：探针 12 次 + 重测 20 次，合计 32 次，时限 120 分钟。需要用户先授权。
- 每轮开始前记录：问题 ID、唯一改动、预期信号、对照基线。每轮只验证一个假设（探针和重测分两轮）。

### 提示变化的联动

- 提示改动会改变策略指纹。读 `backend-ts/test/extraction-policy-version.test.mjs`，按其约定更新版本，避免旧结果被当新策略复用。
- 测试：`extraction-protocol.test.mjs`、`extraction-flow.test.mjs`、`extraction-policy-version.test.mjs`；新增一条断言，提示含「必须填」与「不要填」两类对照例的结构标记（不断言模型行为）。

## 5. 任务 D：存量候选重裁决的开发者入口

### 背景

R1 实测三个现有入口都无法对存量候选重裁决：

- `abandon-unknown`：历史是「失败」而非「未知」，返回 `control_conflict`。
- `continue`：源链戳与提取提示变更后不一致，且全量提取目标已完成，返回 `no_pending_history`。
- 裁决侧：`adjudication-actions.ts` 里「候选最近一次已记录裁决结果所依据的冻结快照是否一致」（`decidedWithSameBasis` 一类判断）会跳过已决定的候选。

结果：修复后新产生的候选受益，但已有的待确认候选不会自己变好。

### 方案

参照 ADR-173 的开发者批量重新认证，做一个**仅开发者宿主可用**的入口：

1. 范围：单个已确认联系人的 `pending` 候选；不跨联系人；不新增后台常驻能力。
2. 行为：对选中候选刷新「信任基线」（策略修订号），使其按新规则重新进入裁决；不删除候选、不改候选正文与来源。
3. 约束：受限条数（`limit`，默认 20）、可停止、幂等；预算沿用逐物理请求台账；未知回执不盲重放。
4. 记录：每条候选的结果写执行事件；对账本报告用量。
5. 先读：`backend-ts/src/memory/sqlite/control.ts` 的 `continue`、`runs.ts` 的 intentRevision 逻辑、ADR-173 的编排器与面板实现提交（`6a1ea82de`、`76b9df33b`）。

### 验证与门禁

- 合成数据单元测试，覆盖：只处理 `pending`、重复调用幂等、预算耗尽即停、跨联系人拒绝。
- 真实：先在隔离副本上用一位联系人跑一小批（约 20 次额度），对照改前改后的待确认条数。
- 前置：任务 C 通过。否则重裁决会把有风险的自动采纳规则作用到更多存量候选上。
