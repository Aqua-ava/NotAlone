# 记忆时间信息的完整传递与展示

> Triage: ready-for-agent
> 来源：用户指出历史操作也必须有时间，要求按完整 skill 工作流修改。

## Problem Statement

历史记忆只展示正文，使用户和回复模型难以判断它来自何时，容易把过去的状态
当成当前状态。现有数据库已保留来源消息时间、保存时间和部分有效期，但领域
投影、回复输入与管理界面没有完整保留和呈现。仅修改一个旧记忆正文不能解决问题。

## Solution

给所有候选、联系人记忆和本人记忆统一提供时间信息：来源聊天时间范围、记忆保存时间，
以及已有生效／失效时间。时间类型各自标明；未知时间明确标为未知，绝不把聊天时间、
导入时间或保存时间冒充事件发生时间。旧记忆通过原来源自动获得时间，无须重提取或改写。

## User Stories

1. 作为用户，我希望历史已完成操作也显示来源日期，以免误当成刚发生。
2. 作为用户，我希望看到候选、联系人记忆和本人记忆来自哪一天或哪些天。
3. 作为用户，我希望区分来源聊天时间、记忆保存时间和有效期。
4. 作为用户，我希望来源时间缺失或不完整时明确提示，避免系统补出日期。
5. 作为用户，我希望手动记忆显示录入时间，而不是伪造聊天来源日期。
6. 作为用户，我希望候选回复读取同样的时间信息，并能从保存的依据回看。
7. 作为用户，我希望已有资料立即受益，正文、采纳方法、来源、状态和暂停范围不被改写。

## Implementation Decisions

1. 用一个不可变的记忆时间值对象携带 `recorded_at`、`source_started_at`、
   `source_ended_at`、`source_time_complete`。保存时间可空；来源起止必须成对、带时区，
   同一天不隐藏年份。时间完整表示全部直接证据时间可核实，不是事件真实性。
2. 提取外壳只从候选真正引用的消息计算来源范围，不使用未引用上下文、当前时间或模型
   猜测。已进入有限提取窗口的未知消息时间可安全处理，并明确传给模型；不改变既有
   采纳风险门槛。生产 CLI／后台加载器继续沿用现有排除无日期消息的进度策略，本轮
   不将新的无日期消息纳入增量提取，不切换旧水位顺序或重跑历史。
3. PostgreSQL 读取三类记忆时投影已有 `created_at`，并批量核验同范围、活动来源的
   直接消息引用时间。来源文档或 CLI 观察 UUID 不扩展为全部消息范围；手动来源与
   不能核实的引用保持来源时间未知或不完整。读取不写旧行，无业务 schema 迁移。
4. InMemory 与 PostgreSQL 的公开端口返回同一时间对象，确认、修正、owner 路径与
   检索转换保留时间。实际保存时间与来源聊天时间独立，不把旧版本保存时间当新版本时间。
5. 检索结果、回复上下文、模型输入和回复依据快照传递时间。利用现有上下文 JSON
   保存新元数据，并按 evidence ID 与 owner/contact 从历史快照恢复；旧快照缺字段
   返回未知，不能以当前来源补写当年的生成依据。生成前后核验包含时间变化。
6. API 以可选的 `timing` 对象增加时间字段，旧客户端可兼容。管理界面与回复依据展示
   来源聊天时间、保存／录入时间及非空有效期；多日期显示范围、不完整明确提示。
7. 继续使用当前公开端口和模型适配器，不改第三方库 API，不新增语义 verifier、TTL、
   放行规则或外部自动发送。真实资料只在本机最小范围验收，不交给项目模型服务。

## Testing Decisions

用户已授权按完整流程自主修复和验证；本轮沿用当前公开 seams，不另建测试入口。

- `ExtractionFlow.run` → `MemoryAdoptionService` → `MemoryPort/OwnerMemoryPort`：
  先验证历史事实缺少来源时间的 red，再实现同范围引用日期计算、未知和多日期行为。
- `MemoryPort/OwnerMemoryPort` 写入→读取，以及 `RetrievalReplyContext.build/validate_current`
  和 `LangChainReplyRuntime.generate`：验证时间传播、隔离、删除来源与实际模型输入。
- 记忆和依据 HTTP API、公开 ReplyStore 完成→读取：验证往返快照与旧数据兼容。
- Swift 核心展示策略与真实 App 构建：验证年份、时区、多日期、不完整、未知和有效期。
- 每个执行切片按 red → green，使用独立合成数据；最后隔离库全量测试、类型检查、
  双轴评审、App 重建与最小本机验证，创建中文本地提交，不 push。

## Out of Scope

重提取真实聊天、修改来源消息时间或正文、猜测精确事件发生时间、给所有记忆固定过期日、
采纳风险门槛变更、pending 作为已知事实参与回复、微信发送、云端、依赖升级和远端提交，
以及无日期新消息的生产摄入与提取水位协议变更。

## Further Notes

日期投影直接解决用户指出的旧历史操作问题；不需要把自动记忆改成 manual，也不需要
重建私人聊天评测集。所有仓库样例与回归保持合成，不复制真实姓名、正文或标识。

评审发现原先“未知消息时间可进入窗口”的表述容易被理解为生产加载入口也纳入无日期
新消息。现有水位仅记录最后消息 UUID，按聊天时间排序；直接纳入未知时间消息会让
它落在末尾，后续新消息可能排在水位之前。摄入顺序与聊天顺序之间的无损转换需要
另行设计持久进度协议，不能在本轮只读日期投影中静默切换。因而本轮保留生产加载
范围，明确支持窗口内未知值及旧记忆来源时间未知的传递与展示；该既有摄入限制单独记录。
