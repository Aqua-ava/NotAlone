# 回复准备延迟修复验收

## 根因与改动

准备接口继承桌面 JSON 客户端的 8000ms 默认超时；超时被归为连接失败，界面显示未收到生成结果。该请求尚未调用模型，后端仍可继续完成准备。

同一准备流程重复读取共享消息窗口、依赖候选的大 JSON 和概览依赖；分层记忆即使没有当前发布集合，也先构建完整底层概览。

现在在单次持锁概览或 REPEATABLE READ 只读候选列表内复用完整查询键的来源快照与依赖，退出立即释放；不同复验阶段重新读取。空分层结果先做精确范围及当前世代的存在性查询；命中仍走原持锁复验。客户端超时未修改。

## 测量与实际桌面验收（2026-10-21）

正式服务装配、同一输入、不带性能分析器，开发 App 停止且测试未并发：

|阶段|原实现|修复后|
|---|---:|---:|
|上下文组装|7.676s|2.587s|
|当前来源复验|2.292s|1.757s|
|输入预算检查|0.377s|0.072s|
|上述阶段合计|10.346s|4.416s|

上述不是完整 HTTP 准备耗时，未包含最终持锁保存。最初离线测量漏装分层服务，发现后已废弃该结论，并用正式装配重新对照。

`npm run dev` 实际 App 选择原问题联系人并点击「帮我想想」，显示生成已完成和 3 条可编辑候选。数据库时间戳显示：准备到创建生成请求7.39s，生成请求处理14.27s，整轮完成23.67s。包含本地复验和保存，不能把生成请求处理全部归为模型网络耗时。未发送外部聊天消息。此次证明原超时场景已走通，不代表任意数据量或机器负载下都能在8s内完成。

## 验证

- conda `NotAlone` Python，在 backend 下运行 `python -m unittest`：两条新增批量复验用例、`test_snapshot_read_scope`、`test_layered_capture_availability`，10/10通过，16.564s。
- 原实现红测试：12条共享候选发生12次窗口读取；无发布集合10种状态组合均扫描概览。修复后满足读取预算。
- 隔离 PostgreSQL 回归：`test_overview_reply_source_generations` 1/1，`test_overview_prepared_context` 7/7通过。
- `test_reply_revalidation_batches` 原有两方法的4个子场景失败（旧查询预算和历史版本预期），使用HEAD原模块复跑确认同样失败，不属于本次引入。
- 扩展组合测试300s超时，未宣称全量通过；其中曾报错的准备上下文用例单独及整个模块重跑通过。
- Standards/Spec及分层门禁增量审查均无确认缺陷；`git diff --check`通过。

## 数据影响

不改数据库结构、不新增资料读取范围、不持久化缓存；来源删除、正文/引用变化、原SELF主体变化、连接和联系人隔离继续核验。性能输出只保留耗时、状态和计数；私人正文、身份、凭据不写入仓库。
