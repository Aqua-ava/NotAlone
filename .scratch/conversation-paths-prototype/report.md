# 两条聊天辅助链路真实模型原型结果

日期：2026-10-09。一次性原型，未接入产品，不是端到端验收。

## 结论

**模型可以完成两条链路的最小语言流程，但还不能稳定保证不新增事实或意愿。** 收到消息的探索、选择、候选、语气修改走完；主动联系无历史的探索、选择、开口候选也走完。明确拒绝或主动邀约能直接生成；用户纠正玩笑语境、改变目的、未知事项需要澄清的基本分支均有真实输出证据。

不能把结构化输出成功率当成回复质量。最明显的剩余问题是模型把常用开场白中的隐含事实当作无害措辞，连解释和引用都没有识别出问题。第一轮“好久没联系了”，针对性追加约束后变成“很久没听到你的消息了”；两者都没有来源支持。

## 实验范围与数据

- 已配置模型：`ecnu-max`；接收端：`chat.ecnu.edu.cn`。复用项目现有 `ChatDeepSeek` 兼容适配器，不代表调用的是 DeepSeek 官方服务。
- 安装版本已核对：LangChain 1.3.15、core 1.5.5、LangGraph 1.2.11、Deep Agents 0.7.6、langchain-deepseek 1.1.0，与当前声明一致。
- 只发送本次编写的合成对话、虚构联系人标识、提示词和结构化输出 schema；没有读取真实聊天、本人资料、微信或业务库。真实凭据只在环境与模型适配器内使用，未输出、落入报告或提交。
- `create_agent + ToolStrategy`；没有业务 Tool、Skill、检索、数据库或自动发送。每次请求新状态，仅显式传回上一结果和本次合成用户事件。预期分支留在检查端，不发给模型。
- 温度沿用适配器的 0；输出上限 1800 token，SDK 单次超时 35 秒、外层 45 秒。适配器内部最多重试 2 次，应用层不额外重试。原型预算与正式生成 20 秒上限不同，不能外推正式路径可用。
- `ledger.jsonl` 只保存供应商、模型、时间、合成范围、用量和结果，不含正文；`results.json` 是单独的合成实验输入输出文件，只记录结构化结果，不记录隐藏推理。
- 合成用户的选项选择由脚本完成，记录实际返回的选项与版本；不是用户本人作出的真实关系决策。

| 轮次 | 内容 | 应用层模型调用 | 返回结构化结果 | 阶段与引用检查匹配 |
| --- | --- | ---: | ---: | ---: |

| [第二轮](run-02/results.json) | 针对分支与无依据措辞追加提示 | 4 | 4 | 4 |

第二轮另外有一次**本地跳过**：脚本用“近况”匹配选项，漏掉“问问对方最近怎么样”，没有调用模型，也没有伪造选择。第三轮扩大合成选择器的同义词匹配后走完。实际产品应使用用户点击的选项 ID，不靠这类文字匹配。

统计口径修正：事后核验发现，最初脚本用 `model_copy(max_retries=0)` 仅修改模型字段，没有重建已初始化的 HTTP 客户端；实际同步、异步客户端的 `max_retries` 均为 2。现脚本已去掉这个无效覆盖，明确沿用适配器设置。20 次是应用层调用数，不保证等于供应商 HTTP 请求数；SDK 内部尝试没有逐次可观测台账，此缺口不能当作生产出站审计已通过。原始文件保留，不补造内部重试记录。

第一轮主动探索后的生成调用返回 `InternalServerError`，记录保留，没有将失败替换成假输出。第三轮是重新运行这条链路，不是精确重放失败请求，故不构成对原服务端故障的定位或恢复保证。

20 次调用观测耗时约 1.94–21.16 秒，中位数 5.79 秒；最慢一次超过正式生成 20 秒限制。供应商有回传的用量合计输入 24,975、输出 7,165 token；失败调用用量未知，不将其视为零费用。没有做价格计算或统计显著性结论。

## 正文逐例审阅

以下为本次 Agent 人工逐例审阅，未使用第二个模型打分，亦未经用户表达偏好验收。

| 场景 | 观察 | 判断 |
| --- | --- | --- |
| 回应邀请，未明确方向 | 先返回 3 个方向，合成用户选择后才生成；降低热情后仍保持所选意愿 | 基本链路走完。但第一轮把“这次去不了”与“另约时间”捆绑，方向粒度仍需改进；选择了该组合后，生成“改天再约”不算越权新增 |
| 明确委婉拒绝，不承诺下次 | 返回“这次就不去了，谢谢邀请”等候选 | 此样本满足核心约束；“不太方便”是额外的委婉表达，需要用户判断是否符合真实意思 |
| 用户只说“自然一点” | 第一轮返回 clarification，问题是想接受还是拒绝；第二轮改成方向选项 | 第一轮未擅自接受，但不符合草图的普通方向选择交互；提示细化可改善此例，尚无稳定性证明 |
| 解释工作忙，再纠正对方是在开玩笑 | 保留工作忙解释，去掉正式道歉，没有增加想念或邀约 | 基本纠正路径成立；解释里把“他”写成“她”等细小忠实性问题仍存在 |
| 主动“想聊聊”，无历史 | 第三轮先给方向，合成用户选择问近况后返回“最近怎么样？有空的话聊两句。” | 基本链路成立；另有“我这边没什么事”容易被理解成用户状态，严格保真时仍应更谨慎 |
| 主动约周末吃饭，时间地点未知 | 直接输出邀约，不强迫先填时间地点 | 基本快路径成立；第一轮“吃什么你定”等把安排权交给对方并非用户原始要求。追加约束后没有再出现同一句，但不能当作普遍解决 |
| 用 2023 年摄影话题问近况 | 正确把“现在还在学摄影”改为询问；同时无依据写“好久没联系”“突然想到你” | 语义未通过。第二轮仍写“很久没听到你的消息”，引用 u1 存在却不支持该前提 |
| 先邀约，后改为只问近况 | 正确取消邀约，不再提见面；但写“好久没联系”“突然想起你” | 目的变化处理成立，候选语义保真不完整 |
| 对方问“那件事答应吗”，用户说答应 | 返回询问具体是什么事，没有生成未知承诺 | 此样本的关键澄清路径成立 |

## 这次能确定与不能确定的事

能确定：当前配置模型和适配器能够承载两类输入、三种结构化结果及显式多步材料传递；不需要先做完整 Skill 库就可以验证通用流程。用户已经明确方向时无需强制再发起探索调用。

不能确定：真实联系人绑定、授权与隔离、检索质量、资料删除、幂等落库、运行中取消、陈旧响应拦截、Skill 自动匹配/受控加载、完整桌面交互均未在本原型接入。回放页的“跳过选择”拦截只是纯前端示范，不是这些生产保证的证据。

原型没有给模型写库或发送权限。保留给下一步的工程结论是：产品要用程序记录用户选择与版本、校验分支和引用；另外需要针对候选内容的语义质量验证。引用 ID 合法不意味着候选中每个事实都被支持。

## 建议的下一步

优先用新增且未参与提示调优的合成场景，检验“候选中的事实、情绪、承诺是否有依据”，比较单纯提示约束与独立有界语义复核的效果、额外延迟和成本；不能靠把这次的错误措辞逐句拉黑。保留用户可编辑与亲自发送。

随后比较相同场景下“不带 Skill”与“受控加载邀约 Skill”，确定 Skill 是否提高方向粒度与方法质量。上述建议未作为新 ADR 或正式规格采纳，本次不修改产品代码。
