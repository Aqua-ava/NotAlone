## Implementation Decisions

- 01–04 互不阻塞、各用本聊天所属独立受管工作树；05 等全部实施聊天完成后负责集成、默认验证清单和整体验收。各自从已合并main开始，不在共享root并行改产品。
- 仅优化已有行为；代码、schema和测试留在本地。禁止push、远端分支、PR、发布包、运行打包版、外部聊天发送。
- 联系人确认、owner/contact隔离、来源逐项核验、删除失效、auto/manual区分、完整追踪、时间/条件核验及人工发送不变。
- 不实现尚处讨论的「取消固定上下文限制」，不恢复表达样本；不重复酒馆上下文组织和L2目录排序工作。
- 不连接或修改业务数据库；schema变更仅在独立合成库验证，不自动迁移用户已有资料。
- 所有 App 验收只走 `npm run dev`，先 `npm run dev:status` 并核验/复用已运行实例；不得启动第二个争焦点实例。01–04 优先隔离自动检查，05统一协调实际App和微信验收；未真实验证的环节明确记录。
- 工作树中缺少的忽略态调研证据从启动提示提供的绝对路径读取。每个聊天在自己的工作树更新自己的issue和结果文件；共享root的派发登记由发起聊天维护，不在共享root修改任务状态。

## Testing Decisions

- 先复现和固定基线，再做最小行为回归、相关模块、最终统一全量。必要时独立Standards/Spec审查按仓库skill执行。
- 合成基准保留输入摘要、源码版本、原始样本、p50/p95、等价断言、负结果和资源清理凭据；查询数/JSON体量/堆分配不能冒充用户延迟或RSS。
- 性能计时阶段使用共享文件锁 `/tmp/notalone-optimization-benchmark.lock`（Python fcntl）串行测量；前后交错取样，避免并行测试污染数字。普通测试可并行但数据库/端口/文件名独立。
- 失败先在旧基线单例复现；不能放宽身份、来源、安全、内容正确性或改产品文案迎合旧测试。合并版本须重测，不能拿分支局部通过代替整体验收。
- 每个实施聊天的产物：本地提交/分支/工作树、具体文件、基线与候选、实际命令和结果、数据处理影响、未通过项与已清理资源；证据写到本目录本issue对应的结果文件。无收益或重复已实现的线索可以用证据关闭，不凑改动。

## Out of Scope

真实外部模型质量评测、替换数据库/引入Redis/新框架、用户业务数据迁移、对外发布、改变产品范围和授权、自动发送聊天、扩大OCR范围。长历史分片和大量记忆检索先保留为扩容证据，除非当前基线证明值得实施且能保持逐次来源复验。
