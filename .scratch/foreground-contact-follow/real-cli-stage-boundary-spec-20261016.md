# 真实 CLI／视觉组合的原生阶段边界

## 问题与范围

冻结 v9 的空配置采样已证明小窗公开重开后能够原生获焦，随后也会失焦。原组合从 Root 操作信号开始统计：异步获焦之前的探针会被计入“小窗获焦后零新观察”；微信阶段首个合法零采集暂停也会立即失败，未能等待实际正向观察。信号只协调动作，不能认证 OS 状态，测量起点应由实际原生条件确定。旧两场失败保持，不回溯改分。

只修现有 `real-sync-visual-independence-acceptance.spec.ts` 及其纯证据测试，不改产品、签名包、CLI范围或探针行为，不增 runner／harness。以下门仍是同场、不可重置的严格证据门。

## 阶段与完成条件

- 保存 Root trigger 时刻、首次原生条件观察时刻及测量起点。完整保留前置与阶段内原始测量，不能丢弃不利记录或据失焦重置起点。
- 微信在原25秒总窗口内等待 trigger 后首次成对、完整、合法的 `recognized` 单帧，四项采集／OCR计数各1；此前仅允许完整合法的 `paused` 且四项全0作为等待，另账保存。未知、错误、非法计数及重复／缺配对仍拒绝；没有正向观察就失败。首次合格观察的原启动时刻固定为正向测量起点，后续原严格检查保持。
- 小窗在原70秒总窗口内先等待首次实际 `BrowserWindow.isFocused()`；达到后只固定一次起点与实际CLI审计checkpoint。之后新正式probe仍严格为0，必须有checkpoint之后完整的真实tail started→finished→accepted，并在通过快照仍获焦。失焦后不重启窗口或清空记录；违反正式观察门即失败。等待获焦消耗同一70秒，不再另得70秒。
- Finder原有测量合同保持。全部阶段均受原scope／租约较早截止和预留收尾约束。
- 起点前已开始、起点后才完成或尚在途的probe单列保存，不伪写成阶段内成功采集或消失；“零新观察”始终按真实启动时刻定义。

## 验证与排除项

沿实际纯证据接缝先红后绿：合法零采集暂停只等待、合法正向才建立微信边界；错误／未知／计数不符拒绝；小窗未获焦不起点、首次获焦只固定一次、失焦／重获焦不重置、70秒总预算不延长；边界前在途单列、边界后正式启动仍拒绝；旧tail、失败tail或未accepted不通过。保留全量原件及字段，默认现场仍skip。

类型与最小相关纯回归后完成Standards／Spec审查、本地提交及公开扫描，再用冻结v9的新单联系人有限scope复验。没有真实模型、来信、第二联系人、外部发送或权限更改。修复仅使测量对应实际条件，不认证产品根因、持续OS前台、私聊身份或旧失败已经通过。

## 离线实施记录

仅修改两个既有测试文件。微信合法paused0被旧严格门误拒、助手trigger被旧路径用作获焦起点，两条真实负控均先红后绿。保存信号文件mtime、接收时刻、首次条件、固定起点／截止／CLI checkpoint读取时刻、前置及边界快照在途／后续配对；不能推导独立完成墙钟。微信先等待前置合法闭合再固定正向起点；助手失焦后仍检查新probe，终态再次读原生焦点，起点不重置。

作者视觉10项、协调器11项及类型检查通过；主Agent在Conda NotAlone下复验同21项通过（2.120秒），差异检查通过。主Agent首次误在base环境启动，20项过、一个合成Python环境守卫拒绝；激活规定环境后全过，这是执行环境修正，不作为产品red。独立Standards／Spec三文件最终均0项需修，尚未据此认证实际App通过。
