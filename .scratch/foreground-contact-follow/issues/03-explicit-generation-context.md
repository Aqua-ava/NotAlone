# 03：显式生成与固定上下文

State: open
Triage: ready-for-agent
Blocked by: None

## 交付行为

只有用户明确点击生成操作才提交候选回复任务；请求在取得有效准备回执时固定发起联系人的助手会话、输入版本和有界回复上下文。准备完成后即使切换、编辑或收到新消息，原任务也不能改用后来的界面输入或消息。

本票可在现有单联系人入口独立验证；多联系人有限调度及状态展示由 05 接续。

## 验收条件

- [ ] 打开助手、快捷键唤出、定位成功、联系人/助手会话切换、内容恢复和消息事件都不创建候选回复任务。
- [ ] 单独确认联系人或方向只更新确认/输入；方向探索、纠正和回答不隐式生成候选。已有会生成的“结合新消息继续”等入口明确表达其生成含义。
- [ ] 联系人、方向、预算、资料范围和授权校验通过后，才接受生成并取得可靠准备回执；无法固定材料时明确失败，不虚报已排队。
- [ ] 准备回执对应固定的 owner/contact、助手会话、输入版本、请求身份与有界上下文；准备后再执行不得重新读取当前页面决定原请求输入。
- [ ] 后来的新消息不进入原生成的初始上下文或后续补查，不使请求自动替换/重启；只保留同联系人“尚未结合新消息”提示，用户明确重新生成才取得新材料。
- [ ] 后续只读补查使用原任务的有效资料范围和既有预算；不复制完整历史，也不能用固定快照绕过来源删除、授权撤销、Skill 失效和提交前后版本复验。
- [ ] 同键同输入重放可靠结果，不重复请求/候选或模型调用；同键不同输入报冲突，显式替换及失败重试沿用原有身份与失效规则。
- [ ] 原任务和新任务的上下文及依据可分别回看，候选不自动发送，旧任务结果不能覆盖不同联系人或新的有效请求。

## 测试与完成条件

使用生产桌面公开生成操作、认证 HTTP 和隔离 PostgreSQL；可控模型在准备、执行和返回处形成可观察的延迟。验证准备 → 新消息/编辑/切换 → 执行仍使用原输入及范围，再显式生成使用新材料；核对原/新依据、模型调用次数、幂等冲突和来源失效。

复用现有准备、请求、上下文和生成归属接缝，不另建通用队列或 Worker 步骤。每条已有生成入口都要验证其明确触发语义，不能只改按钮文字。在 `## Answer` 记录最小相关验证、数据影响及剩余风险后改为 `resolved`；真实 App 和自然语言质量由各自证据另行区分。
