# NotAlone 未完成工作总清单

更新日期：2026-10-10。当前建议先从持续会话草图的 Q16 继续讨论，再收束聊天回复策略；工程上优先补齐现有 Mac 闭环的交付和验收条件。新聊天交互的设计与现有版本的验收可以分别推进。

本清单汇总 5 份待收束设计、9 张未关闭任务、1 份待实现的媒体规格及 Windows 后续方向，共 16 个工作入口。按下一步主要阶段分为：**待讨论 8 项、待实现 4 项、待验收 4 项**。阶段之间存在依赖，这些入口不能解释为 16 个互相独立的功能。

以下优先级和次序是排期建议；原任务的 `State`、`Triage`、验收条件与用户已确认事实仍以链接的来源为准。本清单不发布新任务、不改写现行规格，也不授权新的模型调用、真实微信读取或原生桌面验收。

## 依赖与执行顺序

产品设计先推进第 1 项，再与第 2 项共同核对场景入口、候选版本和新消息处理。两份草图收束后，再形成正式规格与实现任务。第 1 项涉及的持久化、临时要求延续、恢复与删除会影响后续接口，应在实现新交互前明确；当前不加入经验沉淀或自进化。

现有 Mac 验收不以两份新草图落地为前置。先补齐完整、可追溯的 CLI/WCDB 输入及受控打包路径，再安排有限验收时段；首个真实同步切片可采用手动确认的唯一联系人、隔离数据库和禁用模型的路径，详见[真实微信前置核查](../observation-model-smoke/acceptance.md)。**CLI 后台同步不依赖前台 OCR**；任务 18 的自动定位可单独补齐，而最终完整 App 交付仍须完成其原定依赖。

原生复制、测试调度和 follow 的相关检查尽量合并到同一次已认可的有限时段，减少反复启动；每项仍记录自己的实际结果，不能用窗口成功、签名通过或普通页面通过替代原生能力。旧 Swift 冒烟入口和旧“微信必须保持前台才能读正文”的条目须按 ADR-023/025/030 核对，视觉采集与 CLI 正文同步分别验证。

记忆质量工作先区分三件事：核心事实覆盖、指代准确率、按维度放行。自动采纳维持当前空放行表；修复或一次局部评测通过不自动放行，也不重开已关闭实验。App 追踪查看可在范围明确后独立推进，便于用户核对已有结果。

## 当前先做什么

**现在先继续第 1 项的 Q16，收束生成中新消息的处理。** 它有明确的讨论起点，不依赖缺失 helper 或原生验收时段；先确定处理中到达新消息时，提示、原生成结果归属及用户选择“结合新消息继续”的行为，再推进预算提示与存储恢复细节。随后回到第 2 项，统一聊天入口、方向建议和 Skill 的职责。

工程上保留第 3 至 7 项的 P1 优先级。完整 helper 输入和时段齐备后，先验手动确认联系人的最小同步闭环，再扩展到原生复制、自动定位和最终 App 集成交付。期间可整理验收材料和缺口，但准备完成不等于实际验收通过。
