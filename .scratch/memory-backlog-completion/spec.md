# 补齐已确认联系人的积压记忆提取

## Problem Statement

用户已认可展示的五条现有记忆语义，进一步指出长聊天的提取完整性，并明确要求继续。只读统计证明有消息停留在记忆水位之后；CLI 后台同步目前没有自动触发提取。恢复实跑又暴露模型未按结构化工具格式返回的问题，不能把任务运行或水位推进冒充完整提取。

## Solution

沿已有 `extract_main → run_extraction → ExtractionFlow` 续跑同一已确认联系人，保留失败与逐批非正文元数据，完成来源核验、原采纳门槛及确定性目录重建／验证。仅修复有运行证据的结构化工具选择问题，不增加模型、依赖、数据库字段或自动采纳类型。当前明确发现的凭据消息在本次请求边界排除，原始业务消息与来源 UUID 不修改。

## Implementation Decisions

- 联系人范围从既有已确认审计读取，并在实际库复核 active 绑定；不能扩大到其他联系人。
- 使用当前配置供应商与模型，目标每批 20 条；持有现有全局 Worker 锁，保护并发恢复。
- 保留起始记忆与水位快照、消息 ID 顺序、全部失败和逐批计数；私人聊天及记忆仅保存于仓库外私有目录。
- 保留工具结果和逐字证据的原校验；强制工具选择只改变返回格式约束，不把格式正确当作语义正确。
- 真实候选仍按原规则进入 pending／auto；用户认可旧五条语义不自动改变其业务采纳状态。
- 以实际新增／更新记录和引用原话形成验收对照；源主张盲审仅作为完整性评审参考，不冒充模型提取。
- 按用户已有“如果不对，哪里出问题就修改”的授权，只通过现有失效接口撤回本轮新增的错误资料；含义不确定的自动记忆暂停参与检索，保留原文和判断供用户验收，不改写旧五条或创建用户确认。

## Testing Decisions

- 公共 seam 为现有提取与来源核验运行时及 CLI；先以真实失败元数据定位，再以合成模型 I/O 验证强制工具选择，缺失／非法结果仍安全失败。
- 变更第三方 `bind_tools` 参数前核对当前官方文档与实际安装版本。
- 完成相关测试、源模块类型检查、全量 Python 测试及 Standards／Spec 两轴评审；本地中文提交，不 push。
- 水位后剩余数、失败／跳过区间、目录验证和三表差分分别报告，不能用成功退出码替代准确率或漏提率。

## Out of Scope

后台同步自动调度的新实现、旧水位前历史重提取、降低采纳门槛、批量人工确认、修改同步授权、外部聊天发送、部署或远端 Git 操作。
