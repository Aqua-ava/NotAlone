# 02 — 本机真实聊天找错一轮

**What to build:** 在用户本机上，对已确认联系人跑一轮真实提取评测（默认只读；是否写入待确认候选由用户当场决定）。只输出聚合统计与判错分类（去向、标签错误类型），不输出消息原文、命题文本或联系人标识。用户抽查判定结果；发现的真实错误经去标识改写成合成用例，经用户过目后加入评测集，供后续维度票使用。

**Triage:** ready-for-human
**State:** open
**Blocked by:** 01（评测骨架）

- [x] 仅在本机运行；不产生包含真实内容的仓库文件
- [x] 输出聚合统计与判错分类，不含原文、命题或联系人标识
- [ ] 用户抽查确认判错分类（部分确认：见 Comments）
- [x] 去标识改写的新用例经用户过目后入库并标注来源为"真实找错"

## Comments

- 只读真实提取共三轮，每轮覆盖 3 位联系人、593 条消息、31 个窗口。聚合区间：接受 120–131 条、被拒 39–80 条、自动采纳 75–84 条、待确认 41–47 条、不生成 3–4 条；运行失败 0–1 个窗口。被拒原因全部为"只引用上下文消息、未引用本批目标消息"（另有个别解析失败），说明模型经常把上下文消息当成提取目标。
- 用户抽查确认判错（已去标识）：
  - 假事（跨话题拼接）：模型把同一窗口内不相干的两件事——他人转述"用户离职突然"与"联系人所在公司"——拼成"用户曾在联系人公司工作"。该事实不存在，且候选因只引用上下文消息被外壳拒绝、未进入记忆；暴露的是模型的跨话题拼接倾向。
  - 记错人（昵称/主体混淆）：命题把用户误写成联系人主体，且命题文本直接引用聊天里的昵称称呼，没有统一使用"用户/联系人"。
- 待用户继续抽查的观察项：瞬时状态与日程（当天没吃饭、次日有面试等）、细碎细节、第三方一次性事件被自动采纳；健康相关细节建议保守处理。最终按用户标注取舍后去标识改写成合成用例。用户对瞬时状态的意见是"过两天没有意义的东西给个时间节点"，即保留但带时效、过期不参与检索，已单独记录为 `memory-accuracy-next` 票 05，不按一刀切排除处理。
- 计划入库的两条合成用例（待用户过目）：①窗口内两件不相干的事（他人转述用户经历 + 另一个话题），期望不产出合并事实；②联系人用昵称称呼用户，期望命题不使用昵称且主体为用户。
- 修复与验证：提示词新增两条规则——不得把窗口里不同话题的人、地点、事件或结论拼成同一条事实；命题文本不写用户或联系人的名字、昵称、备注，统一用"用户""联系人"。合成用例"真假：跨话题拼接""主体：昵称称呼"已入库并标注来源，全量 112 条连续两轮：0 假事、0 记错人，两题均通过；truth_intent 18/18、subject 17/17。失败集合两轮不同（媒体占位解析失败、指代漏提、时间有效性），与既有波动一致，非本次改动引入；reference 维度 13/15 仍是老问题，归下一轮票 01 与 07 的复核范围。残余：模型偶尔仍会尝试引用上下文消息的候选，被外壳拒绝、不入记忆；短消息漏提仍归票 01 处理。
