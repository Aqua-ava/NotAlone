# 旧业务库接管与约束补齐方案

本文记录 2026-10-01 制定的本地升级方案。制定时尚未执行业务库迁移，接管入口尚未实现；下述步骤不能替代现有迁移命令的拒绝保护。用户随后明确回复“同意”，执行和验收记录见 [受控旧库接管任务](../legacy-database-adoption/spec.md)。

## 已核验的状态

2026-10-01，升级审计以 `REPEATABLE READ READ ONLY` 读取系统目录和当前配置 owner 的聚合计数；未读取聊天正文、修改身份或执行删除。正常 App 仍在现有确认范围和总开关下进行同步及状态写入；修复后将原有 50 个补齐失败保存为覆盖无法确认，65 个暂停状态保留。参考库为 Agent 自建、只含合成资料的随机 `_test` 库，应用仓库原样的 001–035 后比对，并已清理。

| 对象 | 001–035 参考库 | 旧库 | 差异 |
| --- | ---: | ---: | --- |
| 表 | 33 | 33 | 无 |
| 列及类型、默认值、非空性 | 341 | 341 | 无 |
| 约束及验证、延迟属性 | 233 | 233 | 1 项定义不同 |
| 索引及有效性 | 85 | 85 | 无 |
| 非系统触发器、非扩展函数 | 0 | 0 | 无 |

比对排除迁移账本；旧库没有 `notalone_schema_migration`。当前结构相近不能证明 001–035 曾连续执行或历史回填完整。

- `source_document_source_type_check` 只允许 `wechat_jsonl`，未满足 025 的 `wechat_jsonl/manual` 契约，手动联系人记忆会失败。
- `background_task_task_type_check` 仅允许 `import`；任务当前步骤和步骤名称也只接受导入的五步。036 的持久化删除契约未具备。
- 当前 owner 的“无来源引用消息、跨范围文档引用、跨范围观察引用、孤儿提取水位、观察计数违反约束”计数均为 0。活动联系人记忆按现有完整契约（文档、观察、仍有有效来源的规范消息）核验，不支持的来源引用为 0。不能把规范消息 UUID 误判成来源丢失。
- 未恢复其他 owner 的历史执行记录，也未证明过去任何时刻的数据完整性；接管前仍需对目标库全部 owner 做同类契约核验。

实机同步另有独立限制：115 个确认绑定中，50 个是 `incomplete / cli_message_table_missing`，65 个仍为 `paused`。升级 PostgreSQL 约束不会使 CLI 找到缺失的微信消息表，也不能据此宣称历史覆盖完成。

## 隔离演练结果

在新建合成 `_test` 库中模拟“结构接近 035、没有账本、来源类型仍为旧约束”：

1. 标准 `migrate` 返回 `legacy_database_untracked`，未创建账本，业务计数不变。
2. `PostgresMemoryStore.create_manual_candidate` 被旧约束拒绝，来源与候选同一事务回滚。
3. `PostgresSourceTasks.request_delete` 被旧任务约束拒绝，来源仍 active，消息和任务计数不变。
4. 仅在此一次性合成库模拟 025 与 036 的约束放宽后，手动候选可创建，删除请求可持久化且重复请求返回同一任务。
5. 复用现有三个公开接缝用例：手动记忆录入/列表/删除；HTTP 来源删除的幂等与范围隔离；删除清理已提交而步骤凭证未提交时的恢复。3 项均通过，无跳过。

演练没有伪造历史账本，也没有验证尚不存在的旧库接管命令。临时合成库已清理；这不是业务库升级成功证据。

## 建议实施顺序

1. **实现显式接管入口并先在合成库验证。** 默认旧库拒绝行为保留。接管必须锁定经审计的结构和允许的具体差异；遇到额外对象、约束不匹配、跨范围或来源链异常时停止。只读预检应输出安全计数与分类，不能输出私人行或底层错误。
2. **区分审计基线与历史执行记录。** 单独记录通过审计的基线、001–035 文件清单及 SHA-256、接管前后结构摘要、实际补齐 SQL 摘要、备份校验与恢复验证结果；不批量插入“001–035 执行成功”。后续迁移命令识别该明确基线，并继续验证历史文件不可变与连续性。基线格式与命令必须作为实现的一部分审查，不能手写记录绕过保护。
3. **停止本地 App、同步与 Worker 的写入后备份。** 保持用户总开关、65 个暂停状态、联系人与绑定身份不变。将备份保存在仓库外的本机受限目录，目录 0700、文件 0600；不上传、不进入模型输入或 Git。对备份做校验，并恢复到专用受限恢复库验证可恢复性。恢复库含真实资料，不能作为合成测试库使用。
4. **重新核验后按事务补齐。** 先补齐已审计的来源类型约束并核验完整 035 契约，再原子记录审计基线；036 通过受管迁移入口执行，SQL 与实际执行记录同事务提交。补齐只放宽已知约束，不清空消息、记忆、来源或历史任务，不修改已执行迁移文件，不重放 003/021 等历史转换。
5. **完成验收后重新启动 App。** 业务库验收仅核验目录、账本/基线与非正文计数；手动记忆和真实删除行为继续在合成库验证。比较升级前后的身份、绑定、来源/消息计数和暂停范围，并确认同步重新连接。能力升级不等于用户授权删除任何真实来源。

接管入口必须覆盖：结构差异拒绝、文件摘要漂移拒绝、重复执行幂等、并发互斥、修复与基线事务回滚、036 中断续跑、来源与联系人隔离、暂停状态保留和凭据不泄露。

## 恢复与批准边界

验收期间保持业务写入停止；若迁移失败，当前事务回滚，必要时恢复已验证的升级前备份，再恢复旧版代码。重新开放业务写入后，不强制恢复旧约束或覆盖新数据，应通过新的受管迁移向前修复；新产生的 `manual` 来源或 `delete` 任务可能不满足旧约束。

需要用户明确决定的范围是：实现受控接管入口，并在本机备份、恢复验证后升级旧业务库。备份与专用恢复副本同样按私人资料保护。未得到此决定前，只保留本方案和合成验证，不执行业务库升级 SQL、真实来源删除、远端连接或发布。

依据：[Agent 工作流](../../docs/agents/workflow.md)的决策模式要求，方案涉及“删除或迁移数据”时询问用户；[数据库迁移说明](../../database/README.md)要求核对结构、约束、历史回填与备份恢复，并明确禁止手写成功记录、重放 001–035 或删除业务库绕过检查。
