# Memory、Skill 与 Prompt 上下文规格

State: open
Triage: ready-for-agent

## Problem Statement

NotAlone 需要帮助用户针对一位已经确认的联系人生成候选回复。当前设计必须同时处理三类信息：

- 当前消息和最近对话，保证回复理解眼前语境；
- 联系人的长期关系资料，保证回复不会忘记已确认的事实、偏好和禁忌；
- 必要时才读取的较早聊天记录，保证可以回答历史问题，又不把全部聊天记录塞进模型上下文。

如果把全部历史直接放进 Prompt，会造成上下文过长、无关信息干扰、隐私范围扩大和删除后残留。如果完全依赖模型自己查询数据库，又无法保证联系人隔离、来源追踪、查询预算和删除语义。

用户希望参考 TencentDB Agent Memory 的分层、检索工具、Skill 渐进加载和 Prompt 注入思路，但只把适合 NotAlone 的 Memory 与 Skill 能力接入现有项目，不在运行时直接依赖 TencentDB，也不引入完整 Resource 系统。

本规格解决的核心问题是：每次候选回复应该查什么、初始 Prompt 应该放什么、模型什么时候可以补查 L0，以及 Memory、Skill、Resource 和现有 NotAlone 领域对象如何分工。

## Solution

NotAlone 保留现有 PostgreSQL、联系人范围、来源证据、`ReplyContext`、`RetrievalPort`、`SkillPort` 和人工发送边界，增加一条受控的 TencentDB 式检索链路：

1. 程序先验证当前会话属于哪个联系人，并保存当前真实消息。
2. 程序直接读取当前消息、有限的最近对话和当前问题相关的少量 `confirmed_memory`。
3. L2 只提供场景/主题导航，帮助缩小 L1/L0 检索范围，不作为新的事实源。
4. 初始 Prompt 不放历史 L0 全量原文；模型需要较早历史时，调用只读的相关性搜索工具，再按需调用时间顺序查询工具。
5. Skill 先以轻量目录提供，只有当前任务需要时才加载一个已校验的不可变 Skill 版本。
6. 每轮使用新的 `ReplyContext` 快照；工具结果作为同一轮上下文继续生成，下一条用户消息到来后重新检索和组装。
7. 程序校验候选回复中的联系人范围、来源和 Skill 版本，用户查看、编辑并亲自发送。

本方案只借鉴 TencentDB 的机制，不复制其完整服务、表结构或代理层。Resource 不是独立记忆层；只有 Skill 明确引用受控的辅助资源时，才按版本和权限读取。

## User Stories

1. 作为用户，我希望候选回复始终绑定到我已经确认的联系人，以便系统不会把资料用错人。
2. 作为用户，我希望未绑定、重名或低置信度的会话先让我选择联系人，以便系统不自动猜测身份。
3. 作为用户，我希望系统先使用当前消息和最近对话，以便回复符合眼前语境。
4. 作为用户，我希望最近对话按时间和说话人保留，以便短句、引用和上下文关系不被打散。
5. 作为用户，我希望系统只读取当前联系人范围内的资料，以便其他联系人的隐私不会进入回复。
6. 作为用户，我希望相关的已确认关系记忆自动进入本次上下文，以便不用手动翻找每一条资料。
7. 作为用户，我希望无关的长期记忆不进入 Prompt，以便模型不会被旧资料干扰。
8. 作为用户，我希望初始 Prompt 不包含全部历史聊天，以便回复速度、成本和隐私范围可控。
9. 作为用户，我希望模型在确实需要时能够查询较早的聊天记录，以便回答“之前我们聊过什么”之类的问题。
10. 作为用户，我希望历史相关性搜索和连续会话读取是两个明确能力，以便模型先定位再阅读上下文。
11. 作为用户，我希望历史搜索结果带有角色、时间、会话和来源信息，以便我能理解它为什么被使用。
12. 作为用户，我希望历史查询有 Top-K、Token、时间和调用次数限制，以便全量历史不会撑满上下文。
13. 作为用户，我希望没有检索结果时系统明确表示未找到，而不是猜测一个历史事实。
14. 作为用户，我希望检索工具失败时仍能基于当前消息和最近对话生成候选，以便偶发查询故障不会让整个回复流程失效。
15. 作为用户，我希望 L0 原始消息被当作证据而不是指令，以便聊天中的恶意文本不能改变系统权限。
16. 作为用户，我希望每条已确认记忆都能回到来源消息，以便我可以核对它是否真的说过。
17. 作为用户，我希望记忆带有状态和有效期，以便过时资料不会默认影响新回复。
18. 作为用户，我希望 L2 只帮助定位相关资料，而不是偷偷生成新的关系事实，以便事实仍由权威记忆和来源决定。
19. 作为用户，我希望 L3 人格画像暂不参与回复，以便系统不会把模型推断固化成我的人格。
20. 作为用户，我希望真实收到的消息和我实际发送的最终消息进入 L0，以便历史记录反映真实对话。
21. 作为用户，我希望模型生成但未发送的候选稿不进入 L0，以便草稿不会被误认为真实表达。
22. 作为用户，我希望记忆提取只读取真实消息，以便模型草稿不会制造虚假关系事实。
23. 作为用户，我希望记忆提取在后台异步运行，以便它不会阻塞当前候选回复。
24. 作为用户，我希望重复导入或重复同步不会产生重复消息、记忆和索引，以便数据保持一致。
25. 作为用户，我希望低风险且明确表达的资料可以按规则自动采纳，以便减少逐条确认的负担。
26. 作为用户，我希望敏感关系推断先保持为候选，直到我确认后才进入默认上下文，以便系统不会擅自判断我的关系。
27. 作为用户，我希望能查看、修改、接受、拒绝或撤销候选记忆，以便我掌握长期资料的控制权。
28. 作为用户，我希望新证据与旧记忆冲突时保留新旧版本和来源，以便系统不会静默覆盖历史。
29. 作为用户，我希望删除来源后相关记忆、索引、缓存和工具结果都失效，以便删除真的会影响后续检索。
30. 作为用户，我希望 Skill 先显示名称、描述和适用场景，以便我知道本轮可能使用什么策略。
31. 作为用户，我希望一次候选回复最多使用一个 Skill，以便多个策略不会互相冲突。
32. 作为用户，我希望只有在需要时才加载完整 Skill，以便默认上下文保持轻量。
33. 作为用户，我希望 Skill 版本不可变且可追踪，以便我知道本轮使用的是哪一版策略。
34. 作为用户，我希望 Skill 不能读取任意文件、数据库或其他联系人，以便策略文本不会扩大权限。
35. 作为用户，我希望 Skill 的辅助 Resource 只在明确允许且确实需要时读取，以便不会引入隐藏的资料层。
36. 作为用户，我希望 Skill 不会修改长期记忆、系统权限或外部聊天渠道，以便策略和事实保持分离。
37. 作为用户，我希望每轮都重新验证联系人、来源、记忆版本和 Skill 版本，以便旧上下文不会在数据变化后继续生效。
38. 作为用户，我希望候选回复告诉我用了哪些依据和 Skill，以便我可以检查生成过程。
39. 作为用户，我希望模型只能引用本轮实际读取并通过校验的依据，以便不会出现虚假的来源。
40. 作为用户，我希望模型返回的是可编辑候选，而不是直接发送的消息，以便最终表达仍由我决定。
41. 作为用户，我希望我修改并亲自发送的最终文本才进入后续真实聊天记录，以便系统不会记录未发送内容。
42. 作为用户，我希望外部模型只收到必要且经过范围校验的文字，以便私人资料不会无控制地外发。
43. 作为用户，我希望检索、Skill 和模型调用都有最小可审计记录，以便发生问题时能追踪使用了什么。
44. 作为维护者，我希望检索实现可以先使用 SQL/全文，再替换或补充向量 Adapter，以便优化不影响领域接口。
45. 作为维护者，我希望索引和缓存可以删除后重建，以便底层资料变更不会留下不可修复的派生状态。
46. 作为维护者，我希望模型运行时只依赖稳定的 Port 和 `ReplyContext`，以便 TencentDB 或其他运行时可以被替换。
47. 作为维护者，我希望相同的测试能覆盖内存 Adapter 和 PostgreSQL Adapter，以便行为不会随存储实现改变。
48. 作为维护者，我希望新链路有明确的回退路径，以便上线时可以恢复到当前消息加最近对话的基础模式。

## Implementation Decisions

### 1. 主测试 Seam 和模块职责

- 使用现有 `ReplyGenerator` 的候选回复生成公开接口作为唯一最高层测试 Seam。输入是已验证联系人范围和一次 `GenerateReply`，输出是已校验、已持久化的候选结果。
- `ReplyContextPort` 负责形成本轮上下文快照；`RetrievalPort` 负责联系人范围内的消息和已确认记忆查询；`SkillPort` 负责目录、不可变版本和受控资源读取；`ReplyRuntime` 负责模型与只读 Tool loop。
- `ReplyGenerator` 负责把这些模块组合起来，并执行引用、范围、输出结构和持久化校验。调用方不需要知道数据库、模型供应商或 Skill 文件的实现细节。
- PostgreSQL Adapter、全文/向量 Adapter、模型 Adapter 和 Skill 读取 Adapter 都位于既有 Interface 之后，不改变领域对象对框架的依赖方向。

### 2. Memory 层级和权威对象

- L0 表示与 TencentDB 对照的原始聊天/规范消息证据层；NotAlone 的权威领域对象仍是 `Message` 及其来源关系。
- `memory_candidate` 是从真实消息提取出的候选，不属于可直接使用的已确认事实层；`pending` 状态不得进入默认 Prompt。
- L1 对应 `confirmed_memory`，必须带来源证据、采纳方式、状态、有效期、版本和删除关系。
- L2 对应 `contact_memory_index` 及其场景/主题导航，只保存少量入口和引用，可以由 L0/L1 重新生成，不能脱离权威对象成为事实。
- L3 画像/人格层本轮不实现，也不把模型推断出的稳定人格写入 Prompt。
- Skill 是独立的回复策略，不属于 Memory 层，不保存联系人事实。
- Resource 只表示 Skill 的可选、版本绑定、受控辅助资源，不作为独立记忆层。

### 3. 每轮基础检索和按需补查

- 用户消息到来后，程序先验证 `owner_id + contact_id` 和已确认会话范围，再读取当前消息和有限的最近完整对话。
- 程序直接使用当前消息执行基础检索，不先增加一次模型查询改写。
- 程序在硬过滤范围内选择少量当前有效的 `confirmed_memory`，必要时使用 L2 主题导航缩小候选范围。
- 历史 L0 不在初始 Prompt 中全量注入。模型发现已有上下文不足，或用户明确询问历史时，才调用历史查询 Tool。
- 相关性搜索先使用类似 TencentDB `conversation_search` 的职责定位消息；需要连续语境时，再使用类似 `conversation_query` 的职责按会话和时间顺序读取有限范围。
- L1 查询与 L0 原文查询保持独立。程序可直接选择 L1，模型也可以在需要核对时调用受限的确认记忆查询 Tool。
- 每轮 L0/L1 历史搜索 Tool 调用默认合计最多 3 次；Top-K、Token、时间、超时和重试预算由运行时配置，并在评测中确定具体值。
- 空结果只表示本次查询未命中，不能被模型解释为历史事实不存在。

### 4. 检索实现

- 所有查询先进行联系人、Owner、删除状态、来源有效性和记忆有效期硬过滤；模型不能通过参数改变范围。
- 首版使用 PostgreSQL 的 SQL 精确条件和全文检索；不引入独立向量数据库或 Resource 数据库。
- 全文、向量和未来可能的重排只负责候选相关性，不负责联系人授权或事实确认。
- 向量检索是后续补充路径：只有评测表明全文检索在同义表达或长历史场景不足时才加入。
- 混合结果由程序合并、去重和排序；相关性接近时优先当前有效且较新的资料。
- 向量或索引不可用时回退到 SQL/全文路径，不影响当前消息和最近对话生成。
- 索引异步生成，Embedding 或分词规则变更时支持重建；原始 L0/Message 不因索引重建而改变。

### 5. Prompt 和 `ReplyContext`

- `ReplyContext` 是一次候选回复任务的有界快照，不是跨轮的隐藏记忆。
- 快照包含已验证范围、当前 Message、近期消息、相关 L1、必要的 L2 导航、Skill 目录、可选的已加载 Skill、引用、检索轨迹和版本信息。
- 逻辑 Prompt 顺序为：系统规则与 Tool 说明 → 当前 Skill（如有）→ 当前用户要求与近期对话 → 相关 L1/L2 → 本轮 Tool 返回的 L0/L1 证据。
- L0/L1/L2 明确标记为数据或证据，不能覆盖系统规则、用户当前要求或 Tool 权限。
- 初始 Prompt 不包含历史 L0 全量原文、全部 L1、全部 L2、未确认候选、未发送草稿、未选 Skill、原始视觉帧或其他联系人的资料。
- 工具返回的历史 L0 作为同一轮 Tool 结果加入上下文，不创建新的用户消息，也不成为下一轮默认隐藏上下文。
- Prompt 超预算时按当前用户要求、当前消息、近期对话、相关 L1/L2、历史 Tool 结果的顺序保留。
- 生成前再次验证所有依据属于当前联系人；生成后再次验证候选引用和 Skill 版本。

### 6. Skill 运行方式

- Skill 目录提供名称、描述、适用场景、状态和版本等轻量元数据。
- 目录可以在会话初始化时作为稳定内容缓存；当前消息、L1、L2、L0 Tool 结果和联系人范围每轮刷新。
- 用户明确选择优先；没有用户选择时，程序可以缩小目录，模型在有效目录内选择。
- 每轮最多加载一个 Skill，也可以不加载；没有匹配或加载失败时使用默认回复策略。
- 完整 Skill 正文只在需要时加载一个不可变版本；辅助 Resource 只读取该版本内预先允许的相对路径。
- Skill 不能直接读取数据库、其他联系人、任意文件、外部 URL 或原始聊天资料，不能注册 Tool/MCP/Shell，不能执行脚本，不能写 Memory 或发送消息。
- Skill 目录缓存绑定 Owner、Skill 库修订和当前运行范围；Skill 更新、停用、删除、联系人切换或范围变化后失效。

### 7. 消息、记忆和后台任务

- 当前真实收到的消息和用户实际发送的最终消息写入 L0/Message；模型候选稿单独保存，不进入 L0。
- 历史导入和增量同步通过同一消息写入和去重语义；来源 ID、消息 ID 或等价幂等键防止重复。
- L0 记录保留发送者、时间、方向、联系人、会话和来源；原始证据只追加，修正通过上层对象或新版本表达。
- 消息成功提交后再创建异步记忆提取、L2 更新和索引任务；这些任务失败不回滚已提交的消息，也不阻塞当前回复。
- 自动提取结果必须带来源、置信度、风险和有效期；低风险明确资料可按规则标记 `auto` 采纳，敏感关系推断在用户确认前保持候选状态。
- 用户明确纠正记忆时创建新的用户确认版本，旧版本保留但标记失效；冲突不能静默覆盖。
- L0/L1/L2 和 Skill 的删除、失效、更新会使相关索引、缓存、Tool 结果、运行摘要和旧 `ReplyContext` 失效，并由可重试后台任务完成清理或重建。
- 后台任务按既有任务、步骤、租约、幂等和重试规则运行；任务记录不保存完整聊天正文。

### 8. 候选回复与人工发送

- Runtime 返回结构化候选，包含文本、依据引用、可选 Skill 标识和必要的风险/不确定性信息。
- 程序拒绝不存在于本轮上下文、跨联系人或已删除来源的引用；无效结构化结果不得直接展示为可发送结果。
- 候选依据和实际使用的 Skill 版本在应用内可查看，但不把内部检索分数或工具细节发送给联系人。
- 候选始终只在应用内展示和编辑；Agent 不拥有外部聊天发送 Tool。
- 用户修改并亲自发送后，只有最终实际发送内容才可以进入后续 L0 和记忆提取；未发送候选不参与长期记忆。

### 9. 隐私、缓存和追踪

- 外部模型只接收经过联系人范围、字段白名单、Token 预算和供应商政策校验的必要文字。
- 供应商地域、留存、训练使用、删除能力和加密策略未知或不满足要求时，生产调用必须拒绝或改用已批准的本地路径。
- 可缓存系统规则、Tool 说明、Skill 目录和版本元数据；不可缓存包含旧联系人资料的完整 Prompt、历史 L0 全文、已删除资料或旧 Skill 正文。
- 每轮记录最小的 Memory/Skill/检索版本、引用 ID、工具状态、延迟和用量；普通日志不复制完整 Prompt、聊天原文、Skill 正文或联系人名称。
- 检索记录和出站台账遵守现有留存、查看和删除策略，删除后必须验证对应内容不可再检索。

### 10. 实施顺序和回退

- 第一阶段复用现有 ReplyContext 和 Port，补齐当前联系人近期消息、相关 L1、L0 相关性搜索和会话顺序查询的统一行为。
- 第二阶段接入现有 Skill Library 的目录、不可变版本、按需资源和缓存失效，并完善 L2 目录的异步生成和版本验证。
- 第三阶段完善全文检索评测、混合排序和向量补充；向量能力必须由数据评测触发。
- 新链路通过 feature flag 逐步启用，异常时回退到当前消息加最近对话的基础模式。
- 不照搬 TencentDB 的表结构；现有消息、候选记忆、确认记忆、联系人目录、回复和 Skill 数据模型继续作为权威模型。

## Testing Decisions

### 测试 Seam

- 主要测试通过现有 `ReplyGenerator` 的公开生成接口完成，验证从已验证联系人请求到候选回复结果的外部行为。
- `ReplyContextPort`、`RetrievalPort`、`SkillPort`、模型 Runtime 和存储 Adapter 作为注入的替身或具体实现，不把内部字符串拼接、SQL 语句或模型 Prompt 私有细节作为测试目标。
- 当需要定位具体模块时，使用同一主 Seam 下的 Adapter 测试；只有数据库索引、删除事务或 Skill 包校验等存储/文件行为才增加较低层的集成测试。

### 好测试的标准

- 测试验证用户能观察到的候选、依据、错误、隔离、删除和发送边界，不验证某个函数内部恰好调用了几次。
- 测试使用合成或匿名化联系人和消息，不使用真实聊天记录、真实联系人名称或真实凭据。
- 每个查询结果都通过真实的联系人范围和来源校验；测试不能为了方便绕过这些约束。
- 测试覆盖正常路径、空结果、冲突、过期、删除、超预算、工具失败、Skill 失败和重复任务。
- 涉及 PostgreSQL 的测试在真实迁移后的隔离测试库中运行；没有端到端验证时，不宣称真实聊天渠道已经集成可用。

### 必须覆盖的行为

1. 同一联系人请求能够得到当前消息、近期对话和相关有效 L1。
2. 历史 L0 默认不进入初始 Prompt；模型调用相关性搜索后可以获得 Top-K 原文。
3. 相关性搜索和时间顺序查询返回不同职责的受限结果。
4. 查询结果包含角色、时间、会话和来源标识，并在结果超限时稳定截断。
5. 空结果不会导致模型编造历史事实。
6. L0/L1 工具不能通过参数读取其他联系人或其他 Owner。
7. L0 中包含类似指令的文本时，模型仍将其作为数据而不是系统指令。
8. L1 只接受有效状态、有效期和完整来源；待确认、失效和已删除资料不会进入 Prompt。
9. L2 版本过期、底层 L1 变化或来源删除后，旧索引不能继续被使用。
10. 首版 SQL/全文检索可用；向量不可用时自动回退，原始 Message 不变。
11. Skill 目录先加载，完整正文按需加载；每轮最多一个 Skill，没有匹配时走默认策略。
12. Skill Resource 只能读取当前版本允许的资源，路径遍历、符号链接和脚本能力被拒绝。
13. Skill 不能写 Memory、改变 Tool 权限、访问其他联系人或发送外部消息。
14. 当前联系人变化、Skill 修订变化或来源删除后，动态缓存和旧上下文失效。
15. 当前真实消息写入后才触发异步提取；候选草稿不会进入 L0 或长期记忆。
16. 自动采纳记录 `auto` 和来源；敏感关系推断在适用决策生效后仍需要用户确认。
17. 重复导入、重复同步和后台重试不会产生重复实体或重复派生索引。
18. 冲突记忆保留版本和来源，不能静默覆盖。
19. 删除 L0、L1、L2 或 Skill 后，相关索引、缓存、Tool 结果和 ReplyContext 不可继续使用。
20. Runtime 的候选引用只能来自本轮真实读取的证据，并且经过联系人范围校验。
21. 结构化输出失败、Tool 超时和 Skill 加载失败会安全回退，不会自动发送。
22. 用户编辑并亲自发送的最终文本可以进入后续 L0；未发送候选不会进入。
23. `ReplyGenerator` 的结果包含可查看的依据和实际 Skill 版本，但不泄露其他联系人或内部 Prompt。
24. feature flag 关闭或新链路故障时，基础当前消息加最近对话模式仍然可用。

### 质量指标

- 跨联系人或跨 Owner 泄露必须为 0。
- 记录空结果率、降级率、引用纠错率、候选拒绝率、Tool 次数、Token、延迟和失败率。
- 记录 Skill 目录命中、完整加载失败和用户改选率。
- 只有评测证明全文检索不足时，才进入向量检索评估；具体阈值由合成评测和用户反馈确定。

## Out of Scope

- 直接部署或运行时依赖 TencentDB、TencentDB Gateway 或完整 MemoryProxy。
- 复制 TencentDB 的数据库表结构、身份模型或所有代理层能力。
- 把聊天数据库改造成独立的通用 Resource 记忆层。
- L3 人格画像和未经用户确认的稳定人格推断。
- 初始 Prompt 注入全量历史 L0、全量 L1 或全部 Skill 正文。
- 独立向量数据库、强制 Embedding 服务和首版 Rerank 服务。
- Skill 脚本执行、任意文件访问、网络下载、Tool/MCP 自注册和外部聊天发送。
- 模型自动修改联系人、Memory、Skill、权限或系统设置。
- 未发送候选稿进入 L0、`memory_candidate` 或 `confirmed_memory`。
- 长周期关系分析任务、开放式自治 Agent、跨联系人知识合并和后台全局聊天抓取。
- 真实聊天渠道的自动发送和没有人工确认的外部操作。
- 端侧和云端加密、供应商地域、留存及密钥管理的具体实现；这些仍按现有隐私规格作为生产前置条件单独完成。

## Further Notes

- 本规格是对当前讨论和 TencentDB 研究结果的可执行整理，不代表规格范围内的所有能力已经实现。
- TencentDB 的机制参考包括：L0 对话工具查询、相关性搜索与时间顺序查询分离、Skill 目录与正文渐进加载、稳定注入内容缓存，以及每轮动态上下文处理。NotAlone 仍以自身联系人、来源和删除契约为最高约束。
- 本规格确认的唯一主测试 Seam 是 `ReplyGenerator` 的候选回复生成入口；实现任务应优先在这个 Seam 上形成可观察的纵向切片。
- 现有 ADR-002 关于关系记忆“风险字段不阻塞自动采纳”的文字，与本规格“敏感关系推断需用户确认”的决定存在冲突。该冲突必须通过新增或修订 ADR 解决，不能由实现者静默选择；在复审完成前，相关实现任务应先处理该决策前置项。
- 现有 ADR-005、ADR-006、ADR-009、ADR-010、ADR-011、ADR-014、ADR-015 和 ADR-019 的联系人隔离、来源证据、`ReplyContext`、有界 Runtime、Skill 版本、异步任务、目录重建和受控 Resource 约束继续有效。
- 当前研究笔记提供 TencentDB 的源码和官方来源索引；研究证据只能说明参考项目的行为，不能证明 NotAlone 已经完成集成或真实聊天渠道端到端可用。
- 规格发布后可以继续拆成 L0/L1 检索、Prompt 上下文、Skill 按需加载、L2 异步索引、删除失效和评测等独立任务；任务之间应明确真实阻塞关系。
