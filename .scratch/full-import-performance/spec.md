# 完整导入性能优化

Triage: ready-for-agent
State: resolved

## Problem Statement
上一轮追踪批写明显减少 SQL，但完整历史导入收益约 4%。在最新 main 7e0b086960f82320216ad983235f01dcdfb394de 上，10000 条完整导入中业务写入与追踪保存约占 78%；追踪实际 JSON 约 29 MB，不能用小型过滤记录代替测量。

## Solution
保持同一联系人导入、原子事务和完整可追溯资料，分别优化业务写入及概览失效、真实追踪及预览流水线。最终统一提供相同合成负载的完整导入前后时间、尾延迟、Python 峰值内存与数据库工作量。

## User Stories
1. 用户导入已确认联系人的历史时，更快完成完整提交。
2. 用户在小批和大批导入后都能查看完整、顺序正确的原始、规范化及处理追踪。
3. 用户重复导入时仍能获得准确的新增与复用结果。
4. 用户删除资料后，追踪及概览不会因并发写入重新出现。
5. 用户预览文件时无需付出不会保存的逐条追踪构造成本。
6. 用户在文件发生变化后必须重新确认，不能复用旧预览正文。
7. 用户获得可复现的实际完整导入数据，了解吞吐和内存的取舍。

## Implementation Decisions
- 两路独立执行，均基于上述最新 main；根负责人统一基准、审查、合并和验证。
- 业务路使用有界多行批写替代消息、微信元数据及来源引用的逐行执行；目标每块最多 500 行或约 2 MiB，超大单行保留且不截断。
- 新迁移仅调整消息和来源引用的 INSERT 概览失效为语句级 transition table，保留原有 UPDATE/DELETE 语义、作用域、来源标识依赖和 owner 锁顺序。
- 追踪路比较真实负载下 VALUES 与 COPY 的成本，按证据选用；紧凑 UTF-8 序列化及减少无用中间表示不得破坏不可变快照和公开接口。
- 预览可以不构造逐条 ProcessingRecord；提交必须重新读取文件并验证字节 SHA、确认身份和联系人范围。
- 读取按实际字节有界增长，保留同一普通文件 fd、64 MiB + 1 累计上限、短读继续与完整字节摘要；不对小文件预先请求完整文件上限的缓冲区。
- 每次 capture_execution 仍实际读规则文件并计算摘要；不更改每条追踪的规则捕获粒度。
- 事务、墓碑整批拒绝、捕获 UUID、位置、消息与来源回执、异常回滚和重复导入行为保持。
- 所有开发数据均为本机随机自有测试库与合成资料；不操作业务库，不调用外部模型。

## Testing Decisions
使用已经随方案确认的现有公开 Seam：import_file/build_preview、ProcessingRecord 公开方法、source processing store/save_processing_batch、overview store 的公开读写及删除服务。只断言可观察结果，不绑定私有实现形状。沿用现有 PostgreSQL 集成测试，覆盖跨批、超大行、重复导入、联系人隔离、删除竞态及事务回滚。性能计数与计时分开；时间不启用 profiler/tracemalloc，内存独立采样。真实 dev App 合成导入与重复导入验收，由根负责人协调独占桌面。

## Out of Scope
跨执行正文或摘要缓存、规则文件按批捕获、全流式导入重构、增量提交、模型或依赖变更、真实私人资料、正式库迁移、发布打包、push、远端分支和 PR。

## Further Notes
基线 10000 条约 4.18 秒仅用于定位，不作为最终比较。最终以同一个版本化基准同时测量基线和集成提交，保留全部样本、输入摘要及自有数据库清理凭据。未经端到端验证不得宣称桌面集成有效。

## Answer

两路均由最新 main 7e0b0869 启动，最终集成 93b0b886：业务及追踪同事务 COPY、语句级 INSERT 概览失效、紧凑不可变快照、预览去掉无用追踪及有界读取分配。独立 Standards / Spec 均 0 项发现。

最终相同合成文件、每版每规模 21 个交错样本，完整导入中位数：100 条 0.050756→0.040214 秒（-20.8%），1000 条 0.411367→0.277308 秒（-32.6%），10000 条 4.383175→3.284805 秒（-25.1%）。万条 P95 5.417937→3.849040 秒，Python 峰值 115.08→107.06 MiB。预览与数据库工作量另列，未把后台模型提取计入完整提交时间。

83 项相关集成、52 项导入单元通过，根负责人最终组合再跑 52 单元与 6 业务集成通过；已知全量基线失败、第一版实际 App 成功及最终 UI 双实例限制均明确记录。12 份原始计数/时间/内存/阶段 JSON 的清理标志全部通过；额外查询 18 个精确自有库均不存在。详见 [报告](report.md)、[验证](verification.md)、[审查](review.md) 及 results/ 原始数据。
