# 完整历史导入性能对照

万条完整导入中位耗时 4.383→3.285 秒，减少 25.1%；P95 5.418→3.849 秒，减少 29.0%。

## 测量范围

基线为本轮开始时最新 main `7e0b086960f82320216ad983235f01dcdfb394de`。同一版本化基准分别归档两版源码和迁移，在本机 PostgreSQL 16.14、Python 3.12.13、psycopg 3.3.4、arm64 上运行；连接走本地 Unix socket。

最终被测代码为 `93b0b88617b9016e360e77fb68dbddd78fe7f2c4`，随后提交的报告和原始 JSON 不改变被测生产代码。

完整导入计时从读取 JSONL 到原子事务提交，包含解析、规范化、业务资料、真实完整追踪和回执，不包含确认预览或提交后的后台模型提取。输入为固定的中文合成资料；每种规模对照两版的字节 SHA 必须相同。每轮数据库独立，结束精确删除并核验，不读取私人联系人或业务库。

每版、每种规模保留 21 次样本，分三块交错运行：旧/新、新/旧、旧/新，每块预热一次再测七次。报告中位数和 nearest-rank P95。计时不启用计数、profiler 或 tracemalloc；SQL/协议计数、Python 峰值内存、阶段定位分别独立执行。Python 峰值不是进程 RSS，协议消息、Sync 和驱动等待次数不是网络往返次数。

| 100 | 0.051 | 0.040 | 20.8% | 0.059 | 0.044 |

## 实现与数据边界

- 消息、微信元数据和来源引用按最多 500 行／约 2 MiB 写入，超大单行完整保留；全部仍在同一事务，保留约束、完整回滚、来源关联和重复导入行为。
- 089 仅将消息及来源引用的 INSERT 概览失效改为语句级 transition table；UPDATE/DELETE 保留原有语义，依赖闭包、联系人范围和 owner 锁保持。
- 真实逐条追踪使用 COPY 和紧凑 UTF-8 JSON，保留不可变快照、UUID、顺序、回执和整批墓碑检查。JSON 编码量下降不能解释为 PostgreSQL JSONB 存储等比下降。
- 预览不构造不会保存的逐条追踪；提交重新读取文件并校验字节摘要和确认身份。每次规则捕获依旧实际读取规则文件并计算摘要，没有按修改时间或跨执行缓存。

## 优化选择依据

第一版集成 `dfb80f88` 已完成同样的 21 样本交错对照：万条完整导入中位数 4.468→4.189 秒，减少 6.2%。没有用 SQL 数量的大幅下降替代这项实际耗时结果。

继续检查发现，三类业务多行 VALUES 每 500 行分别有 4000／3500／3000 参数；驱动会反复转换超出缓存门槛的占位符。业务写入仍占显著阶段时间，因此进一步用同事务 COPY 避免巨型占位符转换，再重新测量完整导入。阶段包装数据仅作为选择依据，不并入最终时间样本。

此外，小文件与万条预览在第一版的 Python 峰值都约 64 MiB。读取器一次请求“文件上限 + 1”会先申请该容量，遮蔽后续对象减少；进一步改为累计有界分块读取，只在空读时结束，保留读取期间文件增长的超限检测、实际字节 SHA 和安全错误映射。该调整不改变先完整读取、再解析和原子提交的流程。

## 复现入口

从仓库根目录使用工程约定的 Conda NotAlone Python，以下命令得到新版第一块七个保留样本（基准内部另做一次预热）：

```sh
PYTHONHASHSEED=0 NOTALONE_DISABLE_DOTENV=1 PYTHONDONTWRITEBYTECODE=1 \
python backend/benchmarks/source_processing_batch.py \
  --repo . --revision 93b0b88617b9016e360e77fb68dbddd78fe7f2c4 \
  --mode time --sizes 100 1000 10000 --profiles import_file preview \
  --samples 7 --output new-time-1.json
```

分别对上述基线和最终提交按“旧/新、新/旧、旧/新”运行三块，输出文件使用不同名称，再按规模合并各版 21 样本。单独改用 `--mode memory` 测峰值；`--mode count` 和 `--mode phases` 只传 `--profiles import_file`。基准拒绝外部连接覆盖，精确清理自身随机数据库；无需桌面、外部模型或业务数据。
