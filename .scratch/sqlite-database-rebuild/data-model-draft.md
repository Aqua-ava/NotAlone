# SQLite 重建：数据模型讨论草案

State: open

> 对应[数据库重建规格](spec.md)。本文记录拟保存的数据、关系、约束和事务；字段及表名均为提案，尚未创建或验证。更具体的候选表、精简依据和旧结构映射见[数据库精简方案](schema-plan.md)；产品操作与行为见[独立规格](../sync-memory-behavior/spec.md)。

## 数据边界

用户已确认一个 SQLite 业务数据库保存用户及所有联系人的业务资料。按 owner 和联系人隔离私密资料；消息及来源、本人和联系人记忆、证据、版本、处理进度、任务及删除链均需明确归属。初始 SQLite 库为空，旧 PG 业务数据不迁入；开发与测试使用独立数据库。

## 核心数据关系草图

以下是逻辑关系，供继续讨论；线条不代表已确定的 SQLite 表、列名或实现方式。

```text
用户（owner）
 ├─ 联系人 A ─ 会话绑定 ─┬─ 消息 A1 ─┬─ 来源引用 ─ 来源记录
 │                       │           └─ 来源引用 ─ 另一来源记录
 │                       └─ 消息 A2
 │                            └─ 证据 ─ 联系人 A 的记忆／候选
 ├─ 联系人 B ─ 会话绑定 ─── 消息 B1
 │                            └─ 证据 ─ 联系人 B 的记忆／候选
 └─ 本人记忆 ── 证据 ── 属于 A 或 B 的有效消息和来源
```

- 一条规范消息可有多个来源引用；一个来源记录只归属一位联系人。来源引用的两端必须属于同一用户和联系人。
- 联系人记忆、候选和直接证据归属于该联系人，不能引用另一联系人的消息；本人记忆归用户，允许关联不同联系人的真实来源，但每条来源依赖仍需核验原联系人身份。
- 某来源失效后，不能仅凭共享数据库或另一来源自动恢复旧证明；是否保留底层消息、撤下或重新核验记忆，按真实有效依赖与删除合同处理。
- 完整提取追踪单独关联实际参与窗口、来源及结果；无正文模型调用回执是另一类记录。最终约束须通过外键、唯一性约束与必要的业务复验共同验证，不能只依靠展示名称或页面筛选。
- 对身份暂时无法核验、因而不能判断是否重复的消息，保留经授权联系人范围内的原始记录供后续核验，隔离于正常消息与生成依据；关联来源并支持清空和删除。可能需要独立表或受控状态，尚不能据此确定最终表数。

## 实体与关系提案

下表是逻辑实体，不要求一行对应一张表；具体是否合并须由约束和业务接口决定。归属于联系人的记录必须保留并核验 `owner_id + contact_id`，不能只靠连接后过滤昵称。

| 逻辑实体／候选名称 | 保存的事实 | 主要关系与约束 |
| --- | --- | --- |
| `owner`、`contact` | 用户与稳定联系人身份、展示资料及资料修订 | 昵称变化不换身份；联系人不能通过消息文本猜测建立 |
| `owner_channel_identity`、`channel_identity`、`conversation_binding` | 微信账号、对方稳定渠道身份及已验证桌面绑定 | 绑定同时包含用户、渠道账号、联系人和外部会话；账号变化不得复用旧读取授权 |
| `sync_scope`、联系人选择记录 | 同步总开关、逐人选择与授权版本 | 总开关不等于选人；恢复设置不自动加入新私聊或撤销排除 |
| 历史检查点、增量检查点、缺口记录 | 已可靠提交的读取位置、覆盖状态和失败事实 | 按联系人及实际账号／绑定范围保存；历史位置、消息身份、显示顺序是三个概念 |
| 联系人清空记录、逐消息自动读取抑制 | 无正文清空边界、单调清空代次、必要的稳定消息身份 | 清空无已存消息时仍有效；重启、重选和重绑不自动解除；不能只保存一个“最后删除时间” |
| 明确历史恢复操作 | 用户确认的联系人、账号、范围、执行状态与授权代次 | 只放行本次恢复的全部本机可读历史；不恢复旧来源 UUID、证明或已删除记忆 |
| 来源记录、`local_wechat_observation` | 一次单联系人 CLI 捕获的来历、读取模式、工具版本和必要原始引用 | 历史、增量、补齐及明确历史恢复可区分；原始载荷的最小保留字段另行核验，不默认复制完整 CLI 输出 |
| `message`、渠道消息元数据 | 文字正文或媒体占位、发送方、原始时间与可靠消息身份 | 不用正文哈希猜测重复；缺失时间保留未知；媒体占位不成为记忆输入 |
| `source_record`（修订旧来源引用的候选） | 一次原始出现，属于来源批次，核验后可关联规范消息 | 支持先保存待核验原始记录；同一消息可关联多次出现，已关联双方须属于同一用户和联系人。具体基数及键见消息存储细化草稿 |
| 本次点击的协调记录（候选名 `memory_processing_run`） | 启动时选中的联系人、本次控制意图和各范围轮次关联 | 只协调控制与展示，不成为跨联系人聊天容器；启动后新增勾选不扩张本次范围 |
| `memory_processing_scope`、`memory_processing_round` | 各联系人／本人处理范围、固定轮次、阶段和控制代次 | 本人范围归 owner，与联系人轮次独立识别；协调记录关联它们，不伪造同一种进度单位 |
| 本轮目标、提取窗口成员 | 本轮文字目标，以及仅作理解的有界前文 | 显式标记 target/context；冻结实际身份与版本，不只存一条可能持续变大的查询条件 |
| 消息处理回执、阶段回执 | 哪些目标已完成提取核验，各适用阶段是否完成 | “无新记忆”可为成功；提取成功后主题失败，只补未完成阶段，不再次提取；成功不由产出条数推断 |
| `memory_candidate`、候选证据与核验记录 | 候选、实际参与窗口、直接证据、拒绝／待定／采纳结果 | 理解上下文、直接证据与完整删除依赖分开记录；自动采纳标记 `auto` |
| 记忆提取追踪及其事件、来源依赖 | 提取窗口、实际模型输入输出、阶段事件、候选关联和过程结果 | 用户确认新库保留完整过程，以便回看和排查；含正文的追踪与无正文模型调用回执分开，并按完整参与窗口及来源依赖清理 |
| `confirmed_memory`、`owner_memory` 及版本／人工决定 | 关系资料、本人资料、修正、撤销和来源支持 | 本人记忆不复制到每个联系人；其来源仍回指真实联系人，删除时不能因 owner 归属而豁免 |
| 场景文档、长期画像、目录与概览依赖 | 已有业务中的 L2/L3 内容、版本与底层资料依赖 | 主题／画像内容与无正文概览清单分开；可重建投影不成为独立事实来源，来源删除先失效 |
| 助手会话、输入、候选版本、选择与修改 | 用户与助手的讨论及候选回复历史 | 联系人隔离；复制或选择不证明已经发送；实际会话文件仍有独立删除路径，不宣称全部可塞入 SQLite |
| Skill 业务状态与版本引用 | 启用、发布状态、校验摘要和受管文件引用 | 沿现行目录权威合同保存用户 Skill；不把重置业务库解释为删除用户维护的目录 |
| 用户明确保存的长期表达偏好及版本 | 用户主动维护的表达偏好、适用范围、来源和删除状态 | 独立于关系记忆和 Skill；可以按用户或具体联系人适用，旧 PG 偏好不迁入空库 |
| `background_task`、步骤、租约 | 历史同步、处理、删除等工作的执行状态及领取事实 | 任务与轮次不互相冒充；领取、续租、结果提交必须复验有效控制与清空代次 |
| `model_call_receipt`、`outbound_ledger_entry` | 物理模型尝试、请求状态、用量和最小出站事实 | 调用返回、业务提交、目标成功分别记录；未知调用不自动重放；不得保存聊天正文或任意错误载荷 |
| 删除任务、存储面清理步骤、最小删除凭证 | 已请求、处理中、失败及复核完成的真实删除进度 | 数据库、会话文件和受管副本分别核验；只有不可检索复核通过才算删除完成 |

## 消息与来源

同一条微信消息可能先由增量读取，再由历史分页或补齐重复读取。草案保留一条规范消息与多个来源引用，不把“每次 CLI 返回一条”直接变成新的聊天记录。

稳定身份的唯一性必须包括实际用户、渠道账号、联系人及适配器所能保证的消息标识组合。`local_id` 允许重复或下降，不能单独成为全局唯一键或时间水位；不透明 cursor 只按 CLI 合同用于续读，不做数值比较。准确的 SQLite 唯一约束需在锁定 CLI 合同查证后确定。

保存可靠排序信息及确定性同序规则，不用来源 UUID 或插入时间冒充原始发送时间。历史缺口、时间未知及身份不可靠须可区分。

## 清空的存储与提交边界

- 保存联系人范围的删除请求、清空代次、必要的无正文自动读取抑制和清理状态；即使尚无已保存消息，清空代次也须有效。
- 在同一事务中更新删除资格和控制代次，撤销旧历史目标及相关处理的写入资格；读取和处理结果提交时复验当前代次、来源、账号及绑定。
- 消息、来源引用、证据及其派生资料按依赖关系清理或失效；数据库、助手会话和其他文件的清理分别记账，避免假设跨存储面原子提交。
- 记录明确历史恢复操作的范围、状态和来源；恢复不直接抹去全部旧抑制或复用旧来源。
- 精确历史截断依赖渠道可证明的边界。现有抑制只覆盖已捕获的稳定消息身份；来源集合令牌不能替代单调清空代次。不用秒级时间或单独的 local_id 假定准确分界。

清空及重新同步的完整业务行为和执行提案见[独立产品规格](../sync-memory-behavior/spec.md)。

## 处理进度的存储约束

处理协调记录应关联各联系人和本人范围的轮次，以及固定目标和仅作上下文的消息；实际引用、来源依赖和资料版本须可追溯。目标结果、阶段结果、任务控制与模型调用回执分别保存，正常无产出与失败、未知结果可区分。消息集合不能仅用时间上界代替，提交须复验范围、来源、版本与控制代次。

联系人来源失效时，本人资料及跨来源结果须按真实依赖撤下或重新核验，不能只移除联系人标签。暂停、取消、启动时机等产品语义见[独立规格](../sync-memory-behavior/spec.md)。

## 事务与持久化边界

| 操作 | 应原子提交的内容 | 外部等待 |
| --- | --- | --- |
| 保存一个 CLI 页 | 当前账号／授权／开关／代次复验，过滤后的来源与消息、引用、通知及可靠检查点 | CLI 读取在事务外；提交时重新验证 |
| 启动手动处理 | 本次选择快照、目标身份、关联轮次与控制代次 | 事务内不请求模型 |
| 领取／提交一个处理小批 | 领取租约；提交时复验范围、代次、来源和版本；保存结果、来源依赖及阶段回执 | 模型在事务外，迟到结果不获得新资格 |
| 请求清空 | 删除请求、清空代次、旧读取／处理失效与立即不可检索状态 | 文件删除、可靠渠道边界建立须有可恢复步骤，不假装跨文件与数据库原子 |
| 完成清理 | 每个存储面清理回执、残留复核及最终删除状态 | 失败保留未完成状态并允许幂等继续 |

驱动、SQLite 运行时版本、数据路径、外键启用、文本／时间／数值表示、唯一键、短事务与写入调度、WAL、异常退出和损坏恢复都尚未选择或验证。上述提案没有照抄 PG 锁，也不预设某个驱动已经支持现有业务语义。

## 待设计

- SQLite 运行时、驱动、数据路径、外键、数据类型、唯一键、索引、WAL 与故障恢复。
- CLI 实际身份和游标合同，以及历史截断所需的可靠边界；不可用时需明确受阻或覆盖缺口。
- 本人处理结果的来源依赖、各阶段回执、未知模型调用与迟到结果的持久化资格。
- 用户已确认新库继续保存完整记忆提取追踪，沿用 [ADR-037](../../architecture/adr/037-complete-memory-extraction-trace.md) 的可回看与来源删除边界。具体字段、窗口依赖、原始载荷保留方式和 SQLite 存储接口仍需设计与验证；不能用无正文模型调用回执替代含正文的过程追踪。
- SQLite 与助手会话文件、Skill 文件、缓存、任务产物之间的删除接口和失败恢复。
- 旧库和副本识别、停机、切换与复核，采用隔离合成资料验证。

## 已查证的运行时事实

- 项目声明 Node.js ≥24；桌面后台使用 Electron 可执行文件以 Node 模式启动，不能用开发终端的 Node 版本代替实际桌面内嵌版本。后续只读版本探针已确认当前开发 Electron 44.7.0 内嵌 Node 24.21.0、SQLite 3.53.4；结果仅覆盖当前已安装开发依赖，版本与接口依据见[运行时研究](../../research/sqlite-runtime-baseline.md)。
- Node 自带的 `node:sqlite` 是待评估候选，不是已选驱动。Node 24 不同小版本的接口状态和能力有差异，`DatabaseSync` 同步执行，必须核验实际运行时并测量后台阻塞与并发行为。依据：[Node 24.0 SQLite 文档](https://nodejs.org/download/release/v24.0.0/docs/api/sqlite.html)、[Node 24 最新文档](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html)。
- SQLite 官方记录了旧版本在特定多连接并发写入和 checkpoint 条件下的低概率 WAL 损坏问题，3.51.3 及部分修复回补版本已修复；若选用 WAL，须先核验实际内嵌 SQLite 版本和连接方式，不假定本项目受影响或已规避。依据：[SQLite WAL 文档](https://www.sqlite.org/wal.html#the_wal_reset_bug)。
