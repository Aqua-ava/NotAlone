## Problem Statement

当前后端的业务查询、事务、任务领取和桌面启动依赖 PostgreSQL。用户希望使用本机 SQLite，减少独立数据库服务的维护，并从空库重新开始。

## Solution

建立独立的 SQLite 初始结构、版本管理和存储接口，覆盖当前仍需的业务资料与数据生命周期，不迁入旧 PostgreSQL 业务资料。完成隔离验证并准备切换时，精确识别并按已确认范围清理旧 NotAlone 业务库及应用保存的旧业务副本；不将启动失败当作重新清空的理由。

同步、聊天清空和记忆处理的产品行为记录在[独立规格](../sync-memory-behavior/spec.md)。数据库为这些行为提供必要的数据、隔离与事务能力；产品行为的实现与验收在其规格中单独处理。

## User Stories

- **US-01**：作为用户，我希望 App 自行使用本机 SQLite，以减少独立数据库服务的维护。
- **US-02**：作为用户，我希望新数据库从空白开始，以重新建立联系人和资料。
- **US-03**：作为用户，我希望旧 NotAlone PG 业务库在切换时被删除，而不是迁移或保留为旧库备份。
- **US-29**：作为用户，我希望从零重建也清理应用保存的旧助手会话、含聊天内容的缓存与派生文件，同时保留模型密钥、我维护的 Skill 和电脑上的原始资料文件。
- **DB-05**：作为用户，我希望普通重开、升级与重装沿用同一SQLite实例，以保留新库形成的资料和删除决定。
- **DB-06**：作为用户，我希望库损坏、结构漂移或版本不兼容时保留现场并明确报错，以免被自动换空库。
- **DB-07**：作为用户，我希望本人和多位联系人的资料共用一个业务库但严格隔离，以免回复和证据串人。
- **DB-08**：作为用户，我希望同一消息被重复捕获或补齐身份字段时保持内部身份，以免重复保存或处理。
- **DB-09**：作为用户，我希望查看记忆提取的完整输入、输出、阶段和来源，以理解结果并排查问题。
- **DB-10**：作为用户，我希望清除来源时同时处理受影响的追踪、记忆、助手副本和媒体，以免只删表行仍留下内容。
- **DB-11**：作为用户，我希望任务暂停、中断和未知调用结果分别记录，以免重开或重试重复调用模型。
- **DB-12**：作为用户，我希望文件发布或清理中断后能按原操作恢复，以免新结果被旧清理误删。
- **DB-13**：作为用户，我希望身份、约束或事务提交失败时保留可核验状态，以免不完整资料进入生成依据。
- **DB-14**：作为用户，我希望切换前先验证目标和清理范围，以免误动微信原件、模型密钥或我维护的Skill。


## Implementation Decisions

- 用户明确要求按关系型数据库设计原则细化方案：先定义实体、关系、函数依赖、主键／候选键、外键和生命周期，再决定拆表或合表。普通业务事实以第三范式为设计基线；范围隔离、历史快照或经测量需要的冗余必须说明用途及一致性约束。表数本身不能证明设计合理。
- 新建 SQLite 初始结构及后续版本记录，不重放或伪造 PostgreSQL 迁移账本；原迁移和现有业务合同作为设计参考，不要求逐表照搬。
- 一个 NotAlone 本机业务数据库保存用户及所有联系人的业务资料。联系人之间仍以 `owner_id + contact_id` 和必要的关系约束隔离；开发和测试使用独立数据库，不连接或清空用户的业务库。一个业务数据库的决定不意味着 SQLite 不会产生 WAL 等辅助文件，也不改变受管助手会话或用户 Skill 文件的既有存储边界。
- 按用户、联系人、渠道身份、授权、来源、规范消息、删除状态、记忆、证据、任务和调用记录等职责建模。联系人资料按 owner_id + contact_id 隔离，昵称和备注不作为身份。实体、关联和存储约束见[统一数据库草图](greenfield-design.md)。
- 新库继续保存完整的记忆提取过程，包括实际输入输出、阶段结果和来源关联，供回看与排查；含聊天正文的追踪随相关来源及其完整参与窗口的删除范围清理，不能仅靠无正文模型调用回执替代。
- 重构直接依赖 PostgreSQL 查询、锁与事务的存储调用，重新设计领取、并发和提交前复验；写事务保持短小，不在事务中等待外部模型或 CLI。
- 统一逻辑设计采用node:sqlite专用Worker、受控目录、短事务、WAL与版本账本；运行时和约束已有合成证据，完整业务DDL、权限、并发负载、故障恢复和升级按隔离验收执行，不宣称已加密或产品集成通过。
- 新库准备与隔离验证完成后，停止并核对旧运行时及在途任务，精确识别旧业务库和应用持有的旧业务副本。保留模型密钥、用户维护的 Skill 和电脑上的原始资料文件；不保留旧业务库作为本次重置的备份。
- 分别记录数据库、库外助手会话、缓存和受管文件的清理及复核状态，不能把删数据库行视为所有存储面已清理。

## 与其他方案的衔接

- 当前没有手动文件导入产品入口；来源表服务CLI捕获/追溯，不因保留来源实体恢复旧导入流程。manual_confirmation是已确认联系人下的回复定位确认，不授予微信读取或创建联系人权限。
- scope_mode保留表达渠道授权的能力，不表示本轮启用全部私聊。当前首用和同步仅逐人选择；旧全部范围不能迁入空库，后续扩大范围需明确决定。
- 文字同步中的非文字消息仍只占位；媒体Q1–Q11已确认并整合message_media/media_extraction_attempt/media_file，统一草图共77表。手动提取的受管文件存目录、不塞进message/capture_record，也不自动入记忆。
- 官方DSH加载及最小Skill业务关联不因首用或云端方案恢复学习/审核/方法级策略表；原目录与未知状态保护继续有效。
- 云端工程已取消，不列产品待办；本机BYOK和来源删除路径维持，不恢复云端认证、对象存储、代理模型或多设备范围。

## Testing Decisions

- 测试边界沿用既有存储服务和实际业务操作入口；跨同步、记忆、媒体与删除的组合行为在同一隔离数据库及受管目录验证，不为逐表实现另造测试接口。最低结构层验证外键、NULL分支与事务；业务层验证隔离、原子发布与迟到写入；桌面层验证可见状态。合成机制、真实渠道和产品验收分别报告。

- 使用隔离合成资料和临时 SQLite 库验证空库初始化、版本升级、中断恢复、并发写入及损坏或启动失败时不替换旧资料。
- 验证联系人隔离、来源多对多引用、去重、外键与唯一约束、控制代次、任务领取、迟到写入拒绝及依赖删除。
- 在同一隔离测试库中建立多个联系人和用户本人资料，验证跨联系人读取、证据引用和级联清理不会串数据；同时验证本人资料可以安全关联不同联系人的真实来源。
- 使用合成资料验证完整记忆提取追踪的保存、回看与来源关联，以及删除直接证据或仅作上下文的参与来源后，对受影响正文追踪和证明的清理；无正文调用记录按实际删除范围遵守既有保留或清除规则。
- 验证数据写入和可靠检查点原子提交，区分数据库事务与 CLI、模型、库外文件操作；使用故障注入检查部分失败和恢复。
- 旧库切换先在独立合成环境验证目标识别、停机、清理范围与失败重试；不以合成测试声称真实微信端到端可用。
- 受影响的业务集成按[独立产品规格](../sync-memory-behavior/spec.md)分别验证；桌面开发验收遵循仓库热更新规则。

## Out of Scope

- 迁入旧 PostgreSQL 联系人、消息、记忆、排除记录或任务；为本次重置保留旧业务库备份。
- 在数据库重建文档中制定选人、同步按钮、记忆处理和用户交互规则；这些规则在独立产品规格中维护。
- 云端或多设备同步、自动备份、端侧数据库加密、发布打包与远端操作。
- 本轮实际建库、删除数据库、修改业务代码、执行迁移／恢复实验或声称产品已经实现。

## 已确认的数据库决定

- Q29：新库继续保存完整的记忆提取过程，用于回看和排查；涉及的聊天正文与模型输出随相关来源清理，不以无正文调用回执代替。
- Q30：所有联系人及用户本人共用一个 SQLite 业务数据库；按稳定用户与联系人身份隔离，不能因为存入同一库而混用资料。
- Q32：在已核验联系人范围内，消息身份不足以判断是否重复时，隔离保存原始记录待核验；不按正文猜测合并，也不作为正常聊天或生成依据。隔离记录保留来源与删除路径，具体存储结构和恢复方式仍待设计。
- Q33：本轮先细化统一消息表中的非文字占位；图片、语音、视频、文件、表情等都先保留类型与消息位置，不参与记忆提取。具体结构建议及待验证约束见消息存储细化草稿，原图等真实资源模型另行讨论。
- Q34：同一微信账号、同一条仍已核验的私聊在取消／重新选中之间沿用原 binding_id；重新授权由独立授权记录和代次表达，不使旧请求自动恢复资格。
- Q35：消息身份、发送方、内容或类型可靠时，即使精确排序未知也可先保存规范消息；未知排序明确保留，稳定展示兜底不作为真实聊天先后或因果证据。身份本身不明时仍按 Q32 隔离。
- Q36：本人记忆与联系人记忆共用 memory/memory_version 表，以明确的范围字段、约束和必要的触发器区分，不分成两套重复结构。
- Q37：撤销一个仍可合法恢复的自动更新时，在同一条 memory 下新增恢复版本并设为当前，保留恢复来历及操作顺序。恢复须重新核验来源及人工保护，不恢复已删内容，也不把自动内容转为独立手录或用户确认事实。
- Q38：一条任务固定属于一个轮次，消息输入不追加。普通暂停或失败后手动继续沿用原任务和成功步骤，新增执行记录；下一轮消息建立新任务。取消／删除失效的任务不能恢复，未知模型调用不能盲目重发。记忆任务直接关联所属轮次，省去旧跨轮复用语义的多对多归属和 plan 壳。
- Q39：候选回复的模型原稿和手工编辑稿统一存入候选版本结构，从 v1 开始；reply_candidate 只保存候选身份和产生位置，不保留原文与编辑文分处存储的 v0 特例。版本引用、显式选择、来源删除及用户手动发送边界继续有效。
- Q40：场景文档与长期画像共用 memory_document / memory_document_version，以 kind 区分，保留各自段落／条目、推断与矛盾结构及一致发布集合。
- Q41：继续通过 DSH 官方插件加载 Skill，保留原目录，只重建必要业务关联并防止空库孤儿误删。不默认全部停用；仅无法确认来源、审核或启用状态的条目标为待核验。已知启用、已知停用与未知分开记录，不能凭文件存在伪造旧审核／授权，也不迁入旧 PG 业务资料；实际接回和切换仍待后续验证。
- Q42：删除共用统一 deletion_operation，关联明确类型的数据库／文件目标及复核结果，各领域保留自身清理逻辑和范围校验；重试沿同一操作继续。先撤销旧写入资格，清完整受管副本并复核后才完成，不能只凭数据库行已删判成功。精确历史分界及后续读取能力仍须单独证明。

- Q43暂缓（用户明确）：尚未认可94表。先按实际需求列总清单，逐表说明用途、独立理由和合并／不建；旧PG仅查漏，不照搬旧结构。之后再决定共享材料表，不批准新增范围或表数。

- 最新设计方向：从需求、实体和事实关系重新设计表，旧PG最后查漏；表名/字段/键/关系均可重定，尊重已确认决定。94/100/54均非认可方案或表数目标，共享结构仅在新模型有自然同构事实时讨论。

- 2026-10-29消息编辑边界已确认：原聊天正文不直接编辑，关系资料通过记忆修正；当前不建聊天正文版本表。解释/排序的当前修订号用于过期检查，不冒充可读取的正文历史版本；当时真实输入由完整追踪保存。删除权及来源清理继续有效。本次确认不等于批准全部字段或DDL。

- 2026-10-29记忆候选编辑已确认A：保留模型原稿，修改并采纳后生成正式memory_version；不保存采纳前多稿历史，当前不建memory_candidate_version。模型原稿、正式版本、真实决定和来源继续保留；不改变Q39回复候选版本，不额外承诺未提交草稿跨重启恢复。

- 2026-10-29收敛范围已确认：本次Skill仅设计官方加载与最小业务关联，不纳入经验学习、审核发布、方法级停用的业务表。Q41原目录保护、可证启停状态及待核验规则继续有效；本轮仅设计，不执行旧功能下线或文件清理。

- 2026-10-29媒体Q11：确认媒体Q1–Q10规则、三实体及统一删除账本扩展，已整合进总草图；当前77表包含媒体3表。CLI身份/质量证据、SILK解码、SQLite约束和跨文件清理验证仍待实施，不把设计确认标为集成通过。
