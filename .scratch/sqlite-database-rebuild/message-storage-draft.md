## 一条聊天怎么存

假设用户已确认联系人“小林”，微信账号和私聊绑定均已核验。对方发来一条文字：“明晚有空吗？”下面的编号只是说明关系，不是真实微信资料。

| 记录 | 示例 | 作用 |
| --- | --- | --- |
| 用户与微信账号 | 用户 U1、微信账号 W1 | 标记资料属于谁，以及消息来自哪个已验证微信账号。 |
| 联系人 | 联系人 C1，当前展示名“小林” | 保存稳定内部身份；展示名可以改变，不作为身份匹配键。 |
| 会话绑定 | 绑定 B1：U1、W1、C1 与微信私聊定位标识 | 把已核验的微信会话与联系人关联，不能通过昵称猜测。 |
| 来源批次 | 来源 S1：B1 的一次历史读取 | 记录消息从哪个受授权的会话和读取批次进入系统，不把同一条消息的每次读取都当成新聊天。 |
| 规范消息 | 消息 M1：U1、C1、对方发送、文字、“明晚有空吗？”、原始发送时间 | 保存供查看、检索和记忆提取使用的消息；时间无法取得时保持未知。 |
| 原始来源记录 | R1 属于 S1，核验后关联 M1，附来源内定位与必要原始记录 | 表达一次原始出现；身份未核验时仍可单独保存，核验后连接规范消息；原始记录可能包含正文，属于敏感数据。 |

假设后续增量读取再次遇到同一条消息，且渠道身份足以可靠核验：系统复用 M1，不重复生成一条聊天；第二次原始出现 R2 属于 S2，同样关联 M1。R1、R2 及其来源可分别追溯；单个来源删除时，先判断 M1 是否仍有其他有效来源。清空整个联系人的聊天则按已确认范围处理，不因有两个来源而保留 M1。

## 候选记录与字段

以下字段体现用途；实际类型、列名、索引及是否需要其他字段尚未确定。

| 候选表 | 建议保存 | 设计原因 |
| --- | --- | --- |
| `owner` | 内部用户 ID、必要状态 | 建立资料归属，不从聊天文本推断。 |
| `channel_account` | 内部账号 ID、用户 ID、渠道、核验后的账号身份、状态 | 不同微信账号的会话和授权不能混用。 |
| `contact` | 内部联系人 ID、用户 ID、当前展示名、状态 | 同名不合并；昵称和备注只用于展示，不作为稳定身份。昵称变化时的绑定与显示行为，以及名称历史是否另存仍在讨论。 |
| `conversation_binding` | 绑定 ID、用户、账号、联系人、外部会话标识、核验／授权状态及版本 | 稳定会话身份与联系人映射独立；身份冲突时不猜测。 |
| `source_batch` | 来源 ID、用户、联系人、绑定、捕获方式、时间及状态 | 一批受授权读取的来源；建议以一次有界 CLI 返回页为粒度，页内原始出现分别保存。重试、缺口与检查点合同仍需验证。 |
| `message` | 消息 ID、用户、联系人、说话方向、类型、文字或占位、原始时间、可核验渠道消息标识 | 为用户与检索保存一条规范消息；图片、语音等目标为类型占位，不保存媒体正文。 |
| `source_record`（原始出现记录，候选命名） | 来源 ID、批次内序号、用户／联系人范围、原始定位、必要原始记录、核验状态、可空消息 ID | 每条原始出现先属于一个来源批次，待核验时不指向规范消息，核验后可关联同范围的一条消息。消息与多个批次之间的多对多关系由原始出现记录表达。 |

## 基数、键与依赖的具体提案

以下是逻辑键草图，实际 ID 类型和物理索引未定。组合范围键用于落实现有隔离要求，不能只在查询里约定。

| 关系 | 基数 | 键／约束提案 |
| --- | --- | --- |
| 用户 → 联系人 | 1:N | 联系人以 `(owner_id, contact_id)` 为范围身份，名称是普通属性。 |
| 联系人 → 规范消息 | 1:N | 消息以 `(owner_id, contact_id, message_id)` 为范围身份，并复合外键引用联系人；渠道去重候选键另行核验，不能用内部 ID 代替。 |
| 来源批次 → 原始出现 | 1:N | 原始出现以 `(owner_id, contact_id, source_batch_id, record_no)` 唯一；批次内序号描述实际出现位置，不拿可能重复的微信 local_id 冒充此序号。 |
| 原始出现与规范消息 | 每次出现关联 0 或 1 条消息；每条消息可关联多次出现 | 一次 CLI 原始出现至多关联一条规范消息；一条规范消息可关联多次原始出现。可空 message_id 表示尚未建立关联，不表示自动生成一条未知消息。 |

`source_record` 通过复合外键引用同范围的来源批次；关联消息时通过包含 owner、contact、message 的复合外键校验。核验状态和 message_id 的组合需要行内条件：待核验记录没有已确认关联，已规范化记录必须有合法关联。实际枚举值和其他解析失败状态尚未定稿。

如果以后一个原始输入允许拆成多条规范消息，这条 0..1 关联就不成立，需要单独关联表。本轮只论证现有“一条 CLI 消息事件对应至多一条规范消息”的范围，不为未实现输入预建通用关系。

从 `message_source` 修订成原始出现实体，是为了表达 Q32 已确认的真实生命周期；这不是把未知记录塞入正常 message 表。反向要求“活动规范消息必须有有效来源”不能仅靠一条普通外键证明，仍需来源写入和删除事务中的资格复验。

## 范式、JSON 与历史记录

- 当前展示名只由联系人记录维护；不在每条消息里保存一份可独立修改的“当前联系人名”。
- 原始记录和规范消息具有不同职责：前者保存当时输入，后者保存受控解释后的聊天；两份内容并存要标明语义和删除依赖，不能当作两个可竞争更新的事实源。
- 源消息 ID 列表、记忆证据列表等需要关联、索引或级联清理的数据用明确关系表达，不存成逗号字符串或只靠应用解析的 JSON ID 数组。
- 原始协议载荷和完整模型输出可按整体 JSON 保存，但不能因此省略需要校验的关系列。历史快照中的名称与联系人当前名不具有相同时间语义。
- 现有要求保留 owner 与 contact 范围字段时，对必要范围冗余应明确函数依赖及复合外键，而非笼统宣称整套模型已达到第三范式。

## 非文字消息先占位：本轮细化

Q33 已确认本次先定清消息占位结构，用户补充图片、语音、视频、文件、表情等非文字内容都先占位。此前已确认占位不参与记忆提取；未来图片等内容接入及加入记忆需另行明确，保存占位不意味着创建媒体获取或理解任务。

### 一张消息表承载时序，不按媒体类型重复建表

建议现阶段继续使用 `message` 表保存文字和非文字消息。当前没有图片尺寸、语音时长、视频文件等需要独立维护的业务属性，因此不因有 `image`、`voice` 等类型就各建一张实体表。原图、缩略图和理解结果的独立存储模型不在本轮定稿范围。

| 字段草图 | 文字消息 | 非文字占位 | 约束目的 |
| --- | --- | --- | --- |
| `owner_id`、`contact_id`、`message_id` | 必填 | 必填 | 确定用户、联系人和内部消息身份；不从昵称或正文猜测。 |
| `speaker` | 可靠的发送方向 | 可靠的发送方向 | 类型与发送方分开；不能因不知道内容就丢掉谁发送的信息。无法核验的输入按既有隔离规则处理。 |
| `message_type` | `text` | 例如 `image`、`voice`、`video`、`file`、`sticker` 或明确未知类型 | 结构化保存类型；归一化类型和原始渠道类型不混为一项。具体映射及枚举须核验。 |
| `text_content` | 真实文字正文 | `NULL` | 用 NULL 表示当前没有文字正文，不把固定占位标签冒充聊天原文。 |
| `occurred_at` | 可核验的原始时间，未知留空 | 相同 | 不以数据库写入时间冒充原始发送时间。 |
| 写入时间与可靠排序依据 | 独立保存 | 相同 | 时间、消息身份及不透明续读游标分别表达，顺序不能靠 local_id 单调性假定。 |
| 来源关联 | 通过已核验 `source_record` 关联 | 相同 | 保留稳定渠道消息身份、原始类型和来源；具体字段依适配器合同确定。 |

`[图片]`、`[语音]` 等占位标签建议由规范消息类型映射生成，作为展示或受控文本表示；不在 text_content 再保存一份固定标签。原始渠道类型留在来源记录，未知类型明确显示未知占位，不静默丢弃。本提案保留“这里有一条消息”的结构和位置，不表示已经保存图片或其他媒体内容。

### 行约束与关系约束提案

- 范围主键为 `(owner_id, contact_id, message_id)`，并以复合外键引用联系人；全部主键字段明确非空。
- `message_type` 必填；文字消息必须有非空的真实正文，非文字消息在本阶段不保存 text_content。可用行内 CHECK 表达，最终合法类型集合须与实际适配器一致。
- 非文字消息仍经相同来源关联、可靠身份核验、去重和清空流程；没有图片文件不影响已核验消息位置的保存。
- 无法可靠核验消息身份的原始记录先隔离保存在 `source_record`，不为填占位而猜测位置或创建错误规范消息。
- 记忆目标查询按 `message_type='text'` 以及有效来源、处理资格筛选；不能先把 `[图片]` 拼进正文再寄希望于模型自行忽略。
- 同一行不加入一串当前无含义的 `image_path`、`voice_path`、`video_path` 空字段。未来真实资源产生不同属性和生命周期时，再按资源关系设计表并使用后续结构迁移。

### 实现差距与后续边界

现有增量代码会过滤非文字，因此上述结构是重建目标，不是当前已验证行为；须同时验证首次历史与增量归一化、非文字发送方和时间保留、去重、顺序、游标及来源删除。旧过滤日志的回填另按明确数据范围和可靠身份处理；本次空库不迁入旧日志，不用旧库回填要求扩大此次重建。

[旧媒体提取规格](../wechat-media-extraction/spec.md)曾确认文件位于受控本地目录、数据库存必要来源引用与路径，且尚未实现。它不是本轮占位表结构的已实现能力，旧规格中媒体提取或理解建议也不能覆盖用户后来明确的“当前只占位、不进记忆”。原图片讨论最后关于占位是否进入普通回复上下文等未回答问题，仍不能冒充已确认决定。

## 昵称变化与稳定绑定

用户指出：联系人已通过稳定 ID 绑定后，昵称如何变化都不应改变数据库中的联系人归属。这与身份模型一致：`contact_id` 是内部身份，绑定以用户、微信账号及已核验的外部会话定位标识为基础，昵称和备注只是展示信息；同一个有效会话不因名称变更而变成新联系人。稳定身份失效、账号变化或标识冲突时不能猜测合并。

代码查证：当前后台同步按用户、账号范围、稳定会话定位标识和活动绑定查找，不用展示名决定消息归属，见[同步绑定校验](../../backend-ts/src/sync/sync-incremental-store.ts)。已存在绑定是否自动刷新显示名称仍需查证，不能据身份绑定直接推断界面已更新。

前台自动定位属于独立产品边界：当前前台只能从微信窗口标题识别名称，再通过 CLI 名单查找候选会话；现行规则和代码在检测到绑定名称变化时要求用户选择，见[前台定位](../../backend-ts/src/foreground/foreground-location-locator.ts)和 [ADR-076](../../architecture/adr/076-session-list-assisted-name-matching.md)。这不改变后台绑定的身份归属；本数据库草稿不修改该规则。用户是否希望进一步调整前台识别，尚未决定。

单独保存历史昵称是另一个问题。用户尚未选择是否保留名称历史；不应把“身份不依赖昵称”误记成不保留旧名称的决定。来源原始记录和完整记忆追踪仍按已确认的来源与删除规则处理。

## 数据库需要保证的规则

1. **联系人隔离**：消息及其来源引用的用户和联系人必须一致；昵称、备注和正文都不能用于猜测身份。
2. **去重和来源分别处理**：可靠判定为同一消息时只建一条规范消息，但不能丢弃合法来源关系。消息、来源和进度写入必须一起提交或一起回滚。
3. **时间和顺序分开**：原始发送时间缺失时保存未知，不拿写入数据库时间冒充。消息身份、显示排序和读取游标是不同概念。
4. **冲突不猜测**：微信 `local_id` 不能单独当作全局唯一或单调游标；当前代码把缺失创建时间记为同一个哨兵值，是否可能产生身份碰撞需核验真实 CLI 合同。已核验联系人范围内，消息身份不足以判断是否重复时，用户已确认隔离保存原始记录待核验；该记录不能作为正常聊天或生成依据，不能按聊天正文猜测合并，并须保留来源、隔离和删除路径。具体触发条件、隔离存储结构、检查点推进和后续核验方式尚待设计。
5. **删除有路径**：来源引用、原始记录、规范消息、提取追踪和依赖记忆分别按其真实关联清理。完整联系人清空还需要覆盖从未读入的旧历史；仅记住已读消息编号不够。
6. **真实现状与目标区分**：当前 CLI 事件归一化会过滤非文字，不会建立图片或语音规范消息占位；新库保存非文字占位是用户已确认的目标，仍须实现和验证。

## 仍需查证

- Q31 尚未决：用户提出联系人既已按稳定 ID 绑定，昵称变化不应改变归属。先查证后台 CLI 绑定与前台会话识别各自的规则及实现，再讨论是否另存展示名历史；不能把它理解为已经选择了保留或不保留名称历史。
- Q32 已确认：已核验联系人范围内，消息身份不足以判断是否重复时，隔离保存原始记录待核验，不按正文猜测合并，也不把它作为正常聊天或生成依据。原始记录只限授权范围，并随来源和联系人清空路径删除。
- 锁定或实际使用的 CLI 对消息稳定身份、缺失时间、重复 `local_id`、排序与分页游标的保证。不能把目前 PostgreSQL 去重键直接写成已证明的唯一约束。
- 原始来源记录哪些字段是来源复核与删除所必需；不得借“完整追踪”自动扩大媒体读取或保存范围。
- 对身份无法唯一核验的记录，如何实现隔离保存、明确覆盖缺口和后续修复；查明 CLI 真实能力后设计检查点提交与恢复，不把用户选择误记成已经实现。
- 旧联系人 `channel_identity`、`conversation_binding` 及授权表在单 SQLite 方案中的字段与约束是否能安全收敛；不能按表数目标省略必要身份关系。
