## 当前为什么有这么多表

静态分析当前 001–128 迁移，识别到 123 条建表和 8 条删表语句；按出现顺序粗略推算约 115 张业务表，另有迁移执行器的账本表。实际用户库未连接核查：条件分支、历史基线和额外对象可能使数量不同。128 是迁移文件数量，不是表数；启动检查列出的 40 张是最低必需清单，也不是全部表。

按名称粗分的静态估计：助手与回复 17 张、Skill 20 张、分层记忆和质量 16 张、其他记忆和处理 27 张、微信同步和授权 11 张、消息与来源 10 张、用户联系人 5 张、任务删除调用 6 张、表达偏好 3 张。分类用于定位，不代表每类都可整体删除。

来源：[迁移说明](../../backend-ts/database/README.md)、[启动检查](../../backend-ts/src/platform/database/host-storage.ts)、[旧资料升级](../../backend-ts/database/migrations/067_memory_upgrade_batches.sql)、[记忆处理](../../backend-ts/database/migrations/124_memory_processing_lifecycle.sql)。

## 精简原则

1. 从空库和现有业务能力出发设计，不重放原有 128 个迁移，也不为旧数据兼容原样建表。
2. 旧版遗留与已退役功能只有在核对现存调用后才可省略；重建时同步修改查询、删除和模型记账，不靠缺表冒充精简。
3. 将同一对象真正一对一的状态考虑合并到所属对象；把同构的版本或后台任务考虑使用同一组结构。
4. 消息和来源、记忆与证据、含正文追踪与无正文调用回执、目标进度与任务状态仍分别表达。是否分别物理建表由约束和访问路径决定，不能把需要独立删除或检索的关系塞进不可核验的 JSON。
5. 可重建的索引或投影不作为事实源；是否需要持久化由可测性能与恢复成本决定，不预设一定要有表。
6. 总表数是结果，不设硬性数量目标；每张候选表必须能说明数据归属、唯一性、删除路径和使用者。

## 关系型设计准则与逐表契约

用户明确要求讨论数据表本身的设计。候选清单只是初始职责分组，尚未完成范式与关系完整性审查。后续按以下顺序推导结构，不先认定 36 张就是答案：

1. **确定一行代表什么**：实体、一次真实发生、版本或一种关系必须说清楚。名字相似、字段相似，不足以证明可以合表；一个对象有状态，也不意味着每种状态必须单独建表。
2. **说明函数依赖**：普通业务事实以第三范式为基线；非键字段应描述所属记录，避免重复组、对复合键的部分依赖和不必要的传递依赖。当前联系人名称不重复作为每条消息的可变属性；模型输入中的历史名称快照具有不同时间语义，应另作说明。
3. **区分身份和业务唯一性**：内部 ID 标识记录，候选键说明业务上什么不能重复；增加一个 UUID 不能代替去重规则。消息的渠道自然身份尚未核验完整，不能仅用正文、昵称或单独 local_id 定义唯一键。
4. **先写基数再写外键**：每个关系说明 1:1、1:N 或 M:N，以及关联是否可以暂缺。需要强引用的关系必须有明确目标及可执行的外键，不用 entity_type + entity_id 或 JSON ID 数组冒充引用完整性。
5. **把约束放在正确层次**：已知必填、唯一性、范围引用和行内条件尽量由 NOT NULL、UNIQUE、复合外键与 CHECK 保证；活动资格、来源删除、外部调用和跨文件清理仍需事务及业务复验，不能承诺单靠外键完成。
6. **谨慎使用 NULL 和冗余**：NULL 必须表示真实的可选或尚未建立关系，不能兼任多个未知状态。owner_id + contact_id 的范围字段由产品隔离要求保留，需通过复合外键验证；历史快照、缓存和派生计数明确其事实源、版本和失效机制，不假定加入冗余字段后仍自动符合第三范式。
7. **先证明正确，再加索引**：主键与候选键的约束来自语义；查询索引由实际读取和删除路径确定，不能用索引弥补模糊的实体关系。是否保存可重建投影以测量为依据。

每张表的定稿都应列出：一行的含义、字段与类型、主键和候选键、外键和基数、NULL 与默认值含义、状态及生命周期、删除动作、事务边界、索引与访问路径、必要冗余的理由。

### 当前清单需要纠正的具体问题

| 缺口 | 具体风险 | 本轮设计提案 |
| --- | --- | --- |
| `message_source` 把原始出现与已核验关联混在一起 | Q32 的原始记录尚不能对应规范消息，强制 message_id 会使它无法入库，或被错误塞入正常消息 | 改以 `source_record` 表达一次原始出现，先属于来源批次，核验后可关联一条规范消息；精确基数和键见消息存储草稿。 |
| `memory_evidence` 声称可以引用候选或记忆版本，但未指定关系 | 泛化 type/id 不能直接指向两张表并自动保证目标存在、范围正确 | 初步拆为 `candidate_evidence` 与 `memory_version_evidence`；若未来提议共同父实体，必须先证明是真实领域概念及完整生命周期，不能仅为省表创造抽象。 |
| `memory.current_version` 只有字段名称 | 可能误指另一条记忆的版本，或者同一记忆重复版本号 | `memory_version` 约束同一记忆版本号唯一；当前版本用包含 memory 身份的复合引用绑定，不只校验 version_id 存在。 |
| 本人和联系人记忆共用表、contact_id 可空 | SQLite 复合外键包含 NULL 时可能不要求父记录存在；默认把 NULL 当本人也会掩盖错误 | 同表不是天然违反范式，需先证明属性和生命周期同构，再用明确范围条件、独立 owner 外键及适用的 contact 复合外键约束；否则分表。 |
| 以同构为由合并后台状态、文档或台账 | 字段相似不说明依赖、保留期限和删除规则相同 | 保留合并候选身份，逐项证明键、状态、恢复和删除合同等价后再确定。 |

以上是结构审阅结论和提案，尚未实现。拆分证据等调整可能改变原始候选表数；不再把原清单数量作为定稿目标。

## 初始候选表清单（结构审阅中）

以下保留首轮 **36 项候选职责**作为覆盖清单；本轮关系审阅已经指出部分项目需要改名或拆分，不能再据此认定最终表数。字段是说明职责的最小草图，省略字段不表示这些信息无需保存。所有 ID 的实际类型、复合外键、索引和状态枚举尚未定稿。

联系人、消息与来源的具体字段、虚构记录示例及未决问题见[消息存储细化草稿](message-storage-draft.md)。

## 需要证明的关键约束

- 每条联系人范围记录以及消息、来源、记忆证据的关联，都须验证同一 owner 和 contact；本人记忆的证据依赖须保留真实联系人归属。空联系人 ID 不能意外绕过 SQLite 外键检查，必要时使用不同约束、表或事务内复验。
- 一条消息可有多个来源；来源删除只在不再有有效来源时删除消息，清空联系人聊天则按已确认范围处理全部消息与依赖。不能靠正文哈希猜测消息身份。
- 已确认联系人范围内，对无法判断是否重复的消息隔离保存原始记录待核验，不纳入正常聊天或生成依据；必须保留来源和删除路径。可能需要独立表或受控状态，原先 36 张候选清单尚未决定这一物理结构。
- 聊天清空要使旧读取、模型结果、追踪、会话依赖及库外副本失效并完成清理；无正文抑制、渠道可证明的历史边界及新的消息资格分别保存。清空前后同时到达和同秒消息必须通过真实 CLI 能力验证。
- 每轮固定目标、已成功的处理记录、阶段结果、租约及未知模型调用回执分别可恢复；普通暂停、取消和来源删除的资格不同，不能合并成一个布尔状态。
- 每条记忆版本须保留来源或合法手录依据及采纳方式；完整提取追踪的聊天、模型输入输出和上下文来源依赖须可回看与删除。
- 任何状态合并都不能让删除整位联系人、删除单一来源和删除账户留下错误的可恢复正文或错误地清除其他联系人的资料。SQLite 和受管文件不共享原子事务，须用可恢复的步骤记录。
- 诊断、质量评测和 Skill 文件等需要逐一对照真实入口，明确保留、改造或退役，不依据候选表数量推断已经兼容。

## 后续验证与未决项

1. 按现有实际业务入口逐张建立旧表 → 新表／字段 → 使用者／删除路径的覆盖矩阵，并核对动态 SQL 和文件存储；不能只按表名映射。
2. 确定绑定、本人记忆、候选与版本等复合约束；验证 SQLite 外键启用、NULL 行为、唯一键、事务、并发、恢复和实际运行时版本。
3. 评估 `node:sqlite` 或其他驱动、真实 Electron 后台运行时及受影响的 WAL 问题；当前没有确认驱动和 WAL 模式。
4. 使用隔离合成资料逐项验证多联系人、来源去重、完整追踪、用户修改、删除并发、记忆控制及空库启动；UI 或真实微信验收另行报告。
5. 删除旧 NotAlone PG 库及旧业务副本属于最终切换，不在本文讨论或表清单验证阶段执行。
