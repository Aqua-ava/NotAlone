# 聊天回复策略第一版

Triage: ready-for-agent

规格状态：第一版范围与测试接缝已确认，2026-10-11 发布；尚未实现，拆票提案待确认。

## Problem Statement（用户问题）

用户可能需要回应一条消息，也可能主动联系对方。现有“改写草稿／生成回复”输入模式不能充分表达两类场景；用户尚未明确意愿时也缺少可纠正的理解及方向探索。既有原型跑通部分语言流程，但未证明生产集成与语义质量。

## Solution（解决方案）

提供“回应消息”和“主动聊聊”场景入口，保留已有草稿改写能力。用户已明确意愿时直接生成；不明确时先展示简短理解与少量不同意愿的方向，由用户确认。通用流程独立可用，已启用 Skill 可以辅助场景判断但不能替用户决定方向。候选可由一条或一组消息构成，逐条编辑、复制，由用户亲自发送。

## User Stories（用户故事）

1. 作为用户，我希望明确选择回应消息或主动聊聊，不因有历史消息就被当作正在回复。
2. 作为用户，我希望回应时能确认待回复消息，看到简短理解、依据与歧义，并纠正理解。
3. 作为用户，我希望意愿不明时看到少量不同立场的方向，而不是同一立场的语气变体。
4. 作为用户，我希望直接输入或选定自己的方向；已说清楚时不必再次确认。
5. 作为用户，我希望主动联系可从目的开始，不需要先有对方消息或伪造待回复目标。
6. 作为用户，我希望目的明确后同时比较开口方式和候选，不经历两次必选步骤。
7. 作为用户，我希望方向不合适时换一组，也能自行输入，而不被历史习惯排除合理立场。
8. 作为用户，我希望系统可以推荐有依据的方向，但不预选，不保证对方反应。
9. 作为用户，我希望缺少时间地点时先获得不虚构细节的表达，仅在关键信息影响立场时追问。
10. 作为用户，我希望复杂目的先推进当前一步；目的与说法冲突时了解取舍而不被替换目标。
11. 作为用户，我希望选择暂不回应时停止当前候选生成，不创建提醒、定时发送或后台联系。
12. 作为用户，我希望候选可分多条表达，逐条编辑复制，不强迫把全部意思塞进一句。
13. 作为用户，我希望纠正或改口后保留仍有效的要求，无需重新走完流程。
14. 作为用户，我希望未选方向时新消息更新建议，已选方向或正在编辑时只提醒，由我决定更新。
15. 作为用户，我希望 Skill 按当前主要场景匹配、最多使用一个，可关闭或更换，没有合适 Skill 也能完成流程。
16. 作为用户，我希望同一句话在不同前文下得到有依据的不同理解，背景不足时保留不确定性。
17. 作为用户，我希望历史版本、范围校验和删除沿用持续会话契约，候选不会自动发送或成为长期偏好。

## Implementation Decisions（实现决定）

### 场景与既有输入

- “回应消息／主动聊聊”是用户场景；“已有草稿改写”仍保留为可进入的操作，不丢弃已有草稿。切换场景不静默变更输入含义或触发生成。
- 回应路径要求明确目标消息，复用已确认表达方向的单次回复契约。主动路径增加明确的主动联系目的输入，不将目的塞成虚构的对方消息，也不自动回复最近消息。
- 应用层统一核验 owner/contact、绑定和来源后再进入上下文、运行时、存储模块。内部模式扩展按 ADR-043 衔接，不新建绕过既有校验的独立生成链路。
- 有草稿时保留原意及按需补充语气/边界；改写默认不读取关系背景，仍由用户明确开启。没有资料也可从当前消息和用户目的提出条件性建议，不编造关系状态。

### 理解、方向与生成

- 用一句简短语用解释说明联系人表达，列明关键歧义与真实依据；不能把深层动机、心理或关系结果当作确定事实。
- 方向建议以不同意愿为单位，少量展示，可换组或自行输入。推荐不等于选定；缺少依据时不强行推荐，无依据建议只说明适用条件。
- 用户直接给出明确意愿视为确认；模型推测不算确认。选择建议使用建议 ID 与输入版本，不靠文字模糊匹配，过期建议不能应用到新消息快照。
- 缺少一般安排细节不强制追问；未知事项会形成承诺、改变立场或产生实质歧义时只问一个关键问题。复杂目的说明本句推进的一步，不保证最终效果。
- 用户选择暂不回应是有效结果，不强制生成候选，不启动定时任务。纠正理解不改变用户已经明确的意愿；明确改口则以新意愿为准。

### 新消息与持续会话

- 用户主动开启方向探索后，在该任务仍打开、联系人范围有效且方向未确认时，授权范围内的新消息可更新理解和建议；不是全局后台自动调用。关闭任务/窗口或切换离开该任务后停止这种自动更新。
- 更新合并连续通知、只使用有界最新快照，沿用调用次数、超时和重试预算；不能无限轮询或收到任意事件就发起一次模型调用。超预算/失败显示需手动刷新，不自动扩大范围或补扫历史。
- 一旦方向确认、候选开始生成或用户编辑，只提示有新消息。用户“结合新消息继续”才替换生成，沿用持续会话输入版本、取消及迟到结果失效规则。
- 未选方向的探索更新与已发起候选生成分开：停止探索更新不取消因切换/关闭小窗仍应继续的候选生成。整体退出仍按持续会话契约停止。
- 不另造会话存储、版本或删除模型；重用持续会话规格。历史结果能查看，不应恢复已失效建议或已删除来源。

### 候选消息组

- 维持少量备选方案，每个方案可含一条或按顺序展示的消息组，避免把一组里的多条消息误标为互斥候选。
- 逐条编辑、复制，保留所属方案及修改关系；每条所含事实及整组承诺均受当前意愿与来源约束。复制不记作发送，消息顺序不构成自动发送计划。
- 新消息不自动替换已有组或用户编辑；选中版本、修改历史与明确指代复用持续会话规则。来源失效时整个受影响派生方案及恢复副本接受删除检查。

### Skill 职责

- 一个 Skill 面向一类沟通场景，内部可有多个方向与方法；接受、拒绝、委婉或直接不各自拆成 Skill。
- 根据已启用且范围有效的目录匹配当前主要任务，至多加载一个不可变版本；无合适项使用通用流程，显示实际名称/版本，用户可关闭或更换。
- 场景明确时允许在方向确认前读取受控策略内容帮助理解与建议，但加载不确认用户立场；建议与当前意愿冲突时以用户意愿为准。
- 同一任务从探索到生成沿用选定的有效版本；用户明确更换或库 revision 变化时，重新核验并使旧策略结果失效，不能把两个版本同时合并进入本次上下文。
- 方向探索阶段仍无业务 Agent Tool 补查循环、外部查询、脚本或发送能力；只经既有受控 Skill 边界加载有限静态资料，库 revision 与来源删除使旧结果失效。ADR-043 明确修订旧方向建议禁止 Skill 的限制。
- 本轮不创建、安装或设计具体邀约 Skill；用合成包验证机制，不把测试包当作可用场景库。

## Testing Decisions（测试决定）

已确认接缝：公开页面操作 → 后端 HTTP → 隔离 PostgreSQL，真实控制器和业务存储，合成消息与可控模型。复用既有回复、消息事件、Skill 隔离/删除和持续会话验证，不启动真实微信或外部模型。

验证两条完整路径、已有草稿兼容、无历史、明确意愿直达、关键澄清、换组、纠正、暂不回应、消息组逐条编辑复制、未选方向有界更新、方向确认后不自动改口、过期建议及迟到结果拒绝。跨 owner/contact、未启用 Skill、删除/禁用 Skill、删除来源、断线及恢复都必须有负向例。

合成模型测试只证明控制流、范围、持久化和调用边界。保持当前句不变而改变前文的语义对照，以及方向能否覆盖用户意愿，另用真实表达规格的可审阅评价方式；原型结果是开发证据，不当作独立保留集或产品质量通过。

## Out of Scope（排除项）

具体邀约 Skill 或场景库创作、OCR、自动发送、自动读未授权联系人、热梗接入、自动风格学习、经验提炼、定时联系、真实模型调用与评测预算、关系长期效果承诺。不能借本规格扩大持续会话已确认范围。
