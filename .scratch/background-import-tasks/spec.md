# 导入后台任务与联系人记忆目录规格

> Triage: ready-for-agent
> 来源：2026-08-23 至 2026-08-24 grilling 与 domain-modeling 结论；依据 ADR-007、ADR-014、ADR-015、ADR-018。最高测试 seam 已由用户确认：合成 PostgreSQL 导入 -> Worker 步骤执行 -> fake model 记忆提取 -> 确定性目录更新 -> verify。

## Problem Statement

当前 NotAlone 已经可以把单联系人微信 JSONL 导入 PostgreSQL，也可以独立运行记忆提取命令，但两者之间没有后台任务边界。导入成功后，记忆提取不会自动排队；长任务没有固定步骤、租约、恢复、重试和可见进度；联系人记忆目录也还没有实现。

这会带来几个实际问题：消息导入和语义处理的失败边界不清楚；Worker 崩溃后无法知道从哪里恢复；重复导入或重复重试可能重复创建记忆；多个任务同时修改同一联系人时可能互相覆盖；任务记录如果保存模型完整输入输出，会复制敏感聊天内容；目录如果成为新的事实源，又会和 `confirmed_memory` 产生双重权威。

## Solution

在现有导入和记忆提取模块之间增加 PostgreSQL 权威的后台任务层和联系人记忆目录层。一次导入在消息、来源和任务模板创建后，自动拥有固定的业务步骤：

```text
parse -> normalize -> extract_memory -> index -> verify
```

Worker 使用短租约领取步骤，同一联系人同时只运行一个 Worker；不同联系人未来可以并行。记忆提取使用已有的结构化提取与自动采纳规则，联系人目录由确定性代码从当前有效记忆生成，不调用模型。任务失败可以有限自动重试，手动重试复用原任务并跳过已经成功的步骤。消息导入成功不依赖记忆任务成功，来源删除优先停止相关未完成任务并清理派生资料。

## User Stories

1. 作为用户（Owner），我想在导入完成后自动产生记忆处理任务，不必再手动执行第二条命令。
2. 作为用户（Owner），我想先看到聊天记录导入成功，即使后续记忆提取仍在后台运行。
3. 作为用户（Owner），我想看到任务当前处于解析、规范化、记忆提取、索引还是验证阶段。
4. 作为用户（Owner），我想看到已处理数量、重试次数和不含聊天正文的失败原因。
5. 作为用户（Owner），我想让暂时的网络或模型错误自动重试最多三次。
6. 作为用户（Owner），我想让三次自动重试仍失败的任务进入明确的 failed 状态，而不是静默消失。
7. 作为用户（Owner），我想手动重试失败任务，并继续使用原任务身份，而不是创建第二个任务。
8. 作为用户（Owner），我想让手动重试跳过已经成功的步骤，只处理失败步骤。
9. 作为用户（Owner），我想让 Worker 崩溃后，租约过期时由另一个 Worker 接管未完成步骤。
10. 作为用户（Owner），我想让同一个联系人同时只有一个任务执行，避免两个任务同时改写同一份记忆目录。
11. 作为用户（Owner），我想让不同联系人未来可以并行处理，提高多联系人历史导入效率。
12. 作为用户（Owner），我想让同一个来源重复导入时复用原任务状态，不创建重复消息、记忆或索引条目。
13. 作为用户（Owner），我想让同一来源的消息导入、来源记录和任务模板在一次事务中保持一致。
14. 作为用户（Owner），我想让首次历史导入覆盖该来源的全部规范消息，但每次模型调用只看到有上限的批次。
15. 作为用户（Owner），我想让后续增量导入只处理水位之后的新消息，不重复提取整个历史。

17. 作为用户（Owner），我想让低置信度事实保留为 pending 候选，而不是自动进入正式记忆。

20. 作为用户（Owner），我想让没有证据、证据越界或结构无效的模型候选被拒绝。
21. 作为用户（Owner），我想让我的通用事实进入 owner 级记忆，而联系人关系事实进入联系人级记忆。
22. 作为用户（Owner），我想让同一事实在多次聊天中出现时合并为一条记忆，并累积证据，而不是重复堆积。

25. 作为用户（Owner），我想让我手动修改自动记忆后，当前版本标记为 manual，同时保留修改历史和来源关联。
26. 作为用户（Owner），我想让删除过的记忆不会被下一次自动提取静默复活。
27. 作为用户（Owner），我想让联系人记忆目录只显示当前有效记忆，不显示已删除、失效或过期条目。
28. 作为用户（Owner），我想让一条记忆变化时目录可以增量更新，而不是每次都完整重建。
29. 作为用户（Owner），我想让批量变化、目录版本不一致或重建失败时，系统合并重建任务并保留旧目录。

40. 作为开发者，我想用合成 PostgreSQL 数据驱动完整任务生命周期，避免用真实聊天数据测试 Worker。
41. 作为开发者，我想用 fake model 验证合法候选、pending 候选、越界证据、更新裁决和失败重试。
42. 作为开发者，我想让任务步骤的状态迁移由确定性代码控制，模型不能领取任务、跳过步骤或宣布成功。
43. 作为开发者，我想让索引重建不依赖模型，保证同一组有效记忆可以得到可重复的目录。
44. 作为开发者，我想让导入任务、记忆任务和目录更新可以在 Worker 崩溃后恢复，而不是依赖进程内存。

## Implementation Decisions

1. **业务任务边界**：后台任务是 PostgreSQL 权威业务记录，后台任务步骤是固定顺序的可恢复执行单元；两者不使用 Agent Todo 或 LangGraph checkpoint 作为替代。
2. **导入事务**：消息、来源、联系人确认、owner/contact 渠道身份和导入任务模板在一次 PostgreSQL 事务中创建；外部模型调用只在事务成功提交后执行。
3. **任务幂等**：导入任务的幂等范围是已确认的 `owner_id + contact_id + source_document_id`。同一来源重复导入复用原任务；不同来源但消息身份重叠时整批拒绝。
4. **固定步骤**：导入任务使用 `parse -> normalize -> extract_memory -> index -> verify`。解析和规范化已经由导入入口完成时，任务仍记录它们的业务结果，不允许模型自由增加、删除或重排步骤。
5. **状态模型**：父任务支持 queued、running、verifying、succeeded、failed、cancelled；步骤支持 pending、running、succeeded、retryable、failed。v1 不提供用户主动取消入口，但来源删除可以停止相关未完成步骤。
6. **Worker 领取**：同一联系人同时只允许一个有效 Worker 租约；租约过期后可接管。不同联系人可以并行。任务进度由步骤和模板权重确定，模型不能修改进度。
7. **重试**：网络、超时、限流和模型暂时错误最多自动重试 3 次；成功步骤不重做。三次失败后保留 failed 状态；手动重试复用原任务、增加尝试次数并从失败步骤继续。
8. **任务保留**：运行中和未完成任务持续保留；成功、失败和系统取消的终态任务保留 90 天后清理。任务记录只保存对象 ID、数量、时间、步骤状态、模型/规则版本和错误元数据。
9. **输入隐私**：外部模型只接收当前联系人范围内的必要规范化文字和有限窗口；raw JSON、微信渠道 ID、本地路径、数据库连接信息、完整历史和其他联系人数据不得进入模型输入。
10. **模型输出**：模型只能返回结构化候选。候选必须带主体、受控分类、置信度、风险标记、有效期和消息证据引用；证据必须包含当前范围内的 `message_id` 与正文偏移范围。无证据、越界证据或格式错误的候选拒绝。
11. **记忆采纳**：低置信度候选进入 pending；达到确定性门槛的候选按 ADR-002 自动采纳并标记 auto，可撤销。用户确认 pending 或手动录入的内容标记 manual。
12. **主体分流**：真正属于用户自身的通用事实进入 owner 级记忆；联系人事实进入联系人级记忆；关系特定的自我陈述不能因为出现“我”就进入全局 owner 记忆。
13. **记忆演变**：同一主题在同一主体和范围内重复出现时合并证据；新事实替换旧事实时旧记忆失效但保留历史；删除指纹阻止被删除记忆自动复活；有效期到期后不进入检索或目录。
14. **联系人目录**：每个联系人只有一份逻辑上的 `contact_memory_index`。目录只包含当前有效记忆的少量分类、主题摘要和 `memory_ids`，v1 最多 20 个主题，不复制正文，也不是新的事实源。
15. **目录更新**：单条记忆变化优先增量更新；批量变化、版本不一致或更新失败时合并重建。目录使用单调递增的 `memory_revision` 检测过期；新目录验证成功前保留旧目录；目录重建只使用确定性代码，不调用模型。
16. **出站台账**：每次外部提取或裁决调用写入供应商、模型、时间、输入/输出用量、延迟和结果状态；台账不含聊天正文、候选正文或联系人名称。
17. **现有模块复用**：复用现有导入仓储、记忆提取运行时、MemoryPort、owner 级记忆 port、出站台账和来源删除边界；新增任务存储、Worker 处理器和联系人目录持久化边界，不把任务状态塞进 Reply runtime。

## Testing Decisions

1. **最高测试 seam**：使用一个合成 PostgreSQL 端到端 seam，从提交单联系人导入开始，创建任务和步骤，驱动一次 Worker 执行，使用 fake model 提取结构化候选，确定性更新目录并完成 verify。
2. **只测外部行为**：测试任务状态、步骤状态、幂等结果、重试次数、租约接管、隔离范围、目录可用性和删除结果，不测试私有函数的调用顺序或随机 UUID。
3. **导入与任务事务**：验证成功导入创建一份任务和固定步骤；重复提交复用原任务；事务中任一步失败都不留下半成品消息、来源、确认或任务。
4. **Worker 生命周期**：验证同一联系人不能被两个 Worker 同时领取；不同联系人可以独立领取；租约过期可以接管；成功步骤重试时被跳过；失败步骤在第三次后进入 failed；手动重试复用任务。
5. **删除竞态**：验证来源删除会停止相关未完成任务，清理仅由来源支持的候选、已确认记忆和目录；删除期间不能由 Worker 重新生成被删除来源的记忆。
6. **记忆提取**：fake model 覆盖全量首次批次、增量水位、pending、自动采纳、主体分流、重复合并、UPDATE/NOOP、证据越界、格式错误和模型调用失败。
7. **证据与隐私**：验证任务、台账和索引不包含聊天正文或完整模型输入输出；外部模型接收的输入仅限当前联系人、规范化文字和有限窗口。
8. **联系人目录**：验证单条增量更新、批量合并重建、revision 不一致、旧目录保留、新目录原子替换、有效期过滤、删除过滤和 20 个主题上限。
9. **回归 prior art**：沿用现有 PostgreSQL 导入事务、来源删除、记忆采纳和 Worker/水位测试的合成数据库隔离方式；默认不调用真实模型，真实冒烟只在显式凭据和明确授权下运行。

## Out of Scope

- 多账号、多微信身份或跨渠道身份合并；v1 同一 owner/channel 只有一个 active 身份。
- 群聊导入；检测到多个联系人或多个会话身份时仍整份拒绝。
- 用户主动取消任务的 UI 或 API；当前只支持失败重试和来源删除触发的停止。
- Airflow、Temporal、独立队列或跨机器调度平台。
- 自动发送微信消息、切换或滚动微信窗口、读取后台聊天应用。
- 保存原始导出文件副本、模型完整 prompt、模型完整 response 或聊天正文调试快照；有期限的显式调试模式另行设计。
- 语音转写、图片理解、视频理解和附件解析；媒体占位不作为记忆证据。
- 复杂语义本体、自由创建记忆分类、向量数据库和跨联系人记忆合并。
- 产品 UI 的完整视觉设计；本规格只要求任务状态和结果有可查询的业务输出。

## Further Notes

- 当前导入、记忆提取和 owner/contact 记忆存储已经存在；本规格要补齐它们之间的任务和目录运行边界。
- 当前独立记忆提取命令已经验证过 207 条真实本地聊天的提取流程；自动后台任务和联系人目录仍未实现，不能把本规格当作已上线能力。
- 真实数据操作必须使用当前明确授权的本地开发数据库和外部模型范围；测试夹具继续使用合成数据。
- 规格完成后再拆实现任务；任务之间应显式记录数据库迁移、任务存储、目录存储和 Worker 的阻塞关系。

## Worker 启动命令补充规格（2026-08-24）

### Problem Statement

导入已经创建后台任务和固定步骤，记忆提取、目录更新和验证的业务处理器也已经存在，但用户缺少一个
可控的启动入口。直接调用独立记忆提取命令不能完整推进后台任务的步骤状态，也不能统一处理全局并发、
租约续期、自动重试和非正文输出。

### Solution

提供一个全局串行的 Worker 启动命令。用户指定一个联系人后，命令只领取该联系人最早的一个可执行导入
任务，连续执行 `parse -> normalize -> extract_memory -> index -> verify`；进程中断后再次启动，从未完成
步骤继续。命令复用既有模型提取、记忆采纳、目录和验证边界，不新增记忆系统或任务表。

### User Stories

1. 作为 Owner，我想指定一个已确认联系人启动后台任务，而不需要手动调用多个内部处理器。
2. 作为 Owner，我想当前版本同一时间只有一个命令 Worker，避免不同任务同时产生派生写入。
3. 作为 Owner，我想模型或网络暂时失败时自动退避重试，永久失败时得到非零退出结果。
4. 作为 Owner，我想长时间模型调用不会因为步骤租约过期而被错误接管。
5. 作为 Owner，我想没有待处理任务时得到明确的 `idle` 状态，而不是误报成功。
6. 作为 Owner，我想命令输出只包含状态、步骤数量和稳定错误分类，不包含聊天正文、联系人标识或模型完整输入输出。
7. 作为开发者，我想使用合成 PostgreSQL 数据验证锁、步骤顺序、租约续期、重试和最终验证。

### Implementation Decisions

1. 命令使用当前项目环境中的数据库、owner 和模型配置；联系人通过内部 `contact_id` 指定，启动前检查
   数据库、owner、联系人和模型配置，预检查失败不领取任务。
2. 当前 v1 命令使用 PostgreSQL 会话级全局 advisory lock，保证同一时间只有一个命令 Worker；底层
   `owner_id + contact_id` 租约仍保留，未来放开不同联系人并行时不改变数据隔离边界。
3. 一次命令只处理一个联系人最早的一个任务，并在 `verify` 成功后退出；不自动继续处理该联系人后续任务。
4. 暂时失败沿用步骤最多三次自动重试，命令在重试之间使用有限退避；成功步骤不重做，永久失败返回非零
   退出码。
5. `extract_memory` 等长步骤使用租约心跳续期；租约续期失败按暂时错误处理，不能在租约失效后宣布步骤成功。
6. 命令只输出非正文状态；任务、台账和索引继续遵守不保存模型完整输入输出的隐私边界。

### Testing Decisions

1. 在最高可用 seam 测试启动命令的外部行为：全局锁占用时不领取步骤；正常运行依次完成五步；暂时失败
   退避后重试；永久失败返回失败；没有任务返回 `idle`。
2. 使用合成 PostgreSQL 测试全局会话锁的互斥、步骤租约续期和模型运行超过租约时仍能完成。
3. 使用现有 Worker 集成测试验证记忆提取、目录更新、verify、幂等水位和联系人隔离；不调用真实模型。
4. 只有在明确授权并具备配置时，才对本地已确认数据做一次真实命令验证；真实验证只输出任务状态和统计，
   不把聊天正文写入日志或任务记录。

### Out of Scope

- 独立调度器、队列服务、定时触发和多进程并行调度。
- 一次命令处理多个联系人或一个联系人下的全部排队任务。
- 用户主动取消 Worker 的 UI/API。
- 重新设计记忆提取、记忆表、联系人记忆目录或模型结构化输出契约。

### Further Notes

这份补充规格对应一个完整纵向切片，阻塞于已有的 Worker 记忆提取和联系人目录票据；实现记录应单独放在
该切片票据中，不创建第二份后台任务规格。当前真实 207 条来源的水位已经到末尾，后续命令应按幂等
语义跳过已处理消息，再继续必要的任务步骤。
