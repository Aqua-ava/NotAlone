# NotAlone 原生 App 与常驻本地后端规格

Type: task
State: open
Triage: ready-for-agent

## Problem Statement

NotAlone 的核心模块（历史导入、前台增量同步、记忆提取与管理、检索、候选回复、后台任务、Skill 库、出站台账）都已完成并有测试覆盖，但用户与它们的全部交互面是九个命令行命令和一个菜单栏调试工具：

- 候选回复主链没有任何产品入口：`CandidateReplyFlow` 与 `ReplyGenerator` 只有测试在调用，用户无法在真实会话中生成候选回复，模块闭环断在最后一步；
- 菜单栏应用每 3 秒拉起多个子进程（含一次 OCR 截屏）驱动同步，资源浪费、消息延迟受轮询间隔限制，且只能展示状态文字，无法查看消息流；
- 消息正文与记忆正文没有任何命令可读，用户无法查看、核对或修正自己联系人范围内的资料；
- 开源用户拿到仓库后需要手编 `.env`、手动初始化 owner、逐个命令摸索，首次体验门槛过高；
- `wechat-cli` 原生支持 `tail --follow` 事件流，但第一阶段为降低风险采用了一次性轮询，评估一直未兑现。

## Solution

把 NotAlone 升级为带主窗口的原生 macOS 应用，由一个常驻本地后端服务把全部已完成模块串成产品闭环（遵循 ADR-020 与 ADR-021）：

1. **常驻本地后端服务**：新增服务模块，只绑定本机回环地址，启动时生成随机 token；界面到服务端用普通 HTTP 请求，服务端到界面用 SSE 推送事件（新消息到达、任务进度、同步状态变化）。后端复用既有应用层代码（会话验证、前台同步引擎、候选回复流程、记忆采纳、任务执行、Skill 库端口），不重写业务逻辑；九个 CLI 命令全部保留，与 API 构成同一能力的两个薄壳入口。
2. **原生主窗口应用**：SwiftUI 三栏主窗口——左栏联系人列表（含同步状态角标与管理页签），中栏消息流（规范消息按领域定义展示，含媒体占位与引用消息），右栏回复工作区（选消息→表达方向→候选→编辑复制）。菜单栏保留为轻量同步状态入口。探针包保持只读探针的单一职责，作为主窗口应用的子进程被调用。
3. **事件驱动前台同步**：消息读取改用 `tail --follow` 常驻流（兑现 ADR-016 第 3 条原设计），切换联系人停旧启新，崩溃指数退避重启并从水位补读，`TailLifecycle` 既有语义不变；前台与会话变化由 macOS 原生工作区事件触发一次性探针（不再全频率轮询截屏）；低频心跳仅作兜底，`--follow` 不可用时降级回一次性轮询退避，失败关闭语义不变。
4. **开源可用**：源码 + 安装脚本分发（机器级：依赖、建库、迁移、构建）；App 首启向导承担用户级配置（填写模型凭据、初始化 owner——从首次导入提前到首启，修订 ADR-013 的初始化时机）。

功能分四批交付：第一批数据可见（后端服务、主窗口骨架、联系人列表、消息流、同步开关与状态）；第二批回复闭环；第三批记忆管理、导入、任务进度；第四批 Skill 库管理与设置页。

## User Stories

1. 作为用户，我想双击打开一个带主窗口的 NotAlone 应用，而不是在状态栏菜单里调试。
2. 作为用户，我想在菜单栏始终看到前台同步的开关与当前状态，以便不打开主窗口也知道同步是否正常。
3. 作为开源用户，我想运行一个安装脚本就完成依赖、数据库、迁移和构建，而不是照着文档手动执行十几个步骤。
4. 作为用户，我想在 App 首次启动时填写模型供应商凭据，而不是手编 `.env` 文件。
5. 作为用户，我想在 App 首次启动时完成 owner 初始化，而不是等到第一次导入才创建。
6. 作为用户，我想在主窗口左栏看到我的全部联系人列表，包括每位联系人的同步与数据状态。
7. 作为用户，我想在中栏看到某位联系人的规范消息流，包括消息正文、说话人、时间、媒体占位文本和引用消息。
8. 作为用户，我想在 App 里开启或关闭前台增量同步，并立即看到状态变化。
9. 作为用户，我想在微信前台切换会话时被一次性要求确认绑定（首次、重名、改名、证据矛盾），之后自动识别。
10. 作为用户，我想在新消息到达时看到消息流实时更新，而不是手动刷新。
11. 作为用户，我想让消息读取走事件流而不是轮询，以便新消息近实时入库且资源消耗更低。
12. 作为用户，我想选中一条联系人消息并填写表达方向后生成候选回复。
13. 作为用户，我想提交一句自己的原句和改写要求，让系统生成改写后的候选。
14. 作为用户，我想在生成候选前手动指定一个 active 的回复 Skill，也接受系统默认自动选择。
15. 作为用户，我想看到本次候选使用了哪个 Skill 以及回复上下文包含哪些材料，并可移除或补充材料。
16. 作为用户，我想编辑候选回复文本并复制到剪贴板，然后自己去微信发送。
17. 作为用户，我想看到候选回复的生成依据，并可以基于一条历史候选显式继续生成新候选。
18. 作为用户，我想在 App 里查看某位联系人的关系记忆列表（含正文、分类、主题、采纳标记与有效期）。
19. 作为用户，我想手动录入、修正和删除关系记忆，删除后其文本指纹阻止自动复活。
20. 作为用户，我想确认或丢弃低置信的 pending 记忆候选，而不是让它们永远滞留。
21. 作为用户，我想在 App 里选择 JSONL 文件、预览校验结果、选择或新建联系人后完成正式导入。
22. 作为用户，我想在导入完成后一键触发记忆提取任务，并在界面上看到每个步骤的进度与结果统计。
23. 作为用户，我想在任务失败时看到错误分类并可重试，中断后重新触发从未完成步骤继续。
24. 作为用户，我想在 App 里导入、启用、停用、回滚和删除回复 Skill，并预览其内容与辅助资源。
25. 作为用户，我想在设置页管理模型凭据、探针路径、同步参数，并打开探针调试窗口（OCR 文本与裁剪预览）。
26. 作为用户，我想查看出站台账的统计概览，以便核对外部模型调用的范围与成本。
27. 作为用户，我想在后端服务异常时仍能使用既有命令行完成同样的操作，作为兜底。
28. 作为用户，我想在联系人或来源被删除时，App 内所有相关视图同步消失，与既有删除边界一致。
29. 作为用户，我想让所有界面操作保持联系人范围隔离，任何界面不跨联系人展示或生成内容。
30. 作为用户，我想让应用只在本地访问我的数据，后端不监听外网、不上传资料。

## Implementation Decisions

1. **进程与目录形态**：主窗口应用为独立 Swift Package，位于仓库根目录、与探针包平级；后端服务为 Python 包内新增的服务模块。Swift 应用负责拉起并监管后端子进程（沿用既有 conda 环境路径探测经验），退出时一并收掉；一次只能有一个后端实例驱动同步循环。
2. **通信协议**：后端只绑 `127.0.0.1`，启动时生成随机 token；界面操作走 HTTP，服务端事件走 SSE（单向推送、断线重连）。API 可以返回消息正文与记忆正文（用户查看本人资料）；出站台账等对外边界不变。
3. **薄壳架构**：后端 API 与既有九个 CLI 共用同一应用层代码，不复制业务逻辑。`front-sync status` 降级为诊断入口（手动跑一轮看报告），`task-worker` 降级为兜底恢复工具，其余命令语义不变。
4. **事件驱动同步三层混合**：消息读取使用 `tail --follow` 常驻流（每时刻只对当前绑定联系人保持一个流）；前台/会话变化用 macOS 原生工作区事件触发一次性探针；低频心跳兜底，`--follow` 失败降级回一次性轮询退避。`TailLifecycle` 的切换、补读（`cli_catchup`）、手动关闭窗口、失败关闭与去重语义全部保留。
5. **回复闭环接线**：界面发起候选回复任务前，由应用层完成已验证会话范围检查；两种输入形态（回复目标消息 + 表达方向、用户原句 + 改写要求）都暴露；Skill 默认自动、允许手动指定一个 active 版本；候选编辑与复制在端侧完成，代码中仍不存在任何外部发送能力。
6. **任务执行**：用户在界面触发、后端进程内执行任务步骤并推送进度；保持"用户触发"硬边界，不引入定时自动化与无人值守调度。
7. **记忆候选确认**：pending 候选的人工确认与丢弃是本规格新增能力（此前未实现），确认走与自动采纳相同的落库裁决路径（标 `manual`），丢弃则失效候选并计入删除指纹。
8. **首次配置分层**：安装脚本负责机器级事务（依赖、建库、按序迁移、构建应用与探针）；App 首启向导负责用户级事务（模型凭据、owner 初始化）。owner 初始化保持与导入路径相同的事务语义与幂等行为，两个入口不得产生分叉。
9. **分发形态**：源码 + 安装脚本；不做签名打包、不内嵌运行时、不做自动更新（ADR-021）。

## Testing Decisions

1. **主接缝：后端 HTTP API 进程内测试**。用进程内测试客户端直接调用服务应用，不真实起网络进程；这是覆盖串联逻辑的最高接缝，数量上只新增这一个主接缝。
2. **复用既有测试资产**：前台同步使用既有 fake CLI 适配器（已支持 `sessions` 等子命令，需按 `--follow` 流式语义扩展）；模型调用使用既有 scripted fake model；持久层使用既有隔离测试库（随机 owner、只清理自己的合成数据、拒绝非 `_test` 结尾库名）。
3. **Swift 端不做自动化测试**：Swift 与后端的边界用 API 契约钉住（服务端 JSON 结构有契约测试，Swift 侧解析失败即冒烟可见），界面行为通过真实微信手工冒烟验证，沿用既有冒烟记录惯例。
4. **先例**：前台同步端到端测试（fake CLI 驱动观察→绑定→入库全链路）、回复流程 PostgreSQL 集成测试（真实库 + 合成数据）、记忆采纳集成测试（9 例）是本规格各批测试的直接参照。
5. **`--follow` 真实验证前置**：事件驱动消息流在真实微信下的稳定性必须先经只读冒烟（不写库）确认，再替换轮询主路径；验证前一次性轮询保持可用。
6. **测试只验证外部行为**：API 的输入输出、事件顺序与持久化结果，不测服务内部装配细节。

## Out of Scope

- 打包分发、签名、自动更新、容器化（ADR-021 明确暂缓）；
- 云端部署、多用户运行时隔离、账号体系；
- 任何外部聊天发送能力（产品硬边界）；
- 定时自动化、无人值守调度、自治任务；
- 语音转写、媒体内容解析（媒体提取另有独立规格）；
- 非 macOS 平台；
- 菜单栏应用完全移除（本规格保留其为轻量状态入口）。

## Further Notes

- 本规格的全部架构取舍见 ADR-020（常驻后端与事件驱动同步）与 ADR-021（源码分发与双层首次配置）；owner 初始化时机的修订涉及 ADR-013。
- `--follow` 长进程是 ADR-016 的原设计，06/07 任务票记录了第一阶段改为一次性轮询的原因与遗留评估项，实现第一批前应重读这两张票的"剩余风险"部分。
- 领域词汇没有新增：本规格的后端服务、主窗口、事件流等概念属于实现层，不入 `CONTEXT.md`。
- 界面文案、代码注释与文档使用中文；标识符、命令、协议字段保持英文。
