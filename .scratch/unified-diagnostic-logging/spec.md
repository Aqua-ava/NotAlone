日期：2026-11-11。状态：01–05 已实施并完成范围内验收；后台全量的图片夹具遗留问题另见第7节。相关：[现行领域文档入口](../../docs/agents/domain.md)、[来源连续性围栏诊断](../../docs/guides/history-continuity-diagnostics.md)、[记忆提取追踪](../../architecture/current/memory-extraction-trace.md)。

## 1. 背景与目标

### 触发事件

记忆管理页读取联系人王威（`1c43e3c0`）的记忆时：

- 读取约 4.8 秒（在本机库副本上空载复现，三次 4.74 至 4.87 秒），页面一直显示"正在核对记忆资料…"。
- 随后弹出"资料资格或连接已变化，已撤下正文、依据和编辑，请重试读取"。
- 慢的根因已查实：`managementRead` 的来源资格核验被逐条调用 3383 次，每次约 1.35 毫秒，共约 4.6 秒（单条路径 `assertSourceEligibility`，已有批量写法 `eligibleSourceReferences` 未被使用）。
- 失效的触发者无法确认。该文案只在主进程广播 `memory:management-invalidated` 时出现，候选触发源包括：联系人范围版本 `scopeRevision` 变化（切换联系人、连接代数变化、授权或读取范围变化）、`data-lifecycle.ts` 撤下、前台跟随控制器调整读取范围。没有任何日志记录谁触发了它。

### 目标

1. 凡是"失效、中断、超时、降级、拒绝"的决策点，都有一条结构化记录，写明触发者和上一个状态变化。
2. 一次用户操作从界面到后端的所有记录可凭同一个 `traceId` 串起来。
3. 用一条命令即可按时间、模块、级别、`traceId` 检索，并还原时间线。
4. 正式版默认开启轻量日志，对用户体验没有可感知影响，不占用户大量磁盘，不外传任何数据。
5. 覆盖全部模块，而不只是记忆；分批接入，每批可独立验收。

### 非目标

- 不做云端日志上传、远程监控或自动崩溃上报。
- 不记录聊天、图片、记忆正文、昵称、备注、路径、凭据。
- 不替代记忆提取追踪（它记录模型调用的完整过程，受独立删除规则约束）。
- 不引入完整 OpenTelemetry 采集器；只在日志中留好 `traceId` 与耗时，保留日后转换的可能。

## 3. 总体方案

**pino 写本机结构化 JSONL，加自生成关联编号 `traceId`；所有数据只留本机。**

选型理由：

- pino 是 Node 生态里最常用、最快的结构化日志库之一，输出即 JSON 行，支持异步写入与子进程隔离；`pino-roll` 负责按天与按大小滚动。
- 单机桌面应用不需要分布式追踪的采集器与后台服务；"一次操作的记录能串起来"只需要一个 `traceId` 字段。
- 日志中保留 `traceId`、耗时、模块、事件名，日后要图形化时，可转成 OpenTelemetry 格式或喂给本机 Jaeger，业务代码不用改。
- 不选云服务（Sentry、Datadog 等）：聊天、图片与关系资料属敏感数据，外部连接必须有明确范围与用户授权。

### 3.1 日志模块

- 位置：后端与主进程各一份薄封装，共用同一份事件契约（类型、白名单、事件名注册表放在一个共享位置，具体位置实施时按目录约定确定）。
- 入口 `diagnose(event)`：同步校验白名单（成本为微秒级），通过后交给异步写入；失败静默吞掉，不抛错、不改变业务结果、不阻塞调用线程。
- 文件：应用资料目录下 `logs/`，文件名带进程名（如 `main-YYYY-MM-DD.jsonl`、`backend-YYYY-MM-DD.jsonl`），避免多进程抢写同一文件。
- 权限与路径校验：沿用连续性日志的做法（属主资料根目录不可组/其他写，可为 0755；logs 目录 0700、文件 0600，拒绝符号链接与非本人所有）。
- 滚动与封顶：按天滚动；每份上限 5 MiB；总量封顶 50 MiB 与 14 天，超出删除最旧；启动时与每次滚动时清理。主进程与后台各分配 24.5 MiB，另为控制原件与原子替换临时文件合计预留 1 MiB，单控制文件不超过 512 KiB；包含替换过程的实际磁盘峰值也须受限。维护前安全清理私有崩溃临时文件，不删除不可信目标。

### 3.2 关联编号 `traceId`

- 生成：界面发起一次用户操作（打开记忆页、切换联系人、点击重试等）时由渲染进程生成，使用随机 UUID，不含任何业务信息。
- 传递：渲染进程 → IPC（参数中带 `traceId`）→ 主进程 → HTTP 请求头（如 `X-Trace-Id`）→ 后端 Worker → 数据库访问层；后端每条日志都带该编号。
- 后台任务（同步、提取、整理）没有界面发起者，自行生成编号，并把 `run_id`、`task_id` 写进字段，便于与处理记录对应。
- 一次操作触发的失效广播，记录"触发源事件"自己的编号与被中断读取的编号，两者可互相对应。
- 风险：IPC 通道和现有请求校验有严格的键集合白名单，新增字段需同步改校验与测试，不得放宽到接受任意字段。

### 3.3 事件契约与字段白名单

每条记录固定字段：

| 字段 | 说明 |
| --- | --- |
| `time` | ISO 时间戳 |
| `level` | `debug`、`info`、`warn`、`error` |
| `proc` | `main`、`backend`、`renderer` |
| `module` | 固定枚举，如 `contacts`、`memory.management`、`memory.processing`、`history.sync`、`media`、`reply`、`deletion`、`startup` |
| `event` | 固定注册的事件名，如 `management.invalidated`、`request.slow`、`scope.revision_changed` |
| `traceId` | 关联编号，可缺省 |

可选字段（按事件注册表逐个事件声明允许的键）：`reasonCode`（固定枚举）、`durationMs`、`count`、`contactPrefix`（联系人编号前 8 位）、`runId`、`taskId`、`fromRevision`／`toRevision`、`caller`（固定枚举的调用点标识，不含文件路径）、`sqlFingerprint`（语句模板的哈希，不含参数）。

禁止出现：聊天正文、记忆正文、候选正文、昵称与备注、文件路径、凭据、异常原文与堆栈（只留原因码）。

约束机制：

- 事件名与可选键由注册表声明；写入时校验，未注册事件或未声明键直接丢弃并计一次"被拒绝"计数，不写入。
- 单元测试遍历所有调用点，断言字段不越界；另加一个含敏感样例字符串的合成输入，确认任何路径都不会进入日志文件。

### 3.4 必记事件

1. **决策点**（info 及以上）：失效、中断、超时、降级、拒绝、重试。必须带"谁触发的"与"上一个状态变化"。例：`scope.revision_changed`（`fromRevision`→`toRevision`、`caller`＝`select_contact`、`foreground_scope_change`、`connection_generation` 等枚举）；管理控制器 `synchronize`／`release` 的调用者；`data-lifecycle` 撤下的原因。
2. **请求**：IPC 与 HTTP 请求的开始、结束、耗时；超过阈值（暂定 1 秒，可按模块单独设定）记 `request.slow`（warn）；超时与被中止记原因。
3. **后台状态流转**：run、task、batch 的状态变化与原因码（接入见 03 号任务）。
4. **后端慢 SQL**：只记语句模板指纹、调用次数、总耗时，不记参数。本次问题就属于此类：同一语句 3383 次、合计约 4.6 秒；高频重复调用应被聚合成一条汇总记录，而不是 3383 条。
5. **错误**：error 级别，只记原因码、模块和 `traceId`。

### 3.5 级别、采样与默认配置

| 场景 | 默认级别 | 内容 |
| --- | --- | --- |
| 正式版 | info | 决策点、错误、慢请求、状态流转；高频事件聚合或采样 |
| 开发实例（`pnpm run dev`） | debug | 另加请求开始／结束、更细的状态与 SQL 汇总 |
| 排查模式 | debug | 用户或开发者临时开启，限时（如 30 分钟）后自动回到默认 |

- 高频事件必须聚合：同一事件在同一操作内重复发生时合并为一条（带次数与总耗时），不得逐次写盘。
- 采样只用于 debug 级别的高频事件；决策点与错误永不采样。

### 3.6 不影响用户的保证

- 写入异步批量，不在界面或请求主路径上同步写盘；写失败静默。
- 单条记录大小设上限；总量与天数封顶，不会无限增长。
- 日志模块本身出错（磁盘满、权限问题）只停止诊断，不改变业务行为与授权。
- 验证必须实测并报告数据：同一工作负载下，开启与关闭日志的耗时对比（以管理页读取、同步一批、提取一批为样本），记录均值与分位数，不以"理论上很小"代替。
- 实施前先确认 `main`、`backend` 进程的启动耗时基线，防止日志初始化拖慢启动。

### 3.7 用户可控与数据流向

- 设置页增加"诊断日志"：开关（默认开启）、"清除日志"按钮、日志占用大小显示；全部使用中文文案。
- 日志只留本机，不自动上传。反馈问题时由用户点"导出诊断包"主动导出；导出沿用 `diagnostic-export.ts` 的版本化白名单思路，并在导出前再过一遍字段校验。
- 删除联系人、清除历史等删除路径：日志只含联系人编号前 8 位与计数，不含可识别内容；仍需在 `privacy-deletion` 规格中补充"诊断日志不含联系人范围正文，按天数自然过期，用户可一键清除"的说明，并核对是否需要在联系人删除时清理带该前缀的行（实施时评估，不预设结论）。

### 3.8 检索工具

- `pnpm run diag`（脚本放 `desktop/scripts` 或根 `scripts`，实施时按目录约定）：
  - 过滤：`--since 10m`、`--module memory.management`、`--level warn`、`--trace <id>`。
  - `--trace` 输出该编号下跨进程的完整时间线，按时间排序。
  - `--slow` 只看慢请求与慢 SQL 汇总。
- 查询只读本机日志文件，默认不输出任何字段之外的内容。
- 图形化为可选后续项：把 `traceId` 与耗时转换为 OpenTelemetry 格式，喂给本机 Jaeger 查看时间线；不属于第一阶段。

### 3.9 与现有机制的关系

- 现有专用日志（连续性、启动、前台标题、诊断导出）保留，语义和白名单不变；逐步改为经共用模块写入，每次改动单独提交并保持其测试通过。
- 记忆提取追踪不动；诊断日志只记调度与失效，不记模型过程，两者通过 `runId`、`taskId` 关联。
- 临时诊断 `diag-temp.ts` 到期后删除，由其所属会话决定。

## 4. 落地顺序

1. **01 日志模块、滚动、`diag` 命令与隐私单测**：含依赖核对、事件注册表、开销实测方案。
2. **02 关联编号与请求／失效广播接入**：先接联系人范围变化、管理控制器失效、请求耗时与超时、后端慢 SQL 聚合；完成后复现"记忆页读取后被失效"，用日志指出触发源。
3. **03 记忆处理状态流转接入**。
4. **04 其余模块逐个接入**：同步、取图、回复、删除、前台定位、启动等，每个模块一个提交。
5. 另设一张独立任务（不在本方案范围内的修复）：管理页读取改为按联系人批量核验来源。它与日志相互独立，不应等待日志完成。

## 5. 验收标准

- 隐私：字段越界单测通过；含敏感样例的合成输入不会写入日志；日志文件权限与路径校验通过。
- 功能：用真实或合成操作产生一条跨主进程与后端的 `traceId` 时间线，`pnpm run diag --trace` 能完整还原。
- 性能：开启与关闭日志的耗时对比有实测数据，差异在报告中列出；启动耗时无明显回退。
- 容量：连续运行下日志总量不超过封顶，滚动与清理有测试。
- 可控：设置页开关与清除按钮有界面验证（在实际 App 中检查，不只靠构建通过）。
- 问题闭环：02 完成后，能用日志回答"记忆页读取后为何弹出失效提示"，并把答案记入对应任务的 `## Answer`。
