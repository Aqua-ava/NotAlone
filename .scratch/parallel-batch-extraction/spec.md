# 提取批次流水线（模型调用并行、写入与水位串行）

Triage: ready-for-agent

来源：2026-10-22 会话；用户确认采用「批次流水线」方案。决策记录见 [ADR-099](../../architecture/adr/099-parallel-batch-extraction.md)。

## 问题陈述

用户导入一段较长的历史聊天后，记忆提取按批串行执行：每批最多 10 条消息，批内依次调用模型完成提取、来源核验和批量裁决，再串行采纳、写入并推进水位。实测单批耗时 32s／76s／103s，945 条消息约需 1.5~2 小时；其中模型调用占绝大部分，写库只有百毫秒级。用户只能干等，且中途失败要整轮重来。

即使只改提取循环也不够快：当前模型优先级控制同一时刻只允许一个后台模型调用，任务 Worker 还有命令级全局锁；不处理这两处，批次并行后模型调用仍然排队。

## 解决方案

在同一提取任务内引入批次流水线：

- **模型调用并行**：提取与来源核验按批并行执行，默认 3 路、可配置 1~4 路；模型优先级控制允许同数量的后台调用在途。
- **写入与水位串行**：采纳、候选写入、trace 完成与水位提交仍按批序在单写队列中串行，水位只按序前进。
- **失败语义不变**：仍按串行顺序判定失败、跳过区间与自动重试；失败即停止后续批的提交。
- 配置可回退：并发设为 1 即恢复当前串行行为，无需数据迁移。

预期效果：大导入的模型调用耗时降到约 1/3（90 分钟级降到 30 分钟级，含批数较少的固定开销）；真实加速比以并发测试和一次真实导入验证为准，不承诺具体分钟数。

## 用户故事

1. 作为导入大段历史聊天的用户，我希望等待记忆生成的时间显著缩短，以便导入后尽快看到关系资料。
2. 作为用户，我希望任务进度（已处理条数）继续按真实完成量显示，以便判断还要等多久。
3. 作为用户，我希望加速不改变记忆的条数、内容和来源，以便继续信任自动采纳的结果。
4. 作为用户，我希望大导入中途失败时已完成的处理不白费，以便点「继续」后只处理剩余部分。
5. 作为用户，我希望失败后不会漏掉任何一条消息，以便资料完整。
6. 作为用户，我希望并发不会把同一件事写成两条记忆，以便资料不重复。
7. 作为用户，我希望同时使用前台回复时后台提取仍然让路，以便回复不被拖慢。
8. 作为用户，我希望关闭应用时正在跑的提取能安全收尾，以便下次恢复不重复不丢。
9. 作为维护者，我希望并发度可配置，以便在限流、超时或质量异常时回退到串行。
10. 作为维护者，我希望并发上限被硬性限制，以便误配不会把模型费用和失败面放大。
11. 作为维护者，我希望每批仍有一条完整的过程记录（trace），以便事后核对。
12. 作为维护者，我希望模型台账不因跨线程丢账，以便成本可核对。
13. 作为维护者，我希望任务租约在并行工作线程里同样被复验，以便过期执行不会写入资料。
14. 作为维护者，我希望失败、跳过和重试的统计口径与串行一致，以便既有页面和恢复逻辑不用改。
15. 作为维护者，我希望默认值保持串行的调用语义，以便现有测试与调用点逐步迁移，而不是一次性改变行为。

## 实现决策

- **并发入口**：提取命令新增「批次并发度」参数，默认 1（保持现有调用语义）；装配层默认 3，允许 1~4，超出范围直接拒绝。并发度只影响同一任务内的批次，不改变任务级串行（ADR-018 的全局锁不动）。
- **两段式执行**：每批先完成「提取 + 来源核验」（可并行），再进入「采纳 + 写入 + 水位提交」（串行、按批序）。等待提交的批按序号排队，前一批未提交时后一批不得提交。
- **预取上限**：并行在途批数不超过配置并发度；不预读更多批次，避免失败时浪费模型调用。
- **失败中止**：任一批失败即停止后续批的提交；已预取但未提交的批把过程记录收为「停止」，不推进水位、不采纳、不计数为已处理。
- **跳过阈值**：模型输出无效的失败仍按原阈值累计并跳过区间，语义与串行一致。
- **水位**：仍由批的 trace 完成事务推进，只按批序前进；不允许乱序覆盖或跳过空洞。
- **模型优先级控制**：后台模型调用允许有界并发（数量由装配层传入，默认 1 保持现状）；前台请求到达后不再发起新的后台调用，等在途后台调用释放后让出；停止信号唤醒全部等待者。
- **记账**：调用记账的「当前提取范围」由线程本地改为运行内共享，单次调用记录仍按线程归属；停止或丢弃调用仍补记台账。
- **租约复验**：Worker 把步骤租约检查作为回调传入提取入口；并行工作线程在每次模型调用前/后与写前同样复验。
- **trace**：每批仍是一条独立过程记录，批内事件顺序不变；并行只改变不同批之间的写入时序。
- **进度与统计**：进度读取仍按已提交目标累计；不新增界面字段，不改变「已处理 / 总数」口径。
- **可回退**：并发度 1 即当前串行路径；该路径与现有调用点行为一致。

## 测试决策

只测外部行为，不测线程细节。四个 seam（用户已确认）：

1. **提取命令并发入口（单元，最高层）**：用可阻塞的假提取运行时、内存记忆/追踪/水位适配器断言
   - 配置 3 时提取调用在途峰值恰为 3，不死锁、不超过上限；
   - 采纳与水位提交严格按批序，失败批之后不再提交；
   - 失败批不推进水位，预取的后续批过程记录为「停止」；
   - 模型输出无效的连续失败仍触发跳过区间；
   - 默认并发度 1 时与现有串行用例结果一致。
   - 同类先例：现有提取命令单元用例已覆盖分批、水位与失败聚合。
2. **模型优先级控制（单元）**：扩展现有排期用例断言后台并发 N 路在途、第 N+1 个等待、前台到达后不抢占在途但阻止新后台调用、前台结束恢复、停止唤醒全部等待者；原有单路优先级用例保持通过。
3. **串并行终态一致（集成，Postgres）**：同一份合成消息集分别以并发 1 和并发 3 运行，断言确认记忆、待确认候选、水位、过程记录状态与进度回执一致；不写真实聊天或真实模型。
4. **装配透传（轻量单元）**：注入假运行时验证 Worker/执行器把配置的并发度传到提取命令；装配默认 3 且越界拒绝。

验证阶梯按仓库工程工作流：单元用例 → 记忆提取相关单元 → 相关集成 → 全量 Python 测试。真实模型质量与限流表现不在自动验证内；改动后由用户对正在排队的真实导入观察一次实际耗时与本轮结果。

## 不包含

- 放开跨联系人/跨任务并行或移除命令级全局锁（ADR-018 范围，另行决策）。
- 并行「采纳」内部处理（相似度、版本裁决、写入）；写入仍单队列。
- 调整批大小、上下文条数、模型或供应商、提示词。
- 新增界面上的并发度设置或进度字段。
- 数据库结构变更、历史数据重算或重新提取。
- 真实模型质量/限流验收与打包版验收。
