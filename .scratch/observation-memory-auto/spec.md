# 微信增量观察后的自动记忆任务

> 状态：实现范围已确认，按顺序实现并以合成 PostgreSQL 验收。

## 用户问题

本地微信 CLI 已在已确认联系人的范围内写入观察来源、规范消息和联系人水位，也发布了 `message.created` 事件；事件目前只服务消息流。历史导入已经能在事务提交后唤醒原记忆任务，但增量观察不会创建或唤醒可恢复的记忆任务，导致新消息不会自动进入提取、索引和核验流程。

## 目标行为

对一批可靠的本地微信增量观察，后端在观察写入事务提交后为同一 `owner_id + contact_id` 建立或重新排队一个 observation 记忆任务，并唤醒现有 `TaskHost`。重复批次和并发事件合并；任务沿用已有 Worker、联系人租约、全局锁、模型优先级、来源复验、失败预算和状态查询。消息、来源和游标提交成功不因任务唤醒失败而回滚。

任务按联系人维护单一可恢复身份：运行中或排队中到达的新观察只保留待处理唤醒；已完成的任务在新观察到达后重置到新的排队轮次；失败任务只有在新观察触发或显式恢复时继续，不重复执行没有新观察的旧终态。Worker 仍按联系人水位处理有效消息，不把任务伪装成来源级独立提取。

## 实现决策

1. 扩展后台任务模型以支持 `observation` 类型；历史 `import` 与删除任务的来源约束和状态保持不变。观察任务不绑定 `source_document_id`，以联系人范围和单一 active 任务身份为边界。
2. 观察任务创建/重排与 `local_wechat_observation` 的可靠写入分属两个提交边界：观察提交成功后再创建任务和唤醒；任务不可用时保留消息与水位，并通过状态/日志返回稳定错误分类。
3. 事件发布只携带现有非正文消息元数据；调度器从事件范围读取最新可靠观察和已确认绑定状态，不能从事件或模型输入接收 owner/contact。
4. 关闭、解绑、删除或来源无效时拒绝新任务；已开始模型调用按现有租约与 5 秒停机协议收尾，晚结果不得复活已取消任务。

## 测试决策

使用公开或应用层任务接缝、真实 PostgreSQL 迁移、合成 CLI 批次和 scripted fake model：

- 新观察提交后自动创建任务并最终得到 succeeded；无需手动 `run`。
- 同一批次重放、同一联系人并发批次和运行中新增批次只产生一次有效执行轮次。
- 不同 owner/contact 隔离；未确认或已撤销绑定不创建任务。
- 全局锁忙后唤醒保留并继续；失败任务可查询、自动重试预算和显式恢复仍有效。
- 新观察到达后终态任务按新轮次排队；无新观察不扫描旧任务，重启不凭旧队列自动执行。
- 关闭、来源删除、绑定撤销及晚事件不创建或复活任务；消息和水位仍保持观察提交结果。

## 不在范围

本轮不改 CLI 读取协议、baseline 之前的历史补齐、游标算法、媒体转写、真实微信读取、外部模型质量、App UI、自动发送、跨进程队列和正式部署。真实模型和真实微信验收在代码接线完成后单独按授权范围执行。
