# 历史同步减负方案（2026-11-07）

状态：ready-for-agent（任务单见 `issues/`）。用户已确认前提：**元数据一致就直接解除围栏、不重读**（2026-11-07）。用户已授权：与现有 ADR 冲突时直接覆盖，但必须新增 ADR 说明并给旧 ADR 补回链。

## 任务单与顺序
01 摸底 → 02 原地恢复（核心）→ 03 真实库 15 位恢复 → 04 并表 `source_proof` → 05 存量副本清理 → 06 删减 → 08 观察期验收；07 界面提示修正独立，可随时做。

## 1. 要的产品行为（用户定义）
- 平时正常同步；用户没开 App 期间漏掉的消息，下次打开后**从上次读到的位置往后补**；开着 App 时增量同步。
- 没有“修复同步”这个日常动作。重启、退出再进入，都应自动接上，不需要人手。
- 只有来源**真的变了**（换账号、换会话、微信数据库被重建）才停下，让用户确认。

## 2. 现状：为什么这么重（实测）
- 后台历史同步 `backend-ts/src/history/sqlite/` 58 个文件 6,281 行 + `history/wechat/` 1,614 行；相关测试 64 个文件约 9,700 行；相关 ADR 43 份；`history_*` 表十余张。
- 产品真正需要的只有：每联系人一个“读到哪”的位置、按来源原始键去重、删除/排除/清空的保护。大部分复杂度来自一层“证明来源连续性”的机制：围栏 `history_continuity_fence`、守卫租约 `history_guard_lease`、连续性范围 `history_continuity_scope`、重新认证 `history_source_recertification*`（及开发者批量修复）、新旧绑定、终态抑制映射、旧副本清理。
- 这层机制自己制造了问题：
  1. 绑定与会话：库已规定“一个联系人同时只有一个有效绑定”，但“修复同步”每次撤销旧绑定、新建绑定、**全量重读**历史进新绑定。实测 16 位联系人各只对应 1 个微信会话，却有 50 个绑定（16 初始 + 34 次修复）；122,150 条消息按“联系人+原始消息键”去重后只有 45,608 条，约 2.7 份/条。
  2. 误围栏：00:05→11:03 新增 219 位围栏，全是修复过的联系人，期间零读取、租约和范围未变；在备份副本上用旧/新代码、正式读取器做“只核元数据”的重验，219/219 全部成功。即多数围栏**不需要读正文就能自证没问题**。
  3. 守卫租约：App 每次退出，租约变成 `lost`，下次启动必须重验，重验入口多（约 20 个 `fenceContinuity` 调用点），任一入口走错就围栏。

## 3. 目标模型（减负后）
每个联系人一行 `source_proof`（取代围栏 + 租约 + 范围三张表）：
- 内容：账号键、会话键、来源代次、物理目标（分片/表实例及文件身份）的摘要；状态只有 `ok` / `needs_confirmation` 两种，附最近一次核对时间。
- 启动或每次读取前做一次**元数据核对**（不读正文）：与存档一致或仅“表/分片增长” → `ok`，直接从各表已存的最大 localId 之后往后读；不一致 → `needs_confirmation`，停读并提示用户（沿用现有“处理同步问题”入口）。
- 去重仍按来源原始键；消息不再因认证代次换绑定。绑定只表示“联系人↔会话”，认证状态不再靠换绑定表达。
- 原生读取器的快照守卫（进程内的文件变化监听）保留，只作为本次读取期间的保护，不再持久化为租约。
- 不变的产品边界：删除、清空、排除、终态抑制、撤回不自动恢复；一次历史只属于一位联系人；候选回复仍由用户手动发送。

## 4. 分阶段（每阶段可独立验收、可回滚）
**阶段 0：摸底（不改产品代码）**
- 盘点 20 个 `fenceContinuity` 调用点与全部读写 fence/lease/scope 的地方，逐个归类：A 真变化才触发（保留语义）、B 过度防御（并入元数据核对）、C 仅为修复服务（随删）。
- 用现有回放夹具（`before-migration-43-20261107.sqlite` 的副本 + 正式 `SharedWechatClient`）固化“219/219 续租成功”为回归基线。
- 明确“元数据一致”的精确判据，写成表格并配反例（换账号、换会话、代次变、分片消失、分片被替换、文件身份变）。
**阶段 1：不再制造副本（止血，小改）**
- `Rotate` 不再新建绑定、不撤销旧绑定。围栏联系人的“修复”改为：做元数据核对，通过则清围栏并从最大 localId 后增量读；不通过保持围栏。
- 现有 15 位围栏联系人用这条路径恢复，**不全量重读**。验收：恢复后绑定数不变、消息数只增不减、耗时秒级。
**阶段 2：并表**
- 新增 `source_proof`，迁移时由 fence/scope/lease 折叠而来（有围栏 → `needs_confirmation`；无围栏且范围匹配 → `ok`）。读写路径切换后删除三张旧表。
- 读取入口统一走一个“核对来源”函数，消除多入口各自判围栏。
**阶段 3：删减**
- 删除：重新认证（`recertify*.ts`、`history_source_recertification*`、开发者批量修复面板与桥）、守卫租约持久化、`history_superseded_cleanup`（先做完下一阶段的存量清理再删）、相关 ADR 标注被替代。
- 目标：`history/sqlite` 代码行数下降不少于 30%，相关测试同步精简；表数量减少。
**阶段 4：清理存量副本**
- 复用已合并的 ADR-175 清理工具，先对 16 位联系人出清单、备份、用户确认后执行；被记忆/候选引用的旧消息保留。
- 注意：阶段 1 之后不再产生新副本，所以清理只做一次。

## 5. 验收标准
- 副本回放：重启 N 次（至少 5 次，含硬中断）后围栏数不增加；换账号/换会话/代次变/分片被替换的反例仍然停读。
- 正常使用：退出再进入，无需任何手动操作即接上，新消息补齐，无重复。
- 数据：消息总数只增不减；每联系人绑定数为 1；引用方（记忆、候选、整理条目）一行不变。
- 回归：删除/清空/排除/终态抑制相关既有测试全部通过；全量对照基线无新增失败。
- 每阶段：验证记录写入 `docs/verification/`，现行规格 `architecture/current/wechat-sync.md`、`privacy-deletion.md` 同步，新增 ADR 覆盖旧条款。

## 6. 风险与取舍
- **围栏原因未记录**：历史 219 位围栏的写入入口没留下，只能靠“元数据一致”判断可恢复。风险是极少数确有改写而元数据不变的情况会漏判。缓解：阶段 1 在续读时加锚点比对——重读已存的最后一段（如每分片最后 N 条）逐条对比，不一致则转 `needs_confirmation`；以及保留阶段 0 的诊断日志（`logs/history-continuity.jsonl`）。
- **原生 cursor 不跨进程**：续读靠“各表已存最大 localId”而不是原生 cursor；需确认读取器支持“从 localId 之后读”（现有增量/`true-delta` 路径应已具备，阶段 0 核实）。
- **覆盖 ADR-144/161/173/175**：用户已授权。ADR-161 的“跨代次删除闭包”因不再有跨代次副本，大部分可删，但已存在的旧副本仍需保留这套处理直到阶段 4 完成。
- **改动面大**：同步核心路径，必须在独立工作树做，真实库只读/副本演练；dev 应用热更新会因源码变化重启，合并前不动主工作区。
