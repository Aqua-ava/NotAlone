# 记忆处理进度与显式恢复

用户已确认：在记忆页面直接显示真实进度，重启后也能看见中断状态，并且可以继续处理。沿用对方／我／待确认三个入口，来源历史折叠。

## 行为
- 页面顶部默认显示紧凑处理状态卡，联系人范围隔离；本人入口显示本人有关的整理或提取状态，明确范围，不把当前联系人进度冒充全局。
- 明确区分等待、提取、整理、完成、中断、失败、主动停止、无任务；已有记忆逐步展示。
- 计数必须来自持久化实际完成批次，展示处理聊天量／可靠总量与可可靠获取的新增、更新数量；不把任务初始message_count或候选数量误作处理总量，不编百分比或ETA。无法获取可靠数量时明确无统计。
- 状态与进度跨进程保存。有效执行租约、当前排队信息用于判定活跃；过期或没有执行者的未完成任务显示中断，不能永久假运行。
- GET/刷新/进入页面不调用模型、不改变任务与授权。中断/失败由用户显式继续；已取消任务以重新处理明确区分，不静默复活。
- 旧取消任务没有可靠回执时，GET显示统计未知；用户点击重新处理历史后可重新核对原任务来源的有效消息，建立本轮目标集。不得把它称为断点续跑，不清空人工修正/删除保护；已有可靠完成回执仍保留。此动作不自动执行。
- 恢复复用既有来源核验、联系人隔离、人工修正保护、删除门禁及幂等/租约机制；重复点击不并发重复执行，已删除来源禁止恢复。不全局打开同步或整理，不启动旧队列扫描。
- 查看详情才显示各任务、停止/失败原因与最近进展。当前来源有效但历史取消原因无审计时只写已停止，不推断具体删除操作。
- 提取完成与背景整理完成独立显示；整理关闭/暂停不假装全部完成。

## 预期验证接口
- 后端真实HTTP + 隔离PG：批次落盘、中断状态、显式恢复、重复请求、跨联系人/删除拒绝。
- 桌面公开bridge与React页面：状态卡、刷新不生成、切换范围不串数据、继续按钮及错误。
- 实际npm run dev App：复用现有实例，以只读实际状态和合成数据验收，不执行真实历史全量提取。
